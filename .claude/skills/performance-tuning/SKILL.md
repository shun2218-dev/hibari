# 性能の問題を直す（測ってから直す）

hibari のための手順。addyosmani/agent-skills の performance-optimization（MIT）の考え方を参考に書き直した。

## 原則

- **測る前に直さない。** 遅い場所の推測はよく外れる。直す前の数字がなければ、良くなったかも言えない。
- **1 度に 1 つだけ変える。** 複数を同時に変えると、どれが効いたか（どれが悪化させたか）が分からない。
- **良くならなければ戻す。** 変わらなかった変更も戻す。速くならないのに複雑になっただけのコードを残さない。
- 速さのために CLAUDE.md の決まり（順序は `seq`、OFFSET を使わない、N+1 にしない、presence は Redis など）を崩さない。
  崩したくなったら、それは設計の変更なので ADR からオーナーに相談する。

## 手順

1. **何が遅いかを数字で言う。** どの API・どの画面・どの操作が、どの条件（件数・人数）で何ミリ秒か。目標の数字も決める。
2. **測る。**
   - SQL: `EXPLAIN (ANALYZE, BUFFERS)` で計画と実際の時間を見る。実行回数は、テストやログでクエリの数を数える（N+1 を探す）。
   - Go: `go test -bench` と `-benchmem`、`pprof`（CPU・メモリ・goroutine）。
   - Redis: 1 回の操作で何往復しているか（パイプラインや Lua にまとめられるか）。
   - web: ブラウザの Performance、React の再描画の回数、送っている要求の数と大きさ。
3. **原因を 1 つに絞る。** 計画のどこ（全件の走査・ソート・ネストしたループ）、どの関数、どの往復が時間を使っているか。
4. **1 つ直す。** 例: 索引を足す（マイグレーション。`CONCURRENTLY` が要るか考える）、1 本の SQL にまとめる、往復をまとめる、要らない再描画を止める。
5. **測り直す。** 同じ条件で比べる。良くなった → 残す。変わらない・悪くなった → 戻す。
6. **残す。** PR の説明に、直す前と後の数字・測り方・試して戻したものを書く。索引やキャッシュを足したなら、なぜ要るかをコメントか ADR に書く。

## hibari で気をつけること

- **索引**は、クエリの形（`WHERE` と `ORDER BY`）に合わせる。`EXPLAIN ANALYZE` で使われることを確かめてから足す。足すとマイグレーションが増え、書き込みが少し遅くなる。
- **キャッシュ**は、何をキーにして、いつ古くなり、誰がどう消すかを決めてから足す。権限の変更（ルール 8）や編集・削除（`change_seq`）を取りこぼさないこと。キャッシュを足すのは設計の変更なので ADR から。
- **コネクションの枯渇**（pgx のプールが空く・待つ）は、トランザクションの中でネットワークを待っていないか（ADR 0065 決定 10）、閉じ忘れがないかを先に疑う。プールを大きくするのは最後。
- **並行に増やす**（goroutine を増やす）なら、終わる条件とリークしないテストも書く（CLAUDE.md「Go 全般」）。
- 測るためのコードやログ（時間の計測・一時的な出力）は、PR に残さない。
