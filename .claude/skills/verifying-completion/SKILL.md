# 終わったと言う前に確かめる

hibari のための手順。obra/superpowers の verification-before-completion（MIT）の考え方を参考に書き直した。

## 原則

- **その場で実行した結果がなければ「通った」と言わない。** 「通るはず」「たぶん大丈夫」は報告ではない。
- 前に実行した結果は、その後にコードを変えたら使えない。変えたら実行し直す。
- 失敗したら、失敗したと書く。出力（失敗したテスト名と理由）を添える。飛ばした確認があれば、飛ばしたと書く。
- 一部だけ実行したなら、どこまで実行したかを書く（「Go のハドルのパッケージだけ」など）。

## 何を言うには何が要るか

| 言いたいこと | 要るもの |
|---|---|
| Go のテストが通る | `make test`（`go test -race -count=1 ./...`）の結果。DB と Redis は実物 |
| Go の lint が通る | `make lint`（`go vet` と golangci-lint）の結果 |
| web のテストが通る | `make web-test` か、`web/` で `npm run lint`・`npm run typecheck`・`npm test` の結果 |
| 生成物が最新 | `make ts-types`・`make openapi`・`make sqlc` の後に `git status` で差分がない、または差分をコミットした |
| 画面が直った | ブラウザ（プレビュー）か Storybook で見た結果。見た目を変えたなら `docs/ui/` のスクリーンショットを撮り直した |
| 不具合が直った | 直す前に失敗したテストが、直した後に通る |
| CI が通った | PR のチェックがすべて成功していること（`ccd_pr` の `get_status`）。手元で通っただけでは CI が通ったとは言わない |
| 実物で動く（音声・映像・通知など） | オーナーが実物で確かめた。自分で確かめられないものは「実物の確認はオーナーに頼む」と書く |

## コミット・PR・マージの前

- 1 コミット 1 論理変更で、各コミットの時点でテストが通る（CLAUDE.md「コミットメッセージ」）。
- PR の説明の「テスト内容」には、実際に実行したものだけを書く。
- マージしてよいのは CI が通った実装の PR だけ。ADR とデザインの PR は、オーナーの確認を待つ。

## 報告の書き方

- 結果を先に書く（通った / 落ちた / 確かめられなかった）。
- 落ちたものは、テスト名と理由を 1 行ずつ。自分の変更のせいか、前から落ちていたかを分けて書く。
- 確かめていないことは、確かめていないと書く。それを確かめた体の書き方をしない。
