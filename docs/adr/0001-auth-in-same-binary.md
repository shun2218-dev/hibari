# 0001. 認証を別サービスにせず同一バイナリに置く

- 状態: 採用
- 日付: 2026-09-13

## 背景

hibari には認証（登録・ログイン・トークン発行）とチャット（ワークスペース・メッセージ・WebSocket）の 2 つのドメインがある。
「認証は独立したサービスにすべき」という一般論はあるが、このプロジェクトは個人の学習用で、運用する人手も 1 人しかいない。

## 決定

- 認証とチャットは **1 つの Go バイナリ（1 プロセス）に同居**させる。
- ただしパッケージは厳密に分ける。`internal/chat` は `internal/auth` を import しない。
- 両者の接点は次の 2 つだけにする。
  1. `internal/platform/authn` が JWT を検証し、context に詰めた **userID / sid**
  2. Redis の `auth:revoked` チャンネルに流れる**失効イベント**
- JWT の検証には公開鍵（JWKS）だけを使い、chat 側から auth への同期的な問い合わせを発生させない。

## 理由

- **運用コスト**: サービスを分けると、デプロイ・監視・サービス間通信の認証・障害の切り分けがすべて 2 倍になる。学習の本題（リアルタイム設計）から外れる。
- **分割の可能性は残す**: 境界を import のルールと 2 つの接点に絞っておけば、将来 auth を別プロセスに切り出すときの変更はルーティングと JWKS の取得方法だけで済む。
- **水平スケールとの相性**: JWT の検証がローカルで完結するので、Phase 5 でサーバーを増やしても auth がボトルネックにならない。

## 検討した代替案

- **最初から別サービスにする**: 境界は物理的に守られるが、ローカル環境・デプロイ・サービス間の通信が複雑になる。1 人の学習プロジェクトには過剰。
- **パッケージも分けない**: 最速で書けるが、chat が users テーブルやトークンの内部に直接触り始め、後から分けられなくなる。
- **外部の IdP（Auth0、Clerk など）を使う**: 認証の実装そのものが学習対象に含まれるので採用しない。

## 結果（トレードオフ）

- 境界はコンパイラではなく規約で守ることになる。レビューと、必要なら import を検査する lint（`depguard` など）で担保する。
- auth のデプロイと chat のデプロイは常に同時に起きる。
- ws-ticket のように「auth 寄りだが chat が消費するもの」は、境界を崩さないよう `platform/authn` に置く（ADR 0007）。
