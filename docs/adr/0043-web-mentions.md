# 0043. メンションの Web 側（入力は `@ハンドル` で書き、送る直前に ID へ変換する）

- 状態: 採用
- オーナーの確認: 2026-09-19
- 日付: 2026-09-19

## 背景

ADR 0041 でサーバー側が決まった。本文には `<@ULID>` / `<!channel>` / `<!here>` を保存し、誰宛てかはサーバーが本文から決める。
API には `mentions`（本文に出てくる宛先のプロフィール）と `mention_count`（そのルームの自分宛ての未読の数）が増えた。新しい WebSocket のイベントはない。

ロードマップの Phase 6.13 で、Web 側としてオーナーと確定しているのは次の 3 つ。

- サイドバーに、未読とは別にメンションの件数のバッジを出す（色は attention の系統。デザインで確認する）
- 入力欄に `@` の補完
- 本文の `@名前` を押すとプロフィールのカード（6.9）が開く

ロードマップは「ルームのメンバーでない人をメンションしたときの入力欄の警告は Web の ADR で決める」としている。この ADR で決めるのはそこと、上の 3 つの作り方。

前提として、Phase 6.10（本文の書式）はまだない。本文はいま `message-item.tsx` が 1 つの `<p>` にそのまま流し込んでいる。

## 決定

### 1. 入力欄は `textarea` のまま。本文は `@ハンドル` で書き、送る直前に `<@ULID>` へ変換する

画面の上では `@tanaka` と書き、サーバーへ送る直前に `<@01J8…>` へ変換する。編集のときは逆に、`<@01J8…>` を `@tanaka` に戻してから `textarea` に入れる。

- 変換できるのは**そのルームのメンバーのハンドルだけ**。`users.handle` は `citext` の UNIQUE（`db/migrations/00001_auth.sql`）なので、ハンドルから人は一意に決まる。大文字小文字は区別しない。
- 解決できない `@なにか` は、ただの文字列としてそのまま送る。サーバーも読めないトークンは無視する（ADR 0041）。
- `@channel` / `@here` は `<!channel>` / `<!here>` に変換する。
- 補完から選んでも、手で `@tanaka` と打っても、同じ本文になる。

### 2. 補完はルームのメンバーと `@channel` / `@here`

- 開く条件は、行頭または空白の直後の `@`。続く文字で、ハンドルと表示名を前方一致で絞る。
- 並びは「ハンドルの前方一致 → 表示名の前方一致」の順。同点なら一覧に載っている順（`ListRoomMembers` の順）。上限は 8 件。
- `@channel` / `@here` は、`@c` / `@h` のように前方一致したときだけ候補に出す。個人より下に置く。
- 非メンバーは候補に出さない（メンションしても知らせないため。ADR 0041）。
- キーボードは ↑↓ で移動、Enter と Tab で確定、Esc で閉じる。確定したら `@ハンドル` + 半角スペースを入れる。
- 候補が 0 件なら閉じる（「候補なし」の箱は出さない）。
- 補完が開いている間は、Enter は確定に使う（送信しない）。

### 3. 本文の表示はチップ。個人は緑、全員宛ては琥珀

| 種類 | 見た目 | 押せるか |
|---|---|---|
| 個人（`<@ULID>`） | `@表示名`。`bg-primary-subtle text-primary` | 押せる（6.9 のプロフィールのカードを開く。いまは何も起きない） |
| `<!channel>` / `<!here>` | `@channel` / `@here`。`bg-attention text-on-attention` | 押せない |

個人のチップはリンクと同じ「押せるもの」なので緑にする。

`@channel` / `@here` はルームの全員に知らせが飛ぶので、個人より目立たせる（オーナーの判断。2026-09-19。Slack に合わせる）。
押せないので琥珀を当てられる（`tokens.md` の「琥珀の要素を押せるようにしない」に触れない）。
自分宛ての行の背景も薄い琥珀なので、そこに埋もれないように、薄い琥珀ではなく地の琥珀で塗る。
ダークテーマの `--color-attention` は黄色寄り（`#d9a441`）なので、Slack のダークの見え方に近くなる。

自分へのメンションのチップは、色を変えない（目立たせるのは下の行の背景でやる）。

#### 追記: `@channel` / `@here` も個人と同じチップにする（2026-09-24。オーナーの判断）

上の表の琥珀をやめ、`@channel` / `@here` も個人と同じ `bg-primary-subtle text-primary` で描く。入力欄のチップ（ADR 0052）も同じにする。
押せないのは変わらないので、個人のチップのホバーの下線は付けない。

- 地の琥珀のチップは、自分宛ての行の薄い琥珀の上でも、そうでない行でも強すぎた。宛先の広さは送る前の確認（決定 6）で伝わっていて、
  読む側は自分宛ての行の背景（決定 4）で気づける。チップの色で三重に知らせる必要はない。
- 緑は「押せるもの」の色（`tokens.md`）だが、行全体がリンクの所（スレッドの一覧）では個人のチップも押せない緑で描いている。
  「メンションは緑のチップ」と読めれば足り、押せない緑のチップはすでにある形なので、新しい例外は増えない。

`mentions` に入っていない ID（ルームから抜けた人など）は、サーバーが `mentions` に載せてくれるので普通に名前が出る。それでも引けなかったら、トークンをそのままの文字列で出す。

### 4. 自分宛てのメッセージは、行の背景を琥珀にする

`bg-attention-subtle` と、左端の琥珀の縦線（送信失敗の赤い線と同じ位置・同じ太さ）。行は押す要素ではないので、琥珀でよい。

- 既読になっても消さない（Slack と同じ。後から遡ったときにも自分宛てだと分かる）。
- `@channel` / `@here` も自分宛てに数える。自分の発言は数えない。
- 「自分宛てか」は表示用の値として渡す（`MessageView.mentionsMe`）。データ層が `mentions` と自分の ID から決める。

### 5. サイドバーは「数字のバッジ = 知らせが要るもの」「太字 = 読んでいないもの」に分ける

Slack と同じ分け方にする（オーナーの判断。2026-09-19）。

| 行 | 数字のバッジ | 名前の太字 |
|---|---|---|
| チャンネル（public / private） | 自分宛てのメンションの数を `@3` として出す。0 なら出さない | 未読があれば太字 |
| DM | 未読の数をそのまま出す | 未読があれば太字 |

- **バッジは「本人に知らせが要るもの」にだけ出す。** チャンネルではそれが自分宛てのメンションで、ただ読んでいないだけの
  チャンネルには数字を出さない。読んでいないことは名前の太字で分かる。
- **DM は 1 通が知らせ**なので、未読の数をそのまま出す（Slack と同じ）。`@` は付けない。
- 未読の数とメンションの数を同時に数字で出すことはしない。1 行に同じ色の数字が 2 つ並ぶと、どちらが何か分からないため。

サイドバーの「スレッド」の行は変えない。API の `mention_count` はルームごとの値で、スレッドごとの件数はないため（ADR 0041）。
スレッドの中でメンションされたことは、そのルームの件数に含まれる。

この変更で、**サイドバーの写っているスクリーンショットは全部撮り直しになる**（未読のチャンネルのバッジが消えて太字になるため）。

### 6. `@channel` / `@here` は送る前に確認する

ルームの全員に知らせが飛ぶので、送信の前に確認のダイアログを出す（オーナーの判断。2026-09-19。Slack に合わせる）。

- 出すのは `@channel` と `@here` だけ。個人へのメンションでは出さない。
- 文言は人数を入れる。`@channel` は「このチャンネルのメンバー N 人に知らせが飛びます。」、
  `@here` は「いまオンラインの N 人に知らせが飛びます。」
- 人数は画面が持っている値から出す（`@channel` はルームのメンバー数、`@here` はそのうちオンラインの人数）。
  実際に行が作られる相手はサーバーが送信の時点で決めるので（ADR 0041）、この数と 1 人 2 人ずれることがある。目安として出す。
- ボタンは「キャンセル」と「送信する」。送信は普通の primary にする（消す操作ではないので danger にしない）。

### 7. メンバーでない人をメンションしたときの警告は、いまは出さない

補完に出ないことが答えで、入力欄には何も出さない。

Web はそのルームのメンバーしか知らないので、`@tanaka` が「ワークスペースにはいるがこのルームにはいない人」なのか「ただの文字列」なのかを見分けられない。
見分けるにはワークスペース全体のユーザーを引く API が要るが、それは Phase 6.9（プロフィールのカード）で必要になるもので、いま先回りして作らない。
6.9 でその API が入ったら、警告を足すかどうかをそのとき決める。

### 8. リアルタイムと状態

- ルームの一覧と `room.read` に乗ってくる `mention_count` を、そのままストアに持つ。
- 新しいメッセージを受け取ったら、自分宛て（`mentions` に自分の ID か `channel` / `here` があり、送信者が自分でない）なら `mentionCount` を 1 増やす。ルームを読んだら 0 にする。サーバーの `room.read` が来たら、その値で上書きする。
- 「自分宛てか」はイベントに載らない（配信は 1 ルーム 1 ペイロード。ADR 0041）。受け取った側が `mentions` を見て判断する。
- 再接続後の `after_seq` の差分でも同じ経路を通るので、追加の同期は要らない。

### 9. 置き場所

`web/lib/chat/mentions.ts` に、本文の解釈（トークン → 表示用の断片）と、`@ハンドル` ↔ `<@ULID>` の変換をまとめる。
Phase 6.10（本文の書式）が入ったら、この解釈をそちらへ吸収する。サーバーの `internal/chat/mention` と同じトークンの形を持つので、形を変えるときは 2 か所を直す（ADR 0041 に書いたとおり）。

Web 側は ULID の厳密な検証（I / L / O / U や桁あふれ）をしない。サーバーが検証済みの本文しか返さないうえ、
表示で使うのは `mentions` に入っている ID だけなので、引けなければそのまま文字列として出せば足りる。

### 新しいトークン

要らない。`--color-primary-subtle` / `--color-primary` / `--color-surface-muted` / `--color-text-secondary` / `--color-attention-subtle` / `--color-attention` は既にある。

## 理由

- **`textarea` を捨てない**: 見た目どおりに `@名前` を持つには `contenteditable` が要るが、IME の変換、貼り付け、元に戻す、モバイルのキーボードを全部自分で面倒みることになる。
  ハンドルが UNIQUE なので、「表示は `@ハンドル`、保存は ID」で同じことができる。テストも文字列の変換として書ける。
- **送る直前に変換する**: 保存された本文が ID なら、その後で相手が改名しても古い発言が指す相手は変わらない（ADR 0041）。
  入力の途中を ID にしないので、書いている人は自分の書いたものをそのまま読める。
- **補完をメンバーだけにする**: 候補に出したのに通知されない、が一番わかりにくい。出さなければ、その食い違いが起きない。
- **チップの色を役割で分ける**: 個人は 6.9 で押せるようになるので緑（リンクと同じ）。`@channel` / `@here` は押せないので、
  琥珀を当てても `tokens.md` の決まりに触れない。宛先の広さがそのまま目立ち方の差になる。
- **自分宛ては行の背景で目立たせる**: 「いま起きていること」なので琥珀。個人のチップまで琥珀にすると、
  「押せない琥珀」と「押せる緑」が 1 行に混ざって規則が読めなくなる。
- **バッジを知らせが要るものだけにする**: 幅の狭いサイドバーに同じ色の数字が 2 つ並ぶと、どちらが何か分からない。
  数字を「知らせが要るもの」に限れば、バッジが付いている行は必ず本人が見るべき行になる。ただの未読は太字で足りる。
- **`@channel` / `@here` を送る前に確認する**: 打ち間違いや書きかけで全員に知らせが飛ぶのは取り消せない。
  確認は 1 回のクリックで済むが、間違って送った知らせは消せない。

## 検討した代替案

- **`contenteditable` のリッチな入力欄**: Slack と同じ見た目になるが、IME と貼り付けの面倒を全部引き受けることになる。Phase 6.10 で書式（太字・コード）を入れるときに改めて考える。
- **`@表示名` で書いて送信時に解決する**: 表示名は重複しうる（UNIQUE なのはハンドルだけ）ので、同姓同名を解決できない。
- **補完で選んだ人を別に持ち、本文とは分けて送る**: サーバーは申告を信じない（ADR 0041）ので、送っても使われない。本文と食い違うだけ。
- **バッジを 2 つ（`@2` と `5`）並べる**: 上のとおり読みにくい。
- **未読の数のバッジを今までどおり全部のチャンネルに出す**: バッジが付いていても見なくてよい行が混ざるので、
  バッジそのものが「見るべき印」として働かなくなる。
- **`@channel` / `@here` を使える人を絞る**: ADR 0041 が「最初は投稿できる人なら誰でも」としている。確認のダイアログで足りる。
- **自分宛ての強調を未読の間だけにする**: 既読の判定を presentational コンポーネントに持ち込むことになるうえ、遡ったときに自分宛てだと分からない。
- **メンションだけの一覧（Slack のアクティビティ）**: ADR 0041 が「作らない」としている。`message_mentions` は後から作れる形にしてある。

## 結果（トレードオフ）

- ハンドルを変えた人をメンションした本文を**編集**すると、`textarea` には新しいハンドルが入る。保存すれば ID は変わらないので実害はないが、書いた文字列は変わる。
- ルームのメンバーでない人のハンドルを書いても、何も起きず、何も言われない。6.9 まではそのまま。
- 本文の解釈が Web 側にも増える。6.10 で 1 つにまとめるまでの二重持ち。
- チャンネルの未読の数がサイドバーから読めなくなる（太字かどうかしか分からない）。DM は今までどおり数が出る。
- サイドバーの写っているスクリーンショットが全部古くなる。撮り直しが要る。
- `@channel` / `@here` を送るのに 1 手間増える。連投するときは毎回出る（「次回から出さない」は持たない）。
- 確認に出す人数は目安で、サーバーが実際に知らせる相手とずれることがある。
- 補完は `textarea` の上に重ねるので、キャレットの位置には追従しない（入力欄の左上に固定で出す）。Slack はキャレットに付くが、`textarea` では位置を測れない。

## オーナーと確定した内容（2026-09-19）

- サイドバーは Slack と同じ分け方にする（数字のバッジは知らせが要るものだけ、未読は名前の太字）→ 決定 5
- 自分宛ての行は琥珀のまま、既読になっても消さない → 決定 4
- `@channel` / `@here` は個人より目立たせる（琥珀。ダークでは黄色寄り）→ 決定 3（2026-09-24 に取り消し。個人と同じチップにする）
- `@channel` / `@here` は送る前に確認のダイアログを出す → 決定 6
- メンバーでない人への警告は出さない → 決定 7

DM のバッジに数字をそのまま出す（`@` を付けない）のは、上の分け方をこのアプリに当てはめた結果で、
オーナーが名指しで決めたものではない。DM は 1 通が知らせなので、知らせの数 = 未読の数になる。

## 実装の順序

1. **この ADR と画面**（`/dev/preview` から撮ってオーナーに見てもらう）← 完了
2. `web/lib/chat/mentions.ts`（解釈と変換）とそのテスト
3. presentational（チップ、自分宛ての行、補完、バッジ）とそのテスト
4. データ層（ストアの `mentionCount`、送信と編集での変換、補完に渡すメンバー）
5. DoD（`docs/roadmap.md`）
