# 0044. 絵文字のリアクション（Phase 6.7。行で持ち、メッセージの change_seq に乗せて配る）

- 状態: 採用
- 日付: 2026-09-20

## 背景

Phase 6.7 は、メッセージに絵文字でリアクションを付けられるようにする（Slack と同じ使い心地。ロードマップ）。
オーナーと確定している前提（2026-09-19）:

- **Unicode の絵文字だけ。** カスタム絵文字は作らない（画像の保存と管理画面が要るため）

ロードマップが「ADR で決めること」に挙げているのは、テーブル・同期・上限と検証・ピッカー・誰が付けたかの表示。
このうち、ピッカー / 誰が付けたかの運び方 / 上限は**オーナーの判断を取った**（2026-09-20。下の各節）。

リアクションは、これまでの機能と違って「**メッセージの中身が変わらないのに、メッセージの見え方が変わる**」最初の例になる。
同期の経路をどこに乗せるかが、この ADR のいちばん大きな判断になる。

## 決定

### 1. テーブル: 1 つの行が「誰がどのメッセージにどの絵文字を付けたか」

```sql
CREATE TABLE message_reactions (
    room_id    uuid        NOT NULL,
    message_id uuid        NOT NULL,
    user_id    uuid        NOT NULL,
    emoji      text        NOT NULL,
    created_at timestamptz NOT NULL,

    PRIMARY KEY (message_id, user_id, emoji),
    FOREIGN KEY (room_id, message_id) REFERENCES messages (room_id, id) ON DELETE CASCADE,
    FOREIGN KEY (room_id, user_id)    REFERENCES room_members (room_id, user_id) ON DELETE CASCADE
);
CREATE INDEX message_reactions_message_id_created_at_idx ON message_reactions (message_id, created_at);
```

- **件数の列を持たない**（`message_mentions` と同じ理由。ADR 0041）。数は行を数えて出す。
  カウンタを持つと、付け外しが同時に来たときに取り合い、1 回ずれると二度と直らない。
- **二重に付けられないことと、付け外しの冪等性を主キーで保証する。** アプリ側の「すでに付いているか」の確認は要らない。
- `room_members` への複合 FK で、**ルームを抜けた・外された人のリアクションは DB が消す**（`thread_members` / `message_mentions` と同じ）。
- 索引は `(message_id, created_at)`。集計を「最初に付いた順」で並べるのに使う（下の 3）。

### 2. 同期: メッセージの `change_seq` を進めて `message.updated` に乗せる

**新しいイベントも、新しい同期の経路も作らない。**

- 付け外しで、そのメッセージの `change_seq` をルームの採番（`AllocateChangeSeq`）で 1 つ進める
- 配信は既存の `message.updated`（`data` は REST と同じメッセージの形）
- 再接続の差分（`after_change_seq`）にも、そのまま乗る

クライアント側も足すものがない。`mergeMessages` が `change_seq` の大きい方を残す規則（ADR 0014）のままで、
リアクションの付け外しが「メッセージが 1 回編集された」のと同じ扱いになる。

**`seq` / `user_seq` / `last_message_at` は進めない。** リアクションはチャンネルの発言ではないので、
未読数（ADR 0033）にもサイドバーの並びにも影響しない。

**行が実際に増減したときだけ `change_seq` を進める。** 同じリアクションを 2 回付けても（再送・二重クリック）、
2 回目は行が増えないので番号を使わず、`message.updated` も配らない。

### 3. レスポンスの形: 絵文字ごとに集計し、先頭 8 人だけ載せる（オーナーと確認）

メッセージに `reactions` を足す。空なら `[]`。

```jsonc
"reactions": [
  { "emoji": "👍", "count": 3, "me": true, "users": ["01J8...", "01J8...", "01J8..."] },
  { "emoji": "🎉", "count": 1, "me": false, "users": ["01J8..."] }
]
```

- 並びは**最初に付いた順**（`MIN(created_at)`）。Slack と同じで、増減で並びが入れ替わらない
- `me` は自分が付けたか（ボタンの色を変えるのに使う）
- `users` は**先頭 8 人まで**の `user_id`。ホバーの「A、B 他 3 人」に使う。名前はクライアントが持っているルームのメンバーから引く

**全員分は載せない。** 100 人が付けたメッセージが 50 件並ぶページで、レスポンスが人数ぶん膨らむ。
ホバーで見せるのは「誰が付けたか、だいたい」なので、先頭の数人と残りの人数で足りる。
ホバーのたびに別 API を叩く案も採らなかった（下の「検討した代替案」）。

### 4. API: 絵文字をパスに置いた PUT / DELETE

```
PUT    /api/v1/rooms/{roomID}/messages/{messageID}/reactions/{emoji}
DELETE /api/v1/rooms/{roomID}/messages/{messageID}/reactions/{emoji}
```

- `{emoji}` はパーセントエンコードした絵文字そのもの（`%F0%9F%91%8D`）。emoji-mart の `id`（`+1` など）は使わない
- どちらも**冪等**。すでに付いている状態の `PUT` と、付いていない状態の `DELETE` は、どちらも 200 で現在のメッセージを返す
- 応答は更新後のメッセージ（`message.updated` と同じ形）。クライアントは楽観的更新の確定に使う

### 5. 検証と上限（オーナーと確認）

- **1 つのメッセージに付けられる絵文字は 20 種類まで。** 21 種類目は 422（`emoji: too_many`）。Slack は 23 種類
  - 1 人が付けられる数は制限しない（種類の上限が実質の上限になる）
- **絵文字の文字列の検証**: サーバーで次を確かめ、外れたら 422（`emoji: invalid_value`）
  - 長さ 64 バイト以内
  - 書記素クラスタ 1 つ（`uniseg` で数える）
  - 先頭のコードポイントが Unicode の `Emoji_Presentation` か `Extended_Pictographic`（肌の色・ZWJ の合成を通すため、先頭だけを見る）
- **絵文字は正規化しない。** 異体字セレクタの有無（`❤` と `❤️`）は別の行になる。
  クライアント（emoji-mart）が出す形を、そのまま保存して比べる

### 6. 付けられる人と、付けられないもの

- **投稿できる人だけ**（`authz.CanWriteRoom`）。参加していない public ルームは読めるだけなので付けられない（403）
- **削除済みのメッセージには付けられない**（404。ADR 0038 で「跡も残さず消える」と決めたので、存在しないものとして扱う）
- **システムメッセージ（参加や名前の変更のログ）にも付けられない**（422。ADR 0033 の「人の発言ではない」に合わせる）
- スレッドの返信には付けられる（同じ `messages` の行なので、特別な扱いは要らない）

### 7. Web: ピッカーは emoji-mart を入れる（オーナーと確認）

**`emoji-mart`（v5）を入れる。** Slack と見た目が近く、検索・肌の色・「よく使う」まで揃っているものを自前で作らない。

ただし **React のラッパー（`@emoji-mart/react`）は使わない。** peer dependencies が `react: ^16.8 || ^17 || ^18` で、
このプロジェクトの React 19 が入っていないため。本体は依存のない素の JS なので、`new Picker({...})` が返す要素を
`ref` の `div` に挿して使う（ライブラリが公式に案内している使い方）。

- **データ（`@emoji-mart/data`）は動的 import にする。** ピッカーを最初に開いたときだけ読み込み、最初の表示に載せない
- **見た目はトークンから渡す。** emoji-mart は自前の CSS 変数（`--em-*`）を持つので、`globals.css` の
  `--color-*` を写して渡す。コンポーネントの中に色の値は書かない（CLAUDE.md ルール 7）
- **ライト / ダークは `data-theme` から明示的に渡す。** emoji-mart の `auto` は OS の設定を見るので使わない（ADR 0031）
- ピッカー自体はテストで描かない（外のライブラリなので、開く・選んだ値が上に渡る、までを自分の部品で確かめる）

**追記（2026-09-20、デザインの実装中に決めた）**

- **モバイルでは下から出るシートにする。** ピッカーは 400px 近く高いので、メッセージに吊るすポップオーバーのままだと
  タイムラインの外にはみ出して上が切れる（`/dev/preview` で実際に切れた）。メンバーのパネル（モバイルではシート）と
  同じ形にそろえ、背景を覆って外を押すと閉じる。md 以上はこれまでどおりメッセージの右上から開く。
- **1 行に並べる絵文字の数は、幅から決めさせる**（`dynamicWidth`）。シートとポップオーバーで幅が違うため。

### 8. 楽観的更新

付け外しは手元で先に反映し、応答（または `message.updated`）で確定させる。失敗したら元に戻す。
送信（ADR 0027）と違って**キューに並べない**。リアクションは順番に意味がなく、主キーで冪等なので、
同じ絵文字を連打しても最後の状態に落ち着く。

## 理由

- **行で持つ理由**: 件数のカウンタは、同時に付け外しされたときに取り合う。`message_mentions`（ADR 0041）で
  同じ判断をしていて、そこで「行を積んで数える」形にそろえてある。
- **`change_seq` に乗せる理由**: リアクションのための同期の経路を足すと、再接続の同期・ページング・
  イベントの取りこぼしの扱いが 2 つに増える。`change_seq` は「このメッセージの見え方が変わった」を表す番号なので、
  リアクションはその定義にそのまま当てはまる。クライアントは 1 行も足さずに追従できる。
- **`user_seq` を進めない理由**: リアクションで未読が増えたら、読んでも読んでもバッジが戻ることになる。
  「チャンネルに出る人の発言 = `user_seq` を進める行」（ADR 0039）の規則からも外れる。
- **絵文字をパスに置く理由**: 主キー（`message_id, user_id, emoji`）とそのまま対応し、PUT / DELETE がそれぞれ
  「その行があること / ないこと」を表す。冪等性が URL の形から読める。
- **emoji-mart の React ラッパーを使わない理由**: peer dependencies に React 19 がない。`--legacy-peer-deps` で
  黙らせると、CI とローカルで別のものが入りうる。本体だけなら依存がなく、React のバージョンに縛られない。
- **`users` を 8 人にした理由**: ホバーの文言が「A、B、C 他 N 人」で足りるため。50 件のページで全員分を載せると、
  人数の多いルームでレスポンスが数十 KB 増える。

## 検討した代替案

- **リアクション専用のイベント（`reaction.added` / `reaction.removed`）**: 差分が小さくなるが、再接続の同期で
  「リアクションだけ取り直す」経路がもう 1 本要る。`change_seq` に乗せれば、同期は 1 本のまま。
- **`messages` に JSON の列で集計を持つ**: 読むのは速いが、同時の付け外しで行を取り合い、集計がずれたときに
  直す手立てがない。行から数えれば、いつでも正しい値を作り直せる。
- **件数のカウンタ列（`message_reactions_summary`）**: 上と同じ理由で不採用。
- **ホバーのたびに `GET /messages/{id}/reactions` を叩く**: レスポンスは軽くなるが、ホバーのたびに往復が増え、
  反応が遅れる。人数が多いリアクションを開いた人だけが払うコストなので悪くないが、**先頭 8 人を載せる方が
  「だいたい誰か」をすぐ出せる**ので採らなかった。全員を見せる画面が要るようになったら、そのときに足す。
- **絵文字を正規化して保存する**（異体字セレクタを落とす）: `❤` と `❤️` が 1 つにまとまるが、保存した文字列と
  クライアントが出す文字列がずれ、`me` の判定や並びで合わせ直しが要る。まとめる価値より、ずれの方が高くつく。
- **emoji-mart を入れず、自前の一覧にする**: 依存が増えず、トークンをそのまま使えるが、Slack と見た目が離れる。
  オーナーと比較して不採用（2026-09-20）。
- **固定の 6〜8 個だけ出す**: 一番小さく済むが、贈り物としては物足りない。オーナーと比較して不採用。

## 結果（トレードオフ）

- リアクションを付けるたびにルームの `change_seq` が 1 つ進む。連打されると、そのルームの差分の番号が速く進む。
  番号は 64bit なので枯渇しないが、`after_change_seq` の 1 ページ（100 件）が埋まりやすくなる。
- **ルームを抜けた人のリアクションは DB が消すが、そのとき `change_seq` は進まない。**
  ほかの人の画面では、そのメッセージを読み直すまで古い数が残る。抜けた人のリアクションが 1 つ残って見えるだけなので、
  そのまま許容する（同期の経路を増やさない方を採る）。
- ピッカーのデータは 1 MB を超える。最初に開いたときだけ読むので最初の表示には載らないが、開いた瞬間に一拍おく。
- emoji-mart の中の見た目は、こちらの部品と完全には揃わない（角丸や余白はライブラリのもの）。
  CSS 変数で色は合わせるが、それ以上は追わない。
