# 0040. メッセージへのリンクとカード（Phase 6.11 の前半。URL の形、見る人ごとに取るカード、長い本文の畳み）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6.11 では、メッセージへのリンクをコピーでき、そのリンクを本文に貼るとリンク先のメッセージのカードが出るようにする（Slack と同じ）。

オーナーと確定している前提（ロードマップ、2026-09-19）:

- メッセージのメニューに「リンクをコピー」を足す
- 本文にリンクがあると、リンク先のメッセージのカードを出す
- 長いメッセージは、カードの中だけ一部を表示して畳む。「すべて表示する」で広げ、広げたあとも「折りたたむ」を残す。タイムラインの普通のメッセージは畳まない
- カードの中身は表示するときに取るだけ。リンク先が後で編集・削除されても、開き直すまでは追従しない
- カードの中身は見る人ごとに authz を通して取る。本文には保存しない。読めないリンクは「表示できないメッセージ」のカードにする

ADR で決めることとして、URL の形、指定したメッセージの前後を取る API、カードの中身をまとめて取る API と別のワークスペースの扱い、新着の線が挙がっていた。

**オーナーの確認: 2026-09-19。** URL の形、読めないリンクの見え方（存在しない ID と区別しない）、削除済みの扱い（読めないリンクと同じ）の 3 点を、下の決定のとおりで確定した。

**前提のズレが 1 つある。** ロードマップは Phase 6.10（本文の書式）を先に置き、「本文から特別な部分を見つける仕組み」をそこで作って 6.11 が乗る想定だった。
6.10 はまだないので、このフェーズでは本文から URL を見つける最小の仕組みだけを作り、6.10 が入ったときにそこへ寄せられる形にする（下の「本文からリンクを見つける」）。

## 決定

### 範囲: Phase 6.11 を前半と後半に分ける

| | 内容 |
|---|---|
| 前半（この ADR） | URL の形、「リンクをコピー」、本文からのリンクの検出、カードをまとめて取る API、カードの表示と畳み |
| 後半（別の ADR） | 指定したメッセージへ飛ぶ（中心のメッセージの前後を取る履歴 API と、スクロール・強調）、新着の線、未読の位置へ飛ぶボタン |

前半だけで「コピーして貼ると中身が見える」は成立する。飛ぶ仕組みは、古いメッセージまで到達するために履歴 API を 1 本足す必要があり、ピン留め（6.12）と検索（6.16）からも使う独立した部品なので分ける。

### URL の形

```
{オリジン}/w/{workspaceID}/r/{roomID}?m={messageID}
{オリジン}/w/{workspaceID}/r/{roomID}?m={messageID}&t={threadRootID}   スレッドの返信
```

- ID はすべて ULID の文字列表現（API と同じ）。既存のルームの画面の URL（ADR 0025）に、クエリを 1 つ足しただけの形にする。
- スレッドの返信には `t` を足す。スレッドのパネルを開くクエリは既存の `?thread=` があるが（ADR 0037）、パーマリンクでは**リンク先のメッセージを指す `m` と、開くパネルを指す `t` を分ける**。`t` があれば、親を引き当てるためにメッセージを 1 回取る往復を省ける。
- 絶対 URL はクライアントが `window.location.origin` から組み立てる。サーバーに「公開オリジン」の設定を足さない（ADR 0021 のとおり Web と API は同じサイトだが、オリジンはクライアントが自分で知っている）。
- システムメッセージ（ADR 0033）にはリンクをコピーできない。メニュー自体を出していないので、入口を足さないだけでよい。

### 本文からリンクを見つける

`web/lib/chat/links.ts` に置く。

- `parsePermalink(href, origin)`: 上の形に一致すれば `{ workspaceId, roomId, messageId, threadRootId }`、そうでなければ `null`。オリジンが違う URL、ID が ULID として読めない URL は `null`。
- `findPermalinks(body, origin)`: 本文を走査して、見つかったパーマリンクを出てきた順に返す。同じ `(roomID, messageID)` は 1 件にまとめる。**1 つのメッセージに出すカードは先頭の 3 件まで。**
- **本文の表示は変えない。** 本文中の URL をリンクにするのは Phase 6.10 の自動リンクの仕事で、ここではやらない。カードは本文の下に並べるだけにする。
  6.10 が入ったら、本文の解釈が `links.ts` の `parsePermalink` を呼んで「この URL はパーマリンクだ」と判断する形になり、この ADR の検出はそのまま使える。

### カードの中身をまとめて取る API

```
POST /api/v1/messages/links
```

```jsonc
// リクエスト（links は最大 20 件）
{ "links": [{ "room_id": "01J...", "message_id": "01J..." }] }

// レスポンス（リクエストと同じ順序・同じ件数で返す）
{ "links": [
  { "room_id": "01J...", "message_id": "01J...", "status": "ok",
    "workspace": { "id": "01J...", "name": "hibari" },
    "room": { "id": "01J...", "name": "general", "kind": "public" },
    "message": { "id": "01J...", "seq": 42, "sender": { "id": "01J...", "handle": "kohaku", "display_name": "kohaku" },
                 "body": "...", "thread_root_id": null, "attachment_count": 0,
                 "created_at": "2026-09-19T08:00:00Z", "edited_at": null, "deleted_at": null } },
  { "room_id": "01J...", "message_id": "01J...", "status": "unavailable" }
] }
```

- **GET ではなく POST。** 副作用はないが、ID の配列を渡す（ADR 0020 の `POST /users/avatars` と同じ理由）。
- **`status` は `ok` と `unavailable` の 2 つだけ。** 存在しないルーム、存在しないメッセージ、読めないルーム、ULID として読めない ID を**区別しない**。
  区別すると、リンクを貼るだけで「その ID のメッセージが実在するか」を当てられる。権限のないリンクは 403 にもせず、1 件ぶんの `unavailable` にして、他のリンクの取得は続ける。
- **見る人ごとに `authz.CanReadRoom` を通す。** 認可はルームの単位なので、**別のワークスペースのメッセージでも、その人が読めるなら `ok` にする。**
  本文を書いた人の権限ではなく、見る人の権限で決まる（貼った人は読めても見る人は読めない private ルームがある）。
- **N+1 にしない。** リンクをルームごとにまとめ、ルーム 1 つにつき `loadRoomAccess` を 1 回だけ呼ぶ。メッセージは `(room_id, id)` の UNIQUE で 1 件ずつ引く（20 件が上限なので、まとめるより読みやすさを取る）。
- **`message` はタイムラインの `messageResponse` とは別の、カード専用の小さい形にする。** `change_seq` / `user_seq` / `client_msg_id` / `thread` の要約 / 添付の一覧は返さない。
  - カードに要らないものを返さないのが第一の理由。加えて、形が違えば**カードのデータをタイムラインの行として使い回せない**ので、「カードは追従しない」（下）という約束がコードの上でも守られる。
  - 添付は件数（`attachment_count`）だけ返す。カードに画像を出すと、リンク 1 件ごとに署名付き GET URL を発行することになり、ADR 0013 の短い TTL（5 分）と噛み合わない。カードには「添付 N 件」の 1 行を出す。
- **削除済みのメッセージも `status: "ok"` で、`deleted_at` の入った tombstone として返す**（本文は空）。どう見せるかはクライアントだけの判断にする。ADR 0038 が「API とデータは変えない。表示だけの判断をクライアントに閉じ込める」とした切り分けに合わせる。
- システムメッセージ（`kind = system`）は `unavailable` を返す。本文がなく、文言はクライアントが作るものなので、カードにする中身がない。

### 削除済みのメッセージのカード（オーナーと確認）

**「このメッセージは表示できません」の 1 種類にまとめ、読めないリンクと区別しない。**

ADR 0038 で、削除したメッセージは画面から跡も残さずに消すと決めた（admin が消しても周りからは何も起きていないように見える）。
カードだけ「削除されました」と出すと、そこだけ削除の跡が残る。

### カードの見え方

- 枠のあるカードを本文の下に並べる。中身は、送信者のアバターと名前、時刻、本文、そして `#ルーム名`。
  **今いるワークスペースと違うときだけ**、ルーム名の前にワークスペース名を出す。
- **リンク先を開くのは、ルーム名の行だけにする。** カード全体を `a` にすると、下の「すべて表示する」を入れ子の
  ボタンにすることになり（不正な HTML）、本文も選べなくなる。飛んだ先でメッセージの位置まで合わせるのは Phase 6.11b。
- **長い本文は畳む**（オーナーと確定済み）。既定で先頭の 6 行まで、または 300 文字まで。超えていたら末尾を `…` にし、「すべて表示する」を出す。広げたあとは「折りたたむ」を出す。
  - **畳むかどうかは、行数と文字数で判定する。実際に描画した高さでは判定しない。** 描画を待たずに決まり、同じ本文なら必ず同じ結果になるので、テストで確かめられる。
    Vitest（jsdom）はレイアウトを計算しないので、高さを測る方式（`scrollHeight` や `ResizeObserver`）はコンポーネントのテストで検証できない。
  - タイムラインの普通のメッセージは畳まない（オーナーと確定済み）。
- 取得が終わるまでは、カードの枠だけを出す（高さが後から変わってタイムラインがずれないように、1 行ぶんの高さを確保する）。
- `unavailable` のカードは「このメッセージは表示できません」の 1 行だけ。ルーム名も送信者も出さない。リンクにもしない。

### カードは追従しない（オーナーと確定済み）

カードの中身は、そのメッセージが画面に出たときに 1 回取るだけ。`message.updated` / `message.deleted` のイベントでも、`after_change_seq` の差分でも取り直さない。
リンク先が編集・削除されても、画面を開き直すまでは古いままになる。

取得は**画面に出ているメッセージのぶんをまとめて 1 回**にする（ADR 0020 のアバターと同じ集め方）。取った結果は `(roomID, messageID)` をキーにして手元に持ち、同じリンクを二度取りにいかない。

### 「リンクをコピー」

- メッセージの「…」のメニュー（ADR 0012 の編集・削除と同じ場所）に足す。**削除済みのメッセージにはメニューを出していない**ので、そのままでよい。
- `navigator.clipboard.writeText` でコピーする。成功したら、メニューの項目の文言を短い間だけ「コピーしました」に変える（トーストの仕組みを新しく作らない）。
- 失敗したら（クリップボードが使えない環境、権限が拒否された）「コピーできませんでした」に変える。`document.execCommand` のフォールバックは入れない（非推奨で、対象の環境がない）。

## 理由

- **URL をクエリにした理由**: `/w/{id}/r/{id}/m/{id}` のようにパスを分けると、Next.js のルートが 1 つ増え、ルームの画面のレイアウトを作り直すことになる。クエリなら、同じルームを開いているときにリンクを押しても、タイムラインを保ったまま位置だけ動かせる（後半の「飛ぶ」で効く）。ADR 0037 がスレッドのパネルを `?thread=` で開いているのと同じ形。
- **seq ではなく ULID を URL に入れる理由**: seq はルームの中でしか意味がなく、API が ID で受けるので、どのみち引き当てが要る。ID なら API のパスにそのまま渡せる。
- **カードの取得を 1 本のエンドポイントにまとめた理由**: 1 画面に 10 枚のカードがあると、1 リンク 1 リクエストでは 10 往復になる。ADR 0020 でアバターをまとめたのと同じ。
- **読めない・存在しないを区別しない理由**: 上の「status」のとおり。区別すると、貼るだけで存在を当てられる。
- **本文にカードの中身を保存しない理由**: オーナーと確定済み。貼った人は読めても、見る人は読めない private ルームがあるため。保存すると、保存した時点の権限で全員に見えてしまう。
- **サーバーで本文を解析しない理由**: サーバーが本文からリンクを見つけてレスポンスに混ぜると、authz が見る人ごとなので、結局メッセージのレスポンスが人ごとに変わる（キャッシュも配信も難しくなる）。クライアントで見つければ、6.10 の本文の解釈と 1 か所にまとまる。
- **畳む判定を文字数と行数にした理由**: 上のとおり、テストできることを優先した。実際の幅で折り返した行数とはずれるが、カードは「中身が分かる程度に見せる」ためのもので、正確な行数に意味はない。

## 検討した代替案

- **Phase 6.11 をまとめて 1 つでやる**: 飛ぶ仕組みと新着の線まで入ると、履歴 API の追加（中心のメッセージの前後）と、スクロール位置の扱いが同じ PR に入る。範囲が大きくなるので分けた。
- **URL をパスにする（`/w/{id}/r/{id}/m/{id}`）**: 上の理由で不採用。
- **URL に seq を使う（Slack の `p1758...` に近い形）**: 上の理由で不採用。
- **1 リンク 1 リクエスト（`GET /rooms/{roomID}/messages/{messageID}`）**: エンドポイントは素直だが、往復が増える。単体のメッセージを取る API は、後半の「飛ぶ」で前後を取る API を足すときに改めて考える。
- **カードの中身を本文に保存する（unfurl を保存する）**: オーナーと確定済みで不採用。
- **読めないリンクにはカードを出さない（本文のまま）**: 貼った人には理由が分からない。オーナーと確定済みで不採用。
- **削除済みを「このメッセージは削除されました」のカードにする**: ADR 0038 の「跡を残さない」と矛盾する。オーナーと比較して不採用。
- **畳む判定を実際の高さで行う**: 見た目は正確になるが、コンポーネントのテストで検証できない。
- **カードをリアルタイムに追従させる**: オーナーと確定済みで不採用。追従させると、ルームをまたいだ購読（自分が入っていないルームの `message.updated`）が要り、絶対ルール 8 の「権限の変更も即座に反映する」を別のルームぶんまで広げることになる。

## 結果（トレードオフ）

- **前半だけでは、カードを押しても古いメッセージには飛べない。** ルームの最新のところが開く（`?m=` は無視される）。後半で解決する。
- **本文中の URL はまだリンクにならない**（Phase 6.10）。カードは出るが、本文のテキストは今までどおり。
- カードの中身は追従しないので、編集された後のカードは古い本文のまま残る。
- 1 つのメッセージに 4 件以上のパーマリンクを貼っても、カードは 3 件までしか出ない。
- 削除済みと読めないリンクを区別しないので、自分が貼った自分のメッセージを消したときも「表示できません」になる。
