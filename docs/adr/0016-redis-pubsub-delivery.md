# 0016. Redis Pub/Sub による複数インスタンスの配信（Phase 5）

- 状態: 採用
- 日付: 2026-09-15

## 背景

Phase 4 の Hub は、単一のインスタンスのメモリの中だけで配信先を解決していた。そのため、`--scale server=2` にすると、別のインスタンスに接続したクライアントにはイベントが届かない。
ロードマップの Phase 5 は「`room:{roomID}` と `user:{userID}` に publish し、各インスタンスは自分が接続を持つルームだけを購読する」と決めていた。ただ、着手した時点で次の点が決まっていなかった。

- ADR 0015 で足したワークスペースの購読と、1 つのイベントが複数のチャンネルに当たるときの重複
- 「購読の ack を受け取ってから REST を読めば取りこぼさない」（`docs/events.md` の同期の手順）を、Redis の購読が非同期でも保てるか
- 権限の変更の再検証（ADR 0015）を、どのインスタンスが行うか
- presence の接続数は Hub が数えていたので、複数のインスタンスに同じユーザーが接続すると壊れる（ADR 0015 の「結果」）
- Redis Pub/Sub の接続が切れて戻ったとき、その間のイベントは失われる。静かなルームでは、次のイベントが来るまでクライアントが欠落に気づけない

## 決定

### 配信の経路
- `chat.Delivery` の実装を `realtime.RedisDelivery` にする。イベントを宛先のチャンネルに publish するだけで、接続を知らない。
- 各インスタンスの `realtime.Broker` が、そのインスタンスの接続が必要とするチャンネルだけを購読し、届いたイベントを Hub の `DeliverLocal` に渡す。Hub は、自分の接続に対して宛先を解決し直す（Phase 4 の Deliver と同じ処理）。
- **自分のインスタンスで起きたイベントも、直接は配らず Redis から受け取る。** 経路を 1 本にして、どのインスタンスでもイベントが同じ順序で並ぶようにする。
- Broker の受信は 1 本の goroutine で行い、Hub への受け渡しも同じ goroutine の中で届いた順に行う。

### チャンネル
| チャンネル | 購読するインスタンス |
|---|---|
| `room:{roomID}` | そのルームを購読している接続を持つ |
| `workspace:{workspaceID}` | そのワークスペースを購読している接続を持つ |
| `user:{userID}` | そのユーザーの接続を持つ（本人宛てのイベント） |
| `realtime:instance:{instanceID}` | 自分だけ（再接続の検知用。後述） |

- イベントは、宛先（Rooms / Workspaces / Users）と、**権限が変わったユーザー（AccessChanges）の `user:` チャンネル**に publish する。再検証は、そのユーザーの接続を持つインスタンスでしかできないため。
- Broker はチャンネルごとに購読の数を数え、0 → 1 で SUBSCRIBE、1 → 0 で UNSUBSCRIBE する。Hub は接続の購読 1 つにつき 1 つ数える。
- 1 つのイベントのコピーは、1 往復のパイプラインで続けて publish する。

### 購読が反映されるまで待つ
- `subscribe` の ack と、接続の登録（本人の `user:` チャンネル）は、**Redis が SUBSCRIBE を処理したことを確かめてから**返す。
- 確かめ方: SUBSCRIBE の後に、番号付きの PING を同じ接続に送り、その PONG を受け取るまで待つ。Redis は 1 つの接続のコマンドを届いた順に処理し、応答も順に返すので、PONG が返った時点で、それより前に送った SUBSCRIBE は処理済み。PONG を受け取った最大の番号を覚えておき、それ以前に SUBSCRIBE を送ったチャンネルは待たずに済ませる。
- 同じ仕組みで `Broker.Sync` を用意する。呼んだ時点までに Redis が受け付けた publish を、Hub に渡し終えるまで待つ（テストで使う）。

### 重複の除去
- 1 つのイベントを複数のチャンネルに publish すると、両方を購読しているインスタンスには複数回届く。
- イベントに ULID を付け、publish したチャンネルの数（fanout）が 2 以上なら、Broker が直近 4096 件の ID を覚えて、2 回目以降を捨てる。最初に届いたコピーで、宛先の全体に 1 回ずつ配る。

### インスタンスの間で運ぶ形
- `realtime` パッケージの内部の形（版の番号付きの JSON）にする。クライアントに見せる JSON（`docs/events.md`。httpx が決める）とは分ける。
- データはドメインの型を JSON にしたもので、種類ごとに戻す型を表で持つ。知らない版や種類は、ログに残して捨てる（ローリングデプロイの間の保険）。
- すべてのイベントの種類について、変換して戻すと元と一致することをテストで確かめる。

### 権限の変更の再検証
- ADR 0015 と同じく、Hub は**イベントを配る前に**、そのユーザーの購読を DB で再検証する。これを、Broker から受け取ったときに、そのユーザーの接続を持つインスタンスが行う。接続がなければ何もしない。
- 再検証は受信の goroutine の中で行う。その間、そのインスタンスのほかのイベントの受け渡しは止まる。権限の変更はまれで、インデックスの効くクエリ 1〜2 本なので受け入れる。

### presence（ADR 0015 の見直し）
- `presence:{userID}` をハッシュにし、**そのユーザーの接続を持つインスタンスの ID をフィールドにして、フィールドごとに TTL（60 秒）を付ける**（`HEXPIRE`。Redis 7.4 以降）。フィールドが 1 つでも残っていればオンライン。
- Hub は、そのインスタンスの中でユーザーの接続が 0 → 1 本になったら Connect、1 → 0 本になったら Disconnect を呼ぶ。接続中は 30 秒ごとに、そのインスタンスのフィールドの TTL を延ばす。
- Connect / Disconnect は Lua スクリプトで行う。**状態の変更と、presence.changed の publish を同じスクリプトの中で行う**。
  - Connect: フィールドを置く。置く前にフィールドがなかったら、online を publish する
  - Disconnect: フィールドを消す。残りがなければ、offline を publish する
- フィールドの数は `HLEN` ではなく `HKEYS` で数える。`HLEN` は、期限が切れてまだ回収されていないフィールドも数えるため（Redis 7.4 の `hlenCommand` は `hashTypeLength(o, 0)`）。
- REST の `online` も、期限内のフィールドが残っているかを Lua スクリプトで 1 往復で読む。
- instanceID は、プロセスを起動するたびに作る ULID。すべてのログにも付ける。

### Redis との接続が切れたとき
- **publish**: `PublishTimeout`（2 秒）で打ち切り、ログに残す。送信 API は、コミットに成功していれば成功を返す（ADR 0004）。
- **購読の確認**: `SubscribeTimeout`（5 秒）で打ち切る。`subscribe` の ack は `internal` になる。接続の登録ができなければ、close コード 1011 で切る（イベントが届かない接続を残さない）。
- **Pub/Sub の接続が切れて戻ったとき**: go-redis は自動で接続を張り直して購読し直すが、それを知らせる API はない。そこで、インスタンスごとの制御用のチャンネル `realtime:instance:{instanceID}` を起動時に購読しておき、**その購読の確認がもう一度届いたら、再接続したと判断する**。
  - 再接続したら、確認を待っている購読を失敗させ、そのインスタンスのすべての WebSocket を **close コード 1012** で切る。クライアントは再接続して、差分を取る（`docs/events.md` の同期の手順）。
- go-redis の `Channel()` は使わず、`ReceiveTimeout` で直接読む。`Channel()` は受け手が遅いとメッセージを黙って捨てるため。直接読めば遅れは Redis の出力バッファに溜まり、上限を超えれば Redis が接続を切るので、上の再接続として検知して 1012 で同期させられる。3 秒なにも届かなければ PING を送り、切れた接続に気づく。

### ロードバランサ（ローカル）
- Caddy をホストの 8080 番に公開し、server のポートは公開しない。振り分け先は `dynamic a server 8080`（DNS を 1 秒ごとに引き直す）で、`--scale` で増えたレプリカと止まったレプリカに追従する。止まったレプリカに当たったら、ほかのレプリカで試し直す（`lb_try_duration` / `fail_duration`）。
- air のビルド先（`/src/tmp`）は、レプリカごとに別のボリュームにする。
- クライアント IP の扱いは ADR 0017。

## 理由

- **自分のイベントも Redis から受け取る理由**: 自分の分だけ直接配ると、同じ接続に届くイベントの順序が「直接の分」と「Redis 経由の分」で入れ替わりうる。1 本にすれば、Redis が処理した順に並ぶ。
- **購読の反映を待つ理由**: 待たないと、ack から SUBSCRIBE が処理されるまでの間に publish されたイベントを取りこぼす。その間に REST を読み終えていると、次のイベントが来るまで気づけない。Phase 4 の保証（ADR 0015）を複数台でも保つ。
- **PING で確かめる理由**: SUBSCRIBE の確認の応答は、再接続したときの購読し直しでも届き、どの SUBSCRIBE への応答かを区別できない。PING に番号を付ければ、確認したい時点を一意に表せる。
- **presence の変更と publish を 1 つのスクリプトにする理由**: インスタンス A の「最後の切断」と B の「最初の接続」が並行したとき、判定と publish を分けると、Redis の中では「offline → online」の順なのに、publish が「online → offline」の順に入れ替わり、接続しているのにオフラインに見える。スクリプトの中なら、状態が変わった順にイベントが並ぶ。
- **HEXPIRE を使う理由**: インスタンスが落ちて Disconnect を呼べなくても、そのインスタンスの分だけが TTL で消える。キーごとの TTL だと、別のインスタンスが延ばし続ける限り、落ちたインスタンスの分が残る。
- **再接続で WebSocket を切る理由**: 切れていた間のイベントは失われている。メッセージは change_seq の欠番で気づけるが、それは次のイベントが来てからで、静かなルームでは気づけない。メンバーの変更や presence には欠番の仕組みがない。すべての接続を切れば、クライアントは既存の同期の手順で揃う。

## 検討した代替案

- **全インスタンスが 1 つのチャンネルを購読する**: 購読の管理も確認の待ち合わせも重複の除去も要らない。ただし、すべてのインスタンスにすべてのイベントが届き、台数とイベント数の積で負荷が増える。ロードマップの決定（接続を持つルームだけを購読する）に合わない。
- **Redis Streams / Kafka で at-least-once にする**: 取りこぼしは減るが、運用するものが増える。ADR 0004 のとおり、差分取得があるので当面は要らない。
- **presence を ZSET にする（メンバーはインスタンスの ID、スコアは期限）**: Redis 7.4 に依存しない。ただし、期限切れのメンバーを自分で掃除する必要があり、時刻の基準（Redis の TIME か各インスタンスの時計か）も決める必要がある。
- **presence をインスタンスごとのキー `presence:{userID}:{instanceID}` にする**: 単純だが、REST の `online` の判定と、0 / 1 の遷移の検出に、パターンでの探索が要る。
- **presence.changed を Lua ではなく Go から publish する**: 上の「理由」の順序の入れ替わりが起きる。
- **再接続しても何もしない**: 次のイベントの change_seq の欠番、または次の再接続まで回復しない。静かなルームや presence では、ずっと古いまま残る。
- **ack を待たずに返し、クライアントに少し待ってから REST を読ませる**: 待つ時間に根拠がない。

## 結果（トレードオフ）

- Redis 7.4 以降が必要になる（compose と CI のイメージを `redis:7.4-alpine` にした）。
- `subscribe` の ack と WebSocket の接続に、Redis の往復が 1〜2 回増える。すでに購読しているチャンネルなら増えない。
- Redis Pub/Sub の接続が切れると、そのインスタンスの全クライアントが再接続して差分を取る。Redis の再起動では、全インスタンスの再接続が一斉に起きる。
- インスタンスが落ちたとき、そのインスタンスにだけ接続していたユーザーの offline は publish されない。REST の `online` は 60 秒で false に戻るが、ほかのクライアントの表示は、メンバー一覧を取り直すまでオンラインのまま残る（ADR 0015 と同じ）。落ちたインスタンスのクライアントは、ほかのインスタンスに再接続するのが普通なので、実際にはオンラインのままで正しいことが多い。
- 権限の変更の再検証の間、そのインスタンスのイベントの受け渡しが止まる。
- 重複の除去は、直近 4096 件の ID しか覚えていない。1 つのイベントのコピーの間に、それ以上のイベントが挟まると、同じ接続に 2 回届くことがある。クライアントはメッセージを `id` で上書きするので、表示は壊れない。
