# 0023. JSON の処理を encoding/json/v2 に統一する

- 状態: 採用
- 日付: 2026-09-16

## 背景

ADR 0022 で、Go の JSON の型から TypeScript の型を生成した。生成器はスライスと map を `T[]` / `Record<string, T>` にするが、`encoding/json`（v1）は `nil` のスライスと map を `null` にする。ハンドラが `make` し忘れると、生成した型と実際の JSON が食い違う。空の一覧は、テストでもレビューでも見落としやすい。

Go 1.27 には `encoding/json/v2` があり、公式のドキュメントは次のように書いている。

- v1 は v2 の上に実装され、v1 の振る舞いは「過去の挙動を保つオプションを付けた v2」である。
- v1 の既定の挙動は安全性の面で劣り、新しく書く JSON の処理には v2 を勧める。

## 決定

- **プロジェクトの JSON の処理をすべて `encoding/json/v2`（と `encoding/json/jsontext`）にする。** 書き出しだけでなく、読み込みも、テストも、Redis に流す JSON も移す。
- `encoding/json`（v1）の import は depguard で禁止する（`.golangci.yml` の `json-v2-only`）。
- サーバーが書き出す JSON（REST のレスポンス、Problem、WebSocket のフレーム）は、`internal/httpx` の `marshalJSON` だけで作る。
  - `json.Deterministic(true)` を付け、map のキーを並べ替える（v1 と同じく、同じ値から同じバイト列を作る）。
- リクエストの読み込み（`decodeJSON`）は `jsontext.Decoder` と `json.UnmarshalDecode` で行う。後ろにゴミが続くボディを拒否する処理はそのまま。
- v1 と意味が変わるタグを直す。
  - ポインタと bool の `omitempty` は `omitzero` にする。v2 の `omitempty` は「空の JSON の値（`""` / `null` / `[]` / `{}`）」を省くので、ポインタが指す `""` を省き、`false` を省かなくなる。v1 と同じ「ゼロ値を省く」は `omitzero`。
  - string・スライス・map の `omitempty` は、v1 と v2 で結果が同じなのでそのまま。
- 生成器のテストに、登録したレスポンスの型をゼロ値のまま `marshalJSON` で書き出し、TypeScript の型が許さない `null` や欠けたフィールドがないことを確かめるテストを足す（`TestTypeScriptResponsesHaveNoUnexpectedNull`）。v1 のままでは 13 の型で落ちることを確認した。

## 理由

- **v2 にする理由**: `nil` のスライスを `[]` にするのが既定なので、ハンドラごとの注意やコーディングのルールに頼らずに、生成した型と JSON が一致する。
- **書き出しだけにしない理由**: 同じ struct のタグを v1 と v2 で別の意味に読むことになり、`omitzero` のような v2 のタグが読み込みの経路では黙って無視される。「なぜここは v1 なのか」を説明し続けるコストが残る。v1 は v2 の上に実装されているので、混ぜても実行時の危険は小さいが、それは移行の途中の状態として許されているだけで、目指す形ではない。
- **読み込みの変化はこのプロジェクトにとって望ましい**
  - フィールド名を大文字小文字まで一致させる。v1 は `"Handle"` を `handle` として読んでいた。クライアントは生成した型で `snake_case` を送る。
  - 重複したキーを拒否する。`{"role":"member","role":"owner"}` のように、検証した値と使う値をずらす入口を塞ぐ。
  - 不正な UTF-8 を拒否する。v1 は黙って U+FFFD に置き換えていた。
- **ゼロ値のテストにする理由**: `nil` のスライスはゼロ値そのものなので、ハンドラごとにテストを書かなくても、登録したすべての型を網羅できる。誰かが v1 に戻したり、`marshalJSON` を通らない書き出しを足したりしても落ちる（後者は depguard でも防ぐ）。

## 検討した代替案

- **コーディングのルールだけにする**（レスポンスのスライスと map は必ず `make` する）: 変更は要らないが、守られているかはレビュー頼みになる。
- **書き出しだけを v2 にする**: 変更は小さいが、上の理由で混在が残る。
- **`writeJSON` で reflect を使って `nil` を空に置き換える**: v2 がやることを自分で作り直すことになり、リクエストのたびに走る。
- **TypeScript の型を `T[] | null` にする**: クライアントの全箇所に `null` の処理が要り、サーバーの都合をクライアントに押しつける。

## 結果（トレードオフ）

- Redis に流す JSON（`internal/chat/realtime` のイベント）で、`nil` のスライスが `[]` になり、受け取ったインスタンスでは空のスライスとして戻る。`len` で扱っていて区別していないので、配信の振る舞いは変わらない。v1 のインスタンスと v2 のインスタンスが混ざっても、`null` と `[]` はどちらも空のスライスとして読めるので、wire の版は上げない。
- v2 は `time.Duration` に既定の表現を持たず、そのままでは読み書きできない。いまは JSON に Duration を載せていない（テストで slog の出力を読むところは `int64` で受ける）。
- v2 は `<` `>` `&` をエスケープしない。レスポンスは `application/json` なので問題ない。
- 読み込みが厳しくなるので、大文字のキーや重複したキーを送るクライアントは 400 か検証エラーになる（テストで固定した）。
- JSON を扱うコードを足すときは、v1 の資料や例をそのまま使えない。タグの `omitempty` と `omitzero` の違いに注意する。
