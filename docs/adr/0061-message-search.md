# 0061. メッセージの検索（Phase 6.16。pg_bigm の 2-gram 索引を「正規化した本文」に張り、authz は読めるルームの集合で絞る）

- 状態: 採用
- 日付: 2026-09-23

## 背景

Phase 6.16 は、ワークスペースのメッセージを検索できるようにする（ロードマップ）。

いちばん大きい論点は**日本語をどう検索するか**だった。Postgres 標準の全文検索（`to_tsvector` / `tsquery`）は、
空白で語を区切る言語を前提にしていて、日本語を分かち書きできない。日本語で使うには、

- **n-gram の索引**（本文を 2 文字や 3 文字の断片に切って GIN に入れ、`LIKE '%語%'` を索引で引く）
- **形態素解析**（MeCab などで語に切る。辞書が要る）
- **別の検索エンジン**（Meilisearch / OpenSearch）

のどれかを選ぶことになる。ローカルの compose と本番の Fly.io（ADR 0046。Postgres は自前のマシン + ボリューム）で
同じものを動かせることも条件になる。

「日本語は 2 文字の語が多いので pg_trgm では引けない」というのは広く言われていることだが、
**この設計で本当にそうなるのかを、実物で測ってから決める**ことにした（Phase 6.10b で「検証せずに妥協を決めない」と決めたのと同じ理由）。

### 検証の結果（2026-09-23）

`postgres:16-alpine` に、日本語のチャット本文を模した 30 万件（52MB、語の頻度は Zipf 分布）を入れて測った。
`max_parallel_workers_per_gather = 0`、3 回実行した最後の `EXPLAIN (ANALYZE)` の値。

| | 「面談」2 文字・939 件 | 「会議」2 文字・63,032 件 | 珍しい語・10 件 | 索引の大きさ | 索引の置き場所 |
|---|---|---|---|---|---|
| **pg_trgm**（標準で入っている） | **23.1ms・Seq Scan** | **23.9ms・Seq Scan** | 0.02ms | 18MB | Postgres 本体 |
| **pg_bigm** | 0.35ms・GIN | 7.7ms・GIN | 0.02ms | 13MB | Postgres 本体 |
| **PGroonga** | 0.62ms | 21.7ms | 0.07ms | **112MB** | Postgres の外（PGDATA 内の別ファイル） |

- **pg_trgm は 3-gram なので、2 文字の検索語では索引が一切使えず seq scan になる**（言われているとおりだった）。
  30 万件で 23ms。メッセージが増えると行数に比例して伸びる。日本語の検索は 2 文字が主役なので、ここは妥協できないと判断した。
- pg_bigm は `postgres:16-alpine` に `icu-dev` と `libxml2-dev` を足せば `make USE_PGXS=1` でビルドできた（約 1 分）。
- PGroonga は公式イメージ（`groonga/pgroonga:4.0.8-alpine-16`）があってビルドは要らないが、
  索引の実体が PostgreSQL のストレージの外（`$PGDATA/base/*/pgrn*`）にあり、本文の 2 倍を超えた。
  よくある語ではむしろ遅い（`&@` 演算子を行ごとに評価する計画になる）。

さらに pg_bigm について、**そのままでは足りないこと**が 2 つ分かった。

- `ILIKE`（大文字小文字を無視）では索引が使えず Seq Scan になる。
- 全角で `ｄｅｐｌｏｙ` と打つと、半角の `deploy` に当たらない。

どちらも、**本文を正規化した式に索引を張る**ことで解決した。`normalize()` は PostgreSQL 13 以降の組み込みで、
`provolatile = 'i'`（IMMUTABLE）なので式索引に使える。

```sql
CREATE INDEX ... ON messages USING gin (lower(normalize(body, NFKC)) gin_bigm_ops);
```

| 検索語 | 結果 |
|---|---|
| `Deploy`（本文は `deploy`） | 6.3ms・索引を使用・4,523 件 |
| `ｄｅｐｌｏｙ`（全角） | 5.8ms・索引を使用・同じ 4,523 件 |
| `面談`（2 文字） | 1.6ms・索引を使用 |
| `議`（1 文字・74,757 件） | 11.5ms・索引は使うが全キーを走査する |

索引の大きさは 13MB（正規化しない場合と同じ）、作成に 3.4 秒。

`room_id` との複合索引（`btree_gin` + `gin (room_id, body gin_bigm_ops)`）も作れることを確かめた（14MB）。
authz の絞り込みを索引に入れる余地があるが、いまの規模では計画が `messages_pkey` を選ぶので、**最初は作らない**（決定 3）。

### Slack で確かめたこと（2026-09-23）

公式ヘルプ「Slack 内で検索する」から分かったこと。

- 上部の検索フィールドに入力し、**モディファイア**で絞り込む。実行後、検索ビューの上部の「フィルター」でも絞り込める。
  つまり Slack は**文字列の修飾子と UI のフィルターの両方**を持つ。
- モディファイアの一覧: `"フレーズ"` / 語の前の `-` で除外 / `in:` / `from:` / `has::絵文字:` / `is:saved`・`has:pin` /
  `before:`・`after:`・`on:`・`during:` / `is:thread` / `with:` / `creator:` / `-in:`・`-from:` で除外
- 3 文字以上の語の一部に `*` を付けると前方一致になる（`rep*` で `reply` や `report`）
- 結果の種類は「メッセージ / ファイル / メンバーディレクトリ / チャンネル / canvas」に分かれる
- アーカイブしたチャンネルの履歴は検索できる（ADR 0059 の背景で確認済み）

未確認（ヘルプに書かれておらず、実物でも確かめていない）:

- **結果の既定の並び順**（「最も関連性が高い」か「最新」か）。並べ替えの UI があることだけが分かっている
  → **解消した**（決定 9 の追記。既定は「関連度順」だった）
- 日本語をどう切っているか（n-gram か形態素解析か）
- ひらがなとカタカナを同じものとして扱うか、全角と半角をそろえるか

### オーナーと確定した内容（2026-09-23）

- **方式は pg_bigm**（上の測定結果を見て確定）
- **並び順は新しい順だけ**。関連度順は作らない
- **絞り込みは、Slack 風の修飾子とフィルターの UI の両方**
- **検索の対象は、読める範囲の全部**: DM・アーカイブ済みチャンネル・スレッドの返信・参加していない public チャンネル

## 決定

### 1. pg_bigm を採用し、Postgres のイメージを自前でビルドする

`db/postgres/Dockerfile` を足し、compose と本番（Fly）の両方がこれを使う。

```dockerfile
FROM postgres:16-alpine
RUN apk add --no-cache --virtual .build build-base curl icu-dev libxml2-dev \
 && curl -sSL https://github.com/pgbigm/pg_bigm/archive/refs/tags/v1.2-20250903.tar.gz -o /tmp/b.tgz \
 && tar xzf /tmp/b.tgz -C /tmp \
 && cd /tmp/pg_bigm-1.2-20250903 \
 && make USE_PGXS=1 with_llvm=no && make USE_PGXS=1 with_llvm=no install \
 && cd / && rm -rf /tmp/pg_bigm-1.2-20250903 /tmp/b.tgz && apk del .build
```

- 版は**タグで固定する**（`v1.2-20250903`）。`latest` を使わない。
- `CREATE EXTENSION pg_bigm` はマイグレーションで行う（`shared_preload_libraries` は要らない）。
- **CI とテストも同じイメージを使う。** 統合テストが素の `postgres:16-alpine` に当たると、拡張がなくて落ちる。
- Postgres のメジャーバージョンを上げるときは、このイメージのビルドが通ることを先に確かめる（`docs/deploy.md` に書く）。

### 2. 索引は「正規化した本文」に張り、検索の対象でない行を部分索引で外す

```sql
CREATE INDEX messages_body_search_idx ON messages
    USING gin (lower(normalize(body, NFKC)) gin_bigm_ops)
    WHERE deleted_at IS NULL AND kind = 'user';
```

- **正規化は `lower(normalize(body, NFKC))`。** 検索語にも同じ関数を通す。これで大文字小文字と全角半角の違いを吸収する（検証済み）。
  ひらがなとカタカナは NFKC では同一にならない。**そこまではやらない**（Slack の挙動も未確認なので、必要なら別の ADR で足す）。
- **削除済み（`deleted_at IS NOT NULL`）とシステムメッセージ（`kind = 'system'`）を部分索引から外す。**
  削除済みは結果に出さない（DoD）。システムメッセージは人の発言ではない（ADR 0033）ので、
  リアクションやピン留めと同じ扱いにする。索引も小さくなる。
- 編集された本文で見つかるのは、`messages.body` を更新しているので自動的にそうなる（DoD）。**検索用の別テーブルを持たない。**

### 3. authz は「読めるルームの集合」を 1 つの CTE にして絞る

絶対ルール 9 のとおり、判定は authz の規則に従う。SQL では `authz.CanReadRoom` と同じ条件を 1 か所の CTE で書く。

```sql
WITH readable_rooms AS (
    SELECT r.id, r.kind
      FROM rooms r
      LEFT JOIN room_members rm ON rm.room_id = r.id AND rm.user_id = @user_id
     WHERE r.workspace_id = @workspace_id
       -- public はワークスペースのメンバーなら参加していなくても読める。private / dm はメンバーだけ
       AND (r.kind = 'public' OR rm.user_id IS NOT NULL)
)
```

- **呼び出す前に、actor がワークスペースのメンバーであることを確かめる**（`CanReadRoom` の最初の条件）。メンバーでなければ 404。
- ルームを 1 件ずつ判定しない（N+1 にしない）。1 本のクエリの中で結合する。
- **アーカイブ済みのルームは除外しない。** アーカイブは「書けない」であって「読めない」ではない（ADR 0059 決定 2）。
- 削除されたルームは行ごと消えているので、何もしなくても出ない（ADR 0059 決定 6）。
- **`readable_rooms` は authz の規則の写しになるので、`authz_test.go` の組み合わせと同じ表を DB のテストでも回す。**
  authz を変えたときにこの CTE を直し忘れると、読めないメッセージが検索で漏れる。

### 4. 並びは新しい順だけ。カーソルは `(created_at, id)`

ルームをまたぐので `seq` は使えない（`seq` はルームごとの番号。絶対ルール 3 が禁じているのは「ルーム内の順序を `created_at` で決めること」で、
ルームをまたいだ一覧の見せ方はその対象ではない。ADR 0058 のアクティビティと同じ整理）。

```sql
 WHERE (m.created_at, m.id) < (@before_at, @before_id)
 ORDER BY m.created_at DESC, m.id DESC
 LIMIT @max_rows
```

- 同じ時刻のときは `id`（ULID）で決める。`OFFSET` は使わない。
- 関連度順は作らない（オーナーの確定）。pg_bigm には語の重みがないので、作るなら自前でスコアを決めることになる。
  必要になったら別の ADR で扱う。
- **総件数（「〜件の結果」）は返さない。** 数えるには全件を走査することになる。
  Slack のように件数を出したくなったら、上限付きの概数（`LIMIT 1000` までを数える）を別に足す。

### 5. 修飾子は**クライアントが解釈し、API は構造化された条件だけを受け取る**

Slack と同じく、入力欄の `in:#general from:@taro` でも、結果の画面のフィルターでも絞り込めるようにする。
**2 つの入り口を 1 つの状態に繋げる**ため、クライアントに次の組を置く。

- `parseSearchQuery(text) → SearchQuery`（入力欄 → 条件）
- `formatSearchQuery(SearchQuery) → text`（フィルターの操作 → 入力欄の表示）

フィルターの UI は `SearchQuery` を編集し、入力欄はそれを整形して見せる。どちらを触っても同じ状態が動く。

Phase 6.16 で作る修飾子:

| 修飾子 | 意味 | `SearchQuery` |
|---|---|---|
| `"..."` | フレーズ（そのままの並びで探す） | `terms[].phrase` |
| `-語` | その語を含むものを除く | `terms[].exclude` |
| `in:#名前` / `in:@表示名` | そのチャンネル / DM の中 | `room_ids` |
| `from:@表示名` | その人の発言 | `sender_ids` |
| `before:` / `after:` / `on:` | 日付で絞る | `before` / `after` |
| `-in:` / `-from:` | 除外 | `exclude_room_ids` / `exclude_sender_ids` |

- **名前から ID への解決はクライアントで行う。** チャンネルの一覧もメンバーの一覧もすでに持っており、
  クライアントが知らないルーム = 読めないルームなので、解決できない名前はそのまま「見つからない」でよい。
  サーバーが名前で受け取ると、読めないチャンネルの存在が「名前が有効かどうか」で漏れる（ADR 0011 と同じ理由）。
- `during:`（月・年）は `before` / `after` に展開してから送る。日付はクライアントの時間帯で解釈し、`timestamptz` にして送る。
- **今回作らない**（スコープ外。必要になったら足す）: `has::絵文字:` / `is:saved` / `has:pin` / `is:thread` / `with:` / `*` の前方一致。
  ファイル・チャンネル・メンバーを探すタブ（Slack の「ファイル」「チャンネル」など）も作らない。検索するのはメッセージだけ。

### 6. 本文の条件の組み立て方

`SearchQuery.terms` は AND で繋ぐ。正規化した式に対して `LIKE` を組む。

```sql
AND lower(normalize(m.body, NFKC)) LIKE @term_1  -- '%' || 正規化した語 || '%'
AND lower(normalize(m.body, NFKC)) NOT LIKE @term_2
```

- 検索語は `%` `_` `\` を**エスケープしてから** `%...%` で挟む。エスケープを忘れると、`%` を含む検索が全件に当たる。
- `NOT LIKE`（除外）は索引を使えないが、肯定の語が 1 つ以上あればそちらが索引を引き、除外は再チェックで効く。
  **肯定の語が 1 つもない検索（`-報告` だけ）は 422 で断る。**
- 空白で区切った複数の語は AND。フレーズは引用符の中をそのまま 1 つの語として扱う。
- `q` の長さの上限を決める（語は 8 個まで、全体で 200 文字まで）。1 文字の語は許す（日本語には 1 文字の語がある）。
  1 文字では索引の全キーを走査する（30 万件で 11.5ms）が、許容する。

### 7. 結果の 1 件は、メッセージの表示に必要なものを一度に返す

結果の行には、本文・送信者・時刻のほかに**ルーム**（どのチャンネルの発言か）と、スレッドの返信なら**親**が要る。

- ルーム名・送信者の表示名は、1 本のクエリの中で `JOIN` して返す（N+1 にしない。`ListMessageViewsByIDs` と同じ考え方）。
- スレッドの返信は `thread_root_id` を返し、押したらスレッドを開く（決定 8）。
- 一致した部分の強調は**クライアントで行う**。サーバーは本文をそのまま返し、
  Web 側が 6.10 の本文の解釈（`web/lib/chat/format`）の上に「一致した範囲」を重ねる。サーバーで HTML を作らない。
- 押したら 6.11 の「指定したメッセージへ飛ぶ」に乗せる（`?message=` のパーマリンク。ADR 0042）。
  読めるかどうかは飛んだ先でもう一度判定されるので、検索の結果が古くても権限は漏れない。

### 8. API

```
GET /api/v1/workspaces/{workspaceID}/search/messages
    ?q=<検索語（修飾子を除いた本文の条件）>
    &room_id=<ULID>（複数可）&exclude_room_id=<ULID>（複数可）
    &sender_id=<ULID>（複数可）&exclude_sender_id=<ULID>（複数可）
    &after=<RFC3339>&before=<RFC3339>
    &limit=<1..50、既定 20>&cursor=<前のページの next_cursor>
```

- 返すのは `{ "items": [...], "next_cursor": "..." }`。`next_cursor` が空なら終わり。
- WebSocket のイベントは**作らない**。検索は要求したときに引くものなので、再接続の同期（絶対ルール 4）の対象にしない。
  開いたまま新しい発言が来ても結果は変わらない（Slack と同じ）。
- ワークスペースのメンバーでなければ 404。`q` が空・肯定の語がない・`limit` が範囲外は 422（`application/problem+json`）。

### 9. 検索の入口は、画面のいちばん上に新しく置く全幅の帯（2026-09-23 の追記）

構築順 2 の途中で、オーナーから Slack の実物のスクリーンショットをもらって確かめた。**背景の「未確認」が 2 つ解消した。**

- Slack の検索欄は、`rail` / サイドバー / メインの**上にある全幅の帯**にある（左に「戻る・進む・履歴」、右にアバターとヘルプ）
- 検索欄を押すと、その場で下に開くパネルになる（チップの行・候補の行・一致したメッセージのプレビュー）
- 結果の画面では**サイドバーが畳まれ、`rail` ＋ 全幅のメイン**になる。上に見出し・フィルターの行・並べ替え
- **並べ替えの既定は「関連度順（デフォルト）」だった**（背景の「未確認」の 1 つめ）
- **件数を出していた**（「1 件の結果」）
- 一致した部分は黄色の地で塗る
- フィルターは「検索フィルター」というダイアログで、中身がスクロールし、下に「フィルターをクリアする」「検索」が固定で並ぶ

実物と違う点が 2 つあるが、**どちらも決定を変えない**（オーナーの確認。2026-09-23）。

| | Slack の実物 | hibari | 理由 |
|---|---|---|---|
| 並べ替えの既定 | 関連度順 | 新しい順だけ | pg_bigm に語の重みがない。自前のスコアは根拠が恣意的になる（決定 4） |
| 件数 | 出す | 出さない | O(1) で出せない（決定 4） |

**決めたこと:**

- **入口は上部の帯**（Slack と同じ）。`ChatLayout` に `topBar` を足し、`rail` とサイドバーはその下から始める。
  帯に置くのは**検索欄と「戻る・進む」だけ**。ワークスペースの切り替えと自分のアバターは `rail` の上下に残す（オーナーの判断）。
- **検索欄はボタンにして、押したときだけ入力欄を持つパネルを重ねる。** 常に入力欄を置くと、閉じる先のないフォーカスを作ることになる。
- **パネルに出すのは候補の行まで**（「〜 の検索結果を表示する［Enter］」と「#〜 で検索する」）。
  Slack は打つたびに一致したメッセージのプレビューも出すが、入力ごとの検索（debounce と前の要求の中断）が要るので 6.16 では作らない（オーナーの判断）。
- **結果の画面ではサイドバーを畳む**（Slack と同じ）。`ChatLayout` の `sidebar` を省くとその列ごと出さない。
- **一致した部分の地に `--color-highlight` を足す**（オーナーの確認。2026-09-23）。
  値は Slack の黄色そのままではなく、hibari の面に合う彩度の高い琥珀にした。
  琥珀（いま起きていること）と黄土（ピン留め）より彩度を上げ、未読の印やピン留めした行と見分けられるようにする。
- **フィルターのダイアログに作るのは送信者・場所・日付の 3 つだけ**（決定 5 の修飾子と同じ範囲）。
  Slack のファイルタイプ・絵文字リアクション・メッセージの状態はスコープ外。

## 理由

- **pg_bigm を選んだのは、索引が Postgres 本体のものだから。** ただの GIN 索引なので、`pg_dump` にも WAL にも
  Fly のボリュームのスナップショットにも、いまの扱いのまま乗る（ADR 0046 のバックアップの手順を変えなくていい）。
  PGroonga は索引が Postgres の外にあり、バックアップと復旧の手順、レプリケーションの考え方がそこだけ別になる。
  「1 つのものを 2 つの仕組みで守る」状態を避けた。将来 `btree_gin` で `room_id` と複合にできる余地があるのも、
  標準の GIN だからこそ。
- **pg_trgm を落としたのは、測った結果 2 文字で索引が使えなかったから。** 追加のイメージが要らない利点は大きいが、
  日本語の検索の主役が seq scan になるのでは機能として成立しない。
- **検索用の別テーブルやマテリアライズドビューを作らないのは、同期のずれを持ち込まないため。**
  メッセージの編集・削除・ルームの削除がそのまま反映される（`messages` を直接引くので、反映のための仕組みが要らない）。
- **修飾子をクライアントで解釈するのは、API を 1 つに保つため。** サーバーが文字列を解釈すると、
  フィルターの UI と修飾子で 2 つの入り口ができ、片方だけが直る事故が起きる。
  名前から ID への解決をクライアントに置くのは、読めないルームの存在を漏らさないためでもある。
- **総件数を返さないのは、O(1) で出せないから。** 未読数で「削除済みも数える近似」を許した（CLAUDE.md）のと違い、
  検索の件数は近似の意味が薄い。出さないほうが正直。

## 検討した代替案

- **PGroonga**: 公式イメージがあってビルドが要らず、関連度スコアと MeCab の形態素解析が使える。
  索引が Postgres の外（本文の 2 倍の大きさ）にあり、バックアップと復旧がそこだけ別の手順になる。
  測定でもよくある語で 20ms 超と速くはなかった。関連度順を作ることになったら、ここに戻ってくる。
- **pg_trgm のまま**: 追加のものが何も要らない。2 文字の日本語で seq scan になるので落とした（上の測定）。
- **形態素解析（MeCab + textsearch_ja）**: 索引が小さく、語の単位で引けるので精度が高い。
  辞書の更新が運用に加わり、辞書にない語（社内の固有名詞、チャンネル名）が引けなくなる。
  チャットは造語と固有名詞が多いので、取りこぼさない n-gram のほうが向いている。
- **外部の検索エンジン（Meilisearch / OpenSearch）**: 日本語も関連度も強い。
  Fly にもう 1 app とボリュームが増え、メッセージの追加・編集・削除・ルームの削除・アーカイブを同期し続ける経路が要る。
  さらに authz を検索側にも持つか、検索結果を Postgres で絞り直すかの二重管理になる。
  「配信は落ちうる前提で設計する」（絶対ルール 4）と同じ問題を検索でも抱えることになるので、今の規模では採らない。
- **`room_id` との複合索引を最初から作る**: authz の絞り込みを索引に入れられる（検証済み・14MB）。
  いまの規模では計画が `messages_pkey` の逆順走査を選ぶので効かず、書き込みのコストだけが増える。
  遅いことが測れてから足す。

## 結果（トレードオフ）

- **Postgres のイメージを自前で持つことになる。** compose・CI・Fly の 3 か所が同じ Dockerfile を使う。
  Postgres のメジャー更新のたびに、ビルドが通るかを先に確かめる作業が増える。
  素の `postgres:16-alpine` では統合テストが動かなくなる。
- **GIN 索引のぶん、投稿が少しだけ重くなる。** GIN は `fastupdate` で挿入を遅延させるので、
  まとまったタイミングで索引の更新が走る。30 万件で索引は 13MB（本文の約 25%）。
- **1 文字の検索は索引の全キーを走査する**（30 万件で 11.5ms）。件数が増えると伸びる。
  遅くなったら `bigm.gin_key_limit` で上限を付けるか、最小の文字数を決める。
- **関連度順がない。** 「よく話題になった語」で探すと、新しいものから順に出るだけになる。
  Slack の既定（未確認）と違う可能性がある。
- **ひらがな・カタカナの違いは吸収しない。** 「ラーメン」で「らーめん」は見つからない。
- 検索の結果は要求した時点のもの。開いたまま新しい発言が来ても増えない。
