# 0006. ワークスペース層・固定ロール・招待リンク

- 状態: 採用
- 日付: 2026-09-13

## 背景

当初の ERD では、ルーム（dm / group）がユーザーの直下にあり、ロールは `room_members.role`（owner / member）だけだった。これには次の問題があった。

- グループへの参加手段がメンバーの直接追加だけで、招待の仕組みがない。
- 誰が何をできるかの権限モデルがない。
- 同じ 2 人の DM が何個でも作れる。

より実践的な題材にするため、Slack / Discord 型の「ワークスペース（サーバー）→ チャンネル」構成と、ロールに基づく招待・管理を入れる。

## 決定

### 階層
- `workspaces` → `rooms`（kind: `public` / `private` / `dm`）→ `messages`。
- コード上は `room` と呼び、UI の表示だけ「チャンネル」にする。コード上の「channel」は Redis Pub/Sub のチャンネルや Go の channel と紛らわしいため。
- DM はワークスペース内に閉じる。`dm_key`（2 人の userID をソートして連結した値）に `UNIQUE(workspace_id, dm_key) WHERE kind = 'dm'` を張る。

### ロール
- ワークスペース単位の固定ロール `owner > admin > member`。ルーム単位のロールとカスタムロールは持たない。
- 判定は 2 つの関数で表す。
  - `canManage(actor, target)`: actor のロールが target より上
  - `canGrant(actor, role)`: 付与するロールが actor 以下で、かつ owner ではない
  - ロール変更 = `canManage(actor, target) && canGrant(actor, newRole)`
- 帰結: admin は member を admin に昇格できるが、他の admin を降格もキックもできない。owner は admin を降格できる。
- **owner は常に 1 人**で、昇格ではなく「譲渡」という別の操作で移す。旧 owner は admin になる。`UNIQUE(workspace_id) WHERE role = 'owner'` の部分 UNIQUE 制約で DB が保証する。
- owner は譲渡するまで退出できない。

### 権限表

| 操作 | owner | admin | member |
|---|---|---|---|
| 招待リンクの作成 | ✓ | ✓ | `invite_policy = all_members` なら ✓ |
| `invite_policy` の変更 | ✓ | ✓ | – |
| public / private ルームの作成 | ✓ | ✓ | ✓ |
| public ルームへの参加（自分で） | ✓ | ✓ | ✓ |
| private ルームへの追加 | ルームのメンバーなら ✓ | 同左 | 同左 |
| ワークスペースからキック | admin, member | member | – |
| ロール変更 | admin ↔ member | member → admin | – |
| owner の譲渡 | ✓ | – | – |
| 退出 | 譲渡した後なら可 | ✓ | ✓ |

### 閲覧
- public ルームは、ワークスペースのメンバーなら参加していなくても読める。投稿には参加が必要。
- private / dm ルームはメンバーだけが読める。参加前の履歴も読める。
- 退出したら、そのルームの `room_members` の行を削除する（在籍期間の履歴は持たない）。

### 招待
- ワークスペース単位の招待リンク（`workspace_invites`）。`max_uses`（null は無制限）、`expires_at`、`revoked_at` を持つ。
- コードはランダム値で、DB には SHA-256 のハッシュだけを保存する。生のコードは作成時に 1 度だけ返す。
- 受け入れると、ワークスペースと `is_default = true` のルームに自動で参加する（同一トランザクション）。
- 使用回数の加算は条件付き UPDATE で行い、並行した受け入れでも上限を超えない。
- すでにメンバーなら、使用回数を消費せずに成功を返す。

### 権限の変更と WebSocket
- キック、ロール変更、ルームからの削除は、該当ユーザーの WS 購読をサーバー側で即座に解除し、イベントを配信する（CLAUDE.md ルール 8）。

## 理由

- **学習の題材として**: 条件付き UPDATE による使用回数の加算、部分 UNIQUE による owner の一意性、行ロックを伴う譲渡、authz レイヤの集約、権限変更のリアルタイムな反映は、いずれも実務で頻出する設計課題。
- **固定ロールにする理由**: カスタムロールや権限ビットは、UI・API・マイグレーションのすべてを複雑にするわりに、学べる本質（階層の比較と一意性の保証）は固定ロールで十分に得られる。
- **owner を 1 人にする理由**: 同格の owner を複数許すと、互いに降格もキックもできないので、悪意ある共同 owner を排除する手段がなくなる。
- **DM をワークスペース内に閉じる理由**: 「同じワークスペースのメンバーとしか DM できない」ので、ブロック機能がなくても見知らぬ人からの DM を防げる。authz も単純になる。
- **招待コードをハッシュで保存する理由**: 招待コードは「知っていれば参加できる」bearer な秘密であり、Refresh Token と同じ扱いにする。DB が漏洩しても有効な招待を作れない。

## 検討した代替案

- **ワークスペース層を入れない（ルーム単位のロールと招待）**: スキーマと API は半分で済むが、Slack / Discord 型の実践的な権限モデルにならない。
- **複数 owner**: 上記の理由で不採用。
- **Discord 型のカスタムロール + 権限ビット**: 表現力は高いが範囲外。
- **招待コードを平文で保存し、一覧で再表示できるようにする**: UX は良いが、秘密の扱いが Refresh Token と不一致になる。一覧では作成者・期限・使用回数だけを表示する。
- **メールアドレス宛ての招待**: Mailer が本実装になってから検討する（Phase 7 以降）。

## 結果（トレードオフ）

- Phase 3 の範囲が大きくなったので、3a（ワークスペース / ロール / 招待 / ルーム）と 3b（メッセージ）に分割した。
- イベントの種類が増える（`workspace.member_removed`、`workspace.role_changed`、`room.member_removed` など）。
- Phase 5 では、ユーザー宛てのイベントを配信するための `user:{userID}` チャンネルが必要になる。
- Phase 1.5 で、ワークスペースの切り替え・招待・メンバー管理の画面がデザインに必要になる。
- スコープ外: ブロック機能、グループ DM、ルーム単位のロール、カスタムロール。
