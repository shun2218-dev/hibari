# 0005. ULID を Postgres の uuid 型で保存する

- 状態: 採用
- 日付: 2026-09-13

## 背景

ID には ULID（`oklog/ulid`）を使う方針だった。一方で ERD の型は `uuid` で、注記には「ULID 文字列でも可」とあり、保存形式が決まっていなかった。

## 決定

- ID はアプリケーション側で ULID として生成する（`platform` の ID 生成器経由）。
- DB には **`uuid` 型（128 ビットのバイナリ）**で保存する。ULID と UUID はどちらも 128 ビットなので、ロスなく変換できる。
- API の入出力では ULID の文字列表現（26 文字の Crockford Base32）を使う。
- 変換は pgx の型登録（または sqlc の型の上書き）で 1 箇所に閉じ込め、ドメイン層では `ulid.ULID` 型で扱う。
- DB の既定値（`gen_random_uuid()` など）は使わない。

## 理由

- **サイズ**: `uuid` は 16 バイト、`text` の ULID は 26 バイト以上に加えて照合順序の比較コストがかかる。インデックスが大きいテーブル（messages）で効く。
- **時刻順の局所性**: ULID は先頭が時刻なので、B-tree への挿入が末尾に集中し、ランダムな UUIDv4 よりページ分割が少ない。
- **型の安全性**: `uuid` 型なら不正な文字列が DB に入らない。
- **テストで固定できる**: アプリで生成するので、Clock と乱数源を差し替えれば ID を決定的にできる。

## 検討した代替案

- **`text` で ULID 文字列を保存**: psql での可読性は高いが、サイズと比較コストで劣る。
- **UUIDv7**: 時刻順の UUID で Postgres 18 ではネイティブに生成できるが、スタックは ULID で確定しているのでそちらに合わせる。性質はほぼ同じなので、将来移行するのも容易。
- **bigserial**: 小さく速いが、ID から件数や作成順が推測でき、クライアント側で事前に生成することもできない（`client_msg_id` と相性が悪い）。

## 結果（トレードオフ）

- psql で見ると UUID 形式で表示され、API の ULID 文字列と見た目が一致しない。デバッグ用に変換関数（SQL 関数か Makefile のヘルパー）を用意する。
- ULID のミリ秒以内の単調性はインスタンスをまたぐと保証されない。ID を順序の根拠にしない（順序は seq。ADR 0002）。
