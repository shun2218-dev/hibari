# 0067. ハドルの一覧・ハドル中の印・ハドルへのリンク（Phase 6.18c。リンクはルームを指し、印はワークスペースの中だけに出す）

- 状態: 採用

## 背景

ADR 0066 の追記 C で、Slack にある次の 3 つを 6.18a から外し、Phase 6.18c で別の ADR にすると決めた（オーナーの判断、2026-09-26）。
6.18a は完了した（ロードマップの DoD 16/16、2026-09-27）ので、その上に足す。

- サイドバーの「ハドルミーティング」の一覧
- ハドル中の印（名前の横・メンバーの一覧・プロフィール・自分のアバター）
- ハドルへのリンクと、本文に貼られたリンクのカード

一覧の画面は、オーナーが示した Slack の実物のスクリーンショット（2026-09-26）をロードマップに記録してある。

- サイドバーの「スレッド」の下に「ハドルミーティング」の行。押すとメインの領域に一覧の画面
- 右上に「＋ 新規ハドルミーティング」
- 上に、よく使う場所でハドルを始める提案のカード（「#… でハドルミーティングを開始しますか？ 過去 1 週間にここで 1 回ハドルミーティングを実施しました」と相手の顔）
- 「最近のハドルミーティング」: 絞り込み（すべてのハドルミーティング / 相手 / 場所）と、1 行ずつ「ヘッドフォンのアイコン・#ルーム名・7 時間前 · 2 分 · 1 件の返信（押すとスレッド）・参加者の顔・「…」のメニュー」

## 決定

### 1. ハドルへのリンクはルームを指す（Slack と同じ）

- URL は `{origin}/w/{workspaceId}/r/{roomId}?huddle=1`。ルームの URL にクエリを 1 つ足した形にする。
  - メッセージのリンク（`?m=`、ADR 0040）・スレッド（`&t=`）と同じく、ページのパスを増やさずクエリで表す。
  - 1 回ごとのハドル（`huddles.id`）ではなくルームを指すのは、Slack と同じく、**始まる前に共有できて、何度でも使える**ようにするため（予定の招待に貼るなど）。
    ルームにハドルは同時に 1 つなので（ADR 0066 決定 3）、「そのルームのいまのハドル」で一意に決まる。
- **リンクは入る権利ではない。** 秘密を含まず、開いた人ごとに authz を通す（ADR 0066 決定 7）。外に漏れても、ルームに投稿できない人は入れない。
- 開いたときの振る舞い（見る人ごと）

| 見る人 | 開いたとき |
|---|---|
| ルームに投稿できる（`CanJoinHuddle`） | ルームを開き、**参加前のプレビュー**（ADR 0066 追記 B）を出す。進行中なら「参加する」、なければ「開始する」 |
| public のチャンネルを読めるが、参加していない | ルームを開き、プレビューに「チャンネルに参加すると入れます」と「チャンネルに参加する」を出す。参加したらそのままプレビューを続ける |
| アーカイブしたルーム | ルームを開き、プレビューに入れないことを出す（409 `room-archived` と同じ文言） |
| ルームを読めない・ない | 読めないルームの URL を開いたときと同じ表示（新しい表示を作らない） |
| 別のハドルに入っている | プレビューはそのまま出す。入ると前のハドルから抜ける（ADR 0066 決定 6。いまの振る舞いのまま） |

- **押しただけでは入らない。** 必ずプレビューを通す。うっかり押したリンクでマイクが会話に流れないようにするためと、マイクの許可と機器の選択を本人にさせるため（ADR 0066 追記 B）。
- コピーする場所
  - ルームのヘッダーのハドルのボタンの横にメニューを付け、「ハドルミーティングのリンクをコピー」を置く（Slack の矢印に当たる）。ハドルが進行中でなくても出す。
  - ハドルの画面（別のタブ）と、チャットのタブの下のハドルの帯。
  - 一覧の各行の「…」（決定 6）。
  - コピーしたら、メッセージの「リンクをコピー」と同じく項目の文言を「コピーしました」に変える（ADR 0040。トーストは出さない）。

### 2. 本文に貼られたハドルのリンクはカードにする（見る人ごとに authz）

- 見つけるのはクライアント（ADR 0040 と同じ。コードの中の URL は数えない）。`?huddle=1` があり `m` がない、同じ origin の `w/{ulid}/r/{ulid}` をハドルのリンクとして扱う。
  `m` があればこれまでどおりメッセージのリンク。カードの数の上限（1 件のメッセージに 3 枚）は、メッセージのリンクと合わせて数える。
- 外部のリンクのプレビュー（ADR 0065）は、同じ origin の URL をすでに除いているので、変えることはない。
- 取得は新しい API にまとめて 1 回で頼む。

```
POST /api/v1/huddles/links
     { "room_ids": ["01J...", ...] }                     最大 20
     → { "links": [
          { "room_id": "01J...", "status": "ok",
            "workspace": { "id": "...", "name": "..." },
            "room": { "id": "...", "kind": "public", "name": "general", "dm_peer": null },
            "huddle": { ...ルームの応答と同じ RoomHuddle... } | null,
            "can_join": true },
          { "room_id": "01J...", "status": "unavailable" }
        ] }
```

- 読めるかは**見る人の権限**で決める（投稿した人の権限ではない。ADR 0040 と同じ）。ルームがない・読めないは、区別せず `unavailable`。
  `can_join` は `authz.CanJoinHuddle`。判断は authz だけがする（ルール 9）。
- `GET /api/v1/rooms/{id}` を部屋ごとに呼ばないのは、タイムラインに何枚あっても 1 回で済ませるためと、読めないルームを 404 ではなく `unavailable` にそろえるため（ADR 0040 の `POST /messages/links` と同じ理由）。
  メッセージのリンクの API に混ぜないのは、応答の形がまったく違い、型を分けた方が読みやすいため。
- カードの形（見る人ごと）

- 形は Slack の実物に合わせる。上の段にヘッドフォンのアイコン・「ハドルミーティングのリンクが共有されました」・「`#ルーム名` 内」（DM なら相手の名前）。下の段にボタン。

| 状態 | 下の段 |
|---|---|
| 進行中でない | `can_join` なら「ハドルミーティングを開始する」（緑。Slack の実物） |
| 進行中で、自分は入っていない | 「ライブ」（琥珀）・入っている人の顔と人数。`can_join` なら「参加する」（緑） |
| 進行中で、自分が入っている | 上と同じで、ボタンの代わりに「参加中」。押すとハドルの画面を前に出す |
| `unavailable` | 上の段だけ「アクセスできないハドルミーティング」（メッセージのリンクの「アクセスできないメッセージ」と同じ扱い）。下の段は出さない |

- 進行中のときの Slack のカードは見ていない。進行中の形は、一覧のカード（決定 6）とそろえる。

- ボタンはどれも決定 1 のリンクを開くのと同じ（プレビューを通す）。
- **カードは生きている状態を映す。** メッセージのリンクのカードは取得した時点のまま更新しない（ADR 0040）が、ハドルは「いま進行中か」が本題なので、古いままでは誤った「参加する」を出してしまう。
  - そのルームを手元のストアに持っている（サイドバーのルーム。購読していて `huddle.updated` が届く）なら、**ストアの状態から描く**。
  - 持っていない（参加していない public のチャンネル、別のワークスペース）なら、取得した時点の状態を出す。押せばプレビューが取り直すので、誤って入ることはない。
  - 入れる（`can_join`）のはメンバーだけなので、「参加する」を出すカードはほぼすべて前者になる。

### 3. ハドル中の印は、Redis の集合で持ち、そのワークスペースにだけ配る

- **出すのは「ハドル中であること」だけ。** どのルームかは出さない（private のルームや DM のハドルの存在を漏らさない）。
- **そのハドルがあるワークスペースでだけ出す。** Slack の「ハドルミーティング中」のステータスがワークスペースごとなのと、hibari のカスタムステータスもワークスペースごと（ADR 0049 決定 5）なのに合わせる。
  別のワークスペースの人に、どこかで通話していることを知らせない。
- 置き場所: Redis の集合 `huddle_members:{workspaceID}`（中身はユーザー ID）。自動で変わる状態なので Postgres に書かない（ルール 5）。
  - 足す・除くのは、いまある「1 人 1 つ」のキー（`huddle_user:{userID}`。ADR 0066 追記 E）を書き換える Lua の中で一緒に行う。入る・移る（別のハドルへ）・抜ける・外される・期限切れのどれも、同じ Lua を通る。
  - 期限は持たない。`huddle_user` と同じく、参加を外すときに必ず一緒に消す（掃除のジョブが期限切れを外すので、残り続けない）。
  - 外すときにどのワークスペースの集合から除くかを知るため、`huddle_user` の値にワークスペースの ID を足す（いまはハドルの ID と参加の ID だけ）。
- イベント: `member.huddle_changed`（宛先はそのワークスペース）。

```
{ "type": "member.huddle_changed",
  "data": { "workspace_id": "01J...", "user_id": "01J...", "in_huddle": true } }
```

  - **集合に入った・出たときだけ**配る（`SADD` / `SREM` が 1 を返したとき）。同じワークスペースの中で別のハドルに移っても、別の端末に移っても配らない。
    別のワークスペースのハドルに移ったら、前のワークスペースに `false`、新しいワークスペースに `true` を配る。
  - 配るのも Lua の中で行う（presence の `syncScript` と同じ。ADR 0016）。入る・抜けるが別のインスタンスで続けて起きても、集合の変化と配る順番が食い違わない。
    配る内容の作り方（Go が先に作って渡すか、Lua の中で組み立てるか）は構築順 3 で決める。外すときは、どのワークスペースかを Lua の中で `huddle_user` から読むので、Go が先に作れない場合がある。
  - Pub/Sub は at-most-once なので落ちうる（ルール 4）。取りこぼしは次の決定の REST で直る。
- REST: ワークスペースのメンバー一覧・1 人の取得（プロフィール。ADR 0050）・ルームのメンバー一覧に `in_huddle`（bool）を足す。
  - 読むのは `SMISMEMBER huddle_members:{workspaceID} u1 u2 ...` の 1 回（N+1 にしない）。
  - `away` と `status` と同じく、メンバー一覧にだけ載せる（ADR 0049 決定 7 の追記）。DM の相手やメッセージの送り主は、クライアントがメンバー一覧から引く。
  - Redis が読めないときは、presence と同じく警告のログを出して `false` にする（一覧を 500 にしない）。
- 再接続の同期: presence と同じく、つながり直したらメンバー一覧を取り直す（ADR 0049 決定 9）。仕組みを足さない。

### 4. ハドル中の印の見た目: ステータスがないときだけ、ステータスの位置に 🎧 を出す（Slack と同じ）

- **本人がカスタムステータスを設定していれば、それを出す。設定していないときだけ、ハドル中は 🎧（ヘッドフォンの絵文字）と「ハドルミーティング中」を出す**（オーナーが Slack の実物で確かめた形）。
  - 出す場所は、いまカスタムステータスの絵文字を出しているところ全部（メッセージの送り主・メンバーのパネル・サイドバーの DM の行・メンバーの一覧・プロフィールのカード）。
  - 絵文字はカスタムステータスと同じ扱いの中身なので、色のトークンの決まり（琥珀）には当たらない。押せないのもカスタムステータスと同じ。
- **ステータスそのもの（Postgres）は書き換えない。** 読む側で「本人のステータス、なければハドル中」に合わせる（ルール 5。ADR 0049 の presence と手動の離席と同じ形）。
  合わせるのは Web の 1 か所（メンバーのステータスの見え方を作るところ。いまの `statusView`）にする。
  書き換えると、抜けたときに元に戻す処理と、その間に本人がステータスを変えたときの扱いが要る。
- **ステータスを設定している人のハドル中は、プロフィールのカードでだけ分かるようにする**（オーナーが「バランスを見て決めたい」とした点。オーナーの確認済み）。
  - カードには、カスタムステータスの行に加えて「🎧 ハドルミーティング中」の行を出す。名前の横は Slack と同じく、カスタムステータスのまま。
  - アバターに印を付けない理由（アバターに付ける案は「検討した代替案」）
    - アバターの右下にはすでに presence のドットがある。サイドバーやメンバーの一覧の小さなアバターに 2 つ目の印を載せると、どちらも読みにくくなる。
    - タイムラインのアバターは過去のメッセージに付くもので、そこに「いま」の状態を出すと、流れの中で同じ人の印が並び、うるさい。
    - 「いま話しかけてよいか」を知りたくなるのは、その人に連絡しようとしたとき。名前やアバターを押して開くプロフィールのカードで分かれば足りる。
- **自分のアバター（レール）**: Slack はアバターの上にステータスの絵文字を載せている（スクリーンショット。ステータスがないので 🎧 が出ていた）。hibari もレール（画面の左端の縦の列）の自分のアバターに、上と同じ規則の絵文字を載せる（オーナーの確認済み）。
  - いまの hibari は、自分のステータスをアカウントのメニューの中にだけ出している。これを足すと、ハドル中でなくても、カスタムステータスの絵文字がレールに出るようになる。
- presence のドットとは独立（ハドル中でも、オンライン・離席・オフラインのドットはそのまま）。
- 形はデザインで決める。新しいトークンが要れば、そのときに確認する。

### 5. 印を出さないようにする設定は作らない

- Slack にもオンとオフの設定はない（オーナーが確かめた。ヘルプの環境設定の記述とは食い違うが、実物に合わせる）。
- 人に見せたくないときは、カスタムステータスを設定すれば名前の横には出ない（決定 4）。ただし、プロフィールのカードとメンバーの一覧の `in_huddle` には出る。

### 6. ハドルの一覧

**入口**
- ホームのサイドバーの「スレッド」の下に「ハドルミーティング」の行を足す。押すと `/w/{workspaceId}/huddles` になり、メインの領域に一覧を出す。
  スレッドの一覧（`/threads`。ADR 0036）と同じ形（パスのルートで、メインの領域に出す）。
  - アクティビティや「後で」のようにサイドバーの列（`?side=`。ADR 0058）にしないのは、Slack の実物がメインの領域に出しているため。
- 行に数は出さない（未読の概念がない）。**進行中の（自分が入れる）ハドルがあるあいだは、行の右に入っている人の顔を出す**（Slack のスクリーンショット。ルームの行の顔と同じ出し方。ADR 0066 追記 C）。

**画面の中身（上から）**
1. 見出し「ハドルミーティング」と、右上の「＋ 新規ハドルミーティング」（決定 8）。
2. **カードの列**: 進行中のハドルのカードを先に、そのあとに提案のカード（決定 7）を並べる。
   - **進行中のハドルのカード**（Slack のスクリーンショット）: 経過時間（「数秒」「12 分」）・場所（`#ルーム名` か DM の相手の名前）・人数（「N 人」）・入っている人の顔・ボタン（「参加する」、入っていれば「参加中」）。
     - 対象は、自分が入れる（メンバーで、アーカイブしていない）ルームの、いま進行中のハドル。
     - 経過時間は「ライブ」と同じく、いま起きていることなので琥珀。ボタンは緑。「参加する」はプレビューを通し（決定 1）、「参加中」はハドルの画面を前に出す。
     - Slack のカードの上半分はハドルのテーマの画像。hibari にハドルのテーマはない（ADR 0066「やらないこと」）ので、画像は置かない。
     - サーバーに新しい API を作らない。サイドバーのルームは全部ストアにあり、`huddle.updated` で生きた状態を持っている（ADR 0066 決定 13）ので、**ストアから描く**。入れるのはメンバーだけなので、ストアにないルームは入れる対象にならない。
3. **最近のハドルミーティング**: 終わったハドル。新しい順。**進行中のハドルは上のカードにだけ出し、終わってからここに入る**（オーナーの確認）。
   - 1 つ目のプルダウンで範囲を選ぶ（Slack と同じ 2 つ）。
     - **すべてのハドルミーティング**（既定）: 自分がいまメンバーのルームのハドルと、自分が入ったハドル。
     - **参加しなかったハドルミーティング**: 自分がいまメンバーのルームのハドルのうち、自分が入らなかったもの。
     - どちらも、**メンバーのルームのハドルは、自分がそのルームに参加した後（`room_members.joined_at` 以降）に始まったものだけ**。
       チャンネルに参加した途端に、参加する前のハドルが「参加しなかった」として並ばないようにするため（Slack の実物では確かめていない）。
     - 参加していない public のチャンネルのハドルは出さない（読めても、自分の会話ではない。アクティビティと同じ線引き。ADR 0058 決定 4）。
       自分が入ったハドルは、その後ルームを抜けても、いま読めるなら出す。
   - 1 行: ヘッドフォンのアイコン・場所・始めた時刻（「23 時間前」）・所要時間・スレッドの返信の数（押すとスレッドを開く。0 件なら出さない）・参加した人の顔（多ければ「+N」）・縦の「…」のメニュー。
   - 絞り込み: 残りの 2 つのプルダウン。「相手」（選んだ人も参加したハドル）と「場所」（選んだルームのハドル）。範囲のプルダウンと組み合わせられる。
   - **行を押すと、会話のハドルのメッセージ（スレッドの親）へ飛ぶ**（オーナーの確認。ADR 0042 のメッセージへの移動）。
   - 「…」のメニュー（Slack の実物の並び）

| Slack の項目 | hibari |
|---|---|
| 参加者を表示する（N 人のメンバー） | 作る。参加した人の一覧（アバターと名前。押すとプロフィールのカード）を出す |
| ブックマークする | 作る。hibari の「後で」（ADR 0054）にハドルのメッセージを保存する。いまはシステムメッセージを保存できない（422）ので、**ハドルのメッセージだけを例外にする**（スレッドの親にできる例外と同じ。ADR 0066 追記 A）。「後で」の一覧では、会話と同じハドルのメッセージの形で出す |
| ハドルミーティングのリンクをコピー | 作る（決定 1。ルームのリンク） |
| ハドルミーティングのトピックを編集 | 作らない（トピックは ADR 0066「やらないこと」） |
| スレッドからハドルミーティングを開始する | 作らない。スレッドに結びついたハドルと考えられるが、hibari のハドルはルームに 1 つ（ADR 0066 決定 3）で、スレッドごとのハドルは前提を変える（「やらないこと」） |

**API**

```
GET /api/v1/workspaces/{workspaceID}/huddles?filter=all|missed&participant_id=&room_id=&before=&limit=
    → { "huddles": [ {
          "id": "01J...", "room": { "id", "kind", "name", "dm_peer" },
          "message_id": "01J...", "started_by": "01J...",
          "started_at": "...", "ended_at": "...",
          "participant_ids": ["01J...", ...],
          "reply_count": 1 } ],
        "next_cursor": "01J..." | null }
```

- 返すのは、終わった（`ended_at IS NOT NULL`）、**いま読める**（`authz.CanReadRoom`）ルームのハドルのうち、
  - `filter=all`（既定）: 自分がいまメンバーで `started_at >= room_members.joined_at` のもの、または自分が `huddle_participants` にいるもの
  - `filter=missed`: 自分がいまメンバーで `started_at >= room_members.joined_at` のもので、自分が `huddle_participants` にいないもの
  - `filter` は `ActivityFilter` と同じく文字列の列挙にし、TypeScript の型にも出す（`HuddleListFilter`）。知らない値は 422。
  - private のルームから外されたら、そのルームのハドルは一覧から消える（検索の ADR 0061 と同じく、いまの権限で見せる）。
  - アーカイブしたルームのハドルは出す（読めるため。ADR 0059）。
- 並びとカーソル: `huddles.id`（ULID。始めたときに採る）の降順。`before` はハドルの ID。`OFFSET` は使わない。
  メッセージではないので、`created_at` で並べないルール 3 には当たらない（始めた時刻の順が、そのまま見せたい順）。
- `limit` は既定 50・上限 100（アクティビティと同じ）。`limit+1` 行を読んで続きの有無を決める。
- 絞り込みは検索（ADR 0061）と同じく、NULL を許す引数にする。`participant_id` は「その人も `huddle_participants` にいる」、`room_id` は「そのルームのハドル」。
- 1 本の SQL で、参加した人は `array_agg`（ADR 0066 の `ListHuddlesOfMessages` と同じ形。20 人までなので小さい）、返信の数はハドルのメッセージの `thread_reply_count` を結合して読む。
  DM の相手は集めて 1 回で引く（スレッドの一覧と同じ）。N+1 にしない。
- 読めるルームの条件は、検索の SQL にある `readable_rooms`（「`authz.CanReadRoom` を変えたらここも直すこと」）と同じ述語を使い、`search_test.go` と同じく authz の表でテストする。
- 索引を足す。
  - `huddle_participants (user_id, huddle_id DESC)`: 自分が入ったハドルを引く。いまは主キー `(huddle_id, user_id)` しかなく、ユーザーから引けない。
  - `huddles (room_id, id DESC)`: メンバーのルームのハドルを新しい順に引く。いまは進行中の部分索引しかない。
- **一覧は取り直しで最新にする。** 一覧のためのイベントは足さない。
  - 画面を開いたときに 1 ページ目を取る。
  - 手元のルームの `huddle.updated` で `huddle: null`（終わった）が届いたら、1 ページ目を取り直す（メンバーのルームのハドルはどれも一覧に入るので、自分が入っていたかは問わない）。
  - 返信の数は、ハドルのメッセージの `message.updated`（スレッドの数が変わる）でそろう範囲だけ手元で直し、それ以外は開き直したときにそろう。

### 7. 提案のカード

- **過去 7 日間に、自分が参加したハドルがあったルーム**を、回数の多い順に最大 3 つ出す（同じ回数なら新しい方）。
  Slack の文言（「過去 1 週間にここで 1 回ハドルミーティングを実施しました」）から、数え方を「その場所で自分が参加した回数」と読んだ。Slack の実物と違えば直す。
- 除くもの: いまハドルが進行中のルーム（進行中の区切りに出る）、いま入れない（`CanJoinHuddle` でない）ルーム。
- カード: 「#ルーム名 でハドルミーティングを開始しますか？」・「過去 1 週間にここで N 回ハドルミーティングを実施しました」・そのルームのハドルに参加した人の顔・「開始する」（プレビューを通す）。
- API: `GET /api/v1/workspaces/{workspaceID}/huddles/suggestions` → `{ "suggestions": [ { "room": {...}, "count": 1, "participant_ids": [...] } ] }`。
  7 日の起点は `Clock` から取る（テストで固定する）。
  一覧と分けるのは、ページをめくるたびに提案を計算し直さないため。

### 8. 「＋ 新規ハドルミーティング」

- 押すとダイアログを出す（Slack の実物）。見出し「ハドルミーティングにメンバーを招待する」、「名前かチャンネル名で検索する」の入力欄、「キャンセル」と「ハドルミーティングを開始する」。
  - 入力すると、メンバーと、自分が投稿できる（入れる）チャンネルの候補を出す。**人を選べばその人との DM、チャンネルを選べばそのチャンネル**でハドルを始める（オーナーが確かめた Slack の振る舞い）。
  - DM がまだなければ作る（ADR 0011 の DM の作り方のまま）。
  - 「ハドルミーティングを開始する」で、選んだ場所の参加前のプレビューを出す（決定 1 と同じ。いきなり入らない）。
- グループ DM はスコープの外（CLAUDE.md）なので、選べるのは 1 人か 1 つのチャンネルだけ。Slack のフリープランの人数の説明と有料プランの案内は出さない。

### 9. ログ

- 新しく出すものはない。`huddle_id` / `room_id` / `user_id` だけを属性にする（ADR 0066 決定 16）。リンクの URL は出さない（ルーム ID を属性にすれば足りる）。

### やらないこと（範囲の外）

| | 理由 |
|---|---|
| 読めない人の「アクセスをリクエストする」 | ADR 0066 決定 7（入れるのは投稿できる人だけ）。承認の流れと通知が要る |
| 1 回ごとのハドルを指すリンク | Slack のリンクはルームを指す（決定 1）。終わったハドルは、会話のハドルのメッセージへのリンク（ADR 0040）で指せる |
| ハドル中の印からどのハドルかを見せる・押して入る | 決定 3（どのルームかを出さない） |
| スレッドから始めるハドル | ハドルはルームに 1 つ（ADR 0066 決定 3）。スレッドごとのハドルは状態の持ち方から変わる |
| 予定したハドル・カレンダーとの連携 | 要望にない |
| 一覧の中の検索・期間の絞り込み | Slack のスクリーンショットにない |
| モバイルのサイドバーの長押しでリンクをコピー | Slack のモバイルの操作。コピーする場所は決定 1 の 3 か所で足りる |

## 理由

- **リンクをルームに向ける**: Slack と同じで、始まる前に配れて使い回せる。ルームのハドルは同時に 1 つなので、指す先が一意に決まる。秘密を持たないので、漏れても authz が守る。
- **ハドル中の印をワークスペースに閉じる**: ステータスがワークスペースごとなのと合わせると、Slack の見え方と一致し、別のワークスペースに通話していることを漏らさない。
- **集合と Lua**: presence と同じ形（Redis の自動の状態・Lua で状態の変化と配ることを一度に・REST で読み直す）なので、新しい考え方を持ち込まない。
- **一覧の進行中をストアから描く**: 生きた状態はすでに `huddle.updated` で手元にあり、サーバーに同じものを返す API を足すと、状態の出どころが 2 つになる。
- **カードを生きた状態にする**: 「参加する」を出すかどうかが本題で、古い状態は誤った操作を招く。ストアにあるルームだけでそれが満たせる。

## 検討した代替案

- **リンクを 1 回のハドル（`huddles.id`）に向ける**: 終わったハドルを指せるが、始まる前に共有できず、終わったリンクは「入れない」だけになる。Slack とも違う。終わったハドルはメッセージのリンクで指せる。
- **ハドル中の印をすべてのワークスペースに出す（presence と同じ）**: 集合が 1 つで済むが、別のワークスペースの人に通話中であることを知らせる。Slack のステータスの見え方とも違う。
- **ハドル中をカスタムステータスとして Postgres に書く（Slack の実装に近い）**: 自動で変わる状態を Postgres に書くことになり、ルール 5 に反する。抜けたときに元に戻す処理と、その間の本人の変更の扱いも要る。
- **ハドル中の印をアバターに付ける**: ステータスを設定している人のハドル中もどこでも分かる（オーナーが挙げた利点）。ただし presence のドットと場所を取り合い、タイムラインの過去のメッセージのアバターにも「いま」の状態が並ぶ。プロフィールのカードで分かれば足りると考えた（決定 4）。
- **印を出さない設定を作る**: Slack の実物にない（決定 5）。カスタムステータスで名前の横からは隠せる。
- **`presence.changed` に `in_huddle` を足す**: presence とハドル中は別々に変わる。1 つのイベントにすると、片方が変わるたびにもう片方も読み直して載せることになり、Lua が 2 つの状態をまたぐ。
- **一覧の進行中もサーバーの API で返す**: ストアと API の 2 つが同じ状態を持つことになる。
- **ハドルのリンクのカードを、ルームの 1 件の取得（`GET /rooms/{id}`）で描く**: 枚数だけ要求が増え、読めないルームが 404 になって `unavailable` にそろわない。

## 結果（トレードオフ）

- ハドルのリンクは、ルームの URL を知っていれば誰でも作れる（`?huddle=1` を足すだけ）。秘密ではないので問題はないが、「招待」の意味は持たない。
- ストアにないルームのカード（参加していない public のチャンネル）は、取得した時点の状態のまま。押せばプレビューが取り直す。
- ハドル中の印は、Redis の集合がワークスペースの数だけ増える。中身はハドル中の人だけなので小さい。
- 一覧は、終わったハドルの取り直しで最新にするので、イベントを増やさない代わりに、開いている間に返信の数がずれることがある（開き直せばそろう）。
- グループ DM がないので、「＋ 新規ハドルミーティング」で複数の人とは始められない。
- ステータスを設定している人がハドル中かは、名前の横では分からない（Slack と同じ）。プロフィールのカードを開けば分かる。
