# 0020. アバター画像のアップロードと配布（Phase 6）

- 状態: 採用
- 日付: 2026-09-16

## 背景

`settings/profile.png` の「画像を変更」に対応する API がない（ADR 0019 では、画像のアバターを出す画面がデザインになかったので先送りにした）。
デザイン側に「画像のアバター」と「プロフィールでの差し替え・削除」を足したので、実装する。

`users.avatar_object_key`（null 可）は Phase 1 のスキーマにある。添付ファイルの仕組み（ADR 0013）はすでにあり、署名付き PUT・HEAD での検証・掃除の形はそこで決めてある。

決めることは 3 つ。

1. アップロードの流れ（添付と同じでよいか）
2. **できあがった画像をどうやって配るか**。アバターはメッセージ・サイドバー・メンバー一覧と、ほぼ全画面に大量に出る
3. 画像を消す手段

## 決定

### エンドポイント

```
POST   /api/v1/users/me/avatar           署名付き PUT URL の発行
POST   /api/v1/users/me/avatar/complete  HEAD で検証し、プロフィールに反映する
DELETE /api/v1/users/me/avatar           画像を外す（頭文字の表示に戻る）
POST   /api/v1/users/avatars             複数のユーザーの署名付き GET URL をまとめて取る
```

### アップロード

- 添付と同じく、**中身はサーバーを経由しない**（CLAUDE.md ルール 10）。`POST /users/me/avatar` に `content_type` と `size_bytes` を渡すと、その 2 つを署名に含めた PUT URL を返す。
- オブジェクトキーは `avatars/{userID}/{uploadID}`（`uploadID` はサーバーが作る ULID）。**キーに userID が入っているので、他人の領域には書き込めない**。
- 添付と違い、**pending の行を作らない**。`complete` は `upload_id` だけを受け取り、サーバーが `avatars/{認証したユーザーの ID}/{upload_id}` を組み立てて HEAD する。存在しなければエラーにする。
  - 「行を作らない」で済むのは、アバターが 1 ユーザーに 1 枚で、状態（pending / attached）を持つ必要がないため。
- 受け付けるのは `image/png` / `image/jpeg` / `image/webp` で、既定の上限は 2 MiB（`AVATAR_MAX_BYTES` / `AVATAR_ALLOWED_TYPES` で変えられる）。SVG は入れない（スクリプトを含められる。ADR 0013 と同じ理由）。
- `complete` が成功したら、**古いオブジェクトを消す**（best effort。消せなくてもログに残して成功にする）。
- `complete` されなかったオブジェクトは残る。添付のような掃除ジョブは作らない（1 ユーザーが失敗のたびに増やせるのは数 MiB で、キーにユーザー ID が入っているため後から追える）。

### 配布: 一覧はまとめて署名、自分の分はレスポンスに載せる

- `POST /api/v1/users/avatars` に user_id の配列（最大 200）を渡すと、**画像があるユーザーの分だけ**署名付き GET URL（TTL 1 時間）を返す。
- 自分のプロフィールを返すレスポンス（`GET /users/me`、`PATCH /users/me`、登録・ログイン・refresh の user）には `avatar_url` を入れる。
- **chat のレスポンス（メッセージの送信者、メンバー一覧、DM の相手）には URL を入れない。** クライアントは画面に出すユーザー ID を集めて、上のエンドポイントで一度に取り、user_id をキーに覚えておく。
- 画像がない・URL の期限が切れた・読み込みに失敗したときは、**頭文字と色のアバターに戻す**（いまの表示がそのまま予備になる）。

### 削除

- `DELETE /users/me/avatar` で `avatar_object_key` を null にし、オブジェクトを消す（best effort）。

## 理由

- **配布をまとめたエンドポイントにした理由**: 素直なのは「ユーザーのプロフィールを返すすべてのレスポンスに署名付き URL を入れる」だが、それには `internal/chat` の 18 箇所のクエリと変換に `avatar_object_key` を足す必要がある。アバターは auth のドメインの持ち物で、chat はメッセージの送信者の ID しか知らなくてよい（CLAUDE.md ルール 1 の「パッケージを厳密に分ける」）。URL の発行を auth の 1 エンドポイントに寄せれば、chat は何も知らずに済む。
  - レスポンスも小さく保てる。署名付き URL は 1 つ 400 バイト前後あり、100 件のメッセージに載せると 40 KB 増える。
  - 代わりに「まず頭文字が出て、少し遅れて画像に変わる」ことになるが、頭文字のアバターは元々の表示なので、崩れて見えることはない。
- **TTL を 1 時間にした理由**: 添付の GET（5 分）より長い。アバターは秘密ではなく、消してもしばらく見えることの害が小さい。短くすると、開きっぱなしの画面で何度も取り直すことになる。
- **pending の行を作らない理由**: 添付は「メッセージに付くまで」の状態と掃除が要るが、アバターは `complete` で users の 1 列を書き換えるだけで、途中の状態に意味がない。キーがユーザーの領域に閉じているので、行がなくても他人の画像を自分のものにはできない。
- **画像の中身を検証しない理由**: HEAD で Content-Type とサイズだけを見る（添付と同じ）。中身が本当に画像かは、表示するブラウザに任せる。サーバーで画像を読むと、デコーダの脆弱性とメモリの消費を抱え込む。

## 検討した代替案

- **すべてのプロフィールのレスポンスに署名付き URL を入れる**: 上記のとおり chat を巻き込み、レスポンスも膨らむ。
- **サーバーが 302 で署名付き URL にリダイレクトする固定 URL（`GET /users/{id}/avatar`）**: `<img>` は Authorization ヘッダーを送れないので、認証をクエリ文字列のトークンに落とすことになる。トークンを URL に載せない方針（CLAUDE.md）と相性が悪い。
- **アバターだけ公開バケットに置く**: 署名が要らず簡単だが、private バケットだけを使う方針（ADR 0008 / 0013）を崩す。誰でも URL を総当たりできる場所に、利用者の顔写真を置くことになる。
- **サーバーで縮小（リサイズ）する**: 中身を読むことになり、上の理由でやらない。上限を 2 MiB にして、縮小はクライアントに任せる。

## 結果（トレードオフ）

- 一覧の画面では、アバターが「頭文字 → 画像」と 1 度差し替わる。
- 認証さえしていれば、ユーザー ID を知っている人は誰でもその人のアバターの URL を取れる（ワークスペースを共有しているかは見ない）。ID は ULID で総当たりできず、アバターは元々ワークスペースの中で見えるものなので、これを許す。ただし「どのワークスペースにも属さない人のアバターも、ID を知っていれば見える」ことは受け入れている。
- `complete` されなかったオブジェクトが残りうる（掃除ジョブを作らない）。増え方が問題になったら、`avatars/` を対象にした掃除を足す。
