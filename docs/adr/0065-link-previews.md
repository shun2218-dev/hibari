# 0065. 外部のリンクのプレビュー（Phase 6.17。投稿の後にサーバーが取得してメッセージに固定し、画像は自前のストレージに写す）

- 状態: 提案
- 日付: 2026-09-25

## 背景

オーナーの要望（2026-09-25）。

- Slack・LINE・X のように、本文に URL を貼ると、そのページの OGP（画像・タイトル・説明）のカードを出す
- カードは既定で出す。**投稿した本人はカードを消せる**（Slack と同じ）。消せるのは本人だけ（オーナーと確認）

ADR 0040 のパーマリンクのカードは「見る人ごとに authz を通して、表示するときに取る」形にした。外部の URL のカードは性質が 3 つ違う。

| | パーマリンクのカード（ADR 0040） | 外部のリンクのカード（この ADR） |
|---|---|---|
| 取りに行くのは | Web（自分の API） | **Go のサーバー**。ブラウザは CORS で他のサイトの HTML を読めない。Next.js の Route Handler にロジックは置けない |
| 中身は見る人で変わるか | 変わる（読めないリンクは `unavailable`） | 変わらない。メッセージを読めれば同じカードが見える |
| 残す状態 | なし | **「消した」を残す**。全員の画面から消え、再接続の同期でも消えたままでなければならない |

### ほかのサービスの振る舞い（2026-09-25 に確かめた）

オーナーから「一般的なやり方に合わせたい」と指示があったので、先に調べた。

| | カードの中身 | サイト側の OGP を変えたら | 画像 |
|---|---|---|---|
| Slack | 投稿した時点で取ってメッセージに付ける | **投稿済みのカードは変わらない**。URL ごとの取得結果を約 30 分使い回すので、それより後に貼ったものから変わる | 自前のプロキシ（`slack-imgs.com`）を通して出す |
| LINE | 貼った時点の内容 | 貼り直してもキャッシュが切れるまで古いまま（テキストは数日、画像は 2 週間ほどという報告がある） | LINE のサーバーを通して出す |
| Discord | 投稿時に作った埋め込みをメッセージに保存する | 変わらない | 自前のプロキシ（`images-ext-*.discordapp.net`）を通す。見る人の IP を相手のサイトに見せないため |

Slack のヘルプ（「リンクの共有とプレビューの設定」）には、ほかに次のことが書いてある。

- 会話で**同じリンクが過去 1 時間以内に共有されていたら**、展開しない（見出しは「ワークスペースの別のメンバーが最近投稿した」）
- **1 件のメッセージにリンクが 5 つより多ければ**、どれも展開しない
- プレビューにマウスを重ね、左に出る「x」で消す。管理者は消すときに「このサイトからのプレビューを今後ブロック」も選べる
- 本人の環境設定で、リンクのプレビューを見ないようにできる

**1 時間の規則は実物と合わなかった**（2026-09-25、オーナーが Slack で確かめた）。同じ人が同じ URL（Qiita の記事）を
同じチャンネルに続けて 2 回投稿すると、**2 回ともカードが出た**。ヘルプの記述は、少なくとも本人が貼り直す場合には当たらない。
別の人が貼った場合は確かめていない。はっきりしない規則を真似るより、持たない方が振る舞いを説明しやすいので、**この規則は採らない**（決定 3）。

同じ画面で、Slack のカードの見た目も確かめた（デザインの参考。構築順 2）。

- 本文の URL は `qiita.com/ozaki25/items/…` のように、スキームを除いて途中で切った形で出る
- カードはタイトル（太字）、説明（2 行で切る）、サイトのアイコン（ファビコン）とサイト名。画像は右にサムネイルとして置く

## 決定

### 1. 投稿の後にサーバーが非同期で取り、メッセージに固定する（Slack と同じ）

- 送信・編集のトランザクションで、本文の URL ごとに **取得待ち（`pending`）の行**を作る。送信の応答は取得を待たない。
- commit の後で取得のジョブに知らせる。取れたら結果を行に書き、**メッセージの `change_seq` を進めて `message.updated` を配る**。
  - 「メッセージが 1 回編集された」のと同じ見え方になるので、ルール 4 の差分同期（`after_change_seq`）にそのまま乗る。リアクション（ADR 0044）や添付の削除（ADR 0045）と同じ入れ方。
- **一度付いたカードは、サイト側が変わっても取り直さない**（上の表のとおり、どのサービスもそうしている）。
- 取得待ち・失敗のカードはクライアントに見せない。取れるまでは何も出ず、取れたら現れる（Slack と同じ）。

### 2. 同じ URL の取得結果は 30 分だけ使い回す

- 取得の結果（タイトル・説明・画像）は URL ごとの行（`link_previews`）に置き、メッセージの側（`message_link_previews`）はそれを指す。
- 取得の前に、**同じ URL を 30 分以内に取った結果があればそれを使う**（Slack と同じ長さ）。同じ URL が一度に何度も貼られても、相手のサイトに何度もアクセスしない。
  30 分を過ぎた後に貼ったものは取り直すので、サイト側の更新はそこから反映される。
- キャッシュのためだけに Redis を使わない。「30 分以内の行があるか」を Postgres に聞くだけにする。
  メッセージから指される行は消せないので、どのみち Postgres に置く必要がある。1 か所にまとめれば、画像のオブジェクトの持ち主も 1 つに決まる（決定 7）。

### 3. 展開する URL（Slack に合わせる）

- 本文の `http://` / `https://` の URL と、文字付きのリンク `<URL|文字>` の URL（ADR 0051 決定 4）。**コードの中の URL は対象外**（表示でもリンクにしていない）。
- **自分のアプリの URL（`AppBaseURL` と同じオリジン）は対象外。** パーマリンクは ADR 0040 のカードが出るし、自分のサーバーを取りに行く意味もない。
  LP（apex。ADR 0063）はアプリとオリジンが違うので、普通のサイトとして展開される。
- 同じ URL が本文に 2 回あれば 1 件にまとめる。並びは本文に出てきた順。
- **本文の URL（コードの外）が 5 つより多ければ、どれも展開しない**（Slack と同じ）。
- **同じ URL を何度貼っても、そのたびに展開する。** Slack のヘルプにある「1 時間以内に共有されていたら展開しない」は、実物と合わなかったので採らない（背景）。
- 本文から URL を取り出す処理は Go 側にも要る。Web の解釈（`body-format.ts`）と結果が一致することを、
  `testdata/format/` に URL の例を足して両方のテストで回して確かめる（ADR 0051 のメンションと同じ方法）。コードの範囲は `internal/chat/mention` の `codeRanges` を共有する。

### 4. 編集したとき

- 編集で**増えた URL** は決定 3 の規則で新しく取得する。
- **無くなった URL** のカードは消す（行を消す）。
- **本人が消したカードは、編集しても戻さない**（消した行は URL が本文から無くなっても残す。あとで同じ URL を書き戻しても出ない）。
- 残った URL のカードは取り直さない（決定 1）。

### 5. 本人がカードを消す

```
DELETE /api/v1/rooms/{roomID}/messages/{messageID}/link-previews/{previewID}
```

- **消せるのは投稿した本人だけ**（オーナーと確認）。authz は編集と同じ `authz.CanEditMessage`（本人で、書けるルーム）。アーカイブしたルーム（ADR 0059）では 409。
- 行は消さずに `removed_at` を立てる（決定 4 のため）。`change_seq` を進めて `message.updated` を配る。何度消しても 204（冪等）。
- **確認のダイアログは出さず、押したらすぐ消す**（オーナーの判断、2026-09-25）。消えるのはカードだけで、本文の URL は残り、リンクとして開ける。
  取り消しの操作もない。誤って押しにくいように、「x」はマウスを重ねたときだけ出す（決定 12）。

### 6. メッセージの形

REST とイベントのメッセージに `link_previews` を足す（見せるものだけ。取得待ち・失敗・消したものは入れない）。

```jsonc
"link_previews": [
  { "id": "01J...", "url": "https://example.com/post/1",
    "site_name": "Example", "title": "記事のタイトル", "description": "記事の説明…",
    "image": { "width": 1200, "height": 630 } }   // 画像がなければ null
]
```

- `url` は**本文に書かれた URL**（リダイレクトの後の URL や `og:url` ではない）。カードのタイトルはこの URL へのリンクにする。本文と違う行き先に飛ばさないため。
- 画像の URL は入れない。添付と同じく、表示するときに署名付きの GET URL を取る（決定 7。ADR 0013 がメッセージに GET URL を入れない理由と同じ）。
- 削除済みのメッセージ（tombstone）では空。
- `site_name` / `title` / `description` はただの文字列。**HTML として描かない**（React のテキストとして出す）。

### 7. 画像は取得したときに自前のストレージへ写す

- 取得したときに `og:image` を 1 度だけダウンロードし、S3 互換のストレージ（ローカルは RustFS、本番は R2）に置く。
  見る人のブラウザは相手のサイトにアクセスしない。
  - **理由 1（プライバシー）**: 相手の画像を直接 `<img>` で読ませると、URL を貼った人がサイトの持ち主なら、**誰がいつカードを見たか（IP と時刻）を集められる**。既読の追跡に使える。Discord / Slack が自前のプロキシを通すのはこのため。
  - **理由 2（表示の安定）**: 後で画像が消えても、`http://` の画像でも、カードが崩れない。
  - **理由 3（ルール 10）**: ほかのサービスは自前のプロキシで配るが、hibari は「ファイルの中身は Go サーバーを通さない」と決めている。取得のときに写して署名付き URL で出せば、ルールを曲げずに同じ効果になる。
- 画像の検査（ADR 0013 の inline 表示と同じ基準）: 中身を読んで判定し（`http.DetectContentType`）、PNG / JPEG / GIF / WebP だけを受け付ける。SVG は受け付けない。
  5MB まで。寸法はサーバーが画像のヘッダーを読んで決める（`image.DecodeConfig`。WebP は `golang.org/x/image/webp`）。条件に合わなければ画像なしのカードにする。
- 見るときは:

  ```
  GET /api/v1/rooms/{roomID}/messages/{messageID}/link-previews/{previewID}/image-url
  ```

  `authz.CanReadRoom` を通し、TTL 5 分の署名付き GET URL を返す（ADR 0013 と同じ。`Content-Disposition: inline`）。
  **貼られた URL そのものが、private ルームや DM の中身**なので、画像も authz の内側に置く。
- オブジェクトのキーは `link-previews/{ULID}`。URL もファイル名も入れない。

### 8. 取得（SSRF の対策）

利用者が書いた URL にサーバーがアクセスするので、**内部のネットワークへの踏み台にされないこと**を最優先にする。
HTTP クライアントは `internal/platform/safehttp` に置き、チャットの知識を持たせない。

- スキームは `http` / `https`、ポートは 80 / 443 だけ。URL にユーザー名・パスワードがあれば拒否する。
- **接続する直前の IP を検査する**（`net.Dialer.Control`）。名前を引いた後ではなく接続する IP を見るので、DNS rebinding（検査のときと接続のときで違う IP を返す）でもすり抜けられない。
  拒否するのは、グローバルなユニキャストでないもの全部（ループバック、プライベート、リンクローカル、マルチキャスト、未指定）、
  `169.254.169.254` などのメタデータ、CGNAT（`100.64.0.0/10`）、ユニークローカル（`fc00::/7`。**Fly の内部ネットワーク `fdaa::/16` を含む**）、
  IPv4 を埋め込んだ IPv6（IPv4-mapped、NAT64、6to4、Teredo。埋め込まれた IPv4 を取り出して同じ検査をする）。
- 環境変数のプロキシを使わない（`Transport.Proxy = nil`）。Cookie を持たない。
- リダイレクトは 3 回まで。行き先ごとにスキームとポートを検査する（IP は上の `Control` が毎回見る）。
- タイムアウト: 接続 3 秒、全体で 8 秒。
- HTML は `Content-Type` が `text/html` / `application/xhtml+xml` のときだけ読む。**先頭の 1MB まで**で、`<body>` に入ったら読むのをやめる。
  文字コードは `golang.org/x/net/html/charset` で決める（Shift_JIS / EUC-JP のサイトが化けないように）。
- `User-Agent` は正直に名乗る（`Mozilla/5.0 (compatible; hibari-bot/1.0; +https://hibari-chat.com)`）。ほかのクローラーの名前を騙らない。
- 取得のジョブは同時に 4 件まで。テストでは `safehttp` の IP の検査を差し替えて、`httptest` のサーバー（ループバック）を取りに行けるようにする。**本番の設定に検査を外す環境変数は作らない。**

### 9. 読むメタデータ

| カードの項目 | 読む順（最初に見つかったもの） | 長さの上限 |
|---|---|---|
| `title` | `og:title` → `twitter:title` → `<title>` | 300 文字 |
| `description` | `og:description` → `twitter:description` → `<meta name="description">` | 1,000 文字 |
| `site_name` | `og:site_name` → URL のホスト名 | 100 文字 |
| 画像 | `og:image:secure_url` → `og:image` → `twitter:image`（相対 URL は取得したページの URL で解決する。画像の取得にも決定 8 の検査をかける） | 決定 7 |

- `title` も `description` もなければ、カードを作らない（失敗として扱う）。
- 空白と改行は 1 つの空白に詰める。上限を超えたら切って `…` を付ける。
- **oEmbed は読まない。** OGP を返さないサイト（普通のクローラーに OGP を返さない X / Instagram など）ではカードが出ないことがある。
  実装のときに主なサイト（YouTube、X、GitHub、Qiita、Zenn、ニュースサイト）を実物で取って結果をこの ADR に追記し、足りなければその時点で oEmbed を足すかをオーナーと決める
  （Phase 6.10b・6.16 と同じく、実物で確かめる前に妥協を決めない）。

### 10. 取得のジョブ

- `pending` の行を `FOR UPDATE SKIP LOCKED` で 1 件ずつ取り、`claimed_until`（1 分後）を立てて commit してから取りに行く。
  **ネットワークを待つ間はトランザクションを持たない。** 複数台で動かしても同じ行を取り合わない（添付の掃除と同じ。ADR 0016）。
- 取れたら、メッセージの行をロックして（編集と同じ順序）、行がまだ `pending` のままなら結果を書き、`change_seq` を進めて配る。
  取得の間に編集で URL が消えていたら、何もしない。
- commit の直後に知らせる経路（プロセス内のチャネル）と、30 秒ごとに `pending` を拾い直す経路の 2 つを持つ。
  前者は速さのため、後者は取りこぼし（知らせる前にプロセスが落ちた、`claimed_until` が切れた）のため。
- 失敗（タイムアウト、4xx / 5xx、HTML でない、SSRF の検査で拒否）は `failed` にして取り直さない。一時的な失敗かもしれないが、Slack も取り直さない。
- 参照されなくなった `link_previews`（30 分を過ぎ、どのメッセージからも指されていない）は掃除のジョブが消し、画像のキーを `storage_deletions`（ADR 0059）に移す。
  メッセージを削除したら、その `message_link_previews` は同じトランザクションで消す（tombstone にカードは要らない）。
- ジョブは `cmd/server/main.go` の `jobs` に足し、context のキャンセルで止まる。goroutine が残らないことをテストで確かめる。

### 11. ログ

URL は本文の一部なので、**ログに URL もホスト名も出さない**（CLAUDE.md のログの規則）。出すのは `message_id` / `preview_id` と失敗の種類（`timeout` / `blocked_address` / `not_html` / `http_status` など）だけ。

### 12. 画面（構築順 2 で描く）

- カードは本文の下（添付の上）に並べる。サイト名・タイトル（リンク）・説明・画像。説明は数行で切る。
- 本人にだけ、カードにマウスを重ねたとき「x」を出す。押すとすぐ消える（決定 5）。モバイルの入口はデザインで決める。
- 画像の大きさの出し分け（小さい画像はサムネイル、大きい画像は下に大きく）はデザインで決める。そのために寸法を返す（決定 6）。
- 取得を待つ間の枠は出さない（取れたら現れる）。

### やらないこと（範囲の外）

| | 理由 |
|---|---|
| 入力中のプレビュー（送る前にカードを見せて消せる） | 送る前の URL を取りに行く API が要る。取得の口が増え、SSRF の面も増える。送った後で消せれば目的は満たせる |
| 本人の設定でプレビューを見ない | 要望にない。足すなら本人が選んだ設定として Postgres に持つ（ルール 5） |
| 管理者によるサイトのブロック | 要望にない（消せるのは本人だけ、とオーナーと確認した） |
| oEmbed（動画の埋め込みなど） | 決定 9 |
| パーマリンクのカード（ADR 0040）と検索結果にプレビューを出す | カードは小さく保つ（添付も件数だけにしている） |

## 理由

- **投稿時に固定する**: 一般的なやり方で、オーナーの指示どおり。加えて、全員に同じカードが見えること、`change_seq` に乗せられて再接続でも揃うこと、表示のたびに外部へアクセスしないことが得られる。
- **URL ごとの行とメッセージごとの行に分ける**: キャッシュ（決定 2）と「消した」状態（決定 5）は持ち主が違う。前者は URL、後者はメッセージ。1 つにまとめると、消したときに他のメッセージのカードまで巻き込むか、キャッシュを持てなくなる。
- **画像を写す**: 決定 7。
- **SSRF の検査を接続の時点に置く**: 名前を引いて検査してから接続する形は、2 回の名前解決の間に DNS の答えを変えられると破られる。`Control` は実際に接続するアドレスを見るので、リダイレクトの先にも同じ検査が自然にかかる。

## 検討した代替案

- **表示するときに取る（ADR 0040 と同じ）**: 「消した」を残す場所が別に要り、見る人ごとに外部へのアクセスが走る。一般的なやり方とも違う。不採用。
- **画像を相手のサイトから直接読ませる**: 実装は軽いが、決定 7 の理由 1 と 2 がそのまま残る。不採用（オーナーと確認）。
- **Go のサーバーで画像をプロキシする**: ほかのサービスと同じ形だが、ルール 10 に反する。写すのと効果が同じなので不採用。
- **キャッシュを Redis に置く**: 決定 2 のとおり、Postgres の 1 か所で足りる。
- **Web で取る（Next.js のサーバー）**: Route Handler にロジックを置かない規則に反する。

## 結果（トレードオフ）

- サイト側が OGP を直しても、投稿済みのカードは変わらない（ほかのサービスと同じ。消して貼り直せば、30 分の後から新しい内容になる）。
- 画像のぶんストレージを使う。30 分の間に同じ URL が貼られたら 1 つの画像を共有するので、同じ画像が重複するのは 30 分を越えて貼り直した場合だけ。
- 消す前に確認しないので、誤って押したカードは戻せない。戻したければ URL を書いたメッセージを送り直す。
- サーバーが利用者の書いた URL に GET を送る。**使い捨てのリンク（ログインのリンクなど）を貼ると、取得で使い切られることがある**（Slack にも同じ性質がある）。Cookie は送らず、GET だけにする。
- OGP を普通のクローラーに返さないサイトでは、カードが出ない（決定 9 で実物を確かめる）。
- 新しい依存: `golang.org/x/net`（HTML の解析と文字コード）、`golang.org/x/image`（WebP の寸法）。どちらも Go のチームの準公式のモジュール。
