# 0029. Web のワークスペースの管理画面（URL、権限の写し、招待コードの扱い）

- 状態: 採用
- 日付: 2026-09-18

## 背景

ロードマップ Phase 6-2 の「本番のページの構築順 6」で、管理画面（設定・メンバー・招待リンク）を画面につなぐ。
API は ADR 0006 / 0011 が、presentational コンポーネントは ADR 0018 が決めている。決まっていなかったのは次のこと。

- 管理画面の URL と、チャットの画面との関係（レイアウトが別なので、同じ `w/[workspaceId]` の下に置けない）
- 「このロールでこの操作ができるか」をクライアントでどう判断するか。サーバーの `internal/chat/authz` を写すのか、毎回サーバーに聞くのか
- 招待リンクの生値（code）をどこまで持つか
- ワークスペースのメンバー一覧に presence（オンライン）がない問題

範囲はオーナーと確認して、**構築順 6 を 3 つの PR に分けた**。この ADR は 1 本目（ワークスペースの管理）。
2 本目は招待リンクの受け入れ（`/j/{code}`）、3 本目はユーザー設定（プロフィール・アバターの変更・デバイス・外観）。
チャンネルの設定と DM の作成も構築順 6 に含めることにしたが、入口のデザインがない（下記「デザインの抜け」）ので、デザインが足されてから行う。

## 決定

### API に `online` を足す

`GET /api/v1/workspaces/{id}/members` に `online`（presence の初期値）を加えた。メンバーの一覧の画面（`workspace/members-*.png`）が
オンライン / オフラインを出すのに、この API だけが presence を返していなかった。ルームのメンバー一覧と同じく、
**ページに残した分だけを 1 回の MGET で読む**（ADR 0015）。Redis に届かなければ全員をオフラインとして扱い、一覧は失敗させない。

### URL とレイアウト
- **`/w/{workspaceID}/admin/{settings|members|invites}`。** `/w/{workspaceID}/admin` は設定に飛ばす。
- 管理画面はチャットの画面（サイドバー・ルーム・メンバーパネル）とは別の全画面のレイアウトなので、
  チャットの側を `app/(app)/w/[workspaceId]/(chat)/` のルートグループに移し、`admin/` がその外に並ぶようにした。URL は変わらない。
- 3 つの画面はどれも左のナビに人数と有効な招待の数を出すので、**どの画面でもメンバーと招待の両方を取る**（`admin/layout.tsx`）。
  一度取ったら画面を移っても取り直さない（同じ取得は 1 本にまとめる `once`）。
- 管理画面でも表示中のワークスペースとして登録する。ワークスペースの購読が続くので、ロールの変更・キック・presence がその場で反映される。
- メンバーでなくなったら（キックされた、URL を直接開いた）入口（`/`）に戻す。チャットの画面と同じ扱い（ADR 0025）。

### 権限の写し
`lib/chat/workspace-views.ts` に、`internal/chat/authz` と同じ規則（`CanManage` / `CanGrant` / `CanCreateInvite` / `CanRevokeInvite`）を写す。

- 写すのは**操作の入口を出すかどうかを決めるため**だけで、判定の正は常にサーバーにある（CLAUDE.md ルール 9）。
- ロールは JWT に入れず（CLAUDE.md）、ワークスペースの `my_role` を DB の値として使う。ロールが変わればイベントで更新される。
- 判定に使う値（自分のロール、招待ポリシー、招待の作成者）はすべてレスポンスに入っているので、追加の取得はしない。

### 手元の状態の進め方
- ロールの変更・キック・退出・譲渡・招待の作成と取り消しは、**応答（または応答がない操作では自分で組み立てた値）で手元の一覧を進める**。
  同じ変更は WebSocket のイベントでも届くので、別の管理者の操作も同じ経路で反映される。イベントが落ちても画面が止まらないよう、
  応答でも進めておく。
- 譲渡（`POST /ownership-transfer`）は 204 で本文がないので、手元では「新しい owner を owner に、いまの owner を admin に」入れ替える。
- ワークスペースに入った人のイベントはない（`docs/events.md`）。招待の受け入れは既定のルームへの `member.joined` として届くので、
  **管理画面を開いていて、まだ一覧にいない人のイベントが来たときだけ**メンバー一覧を取り直す。
- ワークスペース名と招待ポリシーは、入力中だけ手元の値を使い、確定（フォーカスを外す・選ぶ）でサーバーに送る。
  送り終えたら手元の値を捨ててサーバーの値に戻るので、失敗しても画面と DB がずれない。

### 招待コード
- コードの生値は作成の応答にしかない（DB にはハッシュだけ。ADR 0006）。**一覧に入れる前に `code` を落とし**、
  作成のダイアログを閉じたら手元からも消す。閉じた後に再表示する手段は作らない。
- リンクは `${location.origin}/j/{code}`。受け入れのページは 2 本目の PR で作る。
- 一覧の行は常に伏せ字（`hibari.app/j/•••••••`）。デザインどおり。

## 理由

- **管理画面を別のルートにする理由**: `ChatLayout` はサイドバー・本体・パネルを横に並べる 1 つの要素で、その中に全画面の管理画面を置けない。
  ルートグループなら URL を変えずにレイアウトだけ分けられる。
- **どの画面でも両方を取る理由**: 左のナビの「メンバー 6 / 招待リンク 1」はどの画面にも出る。画面ごとに必要な分だけ取ると、
  画面を移るたびに数字が後から入れ替わる。
- **authz を写す理由**: 押せない操作を出して 403 を見せるより、出さない方がよい。毎回サーバーに「できるか」を聞く API は増やしたくない
  （ロールと招待ポリシーはすでに手元にある）。写しがずれてもサーバーが拒否するので、安全側には壊れない。
- **応答でも手元を進める理由**: 配信は落ちうる（ADR 0004）。押した本人の画面が変わらないのは、操作が効いていないように見える。
- **`member.joined` で取り直す理由**: ワークスペースのメンバーが増えたことを知らせるイベントがない。招待の受け入れは必ず既定のルームへの
  参加を伴う（ADR 0011）ので、それを手がかりにできる。すでに一覧にいる人が別のルームに参加しただけなら取り直さない。

## 検討した代替案

- **管理画面をチャットの上のダイアログにする**: デザイン（`workspace/*.png`）は左に独自のナビを持つ全画面で、ダイアログではない。
- **メンバー一覧の presence を諦める**: デザインに「オンライン / オフライン」があり、ルームのメンバー一覧では返している。API をそろえる方が筋がよい。
- **権限の判定をサーバーに問い合わせる**: 往復が増えるうえ、一覧の行ごとに聞くことになる。
- **招待コードを localStorage に持って再表示できるようにする**: サーバーが生値を捨てている設計（ADR 0006）と矛盾する。トークンに準ずる値を端末に残さない。
- **管理画面でも `workspace.member_removed` を待ってから一覧から消す**: 押した本人の画面が遅れて変わる。

## 結果（トレードオフ）

- 失敗の表示がない（`docs/ui/README.md` の未解決）。ロールの変更・キック・譲渡・退出・招待の作成と取り消しが失敗しても、
  画面はサーバーの値に戻る（または何も起きない）だけで、理由はコンソールにしか出ない。
- **デスクトップでは、管理画面からチャットに戻る導線がデザインにない**（モバイルのヘッダーにだけ「戻る」がある）。
  いまはブラウザの戻る操作に頼っている。デザインが足されたら直す。
- 招待リンクをコピーできなかったとき（`navigator.clipboard` がない、権限がない）の表示はない。URL は画面に出ているので手で写せる。
- 管理画面を開いている間、メンバーと招待は取り直さない（イベントで進める）。イベントを落としたまま長く開いていると、
  一覧が古いままになりうる。再接続では購読し直すが、この 2 つの一覧は同期の対象に入れていない。
- 有効期限の選択肢は 30 分 / 1 時間 / 1 日 / 7 日（デザインどおり）。API は 60 秒〜30 日を受け付けるが、画面からは選べない。
- ブラウザでの操作の確認は、ローカルの compose に対して行った（登録 → ワークスペース作成 → 管理画面 → 招待リンクの作成 → メンバー一覧の presence）。
