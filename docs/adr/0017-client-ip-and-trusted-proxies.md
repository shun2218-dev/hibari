# 0017. クライアント IP の決定と信頼するプロキシ

- 状態: 採用
- 日付: 2026-09-15

## 背景

Phase 5 でサーバーの前に Caddy（ロードバランサ）を置くと、サーバーから見た TCP の接続元（`RemoteAddr`）はすべて Caddy になる。本番（Fly.io）でも、前段に Fly のプロキシが入るので同じことが起きる。

IP を使っている箇所は 4 つある。

- レート制限（ログイン・登録・パスワードリセットの IP 単位。ADR 0010）
- `refresh_tokens.ip`（セッションの一覧の表示と監査）
- アクセスログ
- WebSocket のハンドシェイク（アップグレードを拒否したときのログ）

`RemoteAddr` のままでは、全員の IP 単位の制限が 1 つのバケットを共有してしまう。一方、`X-Forwarded-For`（XFF）はクライアントが自由に書けるので、そのまま信用すると IP 単位の制限を回避できてしまう。

## 決定

### 1 箇所で決める
- クライアント IP を決めるのは `internal/httpx` の `resolveClientIP` だけにする。**`RemoteAddr` と `X-Forwarded-For` を読むのはこの関数だけ**にする。
- ミドルウェア（`withClientIP`）がリクエストごとに 1 回だけ求めて、context に入れる。4 つの使用箇所はすべて context から読む（`clientIPFrom`）。

### 決め方
1. `TRUSTED_PROXIES`（CIDR のリスト、環境変数）が**空なら `RemoteAddr` をそのまま使い、XFF は一切読まない**。これを既定値にする。
2. XFF を読むのは、`RemoteAddr` 自体が `TRUSTED_PROXIES` に含まれるときだけにする。
3. XFF は右端から順に見る。`TRUSTED_PROXIES` に含まれるアドレスは飛ばし、**最初に現れた信頼しないアドレス**をクライアント IP にする。
4. 値が壊れていたら（IP として読めない、ポートが付いている）、そこより左は信用できない。それまでに見た中で最も左の信頼するアドレスを使う。XFF が全部信頼するアドレスだった場合も同じにする。
5. IPv4-mapped IPv6（`::ffff:a.b.c.d`）は IPv4 にそろえる。
6. 1 つのアドレスも `/32` や `/128` で書かせる。`10.0.0.1/8` のようにホスト部が残った値は、起動時にエラーにする。

### プロキシの側
- ローカルの Caddy は `header_up X-Forwarded-For {remote_host}` で**上書き**する（追記しない）。Caddy が最前段なので、クライアントが送った XFF を残す理由がない。
- 環境ごとの `TRUSTED_PROXIES` の値は `docs/deploy.md` に書く。

## 理由

- **1 箇所に閉じ込める理由**: 使う箇所ごとに IP を求めると、どこか 1 箇所だけ偽装した XFF を信用する事故が起きる。レート制限では正しくても、監査ログに偽の IP が残る、などの食い違いも起きる。
- **既定を空にする理由**: 設定を間違えたときの影響を、「全員が同じ IP として制限される（厳しすぎる）」側にする。「偽装で制限を逃れられる（効かない）」側にはしない。前者はすぐ気づけるが、後者は攻撃されるまで気づけない。
- **右端から信頼するアドレスを飛ばす理由**: 信頼するプロキシは、受け取った XFF の右に接続元を追記する。そのため、左側ほどクライアントが自由に書ける値になる。右端の 1 つを取るだけだと、プロキシが多段になったときに内側のプロキシのアドレスを取ってしまう。Fly では、XFF の右端にアプリ自身の IP が入るので、実際に多段と同じ形になる。
- **壊れた値で止める理由**: 信頼するプロキシは壊れた値を書かないので、壊れた値はクライアントが書いたものと考えられる。そこを読み飛ばして左へ進むと、クライアントが書いた値を採用してしまう。

## 検討した代替案

- **XFF の右端の 1 つを取る**: 単純だが、多段のプロキシでは誤る。Fly ではアプリ自身の IP を取ってしまう。
- **`Fly-Client-IP` を読む**: Fly では簡単だが、ベンダー固有のヘッダに依存する。ローカルの Caddy との経路が 2 つに分かれる上、Fly の前にさらに CDN を置くと CDN の IP になる。
- **XFF を無条件に信用する**: 前段のプロキシを経由しない直接の接続（設定ミスでポートが開いているなど）から、IP を自由に偽装できる。
- **RFC 7239 の `Forwarded` ヘッダ**: 標準だが、Caddy も Fly も既定では XFF を使う。必要になったら同じ関数の中で対応できる。

## 結果（トレードオフ）

- 環境ごとに `TRUSTED_PROXIES` を正しく設定する必要がある。設定しないと、IP 単位のレート制限が全員で共有される（安全側に倒れる）。
- Fly のプロキシの内部アドレス（`172.16.0.0/12` / `fdaa::/16`）を信頼すると、同じ組織の private network 内のほかのアプリも XFF を書けてしまう。同じ組織に信頼できないアプリを置かない前提にする。
- ローカルの Caddy は、コンテナのネットワークのサブネットと Caddy のアドレスを固定する（`compose.yaml`）。サブネットがほかのネットワークと衝突したら、環境変数で変える。
