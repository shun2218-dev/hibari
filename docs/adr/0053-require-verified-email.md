# 0053. 未検証の email ではチャットを使えないようにする（Phase 6.10.5。検証の状態はアクセストークンで渡し、メールは SMTP で非同期に送る）

- 状態: 採用
- 日付: 2026-09-21

## 背景

ADR 0010 は「email が未確認でもログインと Phase 3 以降の操作は制限しない」とし、ADR 0011 もそれを保った。
ADR 0050 で、オーナーから「本番でも未検証のアドレスでチャットができるのはおかしく、そこを塞げばよい」と指摘があり（2026-09-21）、
別の ADR で扱うと約束した（ADR 0050 の末尾）。6.10 の後に回した（オーナーの判断。ADR 0051）。

いまの状態（2026-09-21 に調べた）:

- **登録の直後にログイン済みになる。** `Register` は利用者とセッションを 1 つのトランザクションで作り、トークンを返す（`internal/auth/service.go`）。
  確認メールはコミットの後に送り、送れなくても登録は成功させる
- **chat は検証の状態を知らない。** アクセストークンのクレームは `sub` / `sid` / `jti` / `iat` / `exp` / `iss` / `aud` だけで、
  `authn.Identity` も `{UserID, SessionID}` だけ。chat が `email_verified_at` を読むのは、プロフィールのカードの 1 か所（ADR 0050 決定 2）だけ
- **検証は「未 → 済」の一方向で、戻らない。** email を変える機能はなく（ADR 0019）、`email_verified_at` は `coalesce` でしか書かれない。
  パスワードの再設定でも検証済みになる（ADR 0010。リンクがその email に届いたので）
- **招待から登録すると行き止まりになる。** 登録の直後の「確認メールを送りました」で止まり、招待に戻れない（ADR 0030 の既知の課題）
- **本番のメール送信がない。** 本番の配線も開発用の `LogMailer`（リンクをログに出すだけ）で、`main.go` に「デプロイの前に非同期で送る実装に差し替える」とある。
  **このまま塞ぐと、本番では確認メールが届かず、新しい人は誰も使えなくなる**
- **メールを同期で送っている。** 本物のメールを送ると、パスワードの再設定で「登録のある人だけ応答が遅い」時間差が出て、アカウントの有無が分かる
  （CLAUDE.md「認証の失敗では、ユーザーの存在有無が判別できる…時間差を出さない」）

オーナーと確定した内容（2026-09-21）:

- **検証するまで chat を全部塞ぐ**（読むのも含めて）
- **chat は検証の状態をアクセストークンのクレームから知る**
- **本番のメール送信も、この ADR で決める**
- **ローカルの開発環境だけは、検証なしでも使えるようにする**

## 決定

### 1. 検証するまで、chat の API と WebSocket は使えない

- chat の API は、アクセストークンが検証済みでなければ **403**（`application/problem+json`、type は `email-unverified`）を返す。
  WebSocket も、ws-ticket を発行しない（同じ 403）ので接続できない。
- auth の API（`/users/me`・確認メールの再送と確認・ログアウト・セッションの一覧・パスワードの変更・プロフィールの更新）は、未検証でも使える。
  検証を済ませるのに要る操作と、自分のアカウントの操作だから。
- **判定は 1 か所に置く。** `platform/authn` のミドルウェア（`RequireVerifiedEmail`）で止め、`httpx` が chat のルートと ws-ticket の発行に付ける。
  chat のコードは検証を知らない（CLAUDE.md ルール 1 と 9。認可の判断は authz、本人確認の状態は authn）。
- 既存の未検証の利用者も同じく塞ぐ（猶予を置かない）。遅くとも次のトークンの更新（15 分）で塞がり、画面から確認メールを再送できる。

### 2. 検証の状態はアクセストークンのクレームで渡す（オーナーと確認）

- auth は、アクセストークンに **`email_verified`**（OpenID Connect と同じ名前）を入れる。値は発行の時点の `email_verified_at IS NOT NULL`。
- `platform/authn` の `Identity` に `EmailVerified bool` を足す。CLAUDE.md ルール 1 の「authn が渡す検証済みの userID / sid」に 1 つ加える（CLAUDE.md を直す）。
- **検証した直後にトークンを取り直す。** Web は確認のあと、refresh で新しいアクセストークンを取る（いまの `session.verifyEmail` は `/users/me` を取り直している）。
  別のタブも、次の refresh（15 分以内）か 403 を受けたときの refresh で追いつく。
- **「JWT にロールや権限を入れない」（CLAUDE.md）とぶつからない理由**: 入れない理由は「失効できないので、取り上げた権限が残る」こと。
  検証は取り上げられない（未 → 済の一方向）ので、古いトークンは「まだ塞ぐ」側にしか間違えない。
  **email を変える機能を足すときは、この前提が崩れる**（変えた email は未検証に戻る）ので、そのときにこの決定を見直す。

### 3. 塞いでいる間の画面と、招待から来た人の戻り先

- 未検証の人が `(app)` の画面を開くと、「確認メールを送りました」の画面（`VerifyEmailPending`。再送とログアウト）を出す。いまの登録の直後の画面と同じ。
- **招待から来た人は、検証のあとに招待の画面へ戻す。** 確認メールのリンクに戻り先（`next`。アプリの中のパスだけ）を載せ、
  `/verify-email` の「完了」のボタンがそこへ進む。別の端末でメールを開いても戻れる（ブラウザに覚えるだけだと、同じブラウザでしか戻れない）。
  戻り先は auth が受け取るときも Web が使うときも、アプリの中のパス（`/` で始まり `//` で始まらない）に限る（いまの `safeNextPath` と同じ規則）。
  これで ADR 0030 の行き止まりもなくなる。

### 4. ローカルの開発環境だけ、検証を外せる（オーナーの要望）

- 設定 `AUTH_REQUIRE_VERIFIED_EMAIL`（既定 `true`）。`false` のときは、`RequireVerifiedEmail` が止めない（トークンのクレームはそのまま入れる）。
- **本物のメールを送る設定（決定 5 の `smtp`）のときに `false` にすると、起動しない。** メールが本当に届く環境で検証を外す理由がないので、
  本番で誤って外れることがない。開発環境（`log`）でだけ外せる。
- `compose.yaml` は `false` にする。開発でも検証を試したいときは `true` にし、ログに出るリンクを開く（いまと同じ）。

### 5. 本番のメールは SMTP で送る。業者は Resend から始める

- `auth.Mailer` の実装に **SMTP**（`net/smtp`。STARTTLS か暗黙の TLS）を足す。
  **特定の業者の SDK や API に依存しない**（CLAUDE.md ルール 10 のストレージと同じ考え方）。どの業者も SMTP で送れるので、替えるのは設定だけで済む。
- 設定 `MAIL_TRANSPORT`（`log` / `smtp`）は**必須**にする（既定を置かない）。本番で設定を忘れて、黙ってログに出すだけになるのを防ぐ。
  `smtp` のときは `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD`（ファイルで渡す）/ `MAIL_FROM` も必須。
- **業者は Resend から始める**（2026-09-21 時点の比較は下。オーナーが比較を見て確定: 2026-09-21）。送信元は独自ドメインのサブドメイン（`mail.<独自ドメイン>` など。ADR 0046）にし、
  SPF / DKIM / DMARC の DNS のレコードを `docs/deploy.md` に書く。

| | Resend | Amazon SES | Postmark | Cloudflare Email Service |
|---|---|---|---|---|
| 無料の範囲 | 月 3,000 通（1 日 100 通） | 恒久の無料枠はない（新しいアカウントに最大 $200 のクレジット、6 か月） | 月 100 通（テスト用） | なし。Workers の有料プラン（月 $5）に月 3,000 通が含まれる |
| 有料 | 月 $20 で 5 万通 | 1,000 通で $0.10 | 月 $15 で 1 万通から | 超えた分は 1,000 通で $0.35 |
| SMTP | ある（465 / 587 など） | ある（東京リージョンで使える） | ある（587。465 はない） | ある（465 だけ。2026-06 に追加されたベータ） |
| 状態 | 正式版 | 正式版（サンドボックスの解除に申請が要る） | 正式版（全アカウントを人が審査） | 送信は公開ベータ（2026-04 から）。DNS が Cloudflare であることが条件 |

### 6. メールは非同期で送る

- auth は、メールを**プロセスの中のキュー**（上限つきの channel）に積んで、すぐに応答を返す。送るのは別の goroutine（ワーカー）。
  **パスワードの再設定で、登録のある人とない人の応答の時間が同じになる**（CLAUDE.md の時間差の禁止）。登録も SMTP の遅さを待たない。
- ワーカーは `context` の取り消しで止まり、停止のときは積まれた分を `ShutdownTimeout` の中で送り切ろうとする（CLAUDE.md の goroutine の決まり）。
- **送れなかったメールは失う**（再試行は数回まで。プロセスが落ちたら積んだ分は消える）。確認メールは画面から再送でき、パスワードの再設定もやり直せるので、許容する。
- ログにリンク（トークン入り）を出さない（CLAUDE.md。例外は開発用の `LogMailer` だけ）。

### 7. 変えないもの

- ADR 0050 決定 2（プロフィールのカードは、検証済みの email だけを返す）は残す。塞いだ後も、将来の OAuth で email が未検証の人が残りうる（ADR 0050 の末尾）。
- パスワードの再設定で検証済みになる（ADR 0010）は残す。
- email を変える機能は作らない（決定 2 の前提に関わるので、作るときにこの ADR を見直す）。

## 理由

- **chat を全部塞ぐのは、他人のアドレスで登録した人が、招待で入ってその人になりすますのを根っこで止めるため**（オーナーと確認）。
  投稿だけを止めると、塞ぐ API を 1 つずつ選ぶことになり、足した API で漏れる。入り口の 1 か所で止めれば漏れない。
- **トークンのクレームにするのは、リクエストごとに DB を引かず、chat が auth を知らないまま判定できるため**（オーナーと確認）。
  chat が毎回 `users` を読む案は常に最新だが、HTTP と WebSocket の入り口ごとに問い合わせが増え、入れ忘れの余地も残る。
  クレームなら判定は authn のミドルウェアの 1 か所になる。古いトークンは「まだ塞ぐ」側にしか間違えないので、ロールを JWT に入れない理由が当たらない。
- **SMTP にするのは、業者に縛られないため。** 業者の API の方が機能（配信の状況の取得など）は多いが、hibari が送るのは確認と再設定の 2 種類だけで、SMTP で足りる。
- **Resend から始めるのは、無料の範囲が今の規模に足り、正式版で、登録の手間が小さいため。** SES は最も安いが、恒久の無料枠がなく、
  サンドボックスの解除に申請が要り、バウンスと苦情の監視も自前になる。Cloudflare は R2 と同じ場所にまとまるが、まだベータで、有料プランが前提。SMTP なので、あとから替えられる。
- **非同期にするのは、時間差でアカウントの有無が分かるのを防ぐため**（本物のメールを送ると必ず起きる）。キューを DB に持つ（outbox）案は失わないが、
  2 種類の短命なメールには重い。
- **開発で外せる条件を「メールが本当に届かない設定」に結びつけるのは、本番で外れる道をなくすため。** 環境の名前（`APP_ENV`）を足すより、
  外してよい理由（メールが届かない）そのものを条件にした方が、設定を取り違えても安全側に倒れる。

## 検討した代替案

- **投稿と招待の受け入れだけを塞ぐ**: 読むことはできるので入り口はゆるいが、塞ぐ API を 1 つずつ選ぶ必要があり、漏れやすい。オーナーと比較して不採用（2026-09-21）。
- **chat が DB を毎回読む**: 常に最新だが、入り口ごとに問い合わせが増える。オーナーと比較して不採用（2026-09-21）。
- **登録の時点ではログインさせない（検証してから初めてログイン）**: 塞ぐ仕組みが要らないが、ADR 0010 の「登録してすぐ再送できる」が崩れ、
  確認メールを別の端末で開いたときに、元の端末のログインが続かない。
- **業者の API（HTTP）で送る**: 配信の状況を取れるが、業者の SDK か API の形に縛られる。
- **Amazon SES / Postmark / Cloudflare Email Service から始める**: 上の表と理由のとおり。SMTP なので、どれにもあとから替えられる。
- **メールのキューを DB に持つ（outbox）**: 落ちても失わないが、テーブルと再送の仕組みが要る。今の 2 種類のメールには重い。
- **環境の名前（`APP_ENV=development`）で検証を外す**: 分かりやすいが、本番で設定を取り違えると外れる。

## 結果（トレードオフ）

- **登録した人は、確認メールを開くまでチャットを使えない。** 招待から来た人も、検証のあとに招待の画面に戻る。
- **検証の直後、別のタブは最大 15 分（次の refresh）遅れて使えるようになる**（403 を受けたら refresh する）。
- **CLAUDE.md ルール 1 の「authn が渡すもの」に `email_verified` が加わる。** email を変える機能を足すときは、この決定を見直す。
- **メールは失うことがある**（プロセスが落ちたとき・業者が落ちたとき）。再送で補う。
- **本番の起動に、メールの設定が必須になる。** Resend のアカウントと DNS のレコードが要る（`docs/deploy.md`）。
- 開発環境の `compose.yaml` は検証を外す。検証の流れを試すときは設定を変える。
- ERD は変わらない（`email_verified_at` はある）。`docs/events.md` も変わらない（WebSocket に入る前に止めるため）。

## 追記: メールの実装（構築順 2。2026-09-21）

- 届ける部分は `internal/platform/mail` に置いた（`SMTP` と `Queue`）。文面は auth の `NewMailer` が組み立てる。業者を替えても文面は変わらず、auth は SMTP を知らない。
- パスワードは `SMTP_PASSWORD_FILE`（ファイルのパス）で受け取る。`JWT_PRIVATE_KEY_FILE` と同じく、本番でシークレットをファイルとして置く形に合わせた。起動時に DB へ接続する前に読む。
- **TLS の方式はポート番号で決める**（465 / 2465 は暗黙の TLS、それ以外は STARTTLS）。設定を 1 つ減らし、業者の案内のポートをそのまま書けばよいようにした。
  **STARTTLS を広告しないサーバーには送らない**（途中の経路で広告を消されて平文にされるのを防ぐ）。証明書は `SMTP_HOST` で検証する。
- 送り直すのは 3 回まで（2 秒、4 秒と間を空ける）。5xx の応答は送り直しても通らないので、1 回で諦める。キューは 1,024 通まで積み、あふれたら積まずにエラーを返す
  （登録は成功させ、再設定はログにだけ残す。いまの扱いのまま）。
- キューは HTTP サーバーが止まってから止め、積まれた分を `SHUTDOWN_TIMEOUT` の間だけ送る。停止の途中で処理を終えたリクエストのメールを送り残さないため。
- ログには宛先・本文・リンクを出さず、メールの種類（`kind`）だけを出す。

## 追記: 業者の比較の訂正と確定（2026-09-21）

最初の表の SES（「最初の 12 か月だけ無料」）は古い情報だったので、公式の料金ページで確かめ直して表を直した。ほかに Mailgun・Brevo・SendGrid・MailerSend・ZeptoMail・blastengine も比べた。
SendGrid は無料プランが 2025-05 に終わり、ほかは今の規模では Resend より高いか、ログの保持が短い。

- **オーナーが比較を見て Resend に確定した。** 1 日 100 通を超える日が出てきたら、SES（最も安い）に移る。SMTP なので設定を変えるだけで済む。
- **Resend の無料の上限（1 日 100 通）はドメインごとではなく、アカウント（チーム）の単位とみている**（料金ページは「Free plan は 1 日 100 通」とだけ書いている。上限はプランに付き、プランはチームで契約する）。
  To / Cc / Bcc の宛先は 1 件ずつ数え、日の区切りは UTC の 0 時（日本時間の 9 時）。
  hibari は 1 通に宛先を 1 つしか入れないので、「1 日に送れる確認と再設定のメールの合計が 100 通」になる。
- **日本の携帯キャリアのメールに届くか**は、どの業者も公式の情報がない。ドメインを取った後に、実物で送って確かめる（DoD の「本番の設定で、確認メールが実際に届く」）。

## 追記: 塞ぐ部分の実装（構築順 3。2026-09-21）

- **止めるのは `httpx` の `requireChatUser` の 1 か所。** `authn.Require` のすぐ内側に `authn.RequireVerifiedEmail` を重ね、chat のルートの登録（`registerChatRoutes`）と `POST /api/v1/ws/ticket` の両方がこれを使う。
  chat のルートは 1 つの登録の関数を通るので、足した API も自動で止まる。`/users/me/presence` のように auth の API と同じパスの下に置いた chat の API も止まる。
- **`email_verified` のクレームがないトークンは未検証として読む**（止める側に倒す）。クレームを足す前に発行されたトークン（最大 15 分）もこれで読める。真偽値でなければ不正なトークン（401）。
- **refresh のたびに DB から検証の状態を読み直す。** Refresh Token を行ロックで読むクエリ（`GetRefreshTokenForUpdate`）で `users.email_verified_at` も一緒に読むので、問い合わせは増えない。
- ws-ticket にも `email_verified` を載せ、消費した `Identity` に戻す（今は WebSocket の中で使わないが、`Identity` を欠けさせないため）。
- **`httpx.Deps` の項目は「外す」の向き（`AllowUnverifiedEmail`）にした。** ゼロ値（設定し忘れ）が止める側になるようにするため。環境変数は決定 4 のとおり `AUTH_REQUIRE_VERIFIED_EMAIL`（既定 `true`）。
  httpx のテストは開発環境と同じく外して組み立て、止めることそのものは `withVerifiedEmailRequired` を付けたテストで確かめる。
- **戻り先（`next`）は、登録（`POST /auth/register`）と再送（`POST /auth/verify-email/request`）のボディで受け取る。** 再送のボディは省略できる。
  アプリの中のパス（`/` で始まり、`//` と `/\` で始まらず、制御文字を含まず、スキームとホストを持たない。512 バイトまで）でなければ 422（`next` のフィールドの検証エラー）にする。
  黙って捨てずに断るのは、戻れないことに利用者も開発者も気づけるようにするため。確認のリンクには `&next=` としてエスケープして載せる。

## 追記: 本物のメールが届くことの確認（2026-09-22）

- `mail.hibari-chat.com` を Resend（東京リージョン）に登録し、ローカルの compose を SMTP の設定（`compose.smtp.yaml`）にして、Gmail のアドレスで登録した。
  - 受信トレイに届いた（迷惑メールではない）。送信から 1 秒で届いた
  - ヘッダは **SPF・DKIM（`mail.hibari-chat.com`）・DMARC がすべて PASS**
  - メールの中のリンクは `/verify-email?token=…` のままで、書き換えられていない（トラッキングを使っていない）
  - リンクを開いて確認でき、`email_verified_at` が入った
- **Resend の DNS のレコードは、決定 5 の追記のときの公式の案内（MX と SPF の TXT）と違い、CNAME 2 つと DKIM の TXT 1 つだった**（`send.mail` と `rsend.mail` が Resend のホストへの CNAME）。バウンスと SPF の中身は Resend 側で管理される。`docs/deploy.md` を実際の形に直した。
- Resend の東京リージョンは、裏で Amazon SES（`ap-northeast-1`）から送っている（Message-ID で分かる）。
- **Resend のトラッキング（click / open）は使わない。** リンクを業者の転送用の URL に書き換えると、ワンタイムトークン入りの URL が外に出るため。トラッキング用のサブドメインを作らなければ働かない（`docs/deploy.md`）。
- **日本の携帯キャリアのアドレスでは試していない**（手元にアドレスがないため）。オーナーの判断で、届く前提で進める（2026-09-22）。
  届かないという報告があれば、Resend の Emails の画面で Delivered / Bounced を見て、業者の側か受け取り側の判定かを切り分ける。
