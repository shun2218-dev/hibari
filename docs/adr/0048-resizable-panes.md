# 0048. パネルの幅はユーザーが変えられるようにし、入力欄は中身に合わせて 16 行まで伸ばす

- 状態: 採用
- 日付: 2026-09-21

## 背景

オーナーの要望（2026-09-21）。Slack に寄せたい。

1. **入力欄が 1 行の窓のまま**だった。`rows={1}` の `<textarea>` に高さを入れ直していないので、改行しても
   長い文を書いても、1 行ぶんの窓の中でスクロールするだけで全体が見えない。
2. **サイドバーと右のパネルの幅を変えたい**（最低幅は設ける）。今後入れるプロフィールのパネル（Phase 6.9）にも同じように効くこと。

1 は `docs/ui/` のスクリーンショットにある姿（1 行の入力欄）から外れないが、2 は
**スクリーンショットに無い操作**なので、実装の前にオーナーの確認を取った（CLAUDE.md「デザイン」）。
`--pane-*` という新しい変数を globals.css に足すことも、同じときに確認した。

**入力欄の高さも引っ張れるようにしかけたが、やめた**（オーナーの指摘、2026-09-21）。
Slack の入力欄は `<textarea>` ではなくリッチテキストの欄で、高さを引っ張る操作は無い。
代わりに **16 行を超えたら中でスクロールする**。引っ張る取っ手は入れる前に取り下げ、
上限だけ 16 行にそろえた（下の決定 3）。リッチテキストの欄そのものは **Phase 6.10（本文の書式）**の範囲なので、
ここでは扱わない。

## 決定

### 1. 中身の高さに合わせて伸ばすのは `useAutosizeTextarea` ひとつに寄せる

`lib/use-autosize-textarea.ts`。`scrollHeight` を測って `style.height` に入れ直す。入力欄（`Composer`）と
メッセージの編集（`MessageItem` の `MessageEditor`）が同じものを使う。

- 測る前に一度 `height: auto` に戻す。戻さないと `scrollHeight` が「いまの高さ」より小さくならず、**文字を消しても縮まない**。
- `scrollHeight` は枠線を含まないので、`offsetHeight - clientHeight` を足す（`box-sizing: border-box` のぶん）。
  足さないと、枠線のある編集欄で最後の行が切れる。
- `useLayoutEffect` で入れる。次のフレームまで待つと、送信して空にした直後に伸びたままの高さが 1 フレーム見える。
- **幅が変わったときも測り直す**（`ResizeObserver`）。横に細くなると同じ本文でも折り返しが増えるので、
  入れたままの高さでは足りなくなる。サイドバーやパネルの幅を変えられるようにした以上、これは普通に起きる。
- 上限は CSS の `max-height` に任せる。そこから先は入力欄の中でスクロールする。

### 2. 大きさの正本は `app/globals.css` の `--pane-*`。TS には数値を持たせない

```css
--pane-sidebar: 288px;
--pane-sidebar-min: 200px;
--pane-sidebar-max: min(480px, 40vw);
```

```css
@utility pane-sidebar {
  width: clamp(var(--pane-sidebar-min), var(--pane-sidebar), var(--pane-sidebar-max));
}
```

- **限界は `clamp()` が守る。** 覚えている値が古くても、窓が狭くても、この範囲から出ない。
- **最大に `vw` / `vh` を混ぜる。** 窓が狭いときに、サイドバーと 2 枚のパネルで本文が潰れるのを防ぐ。
- **エリアを足すのは「変数 4 つ + `@utility` 1 つ + `PANES` に 1 行」**。今後のプロフィールのパネルもこれで乗る。
- Tailwind の任意値（`md:w-[var(--pane-sidebar)]`）にはしない。CLAUDE.md が禁じている書き方に近く、
  `clamp` を書く場所もコンポーネント側になってしまう。

一覧は `docs/ui/tokens.md`「伸縮できるエリア」。

### 3. 中身に合わせて伸びる上限は、px ではなく行数で持つ

```css
--composer-max-lines: 16;
```

```css
@utility composer-lines {
  max-height: calc(var(--composer-max-lines) * 1lh + var(--spacing) * 2);
}
```

上限の意味は「何行まで見せるか」なので、行数で書く。`1lh` はその要素の 1 行ぶんなので、
文字サイズや行送りを変えても意味が保たれる。入力欄とメッセージの編集欄で同じものを使う
（これまで 160px と 240px でばらばらだった）。

16 行は Slack に合わせた（オーナーの調べ、2026-09-21）。高さはユーザーには変えさせない。

### 4. 取っ手は `ResizeHandle` ひとつ。限界は「測って」知る

`components/ui/resize-handle.tsx`。`pane`（どのエリアか）・`grow`（どちらへ引くと大きくなるか）・
`measure`（大きさを読む相手の ref）の 3 つだけを受け取る。

**最小・最大の数値を props でも定数でも持たない。** 正本は CSS なので、`--pane-*` にいったん `0px` と
`1000000px` を入れて、描かれた結果を測って限界を知る（同じ処理の中で元に戻すので、途中の姿は画面に出ない）。
窓の大きさで変わる（`vw`）ので、`resize` のたびに測り直す。

TS 側でも限界で止めるのは、**止めないと引っかかって見える**ため。CSS の `clamp` だけに任せると、
限界の先まで動かしたポインタを同じだけ戻すまで大きさが変わらない。

- 普段は見せない。ポインタを乗せたときと動かしている間だけ 2px の primary の線を出す
  （サイドバーの選択中の縦バーと同じ太さ。緑 = 操作できるもの）。当たりは 8px。
  **線を常に出さないのは、`docs/ui/screenshots/` の見た目を変えないため**でもある。
- モバイル（md 未満）では出さない。幅を変える余地がなく、当たりが本文と重なる。
- 読み上げには `separator` の役で出す（`aria-orientation` / `aria-valuenow` / `-valuemin` / `-valuemax` / `-valuetext`）。
  矢印で 16px ずつ（Shift で 64px）、Home / End で最小・最大、Enter かダブルクリックで既定に戻す。

### 5. 覚えるのは localStorage（端末ごと）。最初の描画の前に当てる

テーマ（`lib/theme.ts`）と同じ扱い。**その端末での見た目の好み**なので、サーバーにも DB にも持たない
（API とマイグレーションが増え、Phase 6 のフロントの作業からバックエンドまで広がる）。

- キーは `hibari:pane-size`、値は `{"sidebar":320,"thread":500}`。
- 読み書きの失敗は「覚えていない」と同じに扱う（プライベートウィンドウ、サイトのデータを消した直後）。
- 壊れた値（文字列・負・NaN）と知らないエリアの名前は捨てる。
- **`<head>` のスクリプトで最初の描画の前に当てる**（`paneSizeBootScript`）。React の描画を待つと、
  既定の幅で 1 度描いてから動くので、開いた瞬間に画面がガタつく。テーマのちらつきを防いでいるのと同じ理由。
- **引っ張っている最中は書かない。** 離したときに 1 度だけ書く（1 回のドラッグで何十回も書かない）。

## 理由

- **数値の置き場所を 1 つにする。** 既定・最小・最大が CSS と TS の両方にあると、必ず片方だけ直す日が来る。
  「CSS に入れて、描かれた結果を測る」は遠回りに見えるが、ずれようがない。
- **`clamp` に守らせると、覚えている値を信用しなくてよい。** 別の端末で広い窓に合わせて決めた値でも、
  ブラウザを狭くしても、壊れた見た目にならない。値そのものは消さないので、窓を広げれば元の幅に戻る。
- **上限を行数で持つと、文字サイズを変えても意味が変わらない。** 「16 行まで」は px で書くと、
  行送りを触った日に黙って別の意味になる。
- **取っ手を普段見せないと、スクリーンショットを撮り直さずに済む。** 既定値も変えていないので、
  `docs/ui/screenshots/` は 1 枚も変わらない。

## 検討した代替案

- **最小・最大を TS の定数で持つ** → `ResizeHandle` が素直になるが、globals.css と二重になる。
  CLAUDE.md「コンポーネント内に色・余白・角丸・フォントサイズの値を直接書かない」の趣旨からも外れる。
- **`md:w-[var(--pane-sidebar)]` のような Tailwind の任意値** → `clamp` を書く場所がコンポーネントになる。
  任意値そのものも CLAUDE.md が禁じている書き方に近い。
- **サーバー（ユーザー設定）に覚えさせる** → 端末をまたいで揃うが、マイグレーション・API・SSR での受け渡しが要る。
  「端末ごとの見た目の好み」はテーマで既に localStorage に置くと決めてある（ADR 0021 系）。
- **入力欄の上辺も引っ張れるようにする** → 一度作ったが取り下げた（上の背景）。Slack に無い操作で、
  リッチテキストの欄（Phase 6.10）に差し替えるときに丸ごと捨てることになる。
- **上限を px で持つ**（`max-h-40` のまま）→ 行送りや文字サイズを変えた日に、上限の行数が黙って変わる。
- **リサイズを CSS の `resize: vertical` に任せる** → ブラウザの取っ手が右下に出るだけで、上辺は引っ張れない。
  幅にも使えず、覚えることもできない。

## 結果（トレードオフ）

- **`ResizeHandle` の「限界を測る」実装が見慣れない。** 変数に極端な値を入れて描かせるので、
  読む人に説明が要る（コメントを厚くしてある）。測るのは `pointerdown` と `resize` のときだけ。
- **パネルが位置の基準になる**（`md:static` → `md:relative`）。取っ手を絶対配置するため。
  `z-auto` のままなので重なりの順は変わらない。
- **入力欄が 16 行まで伸びると、そのぶんタイムラインが狭くなる。** 画面が低いときは窮屈になる。
  Slack と同じ挙動なので、まずはこれで様子を見る。
- **別の端末では幅が揃わない。** localStorage に置いた以上の結果で、テーマと同じ。
- **`docs/ui/screenshots/` は更新しない。** 既定の見た目も既定値も変えていない。
  引っ張ったあとの姿は Storybook の `components/ui/ResizeHandle` で見る。
- **入力欄は `<textarea>` のまま。** 書式・ペースト・リッチテキストは Phase 6.10 で決める。
  そのときこの `composer-lines` の上限（16 行）は、新しい欄にそのまま引き継げる。
