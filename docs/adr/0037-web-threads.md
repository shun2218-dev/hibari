# 0037. Web のスレッド（URL のクエリで開く、送信の列はルームで 1 本、バッジは手元の一覧から数える）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6.5 の構築順 5。ADR 0036 のスレッドの API とイベント（構築順 3・4）と、`docs/ui/` に足した画面（構築順 2）を、Web のデータ層と画面につなぐ。
ADR 0036 は「何をサーバーが返し、何を届けるか」を決めたが、クライアントが決めることが残っていた。

1. 開いているスレッドをどこに持つか（URL か、画面の状態か）
2. 参加しているスレッドの一覧の URL と、サイドバーのバッジの数え方
3. 返信の送信・既読・入力中を、チャンネルの仕組み（ADR 0026 / 0027）とどう分けるか
4. 同期（再接続）でスレッドをどう揃えるか

## 決定

### URL

- **開いているスレッドは、ルームの URL のクエリに持つ**（`/w/{id}/r/{roomId}?thread={rootId}`）。
  「返信」と「N 件の返信」は `router.push`、閉じるのは `router.replace` でクエリを外す。
- **参加しているスレッドの一覧は `/w/{id}/threads`**。ルームの代わりにメインの領域に出す。1 行を押すと、上の URL（そのルームでパネルを開いた状態）に移る。
- 右のパネルは 1 つ。スレッドを開くとメンバーのパネルを閉じ、メンバーを開くとスレッドを閉じる。

### データ層（`lib/chat/store.ts`・`lib/chat/threads.ts`）

- **スレッドは親の ID ごとに持つ**（`threads[rootId]`: 親・返信・既読位置）。返信はルームのタイムライン（`timelines[roomId].messages`）にも入る。
  タイムラインは change_seq のカーソルを進めるために返信も持ち、**表示と既読・「ここから未読」はチャンネルのものだけで決める**（`newestChannelSeq`）。
- 届いたメッセージ（イベント・差分・送信の応答）は、どの経路でも `absorbThreadMessages` を通す。
  - 返信: 開いたことのあるスレッドに足す。**自分の返信なら自分の既読位置を進める**（サーバーがそうしている。`thread.read` は来ない）
  - 親（`thread` を持つ）: スレッドの親と、参加中の一覧の返信数・未読数を書き換える
- **未読数は `last_thread_seq - last_read_thread_seq` で求め直す**（足し引きしない）。そのために一覧の API に 2 つの番号を足した（ADR 0036 の追記）。
- **サイドバーの「スレッド」のバッジは、手元の参加中の一覧から数える**（未読のあるスレッドの数）。一覧はワークスペースを開いたときに全部取る
  （参加しているスレッドの数は多くない前提）。取るまでは、ルーム一覧の `unread_thread_count` を出す。
- `thread.followed` を受けたら一覧を取り直す（一覧の 1 行に要る親の冒頭などがイベントにない）。`thread.read` は既読位置を進める。
- ルームから抜けた・外されたら、そのルームのスレッドを一覧から消す（サーバーも `thread_members` を CASCADE で消している）。

### 送信・既読・入力中

- **返信の送信は、チャンネルと同じルームの送信の列に並べる**（`OutgoingMessage.threadRootId`）。ルームで 1 本なので、チャンネルとスレッドにまたがって送った順に採番される。
  楽観的な表示・失敗・再送（同じ client_msg_id）はチャンネルと同じ（ADR 0027）。チャンネルのタイムラインには `threadRootId` のないものだけを並べる。
- **パネルを開いていて、タブが見えている間は、表示している最新の返信まで既読にする**。チャンネルと違って「いちばん下が見えているか」は見ない
  （パネルは短く、開いた目的が返信を読むことなので）。参加していないスレッドでは送らない。
- 入力中は、パネルの入力欄から `thread_root_id` 付きで送り、`thread_root_id` 付きで届いたものはパネルにだけ出す。
- 編集・削除・「…」メニューは、チャンネルと同じ部品（`useMessageActions`）をパネルでも使う。パネルの中では「返信」を出さない（入れ子にしない）。
- 添付は、パネルの入力欄にもチャンネルとは別のアップローダーを持つ。

### 同期

- 再接続の後（購読の ack の後。ADR 0026）は、ルーム一覧に加えて参加中のスレッドの一覧を取り直し、開いているスレッドも取り直す。
  返信はルームの差分（`after_change_seq`）でも届くが、差分が大きすぎて最新のページで置き換えたときに抜けうるので、パネルは取り直す。
- 取り直しの間は、手元の状態（返信・既読位置）をそのまま見せる。既読位置は後退させない。

### 画面の細部

- 親が見つからない（返信の ID の URL、読めなくなった）ときはパネルを閉じる。その画面はデザインにない。
- 取得中のパネルはヘッダーだけを出す（チャンネルの取得中と同じ）。
- タイムラインの読み上げの名前は、チャンネルが「メッセージ」、パネルが「スレッドのメッセージ」（同じ画面に 2 つ並ぶので）。
- チャンネルの検索をしている間は、サイドバーの「スレッド」を出さない（検索はチャンネルを探すためのもの）。
- 「N 件の返信」は、返信が全部削除されて 0 件になったら出さない（パネルは URL から開ける）。

## 理由

- **URL のクエリにする理由**: スレッドの一覧から「そのルームでパネルを開いた状態」へ移るには、行き先を URL で表すのがいちばん単純。
  リロードや、ほかの人にリンクを送ったときも同じ画面になる。パスにしない（`/r/{roomId}/t/{rootId}`）のは、ルームの画面を作り直さないため
  （ルームのページは `key={roomId}` で作り直すので、パネルの開閉でタイムラインのスクロール位置を失わない）。
- **バッジを手元の一覧から数える理由**: `message.updated`（親）と `thread.read` で 1 行ずつ求め直せば、数え直しの API を呼ばずに済む。
  サーバーの `unread_thread_count` はルーム一覧を取り直したときにしか変わらないので、それだけだとイベントで動かない。
- **送信の列をルームで 1 本にする理由**: 返信もルームの seq を採番する（ADR 0036）。列を分けると、チャンネルとスレッドに続けて送ったときに
  採番の順が入力の順と入れ替わりうる。失敗したら後ろも止める規則（ADR 0027）も、ルーム単位のまま使える。
- **既読を「見えているか」だけで決める理由**: パネルの返信は少なく、開いたらほぼ全部が見えている。スクロールの位置まで見ると、
  チャンネルの既読（`focus`）と同じ仕組みがもう 1 つ要る。

## 検討した代替案

- **開いているスレッドを画面の状態（React の state）だけに持つ**: 一覧から開くときにルームの画面へ状態を渡す経路が要り、リロードで消える。
- **スレッドの一覧を 1 ページずつ取る**: 手元の一覧でバッジを数えられなくなり、イベントのたびにサーバーに数えさせることになる。
- **スレッドの返信をルームのタイムラインに入れない**: change_seq のカーソルに欠番ができ、差分を取り直し続ける（ADR 0014）。
- **パネルでも「いちばん下が見えているか」で既読にする**: 上のとおり仕組みが二重になる。必要になったら足す。

## 結果（トレードオフ）

- ルームのタイムラインの手元のメッセージに、表示しない返信が混ざる。既読や「ここから未読」を決める箇所は、チャンネルのものだけを見る関数を通す必要がある。
- パネルを開いた瞬間に、スクロールしていない返信も既読になる。長いスレッドを途中まで読んで閉じると、残りも既読になっている。
- 参加中のスレッドの一覧を毎回全部取る。数が大きくなったら、ページ単位の取得とサーバーでの数え直しに替える。
- 開いたことのあるスレッドは、ワークスペースを移っても手元に残る（ルームのタイムラインと同じ扱い）。
