# 0003. ORM ではなく sqlc を使う

- 状態: 採用
- 日付: 2026-09-13

## 背景

hibari のデータアクセスには、行ロックを伴う採番（ADR 0002）、条件付き UPDATE による使用回数の加算、部分 UNIQUE 制約、複合外部キー、N+1 を避けた一覧クエリ、`FOR UPDATE SKIP LOCKED` など、SQL の細部に依存する処理が多い。

## 決定

- SQL は `db/queries/` に自分で書き、`sqlc` で型安全な Go コードを生成する。
- ドライバは `pgx` v5 を使う。
- スキーマの正本は `goose` のマイグレーション（`db/migrations/`）で、sqlc はそれを読む。
- ORM（GORM、ent、Bun など）は使わない。

## 理由

- **発行される SQL が見える**: 並行性やロックの挙動を学ぶには、実際に何が実行されるかがコードにそのまま書かれている必要がある。ORM では `SELECT ... FOR UPDATE` や `RETURNING` の扱いが隠れる。
- **コンパイル時の検査**: クエリとスキーマの不整合が `make sqlc` の時点で検出される。手書きの `database/sql` より安全。
- **Postgres の機能をそのまま使える**: `citext`、部分インデックス、`ON CONFLICT`、CTE などを抽象化の制約なしで使える。
- **実行時のオーバーヘッドがない**: 生成されるのは素朴な関数で、リフレクションを使わない。

## 検討した代替案

- **GORM / Bun**: 記述量は減るが、SQL が隠れて学習目的に合わない。複雑なクエリでは結局生の SQL を書くことになる。
- **ent**: スキーマをコードで定義でき型安全だが、生成されるコードが大きく、Postgres 固有の制約を表現しにくい。
- **手書きの pgx**: 自由度は最大だが、スキャン処理の記述が冗長になり、スキーマとの不整合を実行時まで検出できない。

## 結果（トレードオフ）

- 条件によって WHERE 句が変わるような動的クエリは sqlc が苦手。必要になったら `sqlc.narg` による NULL 許容の引数で吸収するか、その箇所だけ手書きの pgx にする。
- トランザクションの境界はユースケース層で明示的に管理する（`Queries.WithTx`）。
- マイグレーションとクエリの両方を書く必要がある。
