# 0059. チャンネルのアーカイブと削除（Phase 6.15。アーカイブはルームの状態として authz が見る、削除は行ごと消してオブジェクトのキーだけを掃除の列に残す）

- 状態: 採用
- 日付: 2026-09-23

## 背景

Phase 6.15 は、使わなくなったチャンネルをアーカイブ（読み取り専用）にし、不要なら削除できるようにする（ロードマップ）。
`rooms.archived_at` の列はマイグレーション 00003 から用意してあるが、どこからも使っていない。

これまでの authz（`internal/chat/authz`）は「**誰が**このルームに何をできるか」だけを見ていた。入力はルームの種類（`kind`）と actor の立場（`RoomActor`）で、
ルームがどういう状態にあるかは入力にない。アーカイブは「**ルームの状態によって**、誰であってもできなくなる操作がある」を初めて持ち込む。
これをハンドラやサービスの `if room.ArchivedAt != nil` に散らすと、絶対ルール 9（認可は 1 箇所に集約する）に反する。

削除は、ルームに付いているもの（メッセージ・スレッド・リアクション・メンション・ピン留め・保存・添付）を全部消す、この設計で最も大きい削除になる。
DB の行は外部キーの `ON DELETE CASCADE` でまとめて消えるが、**ストレージのオブジェクトは DB の外にある**。添付の行（`attachments`）が
CASCADE で消えると、オブジェクトのキーを知る手がかりがなくなる（ADR 0013 がメッセージの物理削除を `NO ACTION` で止めているのも、この理由）。

### Slack で確かめたこと（2026-09-23）

公式ヘルプ「チャンネルをアーカイブまたは削除したい」から分かったこと:

- アーカイブ・削除ともに、#general（全員が入るチャンネル）は対象外
- **アーカイブ**: 既定では、ゲスト以外のメンバーなら、自分がメンバーになっているチャンネルをアーカイブできる（オーナーが種別で絞れる）。
  チャンネル名 →「設定」→「全員に対してチャンネルをアーカイブする」→ 確認の「チャンネルをアーカイブする」
- アーカイブしたチャンネルでは新たなアクティビティはできないが、履歴は残り、検索できる
- **復元**: 「ディレクトリ」の「チャンネル」タブで「アーカイブしたチャンネル」に絞って選び、「設定」→「このチャンネルを復元する」。**チャンネルとメンバーは復元される**
- アーカイブ中の名前は再び使えない。使いたければ、復元してから名前を変える
- **削除**: ワークスペースのオーナーと管理者だけ。元に戻せない。「このチャンネルを削除する」→「はい、完全に削除します」にチェック → 「チャンネルを削除する」。
  アクティブなチャンネルもアーカイブしたチャンネルも削除できる
- 削除すると、そのチャンネルのメッセージも完全に削除される。**チャンネルを削除しても、共有されたファイルは削除されない**（Slack のファイルはチャンネルとは別にワークスペースに属する）

未確認（ヘルプに書かれておらず、実物でも確かめていない）:

- アーカイブ・復元したときに、チャンネルに「〜がチャンネルをアーカイブしました」のようなログの行が残るか（下の決定 4 で「残す」を案にした）
- アーカイブしたチャンネルから、メンバーが自分で抜けられるか
- アーカイブしたチャンネルのメッセージを「後で」に保存できるか

### オーナーと確定した内容（2026-09-23）

- **できる人は Slack と同じ**。アーカイブと復元は、そのチャンネルのメンバー。削除は admin 以上
- **削除したチャンネルの添付ファイルは、ストレージから消す**（Slack とは違う。hibari の添付はメッセージからしかたどれないので、残しても誰も開けない）
- **アーカイブしたチャンネルはサイドバーから外し、サイドバーの検索で探せるようにする**。「ディレクトリ」の画面はまだないので作らない
- **アーカイブ中の名前は使えないまま**（Slack と同じ。いまの UNIQUE の索引をそのまま使う）

## 決定

### 1. 対象とできる人

| 操作 | 対象外 | できる人 |
|---|---|---|
| アーカイブ | DM、`is_default` のルーム、アーカイブ済みのルーム | そのルームのメンバー（admin 以上なら、読めるルームは参加していなくても） |
| 復元 | アーカイブされていないルーム | 同上 |
| 削除 | DM、`is_default` のルーム | admin 以上で、そのルームを読める人（アーカイブ済みでも削除できる） |

- **アーカイブを広く許し、削除だけを絞る。** アーカイブは戻せるので、誤ってアーカイブしても復元で元に戻る。削除は戻せない
- admin 以上は、参加していない public ルームもアーカイブ・復元できる。メンバーが全員抜けたルームを片付けられないと困るため
- 読めない private ルームは、admin 以上でもアーカイブ・削除できない（`CanUpdateRoom` と同じ。読めないルームの存在を 404 で隠す ADR 0011 と揃える）
- アーカイブ中は `is_default` にできない（下の決定 2 で、設定の変更をすべて止める）。`is_default` のルームをアーカイブしたければ、先に既定を外す

### 2. authz にルームの状態を渡す

`authz` の関数に渡すルームの情報を、種類だけから「種類と状態」に広げる。

```go
// Room は authz が見るルームの情報。
type Room struct {
	Kind      RoomKind
	IsDefault bool
	Archived  bool
}

func CanWriteRoom(r Room, a RoomActor) bool {
	return !r.Archived && CanReadRoom(r, a) && a.IsRoomMember
}
func CanArchiveRoom(r Room, a RoomActor) bool   { ... }
func CanUnarchiveRoom(r Room, a RoomActor) bool { ... }
func CanDeleteRoom(r Room, a RoomActor) bool    { ... }
```

- いまの `Can*(kind RoomKind, a RoomActor)` を、すべて `Can*(r Room, a RoomActor)` に置き換える。
  一部だけを置き換えると、アーカイブの判定を忘れた関数が型の上で区別できない。全部を同じ引数にすれば、呼ぶ側はルームの状態を渡さずに呼べなくなる
- アーカイブ中に**止める**のは、ルームの状態を変える操作:
  投稿（スレッドの返信を含む）・編集・メッセージの削除・添付ファイルだけの削除・リアクション・ピン留め・添付のアップロード・参加・メンバーの追加と外す・
  設定（名前・`is_default`）の変更・入力中（typing）
- アーカイブ中も**許す**のは、読むことと、本人だけの状態の操作:
  メッセージ・メンバー・ピン留めの一覧を読む・添付を開く・既読位置を進める・「後で」に保存する・通知の設定を変える・スレッドの通知を変える・自分で抜ける・購読する
  - 本人だけの状態は、ほかの人の画面に何も起こさないので止める理由がない。止めると、アーカイブの前に保存しておきたかったメッセージが保存できなくなる
- アーカイブで止めた操作の API は **409 `room-archived`**（ドメインの `ErrRoomArchived`）を返す。403 にしないのは、権限はあるのに、ルームの状態のために今はできない、という意味だから
  （削除済みのメッセージの編集が 409 `message-deleted` なのと同じ）。authz が false を返したとき、サービスは「アーカイブ中でなければ許されたか」を
  もう一度 authz で確かめて、`ErrRoomArchived` と `ErrForbidden` を分ける（判定の中身は authz の外に書かない）

### 3. アーカイブと送信の競合は `rooms` の行ロックで直列化する

- アーカイブ・復元は `UPDATE rooms SET archived_at = ... WHERE id = $1 AND archived_at IS NULL`（復元は逆）の 1 文で行い、更新されなければ 409
- 送信の採番（`AllocateMessageSeq` / `AllocateThreadReplySeq`）と、編集・削除の採番（`AllocateChangeSeq`）の `UPDATE rooms` に `AND archived_at IS NULL` を足し、
  行が返らなければ `ErrRoomArchived` にする
- どちらも同じ `rooms` の行を更新するので、行ロックで直列化される（ADR 0002 の採番と同じ仕組み）。authz はトランザクションの前に行うので、
  「authz を通った直後にアーカイブされた」送信は、この `UPDATE` で止まる。アーカイブのあとに 1 件だけ投稿が紛れ込むことはない
- リアクション・ピン留めは `AllocateChangeSeq` を使うので、同じ条件で止まる

### 4. アーカイブ・復元でシステムメッセージを残す

- `system.type` に `room_archived` / `room_unarchived` を足す（ADR 0033。sender はアーカイブ・復元した人）
- アーカイブの行は、`archived_at` を入れるのと同じトランザクションで、**入れる前に**書く（入れた後は採番が止まる）
- Slack が行を残すかは未確認（上の「背景」）。残す理由は、あとから開いた人が「いつ・誰が」を履歴で分かるようにするため。残さない場合は、この決定を外すだけで済む

### 5. 開いている人への反映（アーカイブ・復元）

- `room.updated` に `archived_at`（アーカイブされていなければ `null`）を足し、アーカイブ・復元でも配る。宛先は名前の変更と同じ（room、public ならワークスペースも）
- アーカイブしても読めるので、**購読は外さない**。入力欄をアーカイブの表示に替えるのはクライアント
- ルーム一覧（`GET /workspaces/{id}/rooms`）と `GET /rooms/{id}` のルームの形に `archived_at` を足す。一覧はアーカイブ済みも返し、
  サイドバーのチャンネルの節に出さないのはクライアントが決める（検索で探せるようにするため。オーナーの確定）
- 再接続の同期では、ルーム一覧の取り直し（手順 3）で `archived_at` も揃う。新しい経路は足さない

### 6. 削除は行ごと消し、オブジェクトのキーだけを掃除の列に移す

`rooms` の行を消す（論理削除にしない）。消す前に、そのルームの添付のオブジェクトのキーを、ルームに依存しない表に写す。

```sql
-- 行が消えた後に、ストレージのオブジェクトを消すための列（ADR 0059）。どの表にも外部キーを張らない（元の行が消えても残すため）。
CREATE TABLE storage_deletions (
    object_key text        PRIMARY KEY,
    -- これより前には消さない。発行済みの PUT URL で、削除の後にオブジェクトが置かれることがあるため。
    not_before timestamptz NOT NULL,
    created_at timestamptz NOT NULL
);
CREATE INDEX storage_deletions_not_before_idx ON storage_deletions (not_before);
```

削除のトランザクション:

1. `SELECT ... FROM rooms WHERE id = $1 FOR UPDATE`（送信の採番と直列化する）
2. `INSERT INTO storage_deletions SELECT object_key, $now + 15 分, $now FROM attachments WHERE room_id = $1 ON CONFLICT DO NOTHING`（状態を問わず全部）
3. `DELETE FROM rooms WHERE id = $1`（メッセージ・添付・メンバー・リアクション・メンション・保存・スレッドの行は CASCADE で消える）

- **論理削除にしない理由**: `deleted_at` を持つと、ルームを読むすべての問い合わせ（一覧・履歴・アクティビティ・通知・検索）に条件を足すことになり、1 か所の足し忘れで消したはずのルームが見える。
  削除は元に戻さないので、行を残す理由もない
- **キーを別の表に写す理由**: 添付の行を残そうとすると、`attachments.room_id` の外部キーを外す（または `SET NULL` にする）ことになり、添付の不変条件（ADR 0013 の「添付先は同じルームのメッセージ」）が崩れる。
  掃除に要るのはキーだけなので、キーだけを残す
- **`not_before` を 15 分後にする理由**: 削除の直前に発行された PUT URL（有効期間 15 分。ADR 0013）で、削除の後にオブジェクトが置かれることがある。
  その `pending` の行のキーも写しておき、URL が切れた後に消せば、後から置かれたオブジェクトも消える。complete は行がないので 404 になる
- 既存の掃除ジョブ（ADR 0013）に、`storage_deletions` を読む段を足す。`not_before <= now` の行を 100 件ずつ `FOR UPDATE SKIP LOCKED` で取り、オブジェクトを消してから行を消す。
  失敗したらロールバックし、次の実行でやり直す（添付の掃除と同じ。S3 の DELETE は冪等）
- 表の名前を添付に寄せないのは、あとでアバター（ADR 0020）やワークスペースの削除でも、同じ列に積めるようにするため。いまはルームの削除だけが積む
- 大きなルームの削除は、1 つのトランザクションで全行を消すので時間がかかる。いまの規模では受け入れる（「結果」）

### 7. 開いている人への反映（削除）

- `room.deleted` を足す。`{ "workspace_id": "...", "room_id": "..." }`
- 宛先: room の購読者、public ならワークスペースの購読者も、private なら削除した時点のメンバー本人にも（サイドバーに載っていて、ルームを購読していない接続にも届けるため）
  - private の削除をワークスペース全体に配らないのは、読めない private ルームの ID を読めない人に知らせないため（ADR 0011）
- **購読はサーバーが外す**（絶対ルール 8）。各サーバーの Hub は、`room.deleted` を配ったあとに、そのルームの購読を全接続から外す。
  ルームがもうないので、ユーザーごとの確かめ直し（`revalidateUser`）は要らない。後から `subscribe` しても authz で `not_found` になる
- クライアントは、そのルームのものを全部捨てる（サイドバー・メッセージのキャッシュ・ピン留め・アクティビティ・「後で」の行）。
  開いていたら ADR 0035 の「このチャンネルにはアクセスできません」を出す（「存在しないか、閲覧する権限がありません」は削除にもそのまま当てはまる）
- `room.deleted` を取りこぼしたとき:
  - サイドバー: 再接続の同期でルーム一覧を取り直すと、そのルームは返ってこない。一覧にないルームはサイドバーから消える（いまと同じ）
  - 「後で」: 保存の行は CASCADE で消えるので、差分（`after_change_seq`）には出てこない。次に一覧を最初から読むまで残る。押すと 404 になり、ADR 0054 の読めない行と同じく伏せる
  - アクティビティ: 再接続のたびに先頭のページを取り直す（ADR 0058）ので、そこで消える

### 8. API

```
POST   /api/v1/rooms/{roomID}/archive     → 200 ルーム（archived_at 入り）
POST   /api/v1/rooms/{roomID}/unarchive   → 200 ルーム
DELETE /api/v1/rooms/{roomID}             → 204
```

- アーカイブ・復元を `PATCH /rooms/{id}` の `archived: true` にしないのは、できる人が名前の変更（admin 以上）と違い、システムメッセージも残す、別の操作だから。1 つの PATCH に混ぜると、
  「名前とアーカイブを同時に変える」の authz をどちらに合わせるかを決めることになる
- すでにアーカイブ済みのルームのアーカイブ、アーカイブされていないルームの復元は 409 `room-archived` / `room-not-archived`
- 対象外（DM・`is_default`）は 422。権限がなければ 403、読めなければ 404

## 理由

- **状態を authz の引数にする理由**: 「アーカイブ中は投稿できない」は、「参加していなければ投稿できない」と同じ種類の判断で、答えを出す場所を分ける理由がない。
  引数の型を変えれば、コンパイラが呼ぶ側の直し漏れを全部見つける
- **採番の `UPDATE` にも条件を足す理由**: authz はトランザクションの外で読んだ値で判断するので、読んでから書くまでの間にアーカイブされうる。
  seq の採番と同じ行ロックに乗せれば、新しい仕組みを足さずに直列化できる
- **行ごと消す理由**: 決定 6 のとおり。Slack も「完全に削除」で、戻せる削除は作らない
- **購読を Hub が外す理由**: ルームがなくなった以上、そのルームを購読していてよい接続はない。ユーザーごとに DB を確かめ直す必要がなく、配った直後に外せば済む

## 検討した代替案

- **アーカイブの判定をサービスに書く**: authz の関数を変えずに済むが、ルール 9 に反し、新しい操作を足すたびに判定を書き忘れうる
- **アーカイブを 403 にする**: クライアントは「権限がない」と「アーカイブ中」を区別できず、画面の文言を出し分けられない
- **削除を論理削除にして、ジョブが後から行を消す**: 削除の API がすぐ返り、大きなルームでも待たない。一方で、ジョブが消すまでの間、すべての問い合わせに条件が要る（決定 6）。
  いまの規模では 1 つのトランザクションで足りる
- **添付の行を残す（`attachments.room_id` を `SET NULL` にする）**: 掃除ジョブを変えずに済むが、添付の不変条件が崩れ、ルームのない添付という状態が増える
- **削除でもストレージのファイルを残す（Slack と同じ）**: オーナーの判断で採らない（上の「確定した内容」）
- **アーカイブ中の名前を解放する**: 復元のときに名前がぶつかりうるので、復元で名前を変えさせる処理が要る。オーナーの判断で採らない

## 結果（トレードオフ）

- `authz` のルームの関数の引数が全部変わる。呼ぶ側も全部直す（振る舞いはアーカイブの分だけ変わる）
- 削除は戻せない。確認の画面で「はい、完全に削除します」のチェックを要る形にする（Slack と同じ。形はデザインで決める）
- 大きなルームの削除は、行数に比例して時間がかかり、その間 `rooms` の行をロックする（そのルームへの送信だけが待つ）。困ったら、論理削除 + ジョブの形に替える
- 削除したルームの「後で」の行は、`room.deleted` を取りこぼすと次に一覧を最初から読むまで残る（押すと伏せた表示になる）
- 削除したルームへのメッセージのリンク（ADR 0042）は、ほかの読めないルームへのリンクと同じく「アクセスできません」になる
- アーカイブしたルームは、アクティビティ（ADR 0058）にはそのまま残る（読めるので）
