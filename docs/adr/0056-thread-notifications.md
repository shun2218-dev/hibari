# 0056. スレッドの通知（Phase 6.14c。参加は残して「返信の通知」だけを切り替え、明示的なフォローを足す）

- 状態: 提案
- 日付: 2026-09-22

## 背景

Phase 6.14c は、スレッドごとに通知を止められるようにする（ロードマップ。オーナーの要望、2026-09-22）。
6.14b（ブラウザ通知）の規則が「参加しているスレッドの返信」を読むので、6.14b より先に決める（ADR 0055 決定 1）。

### Slack で確かめたこと

公式ヘルプ「スレッドを使用して会話を整理する」（2026-09-22）:

- スレッドの「…」から「**新しい返信の通知を受け取る**」または「**返信の通知をオフにする**」を選べる
- 既定では、**1 対 1 の DM のスレッドはすべて**新しい返信が通知される。チャンネルと複数人の DM では、
  自分が開始したスレッド・返信したスレッド・メンションされたスレッドの新しい返信が通知される
- チャンネルの通知設定に「すべての返信の通知を受け取り、スレッドビューに表示する」がある（この ADR では扱わない）

オーナーが Slack の実物で確かめたこと（2026-09-22）:

- スレッドの中で一度でも（**`@channel` / `@here` を含めて**）メンションされると、以後の新しい返信のたびに通知が届く
- 「返信の通知をオフにする」と、メンションを含まない返信の通知が届かなくなる。**メンションを含む返信は通知される**

2 つ目の前半は、ADR 0041 の「スレッドだけの返信の `@channel` / `@here` は誰も参加させない」と合わない。
ADR 0041 はヘルプの「スレッドの中で使われたときは通知しない」という記述に合わせていたが、実物はそうなっていなかった。**実物に合わせて改める**（下の決定 4）。

ヘルプからも実物の確認からも分からなかったこと: 返信の通知をオフにしたスレッドが、スレッドの一覧から消えるか、未読として数えられるか。
hibari では消さずに残し、見せ方だけを変える（オーナーの判断。決定 2）。

### オーナーと確定した内容（2026-09-22）

- 返信の通知をオフにしても、**スレッドへの参加は残す**。一覧に残り、未読も数える。見せ方だけを変える（チャンネルのミュートと同じ考え方。ADR 0055 決定 1）
- 参加していないスレッドを「**新しい返信の通知を受け取る**」でフォローする操作も作る（ADR 0036 で「必要になってから足す」としていた明示的なフォロー）
- スレッドの中の `@channel` / `@here` でも、対象の人をスレッドの参加者にする（Slack の実物に合わせる。ADR 0041 を改める）

## 決定

### 1. 参加者の行に「返信の通知」を持つ

```sql
ALTER TABLE thread_members
    ADD COLUMN notify_replies boolean NOT NULL DEFAULT true;
```

- `thread_members` の行が「参加」、`notify_replies` が「メンションでない返信も通知するか」
- 本人が選んだ設定なので Postgres に置く（CLAUDE.md ルール 5）。ルームを抜けると行ごと消える（ADR 0036 の FK）ので、入り直したら既定に戻る（ADR 0055 決定 3 と同じ）
- 参加し直すきっかけ（返信・メンション）が来ても **`notify_replies` は戻さない**。オフにした人が同じスレッドで返信するたびにオンに戻ると、オフにした意味がなくなる。
  オフでもメンションは通知されるので（決定 3）、呼ばれたことには気づける

### 2. オフにしたスレッドの見せ方（未読は数える）

- **未読の数え方は変えない**（`thread_seq - last_read_thread_seq`。ADR 0036）。スレッドを開けば既読になる
- スレッドの一覧では、オフにしたスレッドの行を**強調しない**（太字にしない・未読数を出さない）。自分宛ての未読のメンションがあれば、`@N` は出す（ADR 0055 決定 6 と同じ）
- サイドバーの「スレッド」のバッジ（`unread_thread_count`。未読のあるスレッドの数）には、**オフにしたスレッドを数えない**。ただし自分宛ての未読のメンションがあれば数える。
  このバッジは「見てほしいスレッドの数」を知らせるためのもので、オフにしたスレッドで増えると、オフにした意味がなくなる
- 並びは変えない（最後の返信が新しい順。ADR 0036）

### 3. 通知の対象（6.14b が使う規則。ADR 0055 決定 1 の「参加しているスレッドの返信」を具体にする）

```
チャンネル（またはDM）をミュートしている     → 対象にしない（ADR 0055 のまま。メンションでも）
その返信が自分をメンションしている           → 対象（@channel / @here を含む。返信の通知のオン・オフによらない）
参加していて、返信の通知がオン               → 対象（ただし全体・チャンネルの設定が none / 通知しない なら対象にしない）
それ以外（参加していない・オフ）             → 対象にしない
```

- 「チャンネルにも投稿する」を付けた返信（ADR 0039）は、チャンネルの投稿としても判定する（どちらかで対象なら対象。1 回だけ通知する）

### 4. スレッドの中の `@channel` / `@here` でも参加者にする（ADR 0041 を改める）

**スレッドの返信の `@channel` / `@here` は、チャンネルの投稿と同じ人を対象にする。** 対象の人はスレッドに参加し、メンションとして数える。

| 書き方 | 対象 | `thread_members` | `message_mentions` |
|---|---|---|---|
| `@channel` | ルームのメンバー全員 | 全員の行を足す（既読位置は `thread_seq - 1`。すでにいれば何もしない） | `user_id` が NULL の 1 行（ADR 0041 のチャンネルと同じ） |
| `@here` | 送った瞬間にオンラインのメンバー（ADR 0041 と同じ解決） | その人たちの行を足す | 1 人 1 行（ADR 0041 と同じ） |

- 件数の SQL は変えない。スレッドだけの返信のメンションは「参加していて `thread_seq` が既読位置より先」で数えている（ADR 0041）ので、参加させれば `@channel` の 1 行でそのまま全員に数えられる
- **大きなルームでの `@channel` は、メンバーの数だけ `thread_members` の行を入れる。** 送信のトランザクションの中で 1 文の `INSERT … SELECT … ON CONFLICT DO NOTHING` にする。
  上限は設けず、必要になったら測ってから考える（ADR 0041 の `@here` と同じ扱い）
- 送った本人は対象から外さなくてよい（送信で既読位置が進むので、件数にも未読にもならない。ADR 0041）
- 「チャンネルにも投稿する」を付けた返信でも同じ（ADR 0041 の「参加させない」をやめる）

### 5. 明示的なフォロー（「新しい返信の通知を受け取る」）

- 参加していないスレッドで選ぶと、`thread_members` に行を足す（既読位置は親の `last_thread_seq`。**押した時点までの返信は未読にしない**）
- 参加していて `notify_replies` がオフなら、オンに戻す
- フォローできるのは、そのルームのメンバーだけ（`thread_members` の FK。参加していない public ルームでは 403）。authz に `CanFollowThread` を置く
- **フォローをやめる（参加をやめる）操作は作らない。** 通知が要らなければ「返信の通知をオフにする」を使う（決定 2 で一覧に残す判断と合わせる）

### 6. 1 対 1 の DM のスレッドは、2 人とも参加者にする

Slack の既定（DM のスレッドはすべて通知）に合わせる。

- DM のスレッドに最初の返信が付いたとき、親の投稿者と返信した人に加えて、**DM のもう 1 人も参加させる**
- 既存の DM のスレッドは、マイグレーションで 2 人とも参加させる（既読位置は親の `last_thread_seq`。過去の返信を未読にしない）

### 7. API とイベント

```
PUT /api/v1/rooms/{roomID}/threads/{rootID}/me/notifications   {"notify_replies": true | false}
  → 200 {"notify_replies": true, "last_read_thread_seq": 12}   // 参加していなければ last_read_thread_seq は null
```

- `true` は「フォロー」を兼ねる（参加していなければ参加する。決定 5）
- `false` を参加していないスレッドに送ったら、**エラーにせず何もしないで 200** を返す（`notify_replies: false`）。
  参加していないスレッドはもともと通知されないので、結果は頼まれたとおりになっている。画面の状態が古くても失敗させずに済む
- スレッドの親が読めなければ 404、ルームのメンバーでなければ 403（決定 5）
- 参加中のスレッドの一覧（`GET /workspaces/{id}/threads`）と、スレッドの応答に `notify_replies` を足す
- 本人宛てのイベント `thread.notifications_updated`（`workspace_id` / `room_id` / `thread_root_id` / `notify_replies`）を足す。
  フォローで参加したときは、あわせて既存の `thread.followed` も届ける（一覧に加えるきっかけ。ADR 0036）
- 再接続したら、参加中のスレッドの一覧を取り直す（いまと同じ。`notify_replies` も一緒に揃う）

## 理由

- **参加を残して通知だけを切り替える理由**: 参加をやめると既読位置を失い、あとで返信やメンションで参加し直したときに、どこまで読んだかが分からなくなる。
  また「一覧から消えた」スレッドに戻る入口がなくなる。チャンネルのミュートを「隠さず薄くする」にしたのと同じ判断（ADR 0055）。
- **`notify_replies` を返信で戻さない理由**: 決定 1 のとおり。オフの意味を保ち、呼ばれたことはメンションで分かる。
- **スレッドの `@channel` で参加させる理由**: Slack の実物がそうなっていて、書いた人の期待（全員に届く）に合う。
  ADR 0041 はヘルプの記述を根拠にしていたが、記述と実物が違ったので実物を優先する。
- **バッジからオフのスレッドを外す理由**: バッジは件数ではなく「見てほしいもの」の合図で、未読の数え方そのものは変えていない（ADR 0055 の「見せ方だけを変える」の範囲）。

## 検討した代替案

- **オフにしたら参加をやめる（`thread_members` の行を消す）**: 既読位置を失い、一覧からも消える。オーナーと比較して不採用。
- **スレッドの `@channel` を ADR 0041 のまま（参加させない）**: Slack の実物と違う。オーナーの判断で不採用。
- **スレッドの `@channel` でメンションの行を 1 人 1 行にする**: 件数の SQL が `user_id IS NULL` の行を「参加者全員」と読めるので要らない。行が増えるだけ。
- **フォローの解除（参加をやめる）を作る**: 通知を止める手段は「返信の通知をオフにする」で足りる。一覧から消したい要望が出たら足す。

## 結果（トレードオフ）

- 大きなルームのスレッドで `@channel` を書くと、ルームの全員のスレッドの一覧にそのスレッドが入る（Slack と同じ）。
- 返信の通知をオフにしたスレッドも一覧に残り続ける。消す手段はない。
- DM のスレッドは 2 人とも参加するので、マイグレーションで既存の DM のスレッドに行を足す。
- 6.14b の通知の規則は、決定 3 のとおりスレッドの分が 1 段増える。
