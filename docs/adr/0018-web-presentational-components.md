# 0018. Web クライアントの presentational コンポーネントと /dev/preview（Phase 6-1）

- 状態: 採用
- 日付: 2026-09-16

## 背景

Phase 6 は Next.js クライアントを作る。ロードマップは、見た目（6-1）とデータ層（6-2）を分けて進めると決めている。6-1 の成果物は presentational コンポーネントと、`docs/ui/` の全画面・全状態をモックデータで再現する `/dev/preview`。

先に決める必要があったのは次のこと。

- presentational コンポーネントがどこまでを受け持ち、どこからをデータ層に任せるか（時刻の整形、権限の判定、並び順）
- アバターの色の割り当て（`docs/ui/tokens.md` で「Phase 6 で決める」としていた）
- 書体とアイコンの読み込み
- `/dev/preview` とスクリーンショットの対応をどう保つか

## 決定

### コンポーネントの境界
- `web/components/` に画面の単位（`auth` / `chat` / `invite` / `workspace` / `settings`）と共通部品（`ui`）で置く。API もルーターの状態も知らず、**props だけで描く**。
- props は API のレスポンスではなく、表示用の型（`components/chat/types.ts` など）で受け取る。
  - **時刻・サイズ・件数の文言は整形済みの文字列**で受け取る（`timeLabel: "昨日"`、`sizeLabel: "248 KB"`）。「いつを昨日と呼ぶか」は現在時刻とタイムゾーンに依存するので、データ層（6-2）で整形してテストする。
  - **権限の判定結果**を受け取る（メンバーの行の `manage: { kind: "menu", grantableRoles } | { kind: "locked", reason }`、招待の `canRevoke`）。コンポーネントの中で `role === "owner"` から操作の可否を導かない（CLAUDE.md ルール 9）。例外は、ワークスペース設定の「member には読み取り専用で見せる」ような、画面の形そのものがロールで決まるもの。
  - **並び順は受け取った順のまま**描く。seq で並べるのはデータ層（CLAUDE.md ルール 3）。
- 遷移する要素は `next/link`、その場で何かをするものは `button` にする。遷移先の URL は props（`roomHref(roomId)`、`hrefs`）で受け取り、ルートの設計は 6-2 で決める。
- ダイアログやポップオーバーの開閉は `open` の props で外から決める（`/dev/preview` で開いた状態を固定で描くため）。パスワードの表示切り替えのように、画面の外に意味を持たない状態だけをコンポーネントの中に持つ。

### アバターの色
- **ユーザー ID / ワークスペース ID を FNV-1a（32 bit）でハッシュし、6 で割った余り + 1** を `--color-avatar-N` に使う（`web/lib/avatar.ts`）。
- 頭文字は表示名の最初の 1 コードポイント。

### 書体とアイコン
- 書体は `next/font/google` でビルド時に取得して自前で配信する（`web/app/fonts.ts`）。`globals.css` の `--font-sans` / `--font-mono` は next/font が `<html>` に定義する変数を参照する。Zen Kaku Gothic New は可変フォントではないので 400 / 500 / 700 だけを読み、サイズが大きいので preload しない。
- アイコンは `lucide-react` を使い、`components/ui/icons.tsx` を経由して線の太さ（1.75）と `aria-hidden` をそろえる。

### /dev/preview
- 画面の名前を `docs/ui/screenshots/` の PNG のパスと同じにする（`/dev/preview/chat/banner-syncing` ↔ `chat/banner-syncing.png`）。
- `app/dev/preview/catalog.test.tsx` が、**スクリーンショットと一覧が 1 対 1 に対応し、全画面がエラーなく描ける**ことを検査する。スクリーンショットを足したのに再現を忘れると CI が落ちる。
- モックデータの ID は、アバターの色がスクリーンショットと同じになるものを選ぶ。
- 本番のビルドでは `notFound()` を返す。

### デザインの決まりごとの検査
- `components/design-rules.test.ts` が `components/` と `app/` のソースに、Tailwind の任意値（`p-[13px]`）、生の色（`#2f6f62`）、既定のパレット（`text-red-500`）がないことを検査する。

## 理由

- **整形済みの文字列を受け取る理由**: コンポーネントに `Date` と「現在時刻」を渡すと、描画のたびに結果が変わり、`/dev/preview` もテストも時刻を固定する仕組みが要る。整形は純粋関数としてデータ層でテストしたほうが、境界（日付の変わり目、タイムゾーン）を厚く検査できる。
- **判定結果を受け取る理由**: 「admin は他の admin を変更できない」などの規則をコンポーネントに書くと、サーバーの authz と二重になり、片方だけが変わる。クライアントの判定はサーバーと同じ規則を 1 つの関数に置き（6-2）、画面はその結果だけを描く。
- **ID のハッシュで色を決める理由**: 表示名から決めると、名前を変えたときに色が変わり「同じ人」の手がかりが失われる。ULID の先頭はタイムスタンプで、同じ時期に作ったユーザーほど似るので、末尾の違いでも散らばるハッシュにする（`lib/avatar.test.ts` で確認）。
- **next/font を使う理由**: 閲覧のたびに Google Fonts へリクエストしない（プライバシーと表示速度）。フォントの切り替わりによるレイアウトのずれも抑えられる。
- **lucide-react を使う理由**: デザインのアイコンが lucide と同じ 24 グリッドの線画で、必要なアイコンをすべて含む。SVG を手で書き写すより差分が小さく、使ったアイコンだけがバンドルに入る。
- **名前をスクリーンショットと同じにする理由**: どの画面と見比べればよいかを名前だけで分かるようにし、対応の抜けを機械的に検査できるようにする。

## 検討した代替案

- **Storybook を入れる**: 状態の一覧と見た目の確認には十分だが、依存とビルドの設定が大きく増える。ロードマップが `/dev/preview` を指定しており、Next.js の中で同じ書体・同じ CSS のまま確認できるので採用しない。
- **API のレスポンスの型をそのまま props にする**: 変換の手間は減るが、表示に関係ないフィールドがモックデータに必要になり、6-2 で生成する型（Go のイベント定義から作る）の形にコンポーネントが引きずられる。
- **表示名のハッシュでアバターの色を決める**: 上記のとおり、名前の変更で色が変わる。
- **ビジュアルリグレッションテスト（スクリーンショットの差分）を CI に入れる**: フォントの描画が OS ごとに違い、Claude Design のスクリーンショットとも完全には一致しないので、差分の閾値の調整が続く。6-1 では headless Chrome で並べて目で確認し、自動の検査は対応の抜けと描画のエラーまでにする。

## 結果（トレードオフ）

- データ層に「API → 表示用の型」の変換が必要になる。この変換（時刻の整形、グループ化、権限の判定）は 6-2 でユニットテストを厚くする。
- `/dev/preview` のコードは本番のバンドルにも含まれる（描画はしない）。サイズが問題になったら、ルートごとビルドから外す。
- スクリーンショットとの一致は目視で確認している。数 px の余白の違いは残りうる。
