# 0054. ピン留めと保存（Phase 6.12。ピン留めはメッセージの change_seq、保存は本人ごとの change_seq で同期する）

- 状態: 採用
- 日付: 2026-09-22

## 背景

Phase 6.12 は、チャンネルにメッセージをピン留めする機能と、自分用にメッセージを保存する機能（Slack の「後で」）を足す（ロードマップ）。

2 つは見た目が似ているが、**誰の状態か**が違う。

| | 誰の状態か | 見える人 |
|---|---|---|
| ピン留め | ルームの状態 | ルームを読める人の全員 |
| 保存 | 本人の状態 | 本人だけ |

この違いによって、同期の経路が変わる。ピン留めは、リアクション（ADR 0044）と同じく「メッセージの見え方が変わった」ものとして扱える。
保存は、見る人ごとに値が違うので、ルームに配る `message.updated` には載せられない（ADR 0044 の `me` と同じ制約）。
**本人ごとの状態を、WebSocket を落としても取り戻せる形で持つ**のは、この ADR が初めてになる
（ADR 0049 の手動の離席は、再接続のたびにメンバー一覧を丸ごと取り直している）。

### Slack で確かめたこと（2026-09-22）

公式ヘルプ（「チャンネルとダイレクトメッセージにタブを追加して管理する」「メッセージやファイルを「後で」にブックマークする」）から分かったこと:

- ピン留めは、メッセージのメニューの「チャンネルへピン留めする」（DM では「この会話にピン留めする」）で付ける。ヘッダーの「ピン」タブに並ぶ。外すのは「チャンネルからピンを外す」
- 「後で」に登録したアイテムは本人にしか見えない。「進行中」「アーカイブ済み」「完了済み」の 3 つのタブに分かれ、アイテムごとにリマインダーを付けられる
- ヘルプには、ピン留めの件数の上限は書かれていない

オーナーが実物で試したこと（スクリーンショット。2026-09-22）:

- 保存したメッセージが削除されると、一覧のその行は、ゴミ箱のアイコンと「保存したメッセージは削除されました」（英語表示では "A message you saved was deleted."）の 1 行に置き換わる。行は消えず、「進行中」の件数にも数えられたまま
- その行を押すと「ブックマークしたアイテムを外す」の確認ダイアログが出て、「削除」で一覧から外れる
- 削除されていないアイテムでは、ホバーで「完了（✓）」「リマインダー（時計）」「その他（⋮）」が出る。
  その他のメニューは「分割ビューで開く」「新しいウィンドウで開く」「ホームで開く」「アーカイブ」「「後で」から外す」
- 件数は「進行中」のタブにだけ付く

### オーナーと確定した内容（2026-09-22）

- **保存は 3 つのタブ（進行中・アーカイブ済み・完了済み）まで作る。リマインダーは作らない。** リマインダーは通知の配信先の 1 つなので、
  通知の経路を決める Phase 6.14 の後に足す（下の「結果」）
- **ピン留めしたら、チャンネルにシステムメッセージを残す**（「〜がピン留めしました」）
- **保存したメッセージが読めなくなっても、保存の行は残す。** 一覧では中身を伏せ、本人が外せるようにする。もう一度読めるようになったら元に戻る
- **ピン留めできるのは、そのルームに投稿できる人。ルームごとに 100 件まで**

## 決定

### 1. ピン留め: `messages` に 2 列を足す

```sql
ALTER TABLE messages
    ADD COLUMN pinned_at timestamptz,
    -- users は物理削除しない（sender_id と同じ）。
    ADD COLUMN pinned_by uuid REFERENCES users (id) ON DELETE RESTRICT,
    ADD CONSTRAINT messages_pinned_check CHECK ((pinned_at IS NULL) = (pinned_by IS NULL));
-- ピン留めの一覧と、上限を確かめるための件数に使う。ピン留めされた行だけが入る。
CREATE INDEX messages_room_id_pinned_at_idx ON messages (room_id, pinned_at DESC) WHERE pinned_at IS NOT NULL;
```

- 1 つのメッセージは、ピン留めされているかいないかの 2 通りしかない。行を別のテーブルに分けても 1 対 1 になるだけなので、列で持つ。
- 列で持つと、**ピン留めの状態がメッセージの行と同じトランザクション、同じ `change_seq` で変わる**。別のテーブルに分けると、
  「ピンの行はあるが、メッセージの `change_seq` は進んでいない」という中間の状態が作れてしまう。
- ピン留めした人がルームやワークスペースから抜けても、ピンは残す。ピンはルームのもので、付けた人のものではない
  （`message_reactions` がメンバーの行に FK を張って、抜けたら消えるのとは違う）。

### 2. ピン留めの同期: メッセージの `change_seq` を進めて `message.updated` に乗せる

リアクション（ADR 0044 決定 2）と同じにする。**新しいイベントも、新しい同期の経路も作らない。**

- ピン留めと解除で、そのメッセージの `change_seq` をルームの採番で 1 つ進め、`message.updated` を配る
- 再接続の差分（`after_change_seq`）にもそのまま乗る
- **実際に変わったときだけ進める。** ピン留め済みのメッセージをもう一度ピン留めしても、番号は使わず、何も配らない
- メッセージの形に `pinned` を足す。**見る人によらない値**なので、WebSocket でもそのまま配れる

```jsonc
"pinned": { "by": { "id": "01J8...", "handle": "miyuki", "display_name": "高橋 みゆき" }, "at": "2026-09-22T01:00:00Z" }
// ピン留めされていなければ null
```

`by` をユーザーの ID だけにしないのは、`sender` と同じ理由。ピン留めした人がワークスペースを抜けていても、名前を出せるようにする。

### 3. ピン留めのシステムメッセージ: `message_pinned` を足す（オーナーと確認）

ADR 0033 のシステムメッセージに種類を 1 つ足す。

| system_type | いつ | sender | system_data |
|---|---|---|---|
| `message_pinned` | メッセージをピン留めした | ピン留めした人 | `{"message_id": "01J8..."}` |

- ピン留めと**同じトランザクション**で入れる。seq は消費するが `user_seq` は進めない（未読にならない。ADR 0033）
- **解除では残さない。** 解除は「もう見なくていい」という片付けで、チャンネルの全員に知らせる出来事ではない
  （リアクションを外しても何も出ないのと同じ扱い）。同じメッセージを付けたり外したりしても、ログが増えるのはピン留めの回数だけ
- スレッドの返信をピン留めしても、システムメッセージは**チャンネルのタイムライン**に出す。ピン留めの一覧はルームで 1 つなので、
  ログもルームの側に置く
- 文言はクライアントが作る（ADR 0033）。対象のメッセージへは 6.11b の仕組みで飛べるようにする。
  対象がもう読めない・削除済みなら、ADR 0040 と同じく飛ぶ先を出さない
- 文言と見た目はデザインで決め、オーナーに見てもらう（Slack の実際の文言はヘルプで確かめられなかった）

### 4. ピン留めできる人と上限（オーナーと確認）

- **投稿できる人**（`authz.CanPinMessage` を足し、中身はいまのところ `CanWriteRoom` と同じ）。外すのも同じ人。
  判定を別の関数にしておくのは、あとで「admin だけ」に絞るときに、呼ぶ側を直さずに済むようにするため（ADR 0041 の `@channel` と同じ）
- **ルームごとに 100 件まで。** 101 件目は 422（`pinned: too_many`）
- **システムメッセージ**（422）と**削除済みのメッセージ**（404。ADR 0038）はピン留めできない。スレッドの返信はできる
- **ピン留めされたメッセージを削除したら、ピンも外す。** 削除と同じ UPDATE で列を NULL にするので、削除の `change_seq` 1 回で済む。
  削除済みのメッセージが一覧の 100 件の枠を使い続けないようにするため
- 編集してもピンは残る

**上限の確かめ方**: ピン留めのトランザクションの中で、ルームの採番（`AllocateChangeSeq`）でルームの行をロックしてから、
部分インデックスで件数を数える。同じルームのピン留めはルームの行で直列になるので、同時に 2 人が 100 件目を付けても、
101 件にはならない。上限を超えたらロールバックするので、使いかけた番号も戻る。

### 5. ピン留めの API

```
PUT    /api/v1/rooms/{roomID}/messages/{messageID}/pin
DELETE /api/v1/rooms/{roomID}/messages/{messageID}/pin
GET    /api/v1/rooms/{roomID}/pins
```

- `PUT` / `DELETE` はどちらも冪等で、200 と更新後のメッセージを返す（ADR 0044 のリアクションと同じ形）
- `GET /pins` は、ピン留めされたメッセージを**ピン留めした時刻の新しい順**に返す。上限が 100 件なので**ページングしない**
  （`limit` の上限を設ける決まりは、件数の上限そのもので満たす）。読めるのは `CanReadRoom` の人
- 並びは `pinned_at` で決める。メッセージの順序ではなく「ピン留めした順」という別の並びなので、ルール 3（`created_at` で並べない）には当たらない。
  同じ時刻のときは、メッセージの ID で順を決める

### 6. 保存: `saved_messages` の行で持ち、状態を 4 つにする

```sql
CREATE TABLE saved_messages (
    workspace_id uuid        NOT NULL,
    user_id      uuid        NOT NULL,
    message_id   uuid        NOT NULL,
    room_id      uuid        NOT NULL,
    -- 保存し直すたびに振り直す ULID。一覧の並びとカーソルに使う。
    id           uuid        NOT NULL,
    state        text        NOT NULL CHECK (state IN ('in_progress', 'archived', 'completed', 'removed')),
    -- 本人ごとの変更番号。再接続の差分に使う（下の 7）。
    change_seq   bigint      NOT NULL CHECK (change_seq > 0),
    saved_at     timestamptz NOT NULL,
    updated_at   timestamptz NOT NULL,

    PRIMARY KEY (user_id, message_id),
    CONSTRAINT saved_messages_id_key UNIQUE (id),
    CONSTRAINT saved_messages_change_seq_key UNIQUE (workspace_id, user_id, change_seq),
    -- ワークスペースから抜けたら、保存も一緒に消える。
    FOREIGN KEY (workspace_id, user_id) REFERENCES workspace_members (workspace_id, user_id) ON DELETE CASCADE,
    -- メッセージの行が物理的に消えるのは、ルームごと消えるときだけ（論理削除では消えない）。
    FOREIGN KEY (room_id, message_id)   REFERENCES messages (room_id, id) ON DELETE CASCADE
);
-- タブごとの一覧（新しい順）。
CREATE INDEX saved_messages_list_idx ON saved_messages (workspace_id, user_id, state, id DESC);

ALTER TABLE workspace_members
    ADD COLUMN last_saved_change_seq bigint NOT NULL DEFAULT 0 CHECK (last_saved_change_seq >= 0);
```

- **「外す」は行を消さず、`state = 'removed'` にする。** 消してしまうと、別の端末が切断中だったときに「外された」ことを差分で渡せない
  （下の 7）。`removed` は一覧には出さない。同じメッセージをもう一度保存したら、同じ行を `in_progress` に戻し、`id` を振り直す
  （一覧の先頭に来る。Slack も保存し直すと先頭に来る）
- 行が増えるのは「一度でも保存したメッセージの数」までなので、`removed` の行がたまっても際限なくは増えない
- **ワークスペースごと**に持つ（Slack の「後で」もワークスペースごと）。`messages` はワークスペースの列を持たないので、
  行に `workspace_id` を持たせ、保存するときにサービスがルームのワークスペースから入れる
- **保存の行は、読めなくなっても消さない（オーナーと確認）。** ルームから外された・メッセージが削除されたときに後始末をしない。
  見せるかどうかは、読むときに authz で決める（下の 8）
- 状態の移り変わりに制約は付けない。どのタブからどのタブへも動かせる（Slack の「進行中に移動する」も同じ）

### 7. 保存の同期: 本人ごとの `change_seq` と、本人宛てのイベント

**保存の変更も、再接続の差分で取り戻せるようにする**（絶対ルール 4。ロードマップの「WebSocket でしか届かない状態を作らない」）。

- 保存・状態の変更・外すたびに、`workspace_members.last_saved_change_seq` を 1 つ進め、その行の `change_seq` にする。
  採番の仕方はルームの `change_seq` と同じ（`UPDATE ... RETURNING` で、同じ人の同時の変更を行ロックで直列にする）
- 配信は本人宛ての `saved.updated`（`Audience.Users`）。`data` は REST の一覧と同じ 1 件の形（下の 9）。別のタブ・別の端末をそろえる
- 再接続の同期では、`GET /api/v1/workspaces/{workspaceID}/saved?after_change_seq=N` を `has_more` が false になるまで読む。
  `removed` の行も返すので、切断中に外されたものも消せる
- 接続中にイベントを受け取ったときの扱い（カーソル以下は無視・カーソル + 1 は反映・それより先なら差分を取る）は、
  ルームの `change_seq` と同じ（`docs/events.md` の「同期」）

### 8. 読めなくなった保存は、中身を伏せて返す（オーナーと確認）

一覧を返すときに、1 件ずつ**いまの閲覧者で** `CanReadRoom` を通す（ルール 8・9。保存した時点の権限をキャッシュしない）。

- 読めない・削除済みのものは、`status: "unavailable"` にして、メッセージの中身（本文・送信者・ルーム名）を返さない
- ADR 0040 と同じく、**読めないのか削除されたのかを区別しない。** 区別すると、外されたルームのメッセージが消されたかどうかを、
  保存を手がかりに当てられてしまう
- `unavailable` の行も一覧に残り、件数にも数える。本人は外せる（Slack で確かめたのと同じ。外すときに確認のダイアログを出すかと、
  文言はデザインで決める）
- もう一度読めるようになれば（ルームに入り直した、など）、同じ行が `ok` に戻る
- 一覧は 1 ページ分の行を読んでから、ルームごとにまとめて authz を通す（N+1 にしない。ADR 0040 のカードのまとめ取りと同じ）

### 9. 保存の API

```
PUT    /api/v1/rooms/{roomID}/messages/{messageID}/saved        保存する（進行中にする）
PATCH  /api/v1/workspaces/{workspaceID}/saved/{messageID}       {"state": "archived" | "completed" | "in_progress"}
DELETE /api/v1/workspaces/{workspaceID}/saved/{messageID}       外す
GET    /api/v1/workspaces/{workspaceID}/saved?state=in_progress&before={id}&limit=50
GET    /api/v1/workspaces/{workspaceID}/saved?after_change_seq={n}
```

- **保存できるのは、ルームを読める人**（`CanReadRoom`）。参加していない public ルームのメッセージも保存できる。
  システムメッセージ（422）と削除済みのメッセージ（404）は保存できない
- **保存（`PUT`）は冪等。** すでに保存済みなら、状態を変えずに 200 で返す（別のタブで「完了」にしたものを、保存し直して進行中に戻さない）。
  `removed` の行なら進行中に戻す
- **状態の変更と外すのは、読めなくなっていてもできる。** 本人の行を片付ける操作で、メッセージの中身には触れないため。
  パスをルームの下ではなくワークスペースの下に置くのもこのため（ルームを読めるかどうかを入口で問わない）
- 一覧は `id`（保存した ULID）のカーソルで、新しい順（CLAUDE.md の「ページネーション」）。`limit` は既定 50、上限 100
- 一覧のレスポンスに、「進行中」の件数（`in_progress_count`）を載せる。タブの件数に使う

```jsonc
{
  "items": [
    {
      "message_id": "01J8...", "room_id": "01J8...", "state": "in_progress", "change_seq": 12,
      "saved_at": "2026-09-22T01:00:00Z",
      "status": "ok",
      "room": { "id": "01J8...", "kind": "public", "name": "general" },
      "message": { /* REST と同じメッセージの形 */ }
    },
    { "message_id": "01J8...", "room_id": "01J8...", "state": "in_progress", "change_seq": 9,
      "saved_at": "2026-09-21T01:00:00Z", "status": "unavailable", "room": null, "message": null }
  ],
  "in_progress_count": 2,
  "has_more": false
}
```

### 10. メッセージの「保存済み」の印は REST にだけ載せる

メッセージのメニューで、保存済みかどうかでアイコンを変える（Slack のブックマークのアイコン）。この値は見る人ごとに違う。

- REST（履歴・`around_message_id`・`PUT` の応答）のメッセージには `saved: true | false` を載せる
- `message.updated` の配信では省く（ADR 0044 の `me` と同じ。1 つのペイロードを購読者全員に配るため）。
  クライアントは「`saved` の無い更新では手元の値を保つ」
- 手元の値は `saved.updated` と、保存の差分（決定 7）でも直す。メッセージの `change_seq` は進めない
  （保存はルームの全員に関係しないので、ルームの差分に混ぜない）

### 11. 画面の入口はデザインで決める

ピン留めの一覧（Slack ではヘッダーの「ピン」タブ）と「後で」の一覧をどこから開くかは、デザインの段階で描いてオーナーに見てもらう。
「後で」の入口は、Phase 6.14.5 でサイドバーの左のメニューができたらそこへ移る。6.12 では、それまでのつなぎの入口を置く。
一覧を押したら、6.11b の仕組みでそのメッセージへ飛ぶ。

## 理由

- **ピン留めを `change_seq` に乗せる理由**: ピン留めは「このメッセージの見え方が、ルームの全員にとって変わった」もので、
  ADR 0044 がリアクションで使った `change_seq` の定義そのものに当てはまる。同期の経路を増やさずに、クライアントは既存の `mergeMessages` で追従できる。
- **システムメッセージを付けるのに解除では付けない理由**: ピン留めは「全員に見てほしい」という操作で、チャンネルの出来事として残す価値がある。
  解除まで残すと、付け外しを繰り返したときにタイムラインがログで埋まる。
- **保存に本人ごとの `change_seq` を持つ理由**: 保存の状態は本人しか持たないので、ルームの差分には乗らない。
  再接続のたびに一覧を丸ごと取り直す（ADR 0049 のメンバー一覧と同じ）と、保存の数に比例して重くなり、
  しかも一覧はページングしているので、2 ページ目より先の変更（別の端末で外した、など）を取り戻せない。
  差分のカーソルなら、切断中に起きた変更の数だけ読めば済む。
- **外した行を消さない理由**: 行を消すと、差分で「消えた」を渡せない。tombstone を別に持つより、同じ行の状態にする方が、
  「保存し直し」も同じ行の更新で済む。
- **読めなくなった保存を消さない理由**: ルームから外す・メッセージを消す操作に、保存の後始末を足さずに済む。
  見せるかどうかを読むときに authz で決めるので、判断が authz の 1 か所にまとまる（ルール 9）。
  入り直したときに保存が戻るのも、消さないからできる。

## 検討した代替案

- **ピン留めを別のテーブル（`room_pins`）にする**: 「ピンの一覧」を独立に扱えるが、メッセージとは 1 対 1 になるだけで、
  `change_seq` を進めるためにメッセージの行も結局更新する。同じ事実を 2 か所に書くことになる。
- **ピン留め専用のイベント（`pin.added` / `pin.removed`）**: 差分が小さくなるが、再接続の同期にピンの経路がもう 1 本要る（ADR 0044 と同じ理由で不採用）。
- **保存を再接続のたびに取り直す**（ADR 0049 と同じやり方）: 作るものは少ないが、上の「理由」のとおり、ページングした一覧では取り戻せない変更が残る。
  メッセージの「保存済み」の印も、表示中のメッセージの分だけ別に聞き直す必要が出る。
- **保存の状態をメッセージの `change_seq` に乗せる**（`me` と同じく、REST にだけ載せる）: 保存を 1 回するたびに、ルームの全員の差分の番号が進み、
  中身の変わらない `message.updated` が全員に配られる。しかも配った先では `saved` を省くので、本人の別のタブには何も伝わらない。
- **読めなくなった保存を消す**: 一覧がすっきりするが、外す・消す操作のたびに後始末が要り、入り直しても保存が戻らない。オーナーと比較して不採用。
- **リマインダーまで作る**: Slack と同じになるが、期限を見張るジョブと、知らせる手段（6.14 のブラウザ通知）が要る。
  通知の経路を決める前に作ると、6.14 で作り直しになる。オーナーと比較して、6.14 の後に回した。

## 結果（トレードオフ）

- ピン留めのたびに、ルームの `change_seq` が 2 つ進む（メッセージの更新と、システムメッセージ）。seq も 1 つ進む（未読は増えない）。
- 保存の行は、外しても残る。1 人が一度でも保存したメッセージの数だけたまるが、ワークスペースを抜けたら消える。
- ワークスペースを抜けて入り直すと、保存は戻らない（行がワークスペースのメンバーの行に従属するため）。ルームから外されたときは戻る。
- ルームが物理的に消えると（Phase 6.15 で扱う）、保存の行は FK で消えるが、本人ごとの `change_seq` は進まない。
  切断中の端末には「消えた」が差分で届かない。6.15 の ADR で、ルームの削除のときに保存の後始末（`removed` にして番号を進める）をするかを決める。
- リマインダーは 6.14 の後。足すときは `saved_messages` に期限の列を足し、`in_progress` の行だけが持つ形になる見込み
  （状態の列と行の形は変えずに済む）。
