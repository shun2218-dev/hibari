# 0039. チャンネルにも投稿する（返信の行に「チャンネルに出す」を 1 列足し、チャンネルの発言として数える）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6.6 では、スレッドの返信をチャンネルのタイムラインにも流せるようにする（Slack の「チャンネルにも投稿する」）。
ADR 0036 で「あとから足せる形にしておく」とした機能で、ルームの `seq` をスレッドと共有したのはこのためだった。

オーナーと確定している前提（ロードマップ、2026-09-19）:

- スレッドのパネルの入力欄にチェックボックスを置く
- 返信の行にフラグを 1 つ足してチャンネルにも出す

ADR で決めることとして、未読とサイドバーの並び、送信後の変更、削除されたときの見え方が挙がっていた。

## 決定

### スキーマ

`messages` に `in_channel boolean NOT NULL DEFAULT true` を足す。**「この行がチャンネルのタイムラインに出るか」**を表す。

- チャンネルの投稿とシステムメッセージは常に true。スレッドの返信は、「チャンネルにも投稿する」を付けたときだけ true。
- `CHECK (thread_root_id IS NOT NULL OR in_channel)`（チャンネルの投稿を false にさせない）。
- 部分インデックス `messages_room_id_channel_seq_idx` の条件を `WHERE thread_root_id IS NULL` から `WHERE in_channel` に作り直す。
- チャンネルのタイムライン・サイドバーの最後のメッセージを引くクエリの条件も `thread_root_id IS NULL` から `in_channel` に変える。

API では、送信の `also_in_channel`（返信のときだけ指定できる）と、メッセージの `also_in_channel`（流した返信だけ true）として見せる。
DB の列を API と同じ「返信のフラグ」にしなかった理由は下の「理由」に書く。

### 送信

ADR 0036 の返信の送信に、次を足す。

- `also_in_channel: true` を `thread_root_id` なしで送ったら 422（`also_in_channel: invalid_value`）。
- 流す返信では、チャンネルの投稿と同じく **`rooms.last_user_seq` を進めて返信の行の `user_seq` にし、`rooms.last_message_at` も更新する**。
  送信者のチャンネルの既読位置も、その返信まで進める（自分の発言で自分に未読を作らない。ADR 0012）。
- `thread_seq`、親の返信数、`thread_members` の扱いは普通の返信と同じ。スレッドの未読にも数える。
- 冪等性のキーは変えない。同じ `client_msg_id` で `also_in_channel` だけ違う再送は、最初の行を 200 で返す（フラグは最初の送信で決まる）。

### 未読とサイドバーの並び（オーナーと確認）

**流した返信はチャンネルの発言として数える。** チャンネルの未読（`user_seq`）が 1 つ増え、サイドバーの並びも上がる。
「チャンネルに出る人の発言 = `user_seq` を進める行」という規則にそろい、未読のバッジと見える行が食い違わない（Slack と同じ）。

スレッドに参加している人には、同じ返信がチャンネルとスレッドの両方で未読になる。どちらかを読んでも、もう一方は既読にならない（Slack と同じ）。

### 送信後は変えられない（オーナーと確認）

`in_channel` は送信のときに決まり、編集では変えられない。チャンネルから引っ込めたいときは返信を削除する。
後から流すと、その行にだけ過去の位置の `user_seq` を振ることになり、既読位置との引き算（ADR 0033）が壊れる。

### チャンネル側の見え方（オーナーと確認）

流した返信は、チャンネルでは **「スレッドに返信しました」のラベル** を付けて、ルームの `seq` の位置に並べる。ラベルを押すとスレッドを開く。
**親の本文の抜粋は出さない。** レスポンスに足すのは `also_in_channel` だけで、親はクライアントが `thread_root_id` から開く。
スレッドのパネルでは、普通の返信と同じ見え方にする（チャンネルにも投稿したことを小さく示すかは、デザインで決める）。

### 削除（ADR 0038 との整合）

- **流した返信を削除したら、チャンネルからもスレッドからも消える。** 削除は 1 行の論理削除なので、特別な処理は要らない。
- **親を削除しても、流した返信はチャンネルに残る**（返信には触らない。ADR 0036）。ラベルを押すと、削除された親の跡のあるスレッドが開く。
- サイドバーの最後の 1 行は「チャンネルに出ていて削除されていない最後の行」（ADR 0038）のままで、流した返信も対象になる。

### 同期と配信

- 経路は増やさない。`message.created` / `message.updated` / `message.deleted` と `after_change_seq` の差分に、`also_in_channel` が載るだけ。
- クライアントは、`thread_root_id` があればスレッドへ、`thread_root_id` がないか `also_in_channel` が true ならチャンネルへ振り分ける（両方に入ることがある）。
- チャンネルのページング（`before_seq` / `after_seq`）は、流した返信を含めて返す。

## 理由

- **DB の列を「チャンネルに出るか」にした理由**: チャンネルのタイムラインを引く条件（ページング 2 本、サイドバーの最後のメッセージ 2 本）と部分インデックスの条件が、1 列の `in_channel` で書ける。
  「返信のフラグ」として持つと、条件が `thread_root_id IS NULL OR also_in_channel` になり、同じ式を 5 か所に書くことになる。
  部分インデックスは、クエリの条件が索引の条件を含むと Postgres が証明できたときだけ使われるので、書き方が 1 か所ずれると黙って全件の走査に落ちる。
- **API ではフラグとして見せる理由**: クライアントにとって、チャンネルの投稿が `in_channel: true` を持つのは情報がなく、送信のときに意味があるのは返信のときだけ。
- **抜粋を出さない理由**: 抜粋をレスポンスに載せると、親を編集・削除したときに、流した返信すべての `change_seq` を進めて届け直す必要がある（そうしないと古い抜粋が残る）。
  ラベルとスレッドを開く入口だけなら、親の変化は親の行の `message.updated` だけで済む。
- **チャンネルの発言として数える理由**: 上の「未読とサイドバーの並び」のとおり。数えないと、チャンネルに新しい行が出ても未読にならず、気づかれにくい。
- **送信後に変えられない理由**: 上のとおり。Slack も送信後には変えられない。

## 検討した代替案

- **流した返信を別の行（チャンネルの投稿）として複製する**: 既存のクエリは変えずに済むが、編集・削除・リアクションを 2 行に同期する必要があり、冪等性のキーも 2 つになる。ADR 0036 でルームの `seq` を共有したのは、これを避けるため。
- **列を `also_in_channel`（返信のフラグ）にする**: 上の理由で不採用。
- **未読とサイドバーの並びに数えない**: オーナーと比較して不採用。
- **親の抜粋を出す**: オーナーと比較して不採用。必要になったら、クライアントが手元の親を引く形で足せる（API は変えずに済む）。
- **送信後に変えられるようにする**: オーナーと比較して不採用。

## 結果（トレードオフ）

- スレッドに参加している人は、流した返信を 2 か所で既読にする必要がある。
- 流した返信は `change_seq` を 2 つ（返信と親）消費し、さらに `user_seq` も進める。`rooms` の行ロックの時間は普通の返信と変わらない。
- チャンネルのタイムラインで、流した返信の親が画面の外（まだ読み込んでいない過去）にあることがある。ラベルから開くスレッドのパネルが親を取りにいくので、表示は困らない。
- マイグレーションで部分インデックスを作り直す。本番のデータはまだないので、`CONCURRENTLY` は使わない。

## 追記

### 2026-09-19 DB と API（Phase 6.6 の構築順 3）

- `in_channel` には DEFAULT を付けない（マイグレーション 00010）。既存の行は `thread_root_id IS NULL` で埋めた。
  sqlc の引数は Go のゼロ値（false）で渡りうるので、チャンネルの投稿で渡し忘れても、`CHECK (thread_root_id IS NOT NULL OR in_channel)` で止まる。
- `rooms` の採番は、返信の採番（`AllocateThreadReplySeq`）に `in_channel` を渡し、true のときだけ `last_user_seq` と `last_message_at` を進める。
- メッセージのレスポンスの `also_in_channel` は、チャンネルの投稿でも省略せず `false` を返す（クライアントの型を必須のままにするため）。
