# 0058. サイドバーのメニューとアクティビティ（Phase 6.14.5。アクティビティは行を持たず、通知の規則と既読位置から導く）

- 状態: 採用
- 日付: 2026-09-22

## 背景

Phase 6.14.5 は、サイドバーの左にアイコンと文字のメニューを置いてサイドバーの中身を切り替えられるようにし、
メニューの 1 つの「アクティビティ」に、通知の対象になったメッセージを**メッセージ単位で**並べる（ロードマップ。オーナーの要望: 2026-09-21）。

何を通知の対象にするかは 6.14 で決めた（ADR 0055 決定 1、ADR 0056 決定 3、ADR 0057 決定 1）。この ADR は、その規則を
「一覧として後から引ける形」にする。

### Slack で確かめたこと

公式ヘルプ「Slack の新しい『アクティビティ』ビューの紹介」（2026 年 1 月から段階的に提供）と、オーナーが送ってくれた実物のスクリーンショット（2026-09-22）で確かめた。

- アクティビティには、メンション・スレッド・絵文字リアクションなどに加えて、**DM と、「すべての新しい投稿」に設定したチャンネルのメッセージ**も出る
- 上のタブは既定で「すべて」「DM」「メンション」「スレッド」。「＋」と「フィルター」で、「『すべての新しい投稿』に設定…」「絵文字リアクション」「招待」「アプリ」「リマインダー」「VIP」「クリア済みのアイテム」「特定のチャンネルまたはセクション」を足せる。カスタムビューも作れる
- タブの下に、選択のチェックボックス（「すべて選択」「既読メッセージを選択する」「未読メッセージを選択する」「カスタム選択」）、「未読メッセージ」の切り替え、フィルター、検索、「詳細」と「密集」のレイアウトの切り替えが並ぶ
- 一覧は日付の区切り（「8月10日 (月)」）で分かれる。1 件は枠のカードで、送信者のアイコン（右下にチャンネルの `#` の印）、送信者の名前、「# チャンネル名 への投稿」、本文の抜粋（1 行で `…`）、右に日付
- 「密集」では 1 件が 1 行（アイコン・名前・`#`・チャンネル名・抜粋・日付）
- **既読とクリアは別のもの。** アクティビティで既読にするとサイドバーのチャンネルの太字が消えるが、一覧には残る。クリアすると一覧から消え（未読なら既読にもなる）、「クリア済みのアイテム」で後から見られる
- サイドバーの「DM」のバッジは、メッセージの数ではなく**未読の会話の数**

確かめられなかったこと（**未確認**）:

- 左のメニューの並び（ホーム・DM・アクティビティ・後で・その他の順か）と、モバイルでの出し方（下のタブか）
- アクティビティの一覧が、サイドバーの列に出るのか、メインの領域に出るのか（スクリーンショットの幅からは判断できなかった）
- ミュートしたチャンネルのメンションがアクティビティに出るか
- 絵文字リアクションに未読の状態があるか。同じメッセージへのリアクションを 1 件にまとめるか

### オーナーと確定した内容（2026-09-22）

- **メニューはホーム・DM・アクティビティ・後で。** 「後で」（6.12 の保存）はホームのサイドバーから出してメニューに移す。スレッドの一覧はホームに残す。「その他」は置くものがないので作らない
- **「DM」は、最後のメッセージつきの一覧**（相手ごとに最後のメッセージの抜粋と時刻を、新しい順に並べる）
- **アクティビティに並べるもの**: 通知の対象と同じもの（メンション・DM・参加していて通知がオンのスレッドの返信・「すべての新しい投稿」のチャンネル）、**自分のメッセージへのリアクション**、**フィルターのタブ**
- **既読は、いまの既読位置から導く。** 1 件ごとの状態は持たない。クリアは作らない

## 決定

### 1. 左のメニュー

| メニュー | サイドバーの中身 | バッジ |
|---|---|---|
| ホーム | いまのサイドバー（スレッド・チャンネル・DM）。「後で」の行はなくなる | なし（未読のチャンネルは中の太字で分かる） |
| DM | DM の一覧（決定 7） | **未読の DM の数**（会話の数。メッセージの数ではない。Slack と同じ） |
| アクティビティ | アクティビティの一覧（決定 2〜6） | **未読のアクティビティの件数**（決定 5）。琥珀（いま起きていること） |
| 後で | 6.12 の保存の一覧 | なし |

- 今いるメニューは地の色で示す（緑 = 操作できるもの）。バッジは琥珀（CLAUDE.md のトークンの決まりごと）
- **どのメニューを開いているかは URL のクエリ `side` に持つ**（`?side=dms` / `activity` / `later`。ホームは付けない）。
  再読み込み・戻る・リンクの共有で同じ画面に戻れるようにするため。パスではなくクエリにするのは、ルームを開いても残すため
  （`/w/{id}/r/{roomID}?m=...&side=activity`）。パスに持つと、ルームの URL に移った時点でメニューが消える
- アクティビティ・DM・後での一覧で 1 件を押すと、メインの領域にそのルームを開く（決定 8）。**サイドバーの中身はそのまま**（続けて次の 1 件を押せるように）。
  ルームを開いていないときのメインの領域は、いまのワークスペースの最初の画面と同じ
- 6.12 の `/w/{id}/saved` は `?side=later` に置き換える（古い URL は移す）
- 一覧をサイドバーの列に出すか、メインの領域に出すか、モバイルで下のタブにするかは、**デザイン（構築順 2）で実物のスクリーンショットと並べて決める**（未確認のため）。
  私の案は「デスクトップはサイドバーの列、モバイルは下のタブ」。6.12 の保存の一覧はいまメインの領域にあるので、サイドバーの列に移すなら 6.12 のデザインを改める

### 2. アクティビティに並べるもの

**1 件は「メッセージ 1 つ」か「リアクション 1 つ」。** チャンネルごとにまとめない（オーナーの要望）。

メッセージは、次のすべてに当てはまるもの。

- 人の発言（`kind: user`）で、自分が送ったものではなく、削除されていない
- 表示中のワークスペースの、**自分がメンバーのルーム**のもの（決定 4）
- 通知の規則（ADR 0057 決定 1 の表）で「対象」になる。ただし次の 2 点だけ違う
  - **「どのタブも見えていない」の条件は使わない。** アクティビティは後から見る一覧なので、見ていたかどうかによらない
  - **`@here` もメンションに数える。** ADR 0057 が `@here` を外したのは「通知を出すとき自分は離席中で、`@here` の対象ではない」ためで、
    `@here` の行（`message_mentions`）があるのは送った瞬間にアクティブだった人だけ。行がある人には、アクティビティに出してよい

1 つのメッセージが複数の理由に当たるとき（DM で自分がメンションされたなど）も、**1 件として 1 回だけ**出し、理由（`reasons`）を複数持たせる。
タブ（決定 3）はこの理由で絞る。

リアクションは、**自分のメッセージに、ほかの人が付けたもの**（`message_reactions` の 1 行が 1 件）。
メッセージの場合と同じく、自分がメンバーのルームのものだけで、ミュート中のルームのものは出さない（通知の規則に合わせる）。
同じメッセージに付いた複数のリアクションを 1 件にまとめるかは未確認なので、**まとめない**（行を 1 件ずつ出す。まとめるのは表示だけで後から足せる）。

**規則はそのときの設定で読む。** 通知の設定（全体・チャンネルの上書き・ミュート・スレッドの返信の通知）は、一覧を取る瞬間の値で当てはめる。
チャンネルをミュートすると、そのチャンネルの過去の分も一覧から消え、ミュートを外すと戻る。
送った瞬間の設定を残すには、通知の対象ごとに行を書くしかない（下の「検討した代替案」）。

### 3. タブ

「すべて」「DM」「メンション」「スレッド」「リアクション」の 5 つを固定で置く。

- 「すべて」は決定 2 の全部。ほかのタブは理由（`reasons`）で絞る
- 「リアクション」は、Slack では「＋」で足すものだが、オーナーが並べることを選んだので固定のタブにする
- 「『すべての新しい投稿』に設定したチャンネル」はタブにしない（「すべて」には出る）
- タブの下に **「未読メッセージ」の切り替え**を置く（オンなら未読だけ）。既読を既読位置から導くので、サーバーの条件を 1 つ足すだけで作れる
- 作らないもの: カスタムビュー・「＋」でのタブの追加・「密集」のレイアウト・アクティビティの中の検索（Phase 6.16）・選択のチェックボックスとクリア（決定 5）

### 4. 読めるルームだけを出す

**すべての理由で、`room_members` に自分の行があるルームだけを見る。**

- ルームを抜けた・外された・ワークスペースから外れたとき、`room_members` の行が消える（private から外されたときも同じ）。
  その時点から、そのルームのメッセージもリアクションも一覧に出ない。アプリのコードで「読めなくなったか」を判断しない
- public のルームは、参加していなくても読める（CLAUDE.md）が、**参加していない public のルームのメッセージは出さない。**
  通知の設定も未読も参加している人にしかないので、アクティビティの対象にもならない
- `message_mentions` と `message_reactions` は、すでに `room_members` への FK で消える（ADR 0041 / 0044）。
  DM と「すべての新しい投稿」とスレッドの返信は `messages` を直接引くので、`room_members` との結合で絞る
- DoD の「読めなくなったルームのメッセージはアクティビティに出ない」は、API の統合テスト（private から外す・ワークスペースから外す）で確かめる

### 5. 既読は既読位置から導く。クリアは作らない

1 件ごとの「読んだ・クリアした」の状態は持たない。**メッセージの未読は、未読数と同じ物差しで決める**（ADR 0041 のメンションの数え方と同じ）。

- チャンネルに出ているメッセージ（DM を含む）: `messages.user_seq > room_members.last_read_user_seq`
- スレッドだけの返信: `messages.thread_seq > thread_members.last_read_thread_seq`（参加していなければ未読にしない）
- 「チャンネルにも投稿する」を付けた返信（ADR 0039）はチャンネルの物差しで数える

こうすると、**ルームやスレッドを開いて読めば、アクティビティも既読になる。** 既読の API もイベントも足さない（`room.read` / `thread.read` がそのまま使える）。

**リアクションには未読の状態を持たない**（私の案。未確認）。リアクションは seq を持たず、既読位置で表せないため。
未読の件数（メニューのバッジ）と「未読メッセージ」の切り替えは、リアクションを数えない。

**アクティビティの 1 件を押しても、それだけを既読にはできない。** 既読位置は「ここまで読んだ」の 1 つの番号なので、
1 件だけを既読にすると、その前のメッセージもまとめて既読になる。押したらそのメッセージへ飛ぶので（決定 8）、
ルームを開いたときのいつもの既読の進め方（ADR 0042 の未読の扱い）に任せる。

未読の件数（メニューのバッジ）はサーバーが数える。**上限を 100 にして数え、100 以上は「99+」と出す**（全部を数えないため）。

### 6. 一覧の API

```
GET /api/v1/workspaces/{workspaceID}/activity?filter=all&unread=false&before={cursor}&limit=50
GET /api/v1/workspaces/{workspaceID}/activity/unread_count
```

- `filter` は `all` / `dm` / `mention` / `thread` / `reaction`。`unread=true` なら未読だけ（リアクションは出ない）
- `limit` は既定 50、上限 100
- 1 件の形:

```json
{
  "id": "m:01J8...",
  "type": "message",
  "reasons": ["dm", "mention"],
  "unread": true,
  "occurred_at": "2026-09-22T01:00:00Z",
  "room": { "id": "01J8...", "kind": "dm", "name": null, "dm_peer": { "id": "01J8...", "handle": "miyuki", "display_name": "高橋 みゆき" } },
  "message": { /* REST と同じメッセージの形 */ },
  "reaction": null
}
```

  `type: "reaction"` のときは `reaction`（`{ "emoji": "👍", "user": { ... } }`）が入り、`message` はリアクションの付いた自分のメッセージ、`unread` は常に false。
  `reasons` は `dm` / `mention` / `thread` / `channel`（「すべての新しい投稿」）/ `reaction`
- `unread_count` は `{ "count": 12 }`。100 以上は 100 を返す
- **並びは `occurred_at`（メッセージの `created_at`、リアクションの `created_at`）の新しい順**で、同じ時刻は `id` で決める。
  カーソルは `(occurred_at, id)` を詰めた不透明な文字列（CLAUDE.md の「ページネーション」: `OFFSET` を使わない）

**`created_at` で並べることについて。** CLAUDE.md のルール 3 は「ルームの中のメッセージの順序を `created_at` で決めない」で、
それはルームのタイムラインと差分の同期の根拠を seq にするためにある。アクティビティは**ルームをまたいだ一覧**で、
ルームをまたぐ番号はない（seq はルームごと）。リアクションはそもそも seq を持たない。
ここでの並びは見せ方にしか使わず、同期の根拠にしない（再接続では先頭のページを取り直す。決定 9）。

**一覧は N+1 にしない。** 理由ごとの問い合わせを `UNION ALL` で 1 本にまとめ、メッセージ ID で理由を集約してから、
ページの分だけメッセージの中身（送信者・メンション・リアクション・添付）を既存の一括の取り方で引く。
索引は実装で `EXPLAIN` を見て足す（「すべての新しい投稿」のチャンネルが多いと、`messages` をルームの数だけ引くことになるため）。

**通知の規則を Go と TypeScript の 2 か所に持つことになる。** いまは 6.14b のクライアントの `shouldNotify` だけが規則を知っていて、
サーバーは知らない。アクティビティはサーバーが SQL で絞るので、同じ規則をサーバーにも書く。
ずれを防ぐため、**規則の表（入力と、対象になるか）を 1 つの JSON のテストデータにして、Go と Vitest の両方のテストで読む**。
置き場所は実装で決める（候補: `testdata/notification-rules.json`）。

### 7. DM の一覧

**サーバーの変更はない。** ルーム一覧（`GET /workspaces/{id}/rooms`）は、すでにすべてのルームに `last_message`（最後にチャンネルに出たメッセージの抜粋・送信者・削除済みか）と
`last_message_at` を返していて、いまのサイドバーの DM の行もそれを出している。DM の一覧はこの行を並べ直して描く。

- 並びは `last_message_at` の新しい順。スレッドだけの返信は `last_message_at` を進めないので（チャンネルのタイムラインの最後と同じ）、並びも動かない
- ルーム一覧はサイドバーのために最初に取っているので、DM の一覧のために往復を増やさない
- リアルタイムには、いまのサイドバーと同じく `message.created` / `message.updated` / `message.deleted` で手元の値を置き換える
- 相手のアイコン・名前・presence・未読の太字・未読数はいまのサイドバーの DM の行と同じ

### 8. 押したら、そのメッセージへ飛ぶ

アクティビティの 1 件（リアクションを含む）を押すと、ADR 0042 の仕組みでそのメッセージへ飛ぶ（`/w/{id}/r/{roomID}?m={messageID}`、
スレッドの返信なら `&t={rootID}`）。新しい仕組みは作らない。

### 9. リアルタイムでの追加

**メッセージは、クライアントが `message.created` から判断して足す。** サーバーは新しいイベントを配らない。

- 判定は決定 2 の規則。6.14b の `shouldNotify` から「タブが見えていない」を外し、`@here` をメンションに数えたものを、
  1 つの純粋な関数（例: `activityReasons(message, store)`）にして、`shouldNotify` と共有する
- `message.created` は、表示中のワークスペースの購読しているルームにしか届かない（ADR 0015）。アクティビティも表示中のワークスペースのものだけなので足りる
- `message.deleted` なら一覧から外す。`message.updated` では足さない（編集で足したメンションは既読の範囲では数えない。ADR 0041 と同じ）
- `room.read` / `thread.read` を受けたら、手元の 1 件の `unread` を既読位置で求め直し、`unread_count` を取り直す
- `room.notifications_updated` / `notifications.updated` / `thread.notifications_updated` / `room.member_removed` を受けたら、一覧の先頭のページを取り直す
- 再接続では、一覧の先頭のページと `unread_count` を取り直す。アクティビティには `change_seq` のような差分のカーソルを持たせない
  （行を持たないので差分の元がない。切断中に増えた分は先頭のページに入る）

**リアクションだけは、本人宛てのイベントを足す。** リアクションの付け外しは `message.updated` で届くが（ADR 0044）、
集計（絵文字ごとの数と先頭 8 人）しか載らず、「誰がいつ付けたか」が分からないため。

| type | 宛先 | いつ |
|---|---|---|
| `activity.reaction_added` | 本人（メッセージの送信者） | 自分のメッセージに、ほかの人がリアクションを付けた。`data` は一覧の 1 件と同じ形 |
| `activity.reaction_removed` | 本人（メッセージの送信者） | そのリアクションが外された。`data` は `{ "workspace_id", "id" }` |

送り先は 1 人なので、配る量は増えない。配信は `Delivery` を通す（CLAUDE.md ルール 6）。

### 10. 構築順（PR を分ける）

1. 設計: この ADR
2. デザイン: 左のメニュー（デスクトップとモバイル）、アクティビティの一覧（タブ・未読の切り替え・日付の区切り・カード・空の状態）、DM の一覧。story に描いて `docs/ui/` に足し、オーナーに見てもらう
3. サーバー: アクティビティの API・未読の件数・リアクションのイベント、規則の JSON のテストデータ
4. Web: メニューと URL、アクティビティ・DM の一覧、`activityReasons` と `shouldNotify` の共有、リアルタイムの追加、「後で」の移動

## 理由

- **行を持たないのは、`@channel` と「すべての新しい投稿」で人数分を書かないため。**
  通知の対象ごとに行を書くと、`@channel` 1 回でルームの人数分の書き込みになる。ADR 0041 がメンションの件数でカウンタを避けたのと同じ理由で、
  同時送信での取り合いと、消し忘れで二度と消えない行を作りたくない。規則と既読位置から導けば、書き込みは 0 のまま
- **既読をいまの既読位置に揃えると、「アクティビティでは未読なのにチャンネルは既読」というずれが起きない。** 既読の API もイベントも足さずに済む
- **規則を 1 つにする。** 通知・アクティビティ・メンションのバッジが別々の規則を持つと、「通知は来たのにアクティビティにない」が起きる。
  サーバーとクライアントに 2 回書くことは避けられないので、表のテストデータを共有して揃える
- **DM の一覧をルーム一覧から描くのは、サイドバーが最初に取るものにすでに載っていて、往復も変更も増えないため。** DM の数は多くても数百

## 検討した代替案

- **通知の対象ごとに行を書く（`activity_items`）**: 1 件ずつの既読・クリアができ、送った瞬間の設定で固定できる（ミュートしても過去の分が消えない）。
  一方で、`@channel` や「すべての新しい投稿」で人数分の書き込みになり、設定を変えたときに過去の行をどうするかも決めることになる。オーナーの判断で採らない
- **導いた既読 + 本人ごとのクリアの行**: クリアした 1 件だけを本人ごとに記録する形。書き込みは本人の操作のときだけで済むが、今回はクリアを作らない（オーナーの判断）。
  必要になったら、この形で後から足せる（一覧の問い合わせに「クリアの行がない」を足すだけ）
- **アクティビティの中身もサーバーがイベントで配る（`activity.created`）**: 受け取る人ごとに規則を当てるので、`@channel` や「すべての新しい投稿」で人数分の配信になる。
  いまの配信は 1 つのペイロードをルームの購読者に配る形（ADR 0015 / 0016）で、クライアントはすでに規則を持っているので、採らない
- **DM の一覧に専用の API を作る**: 一覧のページングができるが、DM の数は多くないので要らない。往復も増える
- **メニューの状態を URL に持たない（クライアントの状態だけ）**: URL が変わらないので実装は楽だが、再読み込みや戻るで元の画面に戻れない
- **メニューをパスに持つ（`/w/{id}/activity`）**: URL は読みやすいが、1 件を押してルームの URL に移るとメニューが消える。サイドバーの中身を残すには、ルームのパスをメニューごとに増やすことになる

## 結果（トレードオフ）

- ミュートや通知の設定を変えると、アクティビティの過去の分も増減する（そのときの設定で読むため）。Slack がどうしているかは未確認
- アクティビティで 1 件だけを既読にすることはできない。読むにはそのメッセージへ飛ぶ
- リアクションには未読がなく、バッジに数えない
- 「すべての新しい投稿」のチャンネルが多い人は、一覧の問い合わせが重くなりうる。索引で足りなければ、そのときに行を持つ形を考え直す
- 通知の規則を Go と TypeScript の 2 か所に書く。テストデータの共有でずれを検出する
- アクティビティには差分のカーソルがないので、再接続のたびに先頭のページを取り直す（1 ページ分）

## 追記

### 2026-09-22 ホバーで一覧を重ねて出す・「未読メッセージ」のスイッチ（デザインの確認で足した）

オーナーが Slack の実物のスクリーンショットで教えてくれた（デザインの PR の確認のとき）。

- Slack の左のメニューは、**ポインタを乗せるとその一覧をサイドバーの上に重ねて出し**、押すとサイドバーの中身が切り替わる
- 重ねた一覧には、見出しの右に「未読メッセージ」のスイッチがある。アクティビティはタブがなく、一覧だけ
- DM の一覧にも「未読メッセージ」のスイッチがある
- 左のメニューのラベルは 4 文字で折り返す（「アクティ / ビティ」）

オーナーと決めたこと:

- **ホバーで重ねて出すのは DM・アクティビティ・後で。** ホームでは出さない。**今いるメニューでも出さない**（すでにサイドバーに出ているため）
- md 以上だけ（モバイルにはポインタがない）。キーボードのフォーカスでは出さない（押せばサイドバーが同じ一覧に切り替わる）
- 中身はサイドバーに出す一覧と同じ部品の小さな形（`variant="preview"`）。アクティビティは「すべて」だけでタブを出さない。後では「進行中」だけ
- 重ねた一覧の 1 件を押すと、そのルームを開いて一覧を閉じる。サイドバーの中身は変えない
- **DM の一覧にも「未読メッセージ」のスイッチを足す。** 手元のルーム一覧を未読で絞るだけなので、サーバーの変更はない
- アクティビティの「未読メッセージ」も、ボタンではなくスイッチの見た目にする（Slack と同じ。スイッチの部品 `components/ui/switch.tsx` を足した）

データの取り方は変わらない。重ねた一覧のアクティビティは、サイドバーのアクティビティと同じ API（`filter=all`）を読む。
