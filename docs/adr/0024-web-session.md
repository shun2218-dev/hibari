# 0024. Web クライアントの認証の状態（Access Token の置き場所、タブ間の refresh、ページの振り分け）

- 状態: 採用
- 日付: 2026-09-16

## 背景

Phase 6-2 で、本番のページ（ログイン・登録）を作り始める。ADR 0010 と 0021 で決まっていたのは次のこと。

- Refresh Token は httpOnly Cookie（`SameSite=Strict; Path=/api/v1/auth`）で、`X-Hibari-Client: web` のときだけ使う。
- ローテーションに猶予期間がなく、使用済みのトークンが使われると family ごと失効する。**同じ Cookie を持つ複数のタブが同時に refresh すると、全タブがログアウトする**（ADR 0010 の結果）。
- ブラウザから Go の API を直接呼ぶ。Web（`localhost:3000`）と API（`localhost:8080`）はオリジンが違う（ADR 0021）。
- Access Token を localStorage に置かない（CLAUDE.md）。

決める必要があったのは、Access Token をどこに持つか、refresh をタブの間でどう 1 本にするか、ログインしていない人をどこで振り分けるか。

## 決定

### 状態の持ち方（`web/lib/auth/session.ts`）
- **Access Token はメモリにだけ持つ。** ストアの内部に閉じ込め、画面に見せるスナップショット（`loading` / `signed_out` / `signed_in` と user）には含めない。
- ストアは自作で、`useSyncExternalStore` で購読する（ロードマップの 6-2 の方針）。`SessionProvider` をルートのレイアウトに置き、アプリ全体で 1 つにする。
- 起動時（認証を使うページを開いたとき）に 1 回だけ `refresh` → `GET /users/me` でログイン状態を戻す。refresh は user を返さないので 2 本になる。
  - 401 なら `signed_out`。**通信の失敗では `loading` のまま**にし、ログアウトしたと取り違えない。
- API の呼び出しは `session.request()` を通す。
  - Access Token の期限の 30 秒前を切っていたら、呼ぶ前に refresh する。
  - 401 が返ったら 1 回だけ refresh して呼び直す。2 回目も 401 なら `signed_out`。
  - 401 を受けたときに捨てるのは、**そのリクエストで送ったトークンと同じとき**だけ。時間差で返った 401 が、別のリクエストが取り直した新しいトークンまで捨てないように。
- ログアウトは、サーバーに届かなくても画面の状態は `signed_out` にする。

### タブ間の refresh（`web/lib/auth/single-flight.ts`）
- **Web Locks API（`navigator.locks`）の `hibari:refresh` で、タブをまたいで refresh を直列にする。** タブの中では、実行中の Promise を共有する。
- 待っていたタブは、前のタブが受け取った新しい Cookie で refresh する（fetch はレスポンスのヘッダを処理してから解決するので、ロックを放す時点で Cookie は更新済み）。各タブが 1 回ずつローテーションする。
- Web Locks がない環境では、タブの中の共有だけにする。

### ページの振り分け
- ルートグループで分ける。`app/(auth)/` はログインの前（`/login`、`/signup`）、`app/(app)/` はログインが必要な画面。
- **振り分けはブラウザで、refresh の結果を見て行う。** `(app)/layout.tsx` が、`signed_out` なら `/login?next=<元のパス>` に移す。ログイン済みで `/login` を開いたら `next` に、`/signup` なら `/` に移す。
- 状態が分かるまでは何も描かない（ログイン済みの人にフォームが一瞬見える、またはその逆を避ける）。
- `next` は、URL として解決してオリジンが同じパスのときだけ使う（`//evil.example` や `/\evil.example` のようなオープンリダイレクトを防ぐ）。
- 登録の直後は、ログイン状態になっても振り分けを止めて、メールの確認待ちの画面を出す。

### 表示のための小さな判断
- パスワードの強度は長さだけで見積もる（8 / 12 / 16 文字で段階を分ける。数え方はサーバーと同じコードポイント）。
- 「別のアドレスに変更する」は、email を変える API がないので出さない（`VerifyEmailPending` は `onChangeEmail` を渡したときだけ出す）。

## 理由

- **メモリに置く理由**: localStorage や sessionStorage は、XSS で読まれる。メモリに置いても XSS の間は API を呼ばれうるが、トークンそのものを持ち出されて、ページを閉じたあとも使われることはない。リロードのたびに refresh が 1 本増えるが、Refresh Token は httpOnly Cookie にあるので、そのために JS から読める場所へトークンを出す必要はない。
- **Web Locks を使う理由**: ADR 0010 が「猶予期間を設けず、クライアントで対処する」と決めていた。Web Locks はオリジン内のタブとワーカーで共有され、ロックを持ったタブが閉じられたら自動で解放されるので、localStorage に「refresh 中」の印を置く方式のように、閉じたタブの印が残って全員が待ち続けることがない。実際に、同じオリジンの iframe を 5 つ同時に読み込んでも refresh は 5 本とも 200 だった。ロックを通さずに 5 本同時に送ると、1 本だけが 200 で、残りが 401 になり、family ごと失効した。
- **ブラウザで振り分ける理由**: Refresh Token の Cookie は API のオリジンの `Path=/api/v1/auth` にしか付かないので、Next.js のサーバー（proxy やサーバーコンポーネント）からはログインしているかが見えない。見えるようにするには、Cookie を Web のオリジンにも置くか、Next.js に refresh を通す必要があり、ADR 0010 / 0021 で退けた形になる。振り分けは表示のためで、守っているのは API の認可（CLAUDE.md ルール 9）なので、ブラウザで決めても安全性は変わらない。
- **通信の失敗で `signed_out` にしない理由**: サーバーが一時的に落ちただけで、ログインの画面に飛ばされ、`next` の付いた URL で行き来することになる。
- **強度を長さだけで見る理由**: サーバーは文字種の組み合わせを強制しない（NIST SP 800-63B）。記号の有無で強度を変えると、サーバーの規則と違うことを促す。辞書による判定（zxcvbn）は依存が大きい。

## 検討した代替案

- **Access Token を sessionStorage に置く**: リロードで refresh が要らなくなるが、XSS で持ち出せる。CLAUDE.md の localStorage の禁止と同じ理由で採用しない。
- **BroadcastChannel で Access Token をタブの間で配る**: ローテーションが 1 回で済むが、トークンがタブの外に流れる経路が増え、配り終わる前に別のタブが refresh する競合も扱う必要がある。ロックだけで再利用の誤検知は防げるので、そこまではしない。
- **localStorage に「refresh 中」の印を置く**: Web Locks がなかったころの方法。書き込みと読み込みが原子的でなく、タブが閉じられると印が残る。
- **Next.js の proxy（旧 middleware）で振り分ける**: 上記のとおり Cookie が見えない。
- **サーバーの refresh に数秒の猶予期間を足す**: ADR 0010 で退けた（盗まれたトークンの利用を検知できない間ができる）。

## 結果（トレードオフ）

- ページを開くたびに refresh が 1 本と `me` が 1 本走り、その間は画面が空になる。
- タブの数だけローテーションが起きる。refresh_tokens の行も同じだけ増える（失効済みの行の掃除は別の課題）。
- サーバーに届かないときの画面がデザインにない。いまは、ログインが必要な画面では何も描かず、ログインと登録の画面では、フォームを戻してコンソールに出すだけにしている（`docs/ui/README.md` の「未解決」）。
- 別のタブでログアウトしても、ほかのタブは次に API を呼んで 401 になるまで、ログインしたままの表示になる。リアルタイムの失効の反映は、WS クライアント（構築順 3）で扱う。

## 追記（2026-09-16）: パスワードの再設定とメールの確認のページ

メールのリンク（`/reset-password?token=` と `/verify-email?token=`。`internal/auth` の `link`）の受け口と、`/forgot-password` を作った。

- **この 3 つのページはログイン状態を戻さない（refresh しない）。** 呼ぶ API はどれも Cookie も Access Token も使わない（`session.requestPasswordReset` / `resetPassword` / `verifyEmail`）。メールのリンクは、ログインしていない別のブラウザで開かれることもある。
- **再設定は、開いただけではトークンを使わない。** トークンが使えるかを先に確かめる API はないので、フォームを出しておき、送信の結果が `invalid-one-time-token` なら「このリンクは使えません」にする。メールのリンクを先読みするスキャナで、本人が開く前に使えなくなることもない。
  - 成功したら、このタブもログアウトした状態にする。サーバーは全セッションを失効させるが、手元の Access Token は期限まで検証を通る（ADR 0007）。
- **確認は、開いたらそのまま API を呼ぶ。** 「確認する」ボタンを挟む画面はデザインにない。スキャナが先に消費しても、確認済みになるだけで害はない（受信箱に届いたリンクを開けたこと自体が確認の中身）。
  - トークンは 1 回しか使えないので、Strict Mode で effect が 2 回走っても 1 回だけ送る（2 回目は「無効」になり、成功の表示を上書きする）。
  - ログイン中なら user を取り直す。トークンの持ち主がいまのユーザーとは限らないので、`email_verified` を決め打ちで書き換えない。
  - トークンのない `/verify-email` は、無効なリンクと同じ画面にする。ログインしていないときに再送を押したら `/login?next=/verify-email` に回し、戻ってきたこの画面から再送する（再送の API はログインが要る）。
- 2 つのリンクのページは `Referrer-Policy: no-referrer`（`<meta name="referrer">`）にする。URL のトークンを、ページから出ていくリクエストの Referer に載せない。
- 失敗の表示のうち、デザインにないもの（再設定の回数制限と入力エラー、確認の待ち時間と通信の失敗）は、`docs/ui/README.md` の「未解決」に挙げた。
