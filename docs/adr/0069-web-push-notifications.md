# 0069. プッシュ通知（Phase 7.1。Web Push を `Delivery` の配信先に足し、送るかどうかをサーバーが決める）

- 状態: 提案
- 日付: 2026-10-19

## 背景

ADR 0057（Phase 6.14b）のブラウザ通知は、**hibari のタブがどこかで開いている間だけ**届く。タブを全部閉じると何も届かない。
ADR 0057 の「検討した代替案」と CLAUDE.md ルール 6 で、プッシュ通知は Phase 7 で「`Delivery` の配信先を 1 つ足す」形にすると決めてある。
ロードマップの「Phase 7 以降」には「APNs / FCM による Push 通知」とある。

2026-10-19 にオーナーがプッシュ通知の着手を依頼した。デザインは Claude Design のキャンバスで先に作り、オーナーが確認した。

- キャンバス: https://claude.ai/artifact/6f55fBSbN4hHL7GHhai6XB （設定の「通知」・その状態・サイドバーの帯・届く通知の中身・iPhone の案内の 5 枚）

### いまあるもの

- 通知の規則: ADR 0055 決定 1（レベルとミュート）、ADR 0056 決定 3（スレッド）、ADR 0057 決定 1（それを 1 つの関数にしたもの）。判定はクライアントの `shouldNotify` だけにある
- presence: ユーザーごとに `active` / `idle` / `offline` を Redis に持つ。`active` は「画面を見ている接続が 1 つ以上ある」（ADR 0049 決定 1・2）
- セッション: `refresh_tokens.family_id` が sid。ログアウトは `auth:revoked` で sid ごとに知らせる。chat は auth を import せず、`authn.SessionChecker` で有効性を確かめる（ADR 0007）
- `devices` テーブル: 「Phase 7 の Push 用」に器だけある（`platform` と `push_token`）。どこからも行を作っていない（ADR 0019）
- サーバーから利用者の書いた URL へ出ていく道は `platform/safehttp` だけ（ADR 0065 決定 8。接続の直前に IP を検査する）

### オーナーに確認すること

決定の中で、ロードマップや既存の設計と食い違うもの・好みで決まるものを挙げる。それ以外は既存の ADR から導いた。

1. **APNs / FCM ではなく Web Push にする**（決定 1）。ロードマップの書き方と違う
2. **`devices` テーブルを消し、`push_subscriptions` を新しく作る**（決定 3）。ERD の変更
3. **どこかで画面を見ている間は、どの端末にも送らない**（決定 5）
4. **DM のハドルの呼び出しも送る**（決定 6。デザインの 6 枚目）
5. **暗号化と VAPID の署名を自分で書く**（決定 9。ライブラリを入れない）
6. フェーズの番号を **7.1** にする

## 決定

### 1. 方式は Web Push（RFC 8030 / 8291 / 8292）

ネイティブのアプリはまだない（Tauri もモバイルも Phase 7 以降の別の項目）。いまの利用者に届く手段は、ブラウザの Service Worker が受ける Web Push だけ。

- 対応: Chrome / Edge / Firefox（デスクトップと Android）、macOS の Safari 16 以降、**iOS / iPadOS の Safari 16.4 以降はホーム画面に追加した hibari だけ**
- APNs / FCM は、ネイティブのアプリを作るときに、同じ配信先にもう 1 つの送り方として足す（決定 3 の `kind`）

### 2. ADR 0057 のブラウザ通知との分担

- **そのブラウザでプッシュ通知を有効にしたら、そのブラウザでは ADR 0057 の通知係（Web Locks のタブ）が通知を出さない。** Service Worker がプッシュを受けて出す。二重に出さないため
- プッシュに対応していない・有効にしていないブラウザでは、ADR 0057 の通知がこれまでどおり動く
- 通知音（ADR 0057 決定 6）は、Service Worker からは鳴らせない（音を出す API がない）。プッシュの通知の音は OS に任せる。設定の「通知音を鳴らす」はタブの通知だけに効くと書き添える
- 許可を求める帯（ADR 0057 決定 5）は 1 つのまま。押すと、許可を求めてからプッシュの購読まで進む

### 3. 購読は `push_subscriptions` に持ち、sid に結び付ける

```sql
CREATE TABLE push_subscriptions (
    id          uuid        PRIMARY KEY,                 -- ULID
    user_id     uuid        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    sid         uuid        NOT NULL,                    -- refresh_tokens.family_id。外部キーは張れない（family_id は一意でない）
    kind        text        NOT NULL CHECK (kind IN ('webpush')),
    endpoint    text        NOT NULL,
    p256dh      bytea       NOT NULL CHECK (octet_length(p256dh) = 65),
    auth        bytea       NOT NULL CHECK (octet_length(auth) = 16),
    user_agent  text,
    created_at  timestamptz NOT NULL,
    CONSTRAINT push_subscriptions_endpoint_key UNIQUE (endpoint),
    CONSTRAINT push_subscriptions_sid_key UNIQUE (sid)
);
```

- **1 つのセッション（sid）に購読は 1 つ。** ブラウザがログインを持つ単位と、プッシュを受ける単位がどちらもブラウザなので、合わせる。同じ sid で別の endpoint を登録したら置き換える
- 同じ endpoint を別のユーザーが登録したら（同じブラウザで別の人がログインし直した）、その行を新しいユーザーと sid に移す。前のユーザーに届き続けないようにするため
- **ログアウトで消す**: chat が `auth:revoked` を受けて、その sid（`all` ならそのユーザー）の行を消す。Redis Pub/Sub は取りこぼすので、送る直前にも `authn.SessionChecker` で sid を確かめ、失効していたら消す（ADR 0007 と同じ二段構え）
- **`devices` テーブルと `refresh_tokens.device_id` は消す。** 器を作ったときに想定した「端末」は、hibari では sid（ブラウザのセッション）だった。APNs / FCM を足すときは `kind` に `apns` / `fcm` を足す
- ERD（`docs/erd.mermaid`）の変更は、購読の API の PR（構築順 3）で行う

### 4. API

| メソッドとパス | 内容 |
|---|---|
| `GET /api/v1/push/config` | VAPID の公開鍵（`applicationServerKey`）。プッシュを使えないサーバーの設定なら `enabled: false` |
| `PUT /api/v1/me/push-subscription` | いまのセッションの購読を登録する（冪等）。`{ endpoint, keys: { p256dh, auth } }` |
| `DELETE /api/v1/me/push-subscription` | いまのセッションの購読を消す（スイッチをオフにしたとき） |
| `GET /api/v1/me/push-subscriptions` | 自分の購読の一覧（設定の「通知を受け取る端末」）。`is_current` と、`user_agent` から作った端末の名前 |
| `DELETE /api/v1/me/push-subscriptions/{id}` | ほかの端末の購読を止める |

- endpoint は **https で、既知のプッシュのサービスのホストだけ**を受ける（FCM / Mozilla / Apple / Windows）。サーバーが利用者の渡した URL に POST するので、SSRF の踏み台にしない。送るときも `safehttp` の接続直前の IP の検査を通す（POST に使えるように広げる）
- ブラウザが endpoint を変えることがある（`pushsubscriptionchange`）。Service Worker はトークンを持たないので API を呼べない。**ページを開くたびに、いまの購読を `PUT` し直す**（冪等）ことで追い付く

### 5. 送る相手はサーバーが決める

ADR 0057 決定 1 の規則のうち、「どのタブも見えていない」以外をそのままサーバーに移す。

```
次のすべてに当てはまる人に送る:
  - メッセージのルームの参加者で、送信者ではない
  - ADR 0055 決定 1・ADR 0056 決定 3 の規則で「対象」になる（ミュート・レベル・チャンネルの上書き・スレッド・@channel）
  - presence が active ではない（idle か offline）
  - 有効な購読がある
```

- **画面を見ている接続がどこかに 1 つでもあれば、どの端末にも送らない。** 見ている画面で読めるため。Slack のモバイルの既定（「デスクトップで操作していないときだけ」）と同じ形。presence は ADR 0049 の Redis の値をそのまま読む
- `@here` は通知の理由にしない（ADR 0057 決定 1 と同じ理由。送る相手は active ではない人なので、`@here` の対象に入っていない）
- **ワークスペースをまたいで送る。** ADR 0057 は表示中のワークスペースしか通知できなかった（購読の単位のため）。サーバーで判定するので、所属するすべてのワークスペースの通知が届く
- 編集・削除・システムメッセージでは送らない（ADR 0057 と同じ）
- 権限の変更（キック・非公開ルームからの削除）の直後でも送らないよう、判定はメッセージの作成の後に DB の参加者を読む（ルール 8。WS の接続時の認可を使い回さない）
- 規則はサーバー（Go）とクライアント（`shouldNotify`）の 2 か所に置くことになる。**同じ表のテストを両方に置き**、片方だけ変えたら落ちるようにする

### 6. 送るもの

| きっかけ | 対象 |
|---|---|
| `message.created` | 決定 5 |
| `huddle.ringing`（ADR 0066 決定 11） | DM の相手。presence の条件は同じ |

- ハドルの呼び出しは 60 秒で止まる（ADR 0066）。プッシュの TTL を 60 秒にして、遅れて届いた古い呼び出しを出さない
- メッセージの TTL は 24 時間。それより古い通知は、開けば未読で分かる

### 7. 通知の中身（デザインのとおり）

- タイトルと本文は ADR 0057 決定 3 と同じ（「送信者（#チャンネル）」、本文は平文にした最初の 100 文字、添付だけなら「ファイルを 1 件送りました: <名前>」）
- 本文はサーバーで平文にする（`<@ID>` を `@名前` に置き換える）。クライアントの関数と同じ表でテストする（決定 5 と同じ理由）
- **アイコンは hibari のマーク**（`icon.svg` から作る PNG。通知の `icon` は SVG を受けないブラウザがあるため）
- **同じルームの通知はまとめる**: `tag` をルームの ID（スレッドの返信ならスレッドの親の ID）にし、Service Worker が同じ `tag` の通知を見つけたら件数を数えて「新しいメッセージが N 件あります」に置き換える
- 押したら、開いている hibari のタブを前に出してそのメッセージへ飛ぶ（ADR 0042 の `?m=`、スレッドなら `?t=`）。タブがなければ新しく開く。ハドルの呼び出しはハドルの画面を開く
- ペイロードは暗号化される（RFC 8291）ので、プッシュのサービスには本文が読めない。**サーバーのログには本文・endpoint・鍵を出さない**（CLAUDE.md「ログ」）

### 8. 配信の形

- **`Delivery` の実装を 1 つ足す（`PushDelivery`）。** 既存の配信（Redis → Hub）と並べる合成の `Delivery` にする。ユースケースは何も変えない（ルール 6）
- **送るのは、イベントを作ったインスタンスだけ。** Redis で配られた先のインスタンスで送ると、インスタンスの数だけ届く。合成の `Delivery` はイベントを作った側でしか呼ばれないので、そこに置けば 1 回になる
- **送信は配信を止めない。** `Deliver` は上限付きの列に積んで戻り、決まった数の goroutine が送る。列があふれたら捨ててログに残す（ADR 0004 の at-most-once と同じ扱い。開けば未読で分かる）。goroutine は context のキャンセルで止める
- 404 / 410 が返った購読は消す。429 と 5xx は再送しない（ネットワークの向こうで溜めない。次の通知で届く）
- 再起動で列の中身は消える。outbox テーブルで確実に送る形はとらない（結果を参照）

### 9. 暗号化と VAPID の署名は `platform/webpush` に自分で書く

- RFC 8291（aes128gcm）は、標準ライブラリの `crypto/ecdh`・`crypto/aes`・`crypto/cipher` と、すでに使っている `golang.org/x/crypto` の HKDF で書ける
- VAPID の JWT（RFC 8292、ES256）は、すでに使っている `jwx` で署名する
- **RFC 8291 の付録 A のテストベクタ**で、暗号化の結果がバイト単位で一致することを確かめる
- `platform/webpush` はチャットの知識を持たない（受けるのは endpoint・鍵・バイト列・TTL・urgency だけ。`platform/storage` と同じ位置）
- VAPID の鍵（P-256）は、開発では `make keys` で `keys/` に作り、本番は秘密として置く。鍵がなければ `GET /api/v1/push/config` が `enabled: false` を返し、画面はスイッチを出さない

## 理由

- **Web Push の理由**: いまの利用者はみなブラウザで使っている。APNs / FCM はネイティブのアプリがないと受け取れない。ネイティブを作る日まで待つと、タブを閉じたら何も届かない状態が続く
- **サーバーで判定する理由**: タブがないときに送るかどうかを決められるのはサーバーだけ。判定に使う設定（ADR 0055 / 0056）はもともと Postgres にある
- **画面を見ているなら送らない理由**: 見ている画面に新着が出るのに、ポケットの電話も鳴ると、通知を切られる原因になる。presence はすでにこの意味の値を持っている（ADR 0049）
- **sid に結び付ける理由**: ログアウトした端末にメッセージの本文が届き続けるのは、情報の漏れになる。sid はすでに失効の単位で、失効のイベントもある（ADR 0007）。新しい「端末」の概念を作らずに済む
- **`devices` を消す理由**: 一度も使っていない器を残すと、「端末はどちらで表すのか」が 2 通りになる。消すのは行のない表なので、取り消しも簡単
- **自分で書く理由**: Go の Web Push のライブラリは、別の JWT のライブラリを連れてくる（hibari は `jwx` に統一している）。暗号化の部分は 100 行ほどで、RFC にテストベクタがあり、正しさを機械で確かめられる。依存を増やすより、読める形で持つほうが保守しやすい
- **outbox にしない理由**: 通知は落ちても、開けば未読とバッジで分かる（WS の配信と同じ前提。ルール 4）。確実に送るためにメッセージの作成のトランザクションへ行を足すと、全メッセージの書き込みが重くなる

## 検討した代替案

- **APNs / FCM を先に入れる**: 受け取るアプリがない。不採用
- **クライアントの判定を Service Worker でやり直す（全員に送り、SW が出すか決める）**: 設定を SW が持てない（トークンも IndexedDB の同期もない）。送らなくてよい相手にも本文を送ることになる。不採用
- **端末ごとの presence で判定する（見ている端末にだけ送らない）**: デスクトップで見ているのに電話が鳴る。Slack の既定とも違う。不採用
- **`devices` を使い回す**: endpoint と 2 つの鍵の列を足すことになり、`platform` と `push_token` の意味が Web Push に合わない。auth のマイグレーションに chat の都合が入る。不採用
- **`webpush-go` などのライブラリ**: 決定 9 の理由で不採用。暗号化のテストベクタが通らなくなるような問題が見つかれば、見直す
- **すべてのインスタンスで送り、Redis で重複を消す**: 送る前に Redis の往復が要り、取りこぼしで重複も起きる。作った側だけが送れば要らない

## 結果（トレードオフ）

- iPhone では、ホーム画面に追加しないとプッシュが届かない（Apple の制約）。案内の帯とシートで補う（デザインの 3 枚目と 5 枚目）
- 通知の規則と本文の平文化が、Go と TypeScript の 2 か所に置かれる。同じ表のテストで食い違いを止める
- サーバーの再起動や列のあふれで、通知が落ちることがある
- プッシュの通知では、hibari の通知音は鳴らない（OS の音になる）
- ワークスペースをまたいで届くようになるのはプッシュだけ。タブの通知（ADR 0057）は、表示中のワークスペースのままになる
