# 0026. Web の WebSocket クライアント（再接続、購読と同期、既読、外されたときの表示）

- 状態: 採用
- 日付: 2026-09-17

## 背景

ロードマップ Phase 6-2 の「本番のページの構築順 3」で、構築順 2（ADR 0025）の REST だけの画面に WebSocket をつなぐ。
接続・イベント・同期の手順は `docs/events.md` と ADR 0014 / 0015 / 0016 が決めている。クライアントの側で決まっていなかったのは次のこと。

- 再接続の待ち方、接続が黙って死んだときの検出、close コード 4001（セッションの失効）の扱い
- 何をいつ購読するか。「購読してから REST を読む」を、画面の移動やルームの追加のたびにどう守るか
- ADR 0025 が「構築順 3 で見直す」とした 2 つ: ルームを開くたびに最新のページで置き換えること、見ている間に届いたメッセージの既読と「ここから未読」
- キックされた・ルームから外されたときの画面の状態、サーバーに届かない画面（`chat/server-error.png`）をいつ出すか

範囲は、受信（メッセージ・メンバー・ルーム・ワークスペース・presence・入力中の表示）と、再接続・同期・バナーまで。入力中を**送る**のは入力欄と一緒に構築順 4 で行う。

## 決定

### 層の分け方
| ファイル | 役割 |
|---|---|
| `web/lib/chat/connection.ts` | 接続を 1 本持ち、切れたらつなぎ直す。ticket の発行、ack の待ち合わせ、ping、online / offline。イベントの意味は知らない |
| `web/lib/chat/realtime.ts` | 接続の上で、購読と同期を行う。接続の状態を画面の表示（バナー、サーバーに届かない）に変える |
| `web/lib/chat/store.ts` | イベントを状態に反映する（`applyEvent`）。change_seq の欠番の検出と差分の取得（`syncTimeline`） |

`ChatProvider` が 3 つを作ってつなぎ、ログインしている間だけ接続する（ログアウトで外れると接続も閉じる）。

### 接続
- 接続のたびに ws-ticket を発行する。ticket の発行が 401 なら（`session.request` が refresh も失敗させている）、もうつながない。
- 切れたら **指数バックオフ + フルジッター**（0〜上限のランダム。上限は 1 秒から倍にして 30 秒まで）で待つ。30 秒以上つながっていた接続が切れたときは、上限を 1 秒に戻す。
- **close コード 4001 では `session.revalidate()`（手元の Access Token を捨てて refresh）** を呼ぶ。失効していれば `signed_out` になり、ログインの画面に移る。有効ならバックオフしてつなぎ直す。
- **25 秒ごとにアプリケーションの `ping` を送り、10 秒以内に ack がなければ切れたとみなす。** ブラウザの `offline` でも切れたとみなし、`online` で待たずにつなぎ直す。
- ack の待ち受けは、送る前に置く。

### 購読と同期
- 購読するのは、表示中のワークスペースと、そのサイドバーのルーム（`roomLists` の ID）。ストアの変化のたびに、足りない購読を足し、要らない購読を外す（ワークスペースを切り替えたら前のものを外す）。
- **新しく購読したら、ack を待ってから REST で取り直す。** 最初の接続・再接続・ルームの追加のどれでも同じ手順にする。
  - ルームの一覧を取り直す（取得中のものがあれば、それが終わってからもう 1 回取る。購読より前に始まった取得の結果で済ませない）
  - 手元にタイムラインがあるルームは、`after_change_seq` で差分を取る
  - 開いているルームのメンバー一覧が手元にあれば取り直す（presence）。ほかのルームのメンバー一覧は、パネルを開いたときに取る
- 購読が `not_found` なら、同じ接続では試し直さず、一覧を取り直す（読めなくなったルームは一覧から消える）。
- 再接続の後は、ここまでが終わるまで「同期しています」を出し、終わったら「接続が復帰しました」を 3 秒出す。最初の接続ではバナーを出さない（ページが REST で読み込んでいる最中なので）。

### タイムライン（ADR 0025 の見直し）
- **一度開いたルームのタイムラインは手元に残し、開き直したら差分だけを取る。** 購読していない間（別のワークスペースを見ていた）の変更も、差分で揃う。
- 差分の取得が 1 ページ（100 件の変更）で終わらなければ、たどらずに最新のページを読み直す。その間に届いたイベントは残す。
- カーソル（`changeSeq`）は、手元にある連続した change_seq の分だけ進める。レスポンスの `last_change_seq` は、最後のページ（`has_more` が false）のときだけ使う（途中のページで使うと、残りのページを飛ばす）。
- イベントの change_seq がカーソル + 2 以上なら、表示にはすぐ足し、差分の取得を頼む。取得中にもう一度頼まれたら、終わった後にもう 1 回だけ回す。
- 読み込んでいない古いメッセージの編集・削除は、タイムラインに足さない（並びの途中に抜けができ、`before_seq` の読み込みがそれを飛ばす）。番号が続いていれば、カーソルは進める。
- 開いている途中（取得中）に届いたイベントは溜めておき、取得の結果と合わせる。

### 既読と「ここから未読」（ADR 0025 の見直し）
- ルームの画面は「最新を見ているか」（タブが見えていて、タイムラインのいちばん下が見えている）をストアに知らせる。
- **見ている間に届いたメッセージは既読にする。** 既読の API は、送信中に次が届いたら、終わった後にいちばん大きい seq でもう 1 回だけ送る。
- 見ていない間に届いたら既読にしない。見始めたら、表示しているところまで既読にする。
- 「ここから未読」は、開いた時点の位置で固定する（ADR 0025）うえで、次のように動かす。
  - 区切りが出ていないとき（開いた時点で未読がなかった）に、見ている間に届いたら、区切りを後ろに送る（届いたメッセージの前に区切りを出さない）
  - 区切りを消した後に、見ていない間に届いたら、それまでの最新の後ろに出し直す
  - 自分のメッセージ（別のタブからの送信）は、見ていなくても見たものとして扱う
- 未読数は `last_message_seq - last_read_seq` で求め直し、既読位置は後退させない。同じイベントが 2 回届いても、既読の応答とイベントが前後しても数がずれない。

### 外されたとき
- **非公開チャンネルと DM から外された**: 開いているなら、サイドバーとヘッダーを残して本文を「このチャンネルから外されました」にする（`chat/removed-from-channel.png`）。ほかのルームを開いたら一覧から消す。開いていなければすぐ消す。
- **public ルームから抜けた・外された**: 参加していなくても読めるので、「参加する」の状態に戻すだけにする。
- **自分で抜けた（別のタブ）**: お知らせは出さず、ワークスペースの入口に戻す。
- **ワークスペースからキックされた**: ワークスペースの一覧からは除くが、その画面を開いている間は名前とサイドバーを残し、本文を「ワークスペースから削除されました」にする（`chat/removed-from-workspace.png`）。「別のワークスペースに移動」で `/` に戻る。
- 外されたワークスペースとルームは購読の対象から外す（サーバーはすでに外している）。

### サーバーに届かない画面
- **一度はつながった後に、ticket の発行が通信の失敗か 502 / 503 / 504 で 3 回続いたら**、「サーバーに接続できません」の画面（最終接続の時刻と試行の回数）にする。「再試行」はバックオフを待たずにつなぐ。
- 端末がオフラインの間の失敗は数えない（再接続中のバナーで待つ。`ServerUnavailable` のコメントのとおり）。500 など、サーバーが応答している失敗も数えない。

### 入力中の表示
- `typing.started` を受け取ってから 6 秒で消す。同じ人のメッセージが届いたら、その時点で消す。自分（別のタブ）は出さない。
- デザインでは入力欄の上にあるので、入力欄を出すまで（構築順 4）は同じ位置に `TypingIndicator` だけを置く。

## 理由

- **接続と購読を分ける理由**: 再接続の待ち方や ping は、購読の対象やイベントの意味と関係なく、偽のソケットだけでテストできる。購読と同期は、接続の状態の変化とストアの状態だけで決まる。
- **フルジッターにする理由**: サーバーの停止（1001）や配信の経路の張り直し（1012）では、全員が同時に切られる。待ち時間を 0〜上限に散らすと、つなぎ直しが時間方向に均される。
- **4001 で refresh する理由**: REST の Access Token は期限まで検証を通る（ADR 0007）ので、そのまま ticket を発行し直すと、発行は成功してアップグレードだけが 401 になる。ブラウザにはアップグレードの 401 が見えず（1006 にしか見えない）、失敗を繰り返すだけになる。
- **アプリケーションの ping を送る理由**: サーバーの WebSocket の ping はブラウザの JS から見えない。スリープからの復帰や Wi-Fi の切り替えでは、TCP が死んでも close が届かず、配信が止まったまま気づけない。
- **購読の後に一覧を取り直す理由**: 一覧（未読数・最後のメッセージ）は change_seq の対象外（ADR 0014）なので、購読より前の変更は取り直すしかない。ページを開いたときの一覧は、接続より前に読んでいることが多い。
- **タイムラインを残して差分を取る理由**: ADR 0025 が最新のページで置き換えていたのは、手元と最新の間に抜けができうるからだった。change_seq の差分は抜けなく揃うので、読み直す必要がない。開き直しが 1 本の小さな取得で済み、読み込んだ古いページも失わない。
- **遅れすぎたら読み直す理由**: 差分をすべてたどると、長く離れていたルームでは、読み込んでいない範囲の変更のために何ページも取ることになる。1 ページで追いつかないなら、最新のページを読む方が速い。
- **見ているときだけ既読にする理由**: 別のタブを見ている間や、上の履歴を読んでいる間に届いたメッセージを既読にすると、未読のバッジが消えて気づけない。
- **外されたときに画面を残す理由**: デザインがサイドバーとヘッダーを残した状態を描いている。すぐに移動すると、何が起きたか分からない。
- **サーバーに届かない画面の条件**: 端末のネットワークの問題とサーバーの停止を区別するため、オフラインの間は数えない。ticket の発行は REST なので、通信の失敗と、Caddy が上流に届かないときの 502 / 503 / 504 で「サーバーから応答がない」と判断できる。3 回はバックオフの待ち時間の合計で最大 7 秒（ジッターしだいでもっと短い）。サーバーの再起動でこの画面になることもあるが、裏で試し続けていて、つながれば自動で元の画面に戻る。

## 検討した代替案

- **ping を送らず、`online` / `offline` だけで検出する**: 経路の断がオフラインとして報告されないことが多い（スリープ復帰、ルーターの先の断）。
- **再接続のたびに、手元のタイムラインをすべて捨てる**: 同期は単純になるが、読み込んだ古いページとスクロール位置を失い、開いているルームの表示がちらつく。
- **購読は、接続したときに 1 度だけ行う**: ワークスペースの切り替えやルームの追加のたびに、つなぎ直すことになる。
- **購読の ack を待たずに REST を読む**: 1 往復速いが、`docs/events.md` の「購読を先にする」を破り、その間の変更を取りこぼす。
- **スクロール位置に合わせて、見えたメッセージまで既読にする**: 正確だが、IntersectionObserver で要素ごとに追う必要がある。いちばん下が見えているか、で足りる（開いたときも、いちばん下を見せている）。
- **キックされたら、すぐに `/` に移す**: 実装は簡単だが、デザインのお知らせの画面を使わないことになる。

## 結果（トレードオフ）

- 接続のたびに、購読の数だけ（ルームの数 + 1）ack を待ち、一覧の取得が 1 本と、手元のタイムラインの数だけ差分の取得が走る。
- ページを開いた直後は、ページの読み込みと購読の後の取り直しで、一覧を 2 回取る。
- タイムラインを手元に残すので、開いたルームの数だけメモリを使う（ログインしている間は捨てない）。
- 25 秒ごとの ping で、接続ごとにフレームが 1 往復増える。
- 購読していないワークスペースのルームの未読数は、そのワークスペースを開くまで更新されない（ワークスペースの切り替えにバッジはない）。
- 最初の接続に失敗したときも「接続が切れました。再接続しています…」を出す。文言は切れたときのものだが、状態の表示はこれしかない。
- ブラウザの画面を実際に操作した確認（2 つのタブ、ネットワークの切断）は、オーナーが手元で行う。自動の確認は、偽のソケットによるテストと、compose の API に実物の fetch と WebSocket でつないだデータ層の確認（2 人のユーザーでの配信・切断中の送信・編集・削除の同期・入力中・キック）まで。
