# 0068. ハドルのカメラと画面共有（Phase 6.18b。音声と同じセッションにトラックを足し、受ける映像はステージに載せた分だけにする）

- 状態: 提案
- 日付: 2026-09-28

## 背景

ADR 0066 で、ハドルは音声を先に作り（6.18a）、カメラと画面共有は後（6.18b）で別の ADR にすると決めた（オーナーの判断、2026-09-26）。
6.18a（DoD 16/16）と 6.18c（DoD 9/9）は完了した。ロードマップは、この ADR で次を決めるとしている。

- 受けるトラックの選び方
- simulcast
- 同時に映せる人数
- 拡大したハドルの窓
- 費用

「拡大したハドルの窓」は、6.18a の追記 C で**別のタブの大きな画面**にしたので、もうある。この ADR では、その画面に映像を足す形を決める。

### 6.18a から引き継ぐもの

- 参加者 1 人に Cloudflare のセッション（1 本の `RTCPeerConnection`）が 1 つ。いまは音声のトラック（名前は `audio`）を 1 本だけ送る。
- アプリの秘密は Go が持ち、SDP を中継する。**誰のトラックを受けられるかは Go が決める**（ADR 0066 決定 2・9）。
- 権限が変わったら、Go がそのセッションの送るトラックも受けるトラックも全部閉じる（決定 8。`GET session` で読んだトラックを全部閉じるので、トラックが増えても変わらない）。
- 1 つのセッションへの変更は直列にしなければならない。直列にするのはクライアントの 1 本の列（決定 4）。
- `huddle.updated` は差分ではなく全体と版（決定 13）。
- ハドルの画面は、チャットのタブが about:blank のタブに portal で描く。マイク・`RTCPeerConnection` はチャットのタブが持つ（追記 C）。

| 部屋の人数 | 上限は書いていない（アプリの方針） | 6.18a の 20 人のまま |

公式の例（Orange Meets、2026-03 の版）がしていること。

- 画面共有は、カメラ・マイクと**同じセッション**に別のトラックとして送る。画面の音声は取らない（`audio: false`）。画面共有は simulcast にしない。
- 映像を受けるのは**「ステージ」に載せたタイルだけ**。ステージの数は幅 600px 未満で 2、画面共有があれば 5、それ以外は 9。
  載せる順は自分・画面共有・最近話した人。ステージから外れたタイルの映像は閉じる。音声は全員の分を受ける。
- カメラを止めると黒い映像に差し替えて送り続ける（30 秒で片付けられないように）。機器の切り替えは `replaceTrack`（SDP のやり取りなし）。

### Slack のハドルの映像（2026-09-28 に公式のヘルプで確かめた）

| | 公式のヘルプの記述 | この ADR |
|---|---|---|
| 始まり方 | すべてのハドルは音声だけで始まる。参加前のプレビューで音声と映像を選べる | 同じ（決定 1） |
| カメラ | 誰でも付けられる。有料プランは 50 人まで入れるが、**映像を付けられるのは同時に 25 人まで** | hibari の上限は 20 人なので、全員が付けられる（決定 8） |
| 画面共有 | **同時に 2 人まで**。共有した画面はハドルの窓に出て、**押すと大きくなる**。鉛筆のアイコンで**誰でも描き込める**（Mac と Windows のアプリだけ） | 2 人まで・押して大きくする（決定 7）。描き込みは作らない |
| 画面共有の音声 | 「システムの音声を共有する」を選べる（2026-06 に追加） | **確認したいこと 1** |
| そのほか | 背景のぼかしと変更、自分の映像を隠す（モバイル）、リアクション・ステッカー・字幕 | 作らない（「やらないこと」） |
| 並べ方 | グリッドか話している人を大きくするかは、ヘルプに書いていない | **確認したいこと 2** |

### オーナーに確認したいこと

1. **画面共有の音声を入れるか。** 私の案は「6.18b では入れない」。Slack は入れているが、ブラウザでは Chrome のタブの音声くらいしか取れず（Safari と Firefox は取れない）、4 本目のトラックの種類が増える。入れるなら、画面と一緒に送る音声のトラック（`screen_audio`）を足す。
2. **カメラを付けた人が多いときの並べ方。** 私の案は「グリッド（最大 9 つ）。押したタイルは大きくする（ピン留め）」。Slack の実物で、4 人以上がカメラを付けたときの並び方と、タイルを大きくできるかを見てもらえると助かる。
3. **ステージの数。** 私の案はデスクトップで 9、画面共有があるときは共有と 4、モバイルは 4（決定 5）。

## 決定

### 1. カメラと画面共有は、音声と同じセッションに別のトラックとして足す

- 参加者 1 人が送るトラックは、最大で **音声（`audio`）・カメラ（`camera`）・画面（`screen`）の 3 本**。どれも同じ Cloudflare のセッション（同じ `RTCPeerConnection`）に載せる（公式の例と同じ）。
  - 1 本に載せれば、ICE・DTLS の接続も TURN の経路も 1 つで済む。
  - 権限が変わったときに閉じるのも、これまでどおりセッションのトラックを全部閉じるだけ（ADR 0066 決定 8 はそのまま）。
- **どのハドルも音声だけで始まる**（Slack と同じ）。参加前のプレビューで、カメラのオンとオフと機器を選べる（ADR 0066 追記 B で 6.18b に回したもの）。既定はオフ。画面共有は入った後にだけ始められる。
- DM のハドルでもチャンネルのハドルでも同じにする。

### 2. 止めたらトラックを閉じる（止めたまま送り続けない）

- カメラを止める・画面共有をやめるときは、そのトラックを Cloudflare で閉じ、サーバーの参加の状態からも外す。もう一度始めるときは新しく送る。
- 公式の例のように黒い映像に差し替えて送り続ける形にはしない。
  - 受けている人がいれば、黒い映像にも転送量を払う（送り込むのは無料だが、送り出すのは有料）。
  - 「カメラがオンか」をサーバーの状態として正しく持てる。黒い映像を送り続けると、それが止めたのかどうかを状態から区別できない。
  - 代わりに、オンとオフのたびに SDP のやり取りが要る。押してから映るまで少し待つ（1 秒ほど）が、頻繁に押すものではないので受け入れる。
- カメラの機器を替えるときは `replaceTrack` で差し替える（送り続けているので SDP のやり取りは要らない。音声の機器の選択と同じ）。

### 3. 送る・やめるの API

```
POST   /api/v1/huddles/{huddleID}/participants/{participantID}/tracks          カメラか画面を送り始める
       { "kind": "camera" | "screen", "offer": "<SDP>", "mid": "1" }
       → 201 { "answer": "<SDP>" }
DELETE /api/v1/huddles/{huddleID}/participants/{participantID}/tracks/{kind}   やめる（何度でも 204）
```

- 送り始めるときは、クライアントが transceiver を足した offer を渡し、Go が Cloudflare に「この mid を `camera` / `screen` という名前で送る」と頼む。
  音声の「入る」と同じく、**成功してから**参加の状態に書いて配る（ADR 0066 決定 4 と同じ理由）。
- やめるときは Go が Cloudflare のそのトラックを `force: true` で閉じ、状態から外して配る。クライアントは自分の transceiver を止める。
  ブラウザの「共有を停止」でトラックが終わった（`ended`）ときも、クライアントがこれを呼ぶ。届かなくても、30 秒で Cloudflare が片付け、心拍が途絶えれば参加ごと外れる。
- 音声は「入る」と「抜ける」がそのまま送る・やめるなので、この API では扱わない（`kind` は `camera` と `screen` だけ）。
- 同じセッションへの変更は、これまでどおりクライアントの 1 本の列に並べる（決定 4）。406 は 409 `huddle-negotiation-conflict` に変える。
- 入れる人の判定（`CanJoinHuddle`）と「参加 ID がその人のもので、まだ入っている」ことの確かめ方は、音声と同じ（ADR 0066 決定 7）。送るのに別の権限は作らない。

### 4. 参加の状態に、送っているトラックの種類を足す

- Redis の参加（ADR 0066 決定 3）に、カメラと画面のトラックの名前を足す（送っていなければ空）。
- `huddle.updated` の参加者に `camera: bool` と `screen: bool` を足す。変わるたびに版を進めて全体を配る（ADR 0066 決定 13 のまま）。
  トラックの名前と Cloudflare のセッションは、これまでどおりクライアントに見せない（決定 2）。
- 再接続の同期（ルームの応答のハドル）にも同じ値が載る。

### 5. 受ける映像は、ステージに載せた分だけにする

- 音声は、これまでどおり**全員の分を受ける**（ADR 0066 決定 9。小さいので）。
- 映像は、ハドルの画面の**ステージ**（映像を映すタイルの枠）に載せた人の分だけ受ける。公式の例と同じ形。
  - ステージの数はデスクトップで 9、画面共有があるときは共有と 4、モバイルは 4（**確認したいこと 3**）。
  - 載せる順は、自分・押して大きくした人（ピン留め）・画面共有・最近話した人。自分の映像は手元のカメラを映すので、受ける本数には数えない。カメラを付けていない人は載せない（アバターのタイルで出す）。
  - 話すたびにステージが入れ替わってちらつかないよう、入れ替えは数秒に 1 回までにする（数はデザインと実物で決める）。
- **ハドルのタブを閉じて帯だけのとき（追記 C）は、映像を 1 本も受けない。**
- ステージから外れた人の映像は閉じる。受けたまま止める仕組みは SFU にない（背景の表）。
- 見えないものを受けないのは、費用がほぼ「受ける人 × 受ける本数」で決まるため（「結果」の見積もり）。
- 受ける・閉じる API は 6.18a のものを広げ、種類を足す。

```
POST  /api/v1/huddles/{huddleID}/participants/{participantID}/subscriptions
      { "tracks": [{ "user_id": "01J...", "kind": "audio" | "camera" | "screen", "quality": "high" | "medium" | "low" }, ...] }
      → { "offer": "<SDP>", "tracks": [{ "user_id": "01J...", "kind": "camera", "mid": "3" }, ...] }
PATCH /api/v1/huddles/{huddleID}/participants/{participantID}/subscriptions/{mid}   カメラの層を替える（決定 6）
      { "quality": "low" }
```

  - 6.18a の `user_ids` はなくし、`tracks` に置き換える。Web は同じリリースで替えるので、古い形を残さない（ネイティブのクライアントはまだない）。
  - 相手がその種類を送っていなければ、その分だけ失敗として返す（受ける前に抜けた場合と同じ。ADR 0066 決定 9）。
  - 相手と同じハドルにいなければ 403（6.18a のまま）。
- 相手がカメラを止めた・抜けたら、受けていたトラックはクライアントが閉じる（6.18a の抜けた人の音声と同じ）。

### 6. カメラは simulcast で送り、受ける側がタイルの大きさで層を選ぶ

- カメラは **3 つの層**で送る。`rid` は `a`（そのまま。上限 1280×720・約 1.2 Mbps）、`b`（1/2・約 400 kbps）、`c`（1/4・約 150 kbps）。
  - 名前を a・b・c にするのは、Cloudflare の `asciibetical`（a に近いほど望ましい）の順とそろえるため。
  - 数値は目安で、実物で直してよい。
- 受ける側は、タイルの大きさで層を選ぶ（`quality` の `high` → `a`、`medium` → `b`、`low` → `c`）。1〜2 人のときの大きなタイルとピン留めは `high`、3〜4 人のグリッドは `medium`、それより多いときと画面共有の横の列は `low`。
- **層の名前（`rid`）は API に出さない。** クライアントは `quality` で話し、Go が `rid` に引き直す。Cloudflare の語彙を API に漏らさない（ADR 0066 決定 2 と同じ）。送る側の `sendEncodings` の `rid` も、サーバーが決めた値を Web の定数に持つ。
- `priorityOrdering` と `ridNotAvailable` はどちらも `asciibetical` にする。帯域が足りなければ SFU が低い層に落とし、送る側が高い層を送れていなければ次の層にする。
- 層を替えるのは `tracks/update`（SDP のやり取りなし）。タイルの大きさが変わったとき（人数・ピン留め・画面共有の有無・窓の大きさ）にだけ呼ぶ。
- 画面共有は simulcast にしない（公式の例と同じ）。文字が読めることが大事で、小さく縮めた層の使い道がない。

### 7. 画面共有は同時に 2 人まで。見る人が押して大きくする

- **同時に共有できるのは 2 人まで**（Slack と同じ）。3 人目は 409 `huddle-screen-share-full`。
  数えるのと書くのは Redis の Lua の中で一緒にする（2 人が同時に押しても 3 人にならない。6.18a の人数の上限と同じ）。
- 共有された画面は、ステージのいちばん大きな枠に出す。2 つあれば並べ、押した方を大きくする（Slack と同じ）。
- 共有は 1 本の層で送る。`contentHint = "detail"`、フレームレートは上限 15（文字の読みやすさを優先する）。
- **自分のハドルのタブを共有しない**ように、`getDisplayMedia` に `selfBrowserSurface: "exclude"` を渡す（合わせ鏡になるのを避ける）。
- 共有する人の画面には、共有していることを琥珀の印で出し、「共有をやめる」を押せるボタンは別に置く（琥珀の要素を押せるようにしない）。
- 描き込み・カーソルの共有・画面の音声は作らない（「やらないこと」。音声は**確認したいこと 1**）。

### 8. 同時に映せる人数

- **カメラは、入っている全員（上限 20 人）が付けられる。** Slack は同時に 25 人までだが、hibari の人数の上限（20 人）がそれより小さいので、別の上限は要らない。
- 受ける側の本数はステージの数（決定 5）で決まる。送る人数を絞るのではなく、受ける本数を絞る。

### 9. ハドルの画面（構築順 2 で描く）

- **タイル**: カメラがオンの人（ステージに載った人）はタイルに映像、ほかの人は 6.18a と同じアバター。話している人の輪・ミュートの印・名前は映像の上に重ねる。
  自分の映像は左右を反転して映す（鏡と同じ。送る映像は反転しない）。
- **並べ方**: 画面共有がなければグリッド、あれば共有を大きく出して参加者のタイルを横の列にする。タイルを押すと大きくする（ピン留め）。**確認したいこと 2** の答えで直す。
- **操作の列**: マイクの隣にカメラと画面共有のボタンを足す。カメラには機器の選択を付ける（マイクと同じ形）。
- **参加前のプレビュー**: 自分のタイルにカメラの映像を出し、カメラのオンとオフと機器の選択を足す（追記 B）。選んだカメラは端末ごとに覚える（`localStorage`。マイクと同じ）。
- **ハドルの帯**（タブを閉じているとき）: 映像は出さない（決定 5）。操作の列にカメラと画面共有のボタンも並べる（ハドルの画面と同じ列）。
  帯から画面共有を始めたら、共有していることを帯にも出す。
- **会話のメッセージ・サイドバー・一覧**: 変えない。
- **モバイル**: カメラは使える。画面共有のボタンは出さない（モバイルのブラウザには `getDisplayMedia` がない。Slack のモバイルは共有できるがアプリだから）。共有された画面を見るのはできる。
- カメラと画面の許可がない・カメラがない・共有をやめた（ブラウザの「共有を停止」）・3 人目の共有、の表示。
- 色の約束は 6.18a のまま。押せるもの（カメラ・画面共有のボタン）は primary、「いま共有している」は attention（琥珀）で押せるようにしない。新しいトークンが要れば、デザインのときに確認する。

### 10. ログ

- 6.18a のまま（SDP・TURN の認証情報・アプリの秘密を出さない）。足すのはトラックの種類（`kind`）と層（`quality`）だけ。

### やらないこと（範囲の外）

| | 理由 |
|---|---|
| 画面共有の音声 | **確認したいこと 1**。ブラウザで取れるのが Chrome のタブの音声くらいで、トラックの種類が増える |
| 共有した画面への描き込み・カーソルの共有 | Slack もデスクトップのアプリだけ。ブラウザの画面共有の上に座標を合わせて重ねるのは別の大きな仕事 |
| 背景のぼかし・背景の変更 | 映像の中の人を切り出す処理（機械学習のモデル）が要り、ブラウザの負荷も大きい。通話の芯ではない |
| 自分の映像を隠す | Slack もモバイルの設定だけ。要望にない |
| 送る側で人数を絞る（25 人まで、など） | 上限が 20 人なので要らない（決定 8） |
| 受けるトランシーバーを使い回す（`tracks/update` で受けるトラックを差し替える） | SDP のやり取りを減らせるが、公式の説明の本文になく API の定義にだけある。まず閉じて受け直す形で作り、実物でステージの入れ替えが重ければ別に考える |
| 録画 | 6.18a と同じく作らない |

## 理由

- **同じセッションに足す**: Cloudflare のセッションは `RTCPeerConnection` 1 本なので、トラックを足すだけで ICE も TURN も増えない。権限が変わったときに全部閉じる仕組み（ルール 8）も、そのまま効く。公式の例も同じ形。
- **止めたら閉じる**: 費用は送り出す量だけにかかるので、黒い映像を配るのは無駄になる。状態も「送っているか」をそのまま表せる。
- **受ける側で絞る**: 送り込むのは無料で、費用は受ける本数で決まる。送る人数を絞ると「カメラを付けたいのに付けられない」になるが、受ける本数を絞れば画面に見えない分が減るだけ。
- **simulcast**: 9 つのタイルに 720p を 9 本流すのは、受ける人の回線にも費用にも重い。小さなタイルには小さな層で足りる。層の切り替えが SDP のやり取りなしでできるので、タイルの大きさに追従させやすい。
- **層の名前を API に出さない**: 6.18a で Cloudflare の語彙（セッション・トラック名）を API に漏らさないと決めたのと同じ。乗り換えたときに API を変えずに済む。

## 検討した代替案

- **カメラを止めたら黒い映像に差し替える（公式の例）**: オンとオフが速い（SDP のやり取りがない）。ただ、受ける人の分だけ黒い映像に転送量を払い、サーバーの状態から「止めたか」が分からない。不採用。
- **画面共有を別のセッションにする**: 共有だけを別の `RTCPeerConnection` にすると、共有の SDP のやり取りがカメラと音声の列と独立する。ただ、ICE と TURN が 2 つになり、権限の変更で閉じるセッションも 2 つになる。公式の例も同じセッションに載せている。不採用。
- **映っているかを `IntersectionObserver` で決める**: 画面の外に出たタイルの映像を閉じる。スクロールする大きなグリッドには合うが、20 人までなら並べ方を決め打ちできるので、ステージの数で決める方が単純で、費用の見積もりもしやすい。不採用。
- **simulcast をせず 1 つの層で送る**: 送る側の負荷は減るが、小さなタイルにも大きな映像が流れ、費用も受ける側の回線も重くなる。不採用。
- **層をクライアントが `rid` で直接選ぶ**: API は単純になるが、Cloudflare の語彙が API に出る。不採用。
- **Cloudflare の自動の層の選択に任せる（`preferredRid` を空にする）**: 公式の例の既定。帯域には追従するが、タイルの大きさは知らないので、小さなタイルに大きな層が流れる。`preferredRid` をタイルで決め、`asciibetical` で帯域に落とさせる。

## 結果（トレードオフ）

- **費用の見積もり**（無料の枠は SFU と TURN を合わせて月 1,000 GB。1 Mbps を 1 時間受けると約 450 MB。音声は ADR 0066 のとおり 1 本約 50 kbps）
  - 1 対 1 で両方がカメラ（大きなタイルで `high`、1.2 Mbps）: 2 人 × 1.2 Mbps = 2.4 Mbps で 1 時間に約 1.1 GB。**約 900 時間分**
  - 4 人が全員カメラ（2×2 のグリッドで `medium`、400 kbps）: 映像 4 人 × 3 本 × 0.4 Mbps = 4.8 Mbps と音声 0.6 Mbps で、1 時間に約 2.4 GB。**約 410 時間分**
  - 4 人が全員カメラで、1 人が画面共有（1.5 Mbps）。カメラは横の列で `low`: 共有 3 本・カメラ 12 本・音声 12 本で約 6.9 Mbps、1 時間に約 3.1 GB。**約 320 時間分**
  - 上限の 20 人が全員カメラ（ステージは 9 で、自分を除いて 8 本、`low`）: 映像 20 人 × 8 本 × 0.15 Mbps = 24 Mbps と音声 19 Mbps で、1 時間に約 19 GB。**約 50 時間分**。
    ステージで絞らなければ、映像だけで 57 Mbps（1 時間に約 26 GB）になる
  - 6.18a と同じく、Cloudflare には使用量で止める仕組みがない。使いすぎたら設定を外してハドルごと止める（ADR 0066 決定 15）。
- **カメラのオンとオフに SDP のやり取りが要る**（決定 2）。押してから映るまで 1 秒ほどかかる。
- **ステージの入れ替えのたびに、受けるトラックを閉じて受け直す**。話す人が次々に替わると SDP のやり取りが増える。入れ替えを数秒に 1 回までにして抑える（決定 5）。
- **別のタブ（about:blank）の `<video>` に、チャットのタブの `MediaStream` を映せるかは、まだ確かめていない。** 同じ origin の窓どうしなので映せるはずだが、ブラウザごとに実物で確かめる（構築順 4 の最初）。
  映せなければ、ハドルのタブに映像だけを別に受けさせることになり、追記 C の「通話はチャットのタブが持つ」を変える。そのときは実装の前にオーナーに相談する。
- simulcast の層を替えたときに、映像がすぐ切り替わるか（キーフレームを待つか）は、公式のドキュメントに書いていない。実物で確かめる。
- 送る側の負荷が増える（カメラを 3 つの層で符号化する）。古い端末では重いかもしれない。
- 自分のカメラの映像は、自分の画面にだけ反転して映す。相手からは反転していない映像が見える（ビデオ会議のふつうの形）。
