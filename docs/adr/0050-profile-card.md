# 0050. プロフィールのカード（Phase 6.9。email は 1 人分の API だけが返し、管理の入口は既存の写しで決める）

- 状態: 採用
- 日付: 2026-09-21

## 背景

Phase 6.9 は、ユーザーのアイコンか名前を押すと、そのユーザーのプロフィールのカードが開くようにする（Slack と同じ）。

オーナーと確定している前提（2026-09-19）:

- 開く場所はアイコンと名前の両方（メッセージ、スレッド、メンバーパネル。6.13 のメンションの `@名前` も）
- 表示するもの: アバター、表示名、`@handle`、メールアドレス、ワークスペースのロール、presence のドット。
  Phase 6.8 で足した離席とカスタムステータスも出す（ADR 0049 決定 5）
- **メールアドレスは同じワークスペースのメンバー全員に見せる。** メンバーでなくなれば返さない
- 主ボタンは「DM を送る」（既存の DM があれば開き、なければ作る）。3 点メニューに「ハンドルをコピー」「メールアドレスをコピー」、
  操作できる相手のときだけ「ロールの変更」「ワークスペースから外す」
- 自分のカードでは「DM を送る」の代わりに「プロフィールを編集」（設定の画面へ）

**chat の API が他人の email を返すのは、これが初めてになる。** いまの chat は `users` から `handle` と `display_name` だけを読み
（`UserProfile`）、それがメンバーの一覧・メッセージの送信者・WebSocket のイベントに広く乗っている。
email をどこに載せるかで、email が届く範囲が決まる。

## 決定

### 1. email は 1 人分の API だけが返す（オーナーと確認）

```
GET /api/v1/workspaces/{workspaceID}/members/{userID}
```

```json
{
  "user": { "id": "01J8...", "handle": "naoki", "display_name": "佐藤 直樹" },
  "role": "admin",
  "joined_at": "2026-09-01T09:00:00Z",
  "presence": "active",
  "away": false,
  "status": { "emoji": "🍵", "text": "休憩中", "expires_at": null },
  "email": "naoki@example.com"
}
```

- 形は**メンバーの一覧の 1 行と同じものに `email` を 1 つ足しただけ**にする。`presence` / `away` / `status` の意味も一覧と同じ（ADR 0049）。
- **`UserProfile` にも一覧の `Member` にも email を足さない。** email を持つ型はこの応答だけにする。
  `UserProfile` はメッセージの送信者や `member.joined` のイベントにも乗るので、足すと email がルームの購読者全員に流れる。
- 閲覧の判定は authz に置く（CLAUDE.md ルール 9）。`authz.CanViewMemberProfile(actor Role)` は「actor がメンバーなら可」。
  **actor がメンバーでない、target がメンバーでない（外された・別のワークスペース）、target が退会済み、はどれも 404** にする
  （一覧の `ListMembers` と同じく、存在するかどうかを区別させない）。
- カードは**一覧の値ですぐに開き、email の行だけ応答を待って埋める**。名前・アバター・ロール・presence・ステータスは、
  すでに手元の一覧（`listAllMembers`）とそのイベントで最新になっている。
- 応答はカードの中だけで持ち、ストアに入れない。開くたびに取り直す。

### 2. email は検証済みのときだけ返す（オーナーと確認）

`users.email_verified_at` が NULL なら `email` は `null` にする。カードは email の行とメニューの「メールアドレスをコピー」を出さない。

いまは email を検証しないままでもチャットを使える。誰でも他人のアドレスで登録できるので、未検証のアドレスをカードに出すと、
**カードがそのアドレスを本人のものとして保証しているように見える**（なりすましや誤送信の元になる）。
自分のカードも同じ規則にする（例外を作らない。自分の email は設定の画面で見られる）。

### 3. 管理の入口は、ADR 0029 の写しをそのまま使う（オーナーと確認）

「ロールの変更」「ワークスペースから外す」を出すかどうかは、管理画面のために作った
`lib/chat/workspace-views.ts` の判定（`toMemberRowView` の `manage`。`authz.CanManage` / `CanGrant` の写し）で決める。

- **新しく書き写さない。** カードと管理画面が同じ関数を呼ぶので、クライアントの写しは 1 つのままになる。
- 判定の正はサーバーにある（ADR 0029）。写しがずれても、`PATCH` / `DELETE /workspaces/{id}/members/{userID}` が拒否する。
- API の応答には判定結果を載せない。ロールの変更（`workspace.role_changed`）とキック（`workspace.member_removed`）は
  すでに一覧に届くので、**カードを開いている間にロールが変わっても、入口がその場で追従する**。
- 操作は既存の API とダイアログを使う。「ワークスペースから外す」は管理画面と同じ確認（`KickMemberDialog`）を挟む。
  譲渡はカードに出さない（確定事項に無い。管理画面から行う）。

### 4. 「DM を送る」は既存の DM の作成をそのまま呼ぶ

`POST /api/v1/workspaces/{workspaceID}/rooms`（`kind: "dm"`, `user_id`）を呼び、返ったルームへ移る。

- 既存の DM があればそれが返る。同じ 2 人の DM が 1 つであることは `dm_key` の UNIQUE 制約が保証していて、
  並行して作っても 1 つになることは `TestCreateDMConcurrent` で確かめてある（ADR 0006 / 0011）。サーバーに足すものはない。
- クライアントは、押してから応答までボタンを押せなくする（二重に送らない。送っても結果は同じだが、画面の遷移が 2 回起きる）。

### 5. 外された人（一覧にいない人）には、縮めたカードを出す（オーナーと確認）

過去のメッセージの送信者が、もうワークスペースのメンバーでないことがある。そのアイコンや名前も押せるようにし、
**メッセージが持っている名前・`@handle`・アバターだけのカード**を開いて、「このワークスペースのメンバーではありません」と出す。

- DM・email・ロール・presence・ステータス・管理の入口は出さない。メニューは「ハンドルをコピー」だけ。
- 一覧は全件を持っている（`listAllMembers`）ので、**一覧にいなければメンバーではない**と判断し、1 人分の API は呼ばない。
- カードを開いている間に相手が外されたら（`workspace.member_removed`）、縮めたカードに切り替える。

同じタイムラインの中で「押せる名前」と「押せない名前」が混ざらないようにするため。縮めたカードの見た目はデザインの段で描く。

### 6. デスクトップはポップオーバー、モバイルは下から出るシート

- デスクトップは、押したアイコンか名前に寄せて浮かせる（既存の `AnchoredPanel`）。
- モバイルは下から出るシート。絵文字のピッカーと同じ出し方（ADR 0049 決定 10 の追記）。
- 開く・閉じるの約束は既存のポップオーバーと同じ（Esc と外側のクリックで閉じ、閉じたら押した要素にフォーカスを戻す）。
- 開く場所: メッセージ（チャンネルのタイムラインとスレッド）の送信者のアイコンと名前、メンバーパネルの行。
  6.13 のメンションの `@名前` も同じ部品で開く。システムメッセージの主語や DM のヘッダーは確定事項に無いので、今回は開かない。

## 理由

- **1 人分の API にする理由**: email を運ぶ経路を 1 本に絞れる。一覧に足すと、再接続のたびに取り直す一覧が全員の email を運び、
  `Member` を使うすべての画面（管理画面を含む）に email が行き渡る。1 人分なら、email が要るのはカードを開いたときだけ、という
  使い方にそのまま合う。「外されたら返さない」も、メンバーの行が無ければ 404、で自然に成り立つ。
  **カードを開くたびの 1 往復は、表示を待たせない。** カードは一覧の値ですぐに出て、応答を待つのは email の行だけで、
  クエリも主キーでの 1 行の読み取り。ユーザーが押したときにしか起きないので、回数も一覧の取り直しよりずっと少ない。
- **応答をストアに入れない理由**: email には変更のイベントが無い。ストアに置くと、WebSocket でも再接続の同期でも
  更新されない値が残る（絶対ルール 4 の「WebSocket でしか届かない状態」の裏返しで、「どこからも届かない状態」になる）。
  開くたびに取れば、常にその時点の値になる。
- **未検証の email を出さない理由**: 上の決定 2。出して「未検証」と添える案は、添え書きを読み飛ばせば同じ問題が残る。
- **写しを使い回す理由**: 判定をサーバーから返すと、カードを開いたあとのロールの変更で値が古くなり、取り直す仕組みが要る。
  管理画面はすでに写しで動いているので、同じ画面の中に 2 通りの判定が並ぶことにもなる。

## 検討した代替案

- **メンバーの一覧に email を足す**: 追加の往復がなく、カードを一度に全部出せる。ただし上の理由で email の届く範囲が広がる。
  オーナーと比較して不採用（2026-09-21）。
- **未検証の email を「未検証」と添えて出す**: 登録した値はすべて見えるが、デザインに表示を足す必要があり、読み飛ばせば同じ。
  オーナーと比較して不採用（2026-09-21）。
- **1 人分の API が管理の判定結果（変更できるロール・外せるか）を返す**: 判定がサーバーだけで完結し、将来のネイティブアプリも
  写しを持たずに済む。ただしカードを開いたあとにロールが変わると値が古くなり、管理画面の写しと 2 通りが並ぶ。
  オーナーと比較して不採用（2026-09-21）。ネイティブアプリを作るときは、管理画面と一緒にこの判断を見直す。
- **一覧にいない人の名前は押せないようにする**: 画面は増えないが、同じタイムラインの中で押せる名前と押せない名前が混ざり、
  押せない理由が見えない。オーナーと比較して不採用（2026-09-21）。
- **email を auth の API（`/users/{id}`）から返す**: email は auth のデータだが、「同じワークスペースのメンバーか」は chat の判定で、
  auth はワークスペースを知らない。auth に chat の判定を持ち込むことになる。chat はすでに `users` から `handle` と
  `display_name` を読んでいるので、同じ読み方で email も読む（`internal/chat` は `internal/auth` を import しない。ルール 1）。

## 結果（トレードオフ）

- **email を検証しないユーザーのカードには、email が出ない。** いまは未検証のままでもチャットを使えるため、
  そうした人は email を見せられない。検証の要否は別の論点として扱う（下）。
- **カードの email の行は、一瞬遅れて出る。** 行の高さは先に確保し、読み込み中の揺れを出さない（デザインの段で決める）。
- **クライアントの authz の写しを使う場所が 1 つ増える。** 写しがずれたときに影響が出る画面が増えるが、関数は 1 つのまま。
- 新しい WebSocket のイベントも、マイグレーションもない。ERD と `docs/events.md` は変わらない。

### 別の論点: 未検証の email のままチャットを使えること

オーナーの指摘（2026-09-21）: 本番でも未検証のアドレスでチャットができるのはおかしく、そこを塞げばよいのではないか。

この ADR の範囲では決めない。塞ぐには、登録直後の導線（検証するまで何を見せるか）、招待リンクから登録した人の受け入れの順序、
既存の未検証ユーザーの扱い、chat が「検証済みか」をどこから知るか（JWT に入れると検証の直後に古くなる）を決める必要があり、
auth の設計の変更になる。別の ADR で扱う。**塞いだあとも、決定 2 の「検証済みのときだけ返す」は残す**
（塞ぐ前に登録した人や、将来の OAuth で email が未検証の人が残りうるため）。
