# 0042. 指定したメッセージへ飛ぶ（Phase 6.11b。前後を取る API、見つからないときの扱い、未読へ飛ぶ）

- 状態: 提案
- 日付: 2026-09-19

## 背景

ADR 0040（Phase 6.11a）で、メッセージへのリンクをコピーでき、本文に貼られたリンクがカードになるところまでは入った。
まだできていないのは「**飛ぶ**」側で、これが Phase 6.11b の範囲になる。

- リンク（`?m={messageID}`）を開いても、ルームの最新のページが出るだけで、そのメッセージまで移動しない
- カードを押しても、リンク先のメッセージまで移動しない
- 「ここから未読」の線は出るが、未読の位置が読み込んだページより古いと線自体が出ず、そこへ移動する手段もない

いまの履歴の API は `before_seq` / `after_seq` / `after_change_seq` の 3 つのカーソルしか持たない（ADR 0004 / 0014）。
どれも「ある地点から一方向」なので、古いメッセージを真ん中に置いて前後を見せることができない。

この「指定したメッセージへ飛ぶ」仕組みは、6.11b だけのものではない。
ピン留めと保存の一覧（Phase 6.12）と検索の結果（Phase 6.16）を押したときにも、同じ仕組みで飛ぶ（`docs/roadmap.md`）。

## 決定

### 1. 前後を取る API: `around_message_id`

`GET /api/v1/rooms/{roomID}/messages` に、4 つ目のカーソルとして `around_message_id`（ULID の文字列）を足す。
既存の 3 つと同じく、**カーソルは 1 つしか指定できない**（2 つ以上なら 422）。

- 指定したメッセージを真ん中に置いて、前後あわせて `limit` 件までを seq の昇順で返す。古い側が `limit / 2`（切り捨て）件、残りが対象と新しい側
- 対象がチャンネルのタイムラインに出ない返信（ADR 0036）でも、そのメッセージ自身は必ず含める。まわりはチャンネルのタイムラインと同じ規則で選ぶ
- スレッドの返信の一覧（`GET /api/v1/rooms/{roomID}/threads/{rootID}/messages`）にも同じ `around_message_id` を足す。並びはルームの seq を共有しているので、規則は同じ

**seq ではなく ID を受け取る。** リンクが持っているのは ID なので、seq を受け取る形にすると、クライアントが「ID → seq」を引く往復を 1 回増やすことになる。

### 2. 応答に足すもの

```jsonc
{
  "messages": [ /* seq の昇順 */ ],
  "has_more": true,        // 古い側にまだあるか
  "has_more_after": true,  // 新しい側にまだあるか（around_message_id のときだけ true になりうる）
  "around": { "seq": 1234, "thread_root_id": null },  // 見つからなければ null
  "last_change_seq": 5678
}
```

- `has_more` の意味は変えない。「同じ向きにまだあるか」で、`before_seq` と指定なしは古い側、`after_seq` / `after_change_seq` は新しい側を指す。`around_message_id` は向きが 2 つあるので、古い側を `has_more`、新しい側を `has_more_after` に載せる
- `has_more_after` は、ほかのカーソルでは常に `false`
- `around` は、対象が見つかったときだけ入る。`thread_root_id` が入っていれば、クライアントはスレッドのパネルを開く

### 3. 対象が見つからないとき

**最新のページを `around: null` で返す**（404 にしない）。

「そのルームにない ID」「ULID ですらない文字列」「削除済み」を**区別しない**。ADR 0040 でカードについて決めたのと同じ方針で、リンクを貼るだけで実在を当てられないようにする。
削除済みを含めるのは、ADR 0038 で「削除したメッセージは跡も残さず消える」と決めたため。

ルーム自体が読めないときは、いまと同じく 404（`loadRoomAccess` の扱いを変えない）。

クライアントは、最新のページを出したうえで「そのメッセージは見つかりませんでした」という控えめな知らせを 1 行出す。

### 4. 飛んだあとの見せ方

- 対象のメッセージが画面の中ほどに来るようにスクロールし、**数秒だけ強調する**（`--color-attention-subtle` の背景を敷き、時間で消す）
- 強調は時間で消え、押しても消える。URL の `?m=` は残す（再読み込みで同じ所に戻れるようにする）
- 対象がスレッドの返信なら、スレッドのパネルを開いてからパネルの中で飛ぶ

### 5. 未読へ飛ぶ

**新しい API は作らない。** `after_seq = last_read_seq` が「最初の未読とそれより新しいもの」をそのまま返すので、それを使う。

- ルームを開いた時点で未読があり、かつ**未読の位置が読み込んだページより古い**ときだけ、タイムラインの上端に「N 件の未読」と「最初の未読へ」を出す
- 押すと `after_seq = last_read_seq` で読み直し、「ここから未読」の線が画面の上に来るようにスクロールする
- 未読の位置が最初から読み込んだページの中にあるときは、いまと同じで線が出るだけ。バーは出さない
- 線そのものの規則（開いた時点の `last_read_seq` で固定する、開いている間は消さない）は ADR 0025 のまま変えない

### 6. リンクのクエリの名前を `t` から `thread` に変える

ADR 0040 は、スレッドの返信へのリンクを `?m={messageID}&t={threadRootID}` と決めた。
一方、スレッドのパネルを開く既存のクエリは `?thread={rootID}` で（ADR 0037）、同じものに 2 つの名前があることになる。

**`t` をやめて `thread` に統一する。** リンクは `?m={messageID}&thread={threadRootID}` になる。
ADR 0040 のこの 1 点だけを、この ADR で置き換える（ほかの決定は有効なまま）。

まだリリースしていないので、外に出回っているリンクはない。2 つの名前を両方とも読めるようにする方が、あとまで残る複雑さになる。

## 理由

- **ID を受け取る理由**: リンクが持っているのは ID で、seq は持っていない。seq を受け取る形にすると、クライアントは「カードの API で seq を引く → 前後を取る」と 2 往復することになる。サーバーの中では ID から seq を引くのは 1 回の索引の参照で済む。
- **見つからないときに 404 にしない理由**: 404 と 200 の差は、そのルームにその ID のメッセージがあるかどうかを外から確かめる手段になる。ADR 0040 でカードについて「区別しない」と決めたのに、こちらで区別しては意味がない。
- **`has_more_after` を足す理由**: `has_more` を「古い側」と「新しい側」の 2 つに割るのが素直だが、`after_seq` による再接続の同期（ADR 0004）と `after_change_seq`（ADR 0014）が `has_more` の意味に乗っている。そこを変えると 6.11b の範囲を越えて同期の経路に手が入る。向きが 2 つあるのは `around_message_id` だけなので、そこにだけ足す。
- **未読へ飛ぶのに API を足さない理由**: `after_seq = last_read_seq` がちょうど「最初の未読から」を意味する。専用の API を作っても同じ結果になる。
- **未読のバーを「未読が読み込んだページより古いときだけ」出す理由**: 未読が数件なら、開いた時点で線が見えている。そこにバーまで出すと、押しても何も起きないボタンになる。

## 検討した代替案

- **`before_seq` と `after_seq` の 2 回で前後を取る**: API を足さずに済む。ただし (1) 飛ぶたびに 2 往復になる、(2) 対象自身を含めるのに `before_seq = 対象の seq + 1` と書くことになり、seq が整数で連続していることに寄りかかる、(3) そもそも対象の seq を知るための往復がもう 1 回要る。6.12 と 6.16 も同じ仕組みで飛ぶので、API を 1 つ足す方が安い。
- **`around_seq`（seq を受け取る）**: クライアントが ID → seq を引く往復が増える。6.11a のカードの API が seq を返すので実現はできるが、カードを出さずに飛ぶ経路（URL を直接開く、検索の結果を押す）でも毎回それを呼ぶことになる。
- **対象が見つからないときに 404**: 上記のとおり、実在を当てられる。
- **未読の位置を返す専用の API**: `after_seq` で足りる。
- **`t` と `thread` の両方を読む**: リンクの形を変えずに済むが、同じものに名前が 2 つある状態が残る。まだリリースしていないので、いま直す方が安い。

## 結果（トレードオフ）

- `has_more` と `has_more_after` という似た名前が並ぶ。`around_message_id` 以外では `has_more_after` が常に `false` になるのは、読んだだけでは分かりにくい（JSON のコメントと ADR で補う）。
- 飛んだ先から上下にスクロールし続けると、`before_seq` と `after_seq` の両方で読み足すことになる。いまのタイムラインは「古い方へ読み足す」しか持っていないので、新しい方へ読み足す経路を足す。
- 飛んだ先のタイムラインは、最新のメッセージを含まないことがある。その状態で新しいメッセージが届いたときは、手元のタイムラインにつながらないので捨てる（`has_more_after` が `true` の間は、届いたメッセージを末尾に足さない）。いちばん下まで読み進めるか、ルームを開き直すとつながる。
- ADR 0040 のリンクの形を 1 点だけ変える。すでに `t` で作られたリンクは、`thread` に読み替えない（まだリリースしておらず、出回っていないため）。

## オーナーに確認したいこと

1. **新しく増える 2 つの見た目が `docs/ui/` にない。** 「N 件の未読 / 最初の未読へ」のバーと、飛んだ先の強調。どちらも既存のトークン（`--color-attention` 系）だけで作れる範囲だが、`docs/ui/` にない画面を発明しない規則（CLAUDE.md）に触れる。この ADR の案で進めてよいか、先に Claude Design 側に足すか。
2. **リンクのクエリを `t` から `thread` に変える**（決定 6）。ADR 0040 の 1 点を置き換えることになる。
