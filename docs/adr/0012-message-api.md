# 0012. メッセージ API の詳細（Phase 3b）

- 状態: 採用
- 日付: 2026-09-14

## 背景

Phase 3b の着手時点で、ロードマップと ADR 0002 / 0004 が決めていない点があった。

- 冪等な再送で seq を消費しない（欠番を作らない）送信の書き方。ロードマップは「実装前に提案する」としていた
- メッセージの編集・削除の権限。画面（`chat/message-hover-actions.png`）には「…」メニューがあるが、中身がデザインにない
- 履歴 API のカーソルの組み合わせ、件数、並び
- 返信先の検証と、返信のプレビューに返す内容
- 既読位置の更新の規則と、ルーム一覧に出す最終メッセージ・未読数
- `after_seq` の差分取得で、切断中に起きた「既存のメッセージの編集・削除」を取得できないこと

## 決定

### 送信（冪等性と seq）
1 つのトランザクションで次の順に行う。

1. ルームとロールを読み、**送信者の `room_members` の行を `FOR NO KEY UPDATE` でロックしてから** `CanWriteRoom` で判定する
2. `(room_id, sender_id, client_msg_id)` で既存のメッセージを探す。あれば何も書かずに 200 で返す
3. `UPDATE rooms ... RETURNING last_message_seq` で採番する（ADR 0002）
4. `INSERT messages`
5. 送信者の `last_read_seq` を `GREATEST` で進める
6. コミットして 201 を返す

- 手順 1 のロックで、**同じ送信者の同じルームへの送信は必ず直列になる**。同じ `client_msg_id` の 2 本目は 1 本目のコミットを待ち、READ COMMITTED の次の文（手順 2）でコミット済みの行を見つける。一意制約の違反は通常起きず、`UNIQUE(room_id, sender_id, client_msg_id)` は最後の防御として残る。
- ロックは `FOR SHARE` ではなく `FOR NO KEY UPDATE` にする。手順 5 の UPDATE と同じ強さのロックを先に取っておかないと、同じ人の並行した送信が互いの共有ロックを待ってデッドロックする。
- 同じロックで、キック・退出（`room_members` の DELETE）とも直列になる。キックが先にコミットしていれば行が消えているので手順 1 で拒否され、送信が先なら DELETE の方が送信のコミットを待つ。
- `workspace_members` はロックしない。書き込みの可否はロールに依存せず（ルームのメンバーであることだけで決まる）、送信のたびにその行へロックの情報を書き込むのを避けるため。ADR 0011 の「ロールに基づいて判定する操作は `workspace_members` を `FOR SHARE` でロックする」とは別の規則として扱う（コードでは `lockMode` の `memberRowLock`）。
- 再送では本文や返信先を比べずに、既存のメッセージをそのまま返す。
- ロック順は `room_members` → `rooms`。`rooms` の行ロックを持ったまま `room_members` の行を待つ処理はないので、デッドロックにならない。

### 本文
- 空白だけの本文は `required`、4000 文字（rune）を超えたら `too_long`、改行・タブ・CR 以外の制御文字は `invalid_format`。
- 前後の空白は削らない。コードの字下げなどを保つため。

### 返信
- 返信先が存在しない、または別のルームにある場合は、先に SELECT で確かめずに複合 FK（`messages_reply_to_fkey`）の違反として検出し、422（`reply_to_id: invalid_value`）にする。エラーでトランザクションごとロールバックされるので、採番した seq も戻る。
- 削除済みのメッセージへの返信は拒否しない。「削除」と「返信」は並行して起きうるので、拒否しても結局は削除済みへの返信が生まれる。表示側で扱う。
- メッセージのレスポンスの `reply_to` に、返信先の `id / seq / sender / body / deleted` を含める。一覧でも 1 文の JOIN で取得する（N+1 にしない）。

### 履歴（`GET /rooms/{id}/messages`）
- `before_seq` と `after_seq` の同時指定は 422。どちらも指定しなければ最新のメッセージを返す。値が負なら 422、整数として読めなければ 400。
- `limit` は既定 50、上限 100（上限を超えた値は切り詰める）。
- `messages` は**常に seq の昇順**。`has_more` は、同じ向き（`after_seq` なら新しい方、それ以外は古い方）に続きがあるか。1 件多く読んで判定する。
- 最新のページは `before_seq` に int64 の最大値を渡し、`before_seq` 用と `after_seq` 用の 2 本のクエリで書く。「NULL なら条件なし」とすると、汎用の実行計画でインデックスの範囲条件にならず、ルームの全件を走査しうる。
- 読めるかどうかは `CanReadRoom`（public は参加していなくても読める）。削除済みのメッセージは本文を空にした tombstone として返す。

### 編集・削除の権限
| 操作 | 送信者本人 | 送信者以外 |
|---|---|---|
| 編集 | いまも投稿できるなら ✓ | –（owner でも不可） |
| 削除 | いまも投稿できるなら ✓ | ルームを読める admin 以上で、`canManage(actor, 送信者)` を満たすなら ✓。送信者がワークスペースを抜けていれば admin 以上なら ✓。dm は不可 |

- 削除済みのメッセージの編集は 409 `message-deleted`。削除は冪等（削除済みでも 204）。
- 編集で本文が変わらなければ `edited_at` を更新しない。
- 別のルームの ID でメッセージを指定したら 404（`room_id` を条件に含めて読む）。
- 判定は `authz.CanEditMessage` / `authz.CanDeleteMessage`。
- ロック: 編集は送信と同じく `room_members` の行 → メッセージの行（`FOR UPDATE`）。削除は、送信者のロールで判定するので、先に送信者を読み（`sender_id` は変わらない）、actor と送信者の `workspace_members` を `FOR SHARE`（ADR 0011）→ メッセージの行（`FOR UPDATE`）。

### 既読位置（`POST /rooms/{id}/read`）
- 入力は `{"seq": N}`（必須）。`last_read_seq = GREATEST(現在値, LEAST(N, last_message_seq))` の 1 文で更新し、**後退させず、最新の seq を超えさせない**。超えた値をエラーにしないのは、WebSocket と REST の経路が前後しても失敗させないため。
- レスポンスは切り詰めた後の `last_read_seq` と `unread_count`。
- ルームのメンバーだけが更新できる（参加していない public では 403。`authz.CanMarkRoomRead`）。

### ルーム一覧・ルームの取得
- `last_read_seq`（メンバーでなければ null）、`unread_count`（`last_message_seq - last_read_seq`。メンバーでなければ 0）、`last_message`（`id / sender / body / created_at / deleted`。メッセージがなければ null）を追加する。
- 最終メッセージは `messages.seq = rooms.last_message_seq` の行を JOIN し、ルームごとに UNIQUE インデックスで 1 回引く。相対時刻の表示はクライアントが `created_at` から作る。

### エラー（RFC 9457 の `type`）

| type | status | 意味 |
|---|---|---|
| `message-deleted` | 409 | 削除済みのメッセージは編集できない |

## 理由

- **ロックしてから既存を探す理由**: ロードマップの想定案（先に既存を探す → なければ採番して INSERT → 一意制約の違反ならロールバックして読み直す）でも欠番は作らない。ただしエラーコードでの分岐が必要なうえ、トランザクションが中断された後に別の接続で読み直すことになる。さらに、違反の経路は並行テストで狙って通すのが難しい。`last_read_seq` を更新するために `room_members` の行はどのみちロックするので、それを先に取れば、追加のロックなしに競合そのものが起きなくなる。キック・退出との直列化も同じロックで兼ねられる。
- **削除を admin 以上にも許す理由**: 荒らしの投稿を消す手段がないと、ワークスペースの管理が成り立たない。ロールの上下関係（`canManage`）に揃えるので、admin 同士では消し合えない。
- **編集を本人に限る理由**: 他人が本文を書き換えられると、発言の主体が分からなくなる。管理の目的には削除で足りる。
- **dm で他人のメッセージを削除させない理由**: dm は 2 人だけの場で、admin であっても相手の発言を消すのは管理ではない。
- **本文の上限を 4000 文字にする理由**: チャットの 1 メッセージとして十分で、JSON のボディの上限（64 KiB）にも収まる。

## 検討した代替案

- **一意制約の違反を受けてからロールバックして読み直す**: 上記の理由で不採用。
- **`INSERT ... ON CONFLICT DO NOTHING` の後、行が返らなければロールバックする**: 欠番は作らないが、「DO NOTHING でもコミットしてはいけない」という約束が 1 行の書き忘れで壊れ、欠番のバグになる。
- **送信のたびに `workspace_members` を `FOR SHARE` でロックする（ADR 0011 と同じ規則）**: 規則は 1 つで済むが、最も頻繁な書き込みで毎回ロックの情報を書き込むことになる。
- **返信先を先に SELECT で検証する**: 削除済みへの返信も拒否できるが、並行した削除で結局すり抜けるので意味が薄く、クエリが 1 本増える。
- **削除を送信者本人に限る**: 単純だが、上記の理由で不採用。
- **履歴を `before_seq` 用と `after_seq` 用の 2 つのエンドポイントに分ける**: ロードマップのエンドポイント一覧と合わない。

## 結果（トレードオフ）

- **切断中に起きた既存のメッセージの編集・削除は、`after_seq` の差分取得では取得できない**（seq が新しくならないため）。3b では既知の制約として受け入れ、Phase 4 で `docs/events.md` を設計するときに解決策を決める（再接続時に表示中の範囲を取り直す、編集・削除でも増える別の番号を持つ、など）。
- 同じ送信者の同じルームへの送信は直列になる。1 人が 1 つのルームに並行して大量に送る使い方は想定しないので問題にしない。ルーム全体の直列化（ADR 0002 の `rooms` の行ロック）の方が先に上限になる。
- 未読数には削除済みのメッセージも含まれる（ADR 0002 の近似のまま）。
- 送信・編集・削除・既読は、まだ WebSocket に配信しない。Phase 4 で `Delivery` を入れるときに、これらのユースケースのコミット後から配信する。
