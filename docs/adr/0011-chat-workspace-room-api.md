# 0011. ワークスペース / 招待 / ルーム API の詳細（Phase 3a）

- 状態: 採用
- 日付: 2026-09-14

## 背景

Phase 3a の着手時点で、ADR 0006 とロードマップが決めていない点があった。

- `docs/ui/README.md` の未解決の項目: 招待リンク一覧の閲覧・取り消しの権限、招待プレビューのレスポンスの項目
- ADR 0006 の権限表にない操作: ルームの設定変更（`PATCH /rooms/{id}`）、他人をルームから外す操作
- メンバー一覧に出す表示名と handle を chat がどう取得するか（ADR 0001 は、chat が `users` テーブルに直接触ることを懸念として挙げている）
- 画面（ルームのメンバーパネル、「メンバー 4 人」）に必要な `GET /rooms/{id}/members` が、ロードマップのエンドポイント一覧にない
- ADR 0010 で「Phase 3a の着手前に決める」とした、email が未確認のユーザーの扱い

## 決定

### 権限（ADR 0006 の権限表への追加）

| 操作 | owner | admin | member |
|---|---|---|---|
| ワークスペースの閲覧、メンバー一覧 | ✓ | ✓ | ✓ |
| 招待リンクの一覧 | ✓ | ✓ | ✓ |
| 招待リンクの取り消し | ✓ | ✓ | 自分が作成した招待で、いまも作成できるなら ✓ |
| ルームの設定変更（name / is_default） | ✓ | ✓ | – |
| 他人をルームから外す | `canManage(actor, target)` を満たし、private ならルームのメンバーであること | 同左 | – |
| ルームから自分で抜ける | ✓ | ✓ | ✓ |

- DM は参加・追加・削除・設定変更のどれもできない（メンバーは作成時の 2 人で固定）。
- private ルームを読めない admin（ルームのメンバーではない）は、そのルームの設定を変えられない。読めないものは管理もできない。
- 判定は `internal/chat/authz` の純粋な関数（DB に触らない）だけが行う。サービスは判定に必要な事実（ロール、ルームのメンバーかどうか）を DB から読み、関数に渡す（CLAUDE.md ルール 9）。

### 存在を明かさない
- ワークスペースのメンバーでない、またはルームを読めない場合は、403 ではなく **404** を返す。ID を知っているだけの人に、ワークスペースや private ルームの存在を明かさない。
- 読めるが操作が許されていない場合は 403 を返す。

### ユーザーの公開プロフィールの参照
- chat の SQL（`db/queries/chat`）は `users` を **読み取り専用で、公開してよい列だけ** JOIN してよい。対象は `id / handle / display_name / avatar_object_key / deleted_at`。
- `email`、`password_hash` など認証の列と、`refresh_tokens` など auth のテーブルは読まない。書き込みもしない。
- `internal/chat` が `internal/auth` を import しない境界（ADR 0001、depguard）は変わらない。

### ワークスペース
- 作成の入力は名前だけ（`workspace-create-dialog`）。`slug` はサーバーがランダムに生成し、3a では変更できない。
- 作成しても、デフォルトのルームは作らない（`empty-rooms` の画面がある）。`is_default` は admin 以上が `PATCH /rooms/{id}` で付ける。
- レスポンスに `my_role` を含める。クライアントはそれを見て操作の可否を表示する（最終的な判定は常にサーバー）。

### ロールの変更・キック・譲渡の直列化
- 対象の `workspace_members` の行（actor と target）を `SELECT ... FOR UPDATE` でロックしてから、**ロックした後に読んだロール**で判定する。
- 複数行のロックは `user_id` の順に取る。「A が B を降格」と「B が A をキック」が同時に起きても、ロックの順序が一致するのでデッドロックにならない。
- owner の譲渡は、ロックの後に「旧 owner を admin に降格 → 新 owner を昇格」の順で UPDATE する（部分 UNIQUE インデックスは遅延評価できないため）。
- ワークスペースから外れたら（キック・退出）、同じトランザクションでそのワークスペースのすべての `room_members` を削除する。

### 招待
- コードは **128 ビットの乱数を base64url にした 22 文字**。DB には SHA-256 だけを保存する。総当たりは現実的でないので、プレビューと受け入れに回数制限は付けない。
- 作成の入力は `max_uses`（1〜1000 または null）と `expires_in_seconds`（60 秒〜30 日）。期限は Clock の時刻から計算する（クライアントの時計を信じない）。
- 一覧には取り消し済み・期限切れも含め、`status`（`active / exhausted / expired / revoked`）をサーバーが計算して返す。
- **プレビュー（`GET /invites/{code}`）は要ログイン。** 画面は「別のアカウントで開きますか？」を出しており、ログインした状態で開く前提になっている。
  - 有効な招待なら、ワークスペースの `id / name`、メンバー数、public ルームの数、招待者の `handle / display_name`、`already_member`、`expires_at` を返す。
  - 見つからない・取り消し済みは 404 `invite-invalid`、期限切れは 410 `invite-expired`、使用上限に達したら 410 `invite-exhausted`。どれもワークスペースの情報は含めない（`accept-invalid` / `accept-expired` の画面にも出ていない）。
  - すでにメンバーなら、期限切れや上限でも `already_member: true` を返す（取り消し済みは除く）。受け入れでも使用回数を消費せずに成功を返す。
- 受け入れは 1 トランザクションで行う。
  1. `INSERT INTO workspace_members ... ON CONFLICT DO NOTHING`。行が入らなければすでにメンバーなので、何も消費せずに成功を返す
  2. 条件付き UPDATE で `use_count` を加算する。行が返らなければ、理由（期限切れ・上限・取り消し）を読み直してロールバックする
  3. `is_default` のルームに参加する
- 同じユーザーが同時に 2 回受け入れても、2 本目は主キーの一意性の確定を待ってから `ON CONFLICT` になるので、使用回数は 1 回しか消費されない。

### ルーム
- `POST /workspaces/{id}/rooms` は `{"kind": "public" | "private", "name"}` または `{"kind": "dm", "user_id"}`。
- DM の `dm_key` は 2 人の userID（ULID の文字列）をソートして `:` で連結した値。自分自身との DM は作れない（422）。
  - `INSERT ... ON CONFLICT DO NOTHING` で作り、既存の DM があれば 200 で既存を返す（新規は 201）。
  - 既存の DM を返すときも、2 人の `room_members` を `ON CONFLICT DO NOTHING` で入れ直す。ワークスペースを抜けて戻ってきた人が、元の DM に戻れるようにする。
- ルーム一覧は、参加しているルーム（全種類）と、参加していない public ルームを返す（`is_member` で区別）。DM には相手の公開プロフィール（`dm_peer`）を付ける。相手は `dm_key` から求め、プロフィールは 1 回のクエリでまとめて引く（N+1 にしない）。
- `GET /rooms/{id}/members` を 3a に追加する。ルームを読める人なら取得でき、各メンバーのワークスペースでのロールも返す。
- ルームへの参加・追加は冪等にする（すでにメンバーなら何もせずに成功）。参加時の `last_read_seq` は、INSERT の中で `rooms.last_message_seq` を読んで初期化する。

### 一覧 API
- メンバー・ルームのメンバー・招待の一覧は、ID のカーソル（`?after=<ID>&limit=`）でページングする。`limit` は既定 100、上限 200。レスポンスは `next_cursor`（最後のページなら null）を持つ。
- 自分のワークスペース一覧とルーム一覧は、ページングしない。サイドバーは全件を必要とし、1 人が所属するワークスペースやルームの数は実用上小さい。問題になったら見直す。

### email が未確認のユーザー
- 3a の操作も制限しない（ADR 0010 の方針を維持する）。

### エラー（RFC 9457 の `type`）

| type | status | 意味 |
|---|---|---|
| `not-found` | 404 | 存在しない、または見る権限がない |
| `forbidden` | 403 | 見えるが、その操作は許されていない |
| `owner-must-transfer` | 409 | owner は譲渡するまで退出できない |
| `room-name-taken` | 409 | 同じ名前のルームがワークスペースにある |
| `user-not-in-workspace` | 422 | 追加・DM の相手がワークスペースのメンバーではない |
| `invite-invalid` | 404 | 招待が見つからない、または取り消し済み |
| `invite-expired` | 410 | 招待の期限切れ |
| `invite-exhausted` | 410 | 招待の使用上限に達した |

## 理由

- **招待の取り消しを「admin 以上か作成者」にする理由**: 画面どおり（作成できる人は誰の招待でも取り消せる）にすると、`invite_policy = all_members` のときに member が admin の招待を消せてしまう。ロールの上下関係（`canManage`）と矛盾する。
- **一覧を member にも見せる理由**: 招待は作成者・期限・使用回数だけを表示し、コードは再表示しない（ADR 0006）。「誰がどれだけ招待しているか」はメンバー全員に見えてよい情報と判断した。
- **ルームの管理を admin 以上にする理由**: `is_default` は、以降に参加する全員の自動参加に効く。名前の変更やメンバーを外す操作も、荒らしに使われると被害が大きい。作成者に権限を持たせると、ルームごとの所有者という概念が実質的に生まれ、「ルーム単位のロールを持たない」（ADR 0006）方針とずれる。
- **users を JOIN する理由**: メンバー一覧・ルーム一覧はどちらも表示名を必要とする。別のパッケージを経由すると 1 回の JOIN で済むものが 2 回のクエリになる。ADR 0001 の懸念の本体は「chat が認証の内部（トークン・パスワード）に触ること」で、公開プロフィールを読むことではない。読んでよい列を明文化して線を引く。
- **404 にする理由**: private ルームや他人のワークスペースの ID は ULID で推測しにくいが、ログや URL の共有で漏れうる。存在の有無を返さない方が安全で、クライアントの分岐も「見つからない」1 つで済む。
- **行ロックの後に判定する理由**: ロックの前に読んだロールで判定すると、判定と UPDATE の間に自分が降格・キックされても操作が通ってしまう（TOCTOU）。
- **コードを 128 ビットにする理由**: Refresh Token（256 ビット）ほど長くする必要はないが、画面のモック（10 文字）程度では、回数制限なしに総当たりへの耐性を主張できない。22 文字なら URL に載せても十分短い。

## 検討した代替案

- **招待の取り消しを画面どおりにする**: 上記の理由で不採用。`invites-as-member-policy-all` の画面は、他人の招待に「取り消す」を出さない形に直す。
- **招待の一覧も admin 以上に限る**: member 向けの一覧の画面が不要になるが、画面の意図と合わない。
- **ルームの作成者にも管理権限を与える**: 上記の理由で不採用。
- **公開プロフィールの読み取り口を `platform` に作る**: 境界ははっきりするが、一覧のクエリで JOIN できず、2 回のクエリになる。
- **プレビューを未ログインでも見られるようにする**: 招待リンクを未ログインで開いたときにワークスペースの名前を出せるが、画面の流れ（ログイン後に開く）と合わず、`already_member` も返せない。
- **DM を作るたびに毎回 404 か 409 を返す（既存を返さない）**: クライアントが「既存を探してから作る」の 2 往復になり、並行した作成で競合する。

## 結果（トレードオフ）

- ロールの変更・キック・譲渡・招待の受け入れは、WebSocket への通知（`workspace.role_changed` など）をまだ行わない。Phase 4 で `Delivery` を入れるときに、これらのユースケースから配信する。
- `users` の列を chat の SQL が読むので、`users` の列の変更（公開プロフィールの 5 列）は chat のクエリにも影響する。
- ワークスペース一覧・ルーム一覧はページングしないので、所属数が極端に多いユーザーではレスポンスが大きくなる。
- 招待プレビューは要ログインなので、Web クライアント（Phase 6）は、未ログインで招待リンクを開いたらログインさせてから招待のページに戻す必要がある。
