# 0049. 離席とカスタムステータス（Phase 6.8。自動は Redis、本人の設定は DB。合わせるのは読む側）

- 状態: 採用
- 日付: 2026-09-21

## 背景

Phase 6.8 は、presence に離席を足し、Slack と同じカスタムステータス（絵文字と文言）を設定できるようにする。

**この ADR は CLAUDE.md の「やらない」と決めたことを 1 つ取り消す。** これまで presence は
「オンラインのドットだけ。離席や最終オンライン時刻は出さない」としていた（CLAUDE.md ルール 5 と「デザイン」、
`docs/ui/README.md` の「取り込みの過程で設計に合わせて直したこと」）。オーナーの要望（2026-09-19）で離席を足す。
**最終オンライン時刻は引き続き出さない**（「いつから見ていないか」を他人に見せない）。

オーナーと確定している前提（2026-09-19）:

- 状態は 3 つ: オンライン（今の緑のドット）/ 離席（**色なしのアウトライン**）/ オフライン（ドットなし）
- **画面を見ていないときは自動で離席にする。** 見ていても、操作がないまま一定時間（10 分）たったら離席にする
- 複数のタブや端末があるときは、どこか 1 つで画面を見ていればオンライン
- **本人が自分で離席にしたら固定する。** 自動ではオンラインに戻らない（本人が戻すまで）
- カスタムステータスは絵文字 + 文言 + 消える時刻。本人の設定なので DB に持ち、消える時刻は `Clock` で判定する

いまの presence は、`presence:{userID}` のハッシュに「接続を持つインスタンスの ID」をフィールドとして置き、
フィールドが 1 つでも残っていればオンライン、という作りになっている（ADR 0016）。
状態の変更と `presence.changed` の publish は 1 つの Lua スクリプトで行い、順序の入れ替わりを防いでいる。

この ADR のいちばん大きな判断は、**「自動で決まる状態」と「本人が選んだ設定」という性質の違うものを、
どこで 1 つの見た目に合わせるか**になる。

## 決定

### 1. 3 つの状態を、2 つの独立した事実から作る（オーナーと確認）

持つものを 2 つに分ける。

| 事実 | どこに持つか | 何が決めるか |
|---|---|---|
| `presence`（`active` / `idle` / `offline`） | Redis（TTL だけ） | 接続の有無と、その接続が画面を見ているか |
| 本人の設定（手動の離席・カスタムステータス） | Postgres | 本人が選んだこと |

画面に出す 3 つの状態は、**読む側がこの 2 つを合わせて決める**。

```
offline                      → ドットなし
idle または 手動の離席        → アウトラインのドット（離席）
それ以外（active）            → 緑のドット（オンライン）
```

合わせる規則はこの 3 行だけで、Web では `lib/chat/views.ts` の 1 つの関数にまとめる。
サーバーが両方を合わせて 1 つの状態にして配る案は採らなかった（下の「検討した代替案」）。

### 2. Redis: フィールドの値を「そのインスタンスで見ている接続の数」にする

ハッシュの形（`presence:{userID}` のフィールド = インスタンスの ID、フィールドごとの TTL）は変えない。
**値を `'1'` の固定から「そのインスタンスで画面を見ている接続の数」に変える。**

```
フィールドが 0 個            → offline
フィールドはあるが値が全部 0 → idle
1 つでも値が 1 以上          → active
```

- 接続・切断・`activity` による増減を、**1 つの Lua スクリプト（`syncScript`）にまとめる**。
  スクリプトの中で「前の状態」と「後の状態」を計算し、**変わったときだけ `presence.changed` を publish する**。
  状態の変更と publish を同じスクリプトで行う理由は ADR 0016 のまま（インスタンスをまたいだ並行で、
  イベントの順序が Redis の中の順序と入れ替わるのを防ぐ）。
- Hub は、そのインスタンスの「そのユーザーの接続の数」と「そのうち見ている接続の数」を数え、
  どちらかが変わったときにスクリプトを呼ぶ。接続が 0 になったらフィールドを消す。
- TTL の延長（`Refresh`）は、いまと同じ 30 秒ごと。**フィールドが消えていたら、いまの値で置き直す**
  （`'1'` で置き直すと、見ていない接続が突然オンラインに戻る）。そのため `Refresh` は、
  ユーザーごとの「見ている接続の数」を一緒に渡す。
- フィールドの数を `HLEN` ではなく `HKEYS` で数えるのも、いまと同じ理由（期限切れの未回収を数えないため）。

### 3. クライアント → サーバー: `activity` を「変わったときだけ」送る

```json
{ "type": "activity", "active": true }
```

- **接続は「見ていない」から始まる。** WebSocket がつながった直後に、クライアントが今の値を 1 回送る。
  逆（「見ている」から始める）にすると、見ていないタブが再接続するたびに、一瞬オンラインに見える。
- **送るのは値が変わったときだけ。** 変化そのものが少ないので、間引きは要らない。
  ただし、ウィンドウの行き来の連打で何度も往復しないよう、**1 秒だけ待ってからまとめて送る**。
- 「見ている」の条件は、次の 3 つがすべて成り立つこと:
  1. `document.visibilityState === "visible"`（別のタブを見ていない、最小化していない）
  2. ウィンドウがフォーカスされている（`focus` / `blur`）
  3. 最後の操作から 10 分たっていない（`pointerdown` / `keydown` / `wheel` / `touchstart` と、メッセージの送信）
- 10 分の判定は、**1 分ごとの点検**で行う（10 分のタイマーを毎回張り直さない。操作のたびにタイマーを作り直すと、
  スクロール中に数百回の張り直しが起きる。端末のスリープから戻ったときも、点検なら次の 1 分で正しくなる）。
- 上限は既存のフレームの制限（4 KiB）と同じ。`id` を付ければ `ack` が返るのも他のメッセージと同じ。
- 購読していないルームがあっても送れる（接続そのものの属性で、ルームに紐づかない）。

### 4. 手動の離席: ユーザーごとの 1 行（Postgres）

```sql
CREATE TABLE user_presence_settings (
    user_id     uuid        PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
    manual_away boolean     NOT NULL,
    updated_at  timestamptz NOT NULL
);
```

- **ユーザーごと**（ワークスペースごとではない）。「いま離席している」は人の状態で、ワークスペースで変わらない。
  オーナーの確定事項「再ログインや別の端末でも離席のまま」も、これで満たす。
- 行がなければ `false`。設定するときだけ行を作る（`INSERT ... ON CONFLICT DO UPDATE`）。
- API: `PUT /api/v1/users/me/presence` の `{"away": true}` / `{"away": false}`。冪等。
  パスは auth の `/users/me` の下に並ぶが、**ハンドラも DB の行も chat のもの**（`internal/chat` は `internal/auth` を
  import しない。CLAUDE.md ルール 1）。auth は presence を知らないままでよい。

### 5. カスタムステータス: `workspace_members` の 3 列（オーナーと確認）

**ワークスペースごと**に持つ（Slack と同じ。オーナーの判断、2026-09-21）。
すでにワークスペースとユーザーの組を主キーに持つ `workspace_members` に列を足す。新しいテーブルを作らない。

```sql
ALTER TABLE workspace_members
    ADD COLUMN status_emoji      text,
    ADD COLUMN status_text       text,
    ADD COLUMN status_expires_at timestamptz,
    ADD CONSTRAINT workspace_members_status_check
        CHECK (status_emoji IS NOT NULL OR (status_text IS NULL AND status_expires_at IS NULL));
```

- **絵文字は必須、文言は任意**（Slack は文言だけでも `💬` が付く。既定の絵文字はクライアントが入れて送る）。
  CHECK 制約で「絵文字なしの文言」「絵文字なしの期限」を DB が拒む。
- 解除は 3 列を NULL にする。行は消さない（メンバーの行そのものだから）。
- ワークスペースから抜けると行ごと消えるので、ステータスも一緒に消える（後始末が要らない）。
- API:
  - `PUT /api/v1/workspaces/{workspaceID}/me/status` — `{"emoji": "🍵", "text": "休憩中", "expires_at": "2026-09-21T12:00:00Z"}`
  - `DELETE /api/v1/workspaces/{workspaceID}/me/status` — 解除。設定していなくても 204（冪等）
- 検証（外れたら 422）:
  - `emoji`: Phase 6.7 の検証をそのまま使う（`internal/chat/emoji`。書記素クラスタ 1 つ・64 バイト以内・先頭が Emoji）
  - `text`: 100 文字（Unicode のコードポイント）まで。Slack と同じ。前後の空白は落とし、空文字は未設定として扱う
  - `expires_at`: 未来のみ。`Clock` で判定する。null は「消えない」

### 6. 期限切れは、読むときに `Clock` で落とす（掃除のジョブを作らない）

- `status_expires_at <= now` の行は、**読むときにステータスがないものとして返す**。SQL の側で落とす
  （`CASE WHEN status_expires_at IS NULL OR status_expires_at > $now THEN ... END`）。`now` は `Clock` から渡す。
- **期限切れのイベントは配らない。** クライアントは `expires_at` を持っているので、自分でタイマーを張って消す。
  全員に「消えました」を配るには、期限ごとにジョブを起こす必要があり、消えるだけのために経路が 1 本増える。
- 行は残るが、ユーザー × ワークスペースに 1 行の列なので、たまっていかない。次の設定で上書きされる。

**追記（2026-09-21、実装で分かったこと）**

**期限切れを落とすのは SQL ではなく、読み取りの変換 1 箇所（`internal/chat` の `statusOf`）にした。**
`CASE WHEN status_expires_at > $now THEN ... END` は sqlc が式の型と NULL 可能性を推せず、
生成される Go の型が `interface{}` か「NULL にならない `string`」になってしまう（`::text` を付けると後者）。
クエリは素の 3 列を返し、`statusOf(emoji, text, expiresAt, now)` が期限を見て落とす。
呼ぶのはメンバーの行を組み立てる 3 箇所だけなので、忘れても気づける（テストで押さえてある）。

### 7. レスポンスの形: `online` を `presence` に置き換える（オーナーと確認）

REST（ワークスペースとルームのメンバー、DM の相手）とイベントの両方で、`online: boolean` をやめる。

```jsonc
{
  "user": { "id": "01J8...", "handle": "miyuki", "display_name": "高橋 みゆき" },
  "role": "member",
  "presence": "active",          // active / idle / offline
  "away": false,                 // 本人が手動で離席にしている
  "status": { "emoji": "🍵", "text": "休憩中", "expires_at": "2026-09-21T12:00:00Z" }  // ないときは null
}
```

- **2 つのフィールドを足すのではなく、`online` を置き換える。** クライアントは Web だけで、サーバーと一緒に
  デプロイするので、互換のために両方を持つ意味がない。`online: false` と `presence: "idle"` のような
  組み合わせの矛盾を、この先ずっと説明しなくて済む。
- `status` は**見る人によらない**（`me` のような受け取る人ごとの値ではない）ので、WebSocket でもそのまま配れる。

**追記（2026-09-21、実装で決めた）: `away` と `status` を載せるのはメンバー一覧だけにする。**

DM の相手（`dm_peer`）には自動の `presence` だけを載せ、`away` とカスタムステータスは載せない。
メッセージの送信者にも載せない。**クライアントは、ワークスペースのメンバー一覧から ID で引く**。

- 同じ値をレスポンスの 3 か所（メンバー一覧・DM の相手・メッセージの送信者）に載せると、
  どれが最新かが場所によって変わり、更新の経路も 3 本になる
- メッセージは何十件も並ぶので、同じ人のステータスが何度も乗る
- クライアントは再接続のたびにワークスペースのメンバー一覧を取り直す（決定 9）ので、引く先は必ずある

### 8. イベント: `presence.changed` の形を変え、`member.status_changed` を足す

```jsonc
{ "type": "presence.changed",     "data": { "user_id": "01J8...", "presence": "idle" } }
{ "type": "member.status_changed", "data": { "workspace_id": "01J8...", "user_id": "01J8...",
                                             "away": true,
                                             "status": { "emoji": "🍵", "text": "休憩中", "expires_at": null } } }
```

- `presence.changed` の宛先は今までどおり（そのユーザーが所属するワークスペースの購読者）。`online` を `presence` にする。
- `member.status_changed` は、**手動の離席とカスタムステータスの両方**を運ぶ。宛先は
  「そのユーザーが所属するワークスペースの購読者」＋「本人のすべての接続」（別のタブに揃えるため）。
  - 手動の離席はユーザーごとなので、所属するすべてのワークスペースに同じ `away` を配る。
  - カスタムステータスはワークスペースごとなので、**ワークスペースごとにそのワークスペースの値**を入れて配る
    （1 つの publish を全員に配る作りなので、ワークスペースが宛先ならワークスペースごとの値でよい）。
- **イベントを 2 つに分けない。** 手動の離席とステータスは同じダイアログで同時に変わりうるし、
  受け取る側の反映先（メンバーの行）も同じ。2 本あると、片方だけ届いた中間の見た目が生まれる。

### 9. 再接続の同期: ワークスペースのメンバー一覧を取り直す

`presence` も `away` も `status` も欠番の仕組みを持たない（`change_seq` に乗らない）ので、
取りこぼしは**取り直し**で回復する。`docs/events.md` の同期の手順の 5 を次のようにする。

- 開いているパネルのルームのメンバー一覧（今までどおり）
- **ワークスペースのメンバー一覧**（メッセージの名前の横に出すステータスは、ルームのメンバー一覧には載らない人の分も要る。
  メンション（ADR 0041 / 0043）がすでに持っている一覧と同じもので、取り直しの往復は増えない）

### 10. 見た目（既存のトークンで描く）

- **離席のドット**: `border-2 border-text-muted` の輪と `bg-surface` の中身。新しいトークンは足さない
  （`--color-online` はオンラインのまま）。オフラインはドットなし（今と同じ）。
- **ステータスの絵文字**は、メッセージの名前の横・メンバーパネル・サイドバーの DM の行に出す。
  **文言**はメンバーパネルと（6.9 の）プロフィールのカード、それに絵文字の `title` で出す。
  タイムラインに文言を出すと、名前の行が人によって長さばらばらになるため。
- **入口**は、サイドバーの自分のアバターから開くアカウントメニュー（`account-menu.tsx`）に 2 つ足す:
  「ステータスを設定」（ダイアログ）と「離席中にする / 離席を解除する」（その場で切り替え）。
- ダイアログは Slack と同じく、**よく使うものの候補**（会議中 / 移動中 / 食事中 / 集中中 / 休暇中）を並べ、
  期限は Slack と同じ見出し「**次の時間の経過後に削除**」の下に
  「削除しない / 30 分 / 1 時間 / 4 時間 / 今日 / 今週 / **日時を選択**」を並べる。
  **「今日」のような相対の期限は、クライアントが絶対の時刻にして送る**（サーバーはユーザーのタイムゾーンを知らない）。
  「日時を選択」は日付と時刻の入力を出し、**カレンダーはブラウザのものを使う**（自前のカレンダーは作らない）。
- **いつ消えるかは、ステータスのホバー（と読み上げ）で見せる**（Slack と同じ）。
  文言と同じ `title` に「今日 17:00 まで」のように添える。整形はデータ層が `Clock` の時刻で行う。

**追記（2026-09-21、デザインの実装中に決めた）**

- **絵文字のピッカーは、ダイアログの中に流し込まない。** ピッカーは 400px 近く高いので、ダイアログの高さが
  画面を超え、候補と「保存」が見えなくなった（story で実際にそうなった）。リアクションと同じで、
  **md 以上はボタンに合わせて画面に浮かせ、モバイルは下から出るシート**にする（ADR 0044 決定 7 と同じ形）。
- 浮かせる位置の計算（`lib/anchored-position.ts`）に、**アンカーの左端に合わせる `align: "start"`** を足した。
  もとはメッセージの行のような広いアンカー用に右端合わせだけがあり、44px のボタンに使うと、
  パネルがボタンより左にぶら下がって、押したものから離れて見えた。
- **自分のアバターには presence のドットを出さない**（自分の状態はアカウントメニューで分かる）。

**追記（2026-09-21、オーナーが実物で確認して）**

- **期限の見出しと選択肢を Slack の文言に合わせた**（「消える時刻」→「次の時間の経過後に削除」、「消さない」→「削除しない」）。
  **「日時を選択」を足した**（日付と時刻の入力。カレンダーはブラウザのもの）。
- **ステータスのホバーに「いつまで」を出す**（Slack と同じ）。メンバーパネルではロール・文言の横にそのまま出す。
- **ダイアログの節（ラベルと中身）の余白をそろえた**。節ごとに書いていたら距離がばらついていたので、
  入力欄（`Field`）と同じラベルの見た目と余白（6px）を使う 1 つの部品にまとめた。

### 11. 通知（Phase 6.14）との関係

**離席でも通知は止めない。** Slack で通知を止めるのは「おやすみモード」の役目で、離席は「いま見ていない」を
他人に見せるだけの表示。おやすみモードは今回の範囲外（6.14 でも作らない）。

## 理由

- **自動と本人の設定を分ける理由**: 2 つは寿命も正本も違う。自動の状態は接続に付いていて、プロセスが落ちれば
  消えてよい（Redis の TTL）。本人の設定は、再起動や Redis のデータが消えても残らなければならない（Postgres）。
  1 つの値にまとめると、どちらの寿命に合わせるかを決められず、両方に写しを置くことになる。
  合わせるのは 3 行の規則で、写しのずれを直し続ける仕組みより安い。
- **フィールドの値を「見ている接続の数」にする理由**: 状態の判定に必要な情報を、いまと同じ 1 つのキーの中に収められる。
  別のキーに持つと、2 つのキーの読み書きの間で状態が食い違い、Lua の中でも順序を保てなくなる。
- **`activity` を接続ごとに持つ理由**: 「どこか 1 つで見ていればオンライン」（オーナーの確定事項）は、
  接続ごとの値をインスタンスの中で足し、インスタンスをまたいで足せば求まる。ユーザー単位で持つと、
  2 つのタブのうち片方を閉じたときに、もう片方が見ているかどうかを表せない。
- **接続を「見ていない」から始める理由**: 逆にすると、見ていないタブの再接続（Redis の再接続で全員が切られる場合を含む。
  ADR 0016）のたびに、そのユーザーが一瞬オンラインに見える。イベントが 2 回（online → idle）飛ぶのも無駄になる。
- **カスタムステータスを `workspace_members` の列にする理由**: 主キーがすでに「ワークスペース × ユーザー」で、
  メンバーの一覧と同じクエリで一緒に読める（N+1 にならない）。ワークスペースを抜けたときの後始末も要らない。
- **期限切れを読むときに落とす理由**: 期限は「その時刻を過ぎたら見せない」だけで、DB の行の正しさとは関係ない。
  ジョブで消すと、ジョブが遅れた間だけ古いステータスが見え、ジョブそのものの監視も増える。
- **`online` を置き換える理由**: フィールドが 1 つなら、矛盾する組み合わせが存在しない。互換を保つ相手が
  まだいないうちに変えるのが、いちばん安い。

## 検討した代替案

- **サーバーが手動の離席も合わせて 1 つの状態にして配る**: クライアントは届いた値をそのまま出せばよく、
  将来のネイティブアプリでも判定がずれない。ただし、手動の離席（Postgres）を Redis にも写す必要があり、
  DB の書き込みのあとに Redis の書き込みが失敗したときや、Redis のデータが飛んだときに、
  写しを直す経路が要り続ける。オーナーと比較して不採用（2026-09-21）。
- **カスタムステータスをユーザーごとに持つ**: 表示名・アバターと持ち方が揃い、6.9 のカードも 1 か所から読める。
  ただしワークスペースごとに出し分けられない。オーナーと比較して不採用（2026-09-21。Slack に合わせる）。
- **`online` を残して `presence` を足す**: 古いクライアントと両立できるが、両立させる相手がいない。
  2 つのフィールドの関係を説明し続けることになる。オーナーと比較して不採用（2026-09-21）。
- **離席の判定をサーバーの「最後の活動時刻」で行う**（クライアントは操作のたびに心拍を送り、サーバーが 10 分を測る）:
  クライアントの実装が薄くなるが、見ていないタブからも心拍が届くので「画面を見ているか」を表せない。
  送る回数も増える（変化のときだけ、が成り立たない）。
- **ステータスの期限切れを掃除のジョブで消す**: 期限ちょうどにイベントを配れるが、ジョブとその監視が増える。
  クライアントが `expires_at` を持っている以上、見た目は自分で消せる。
- **`presence.changed` にステータスも乗せる**: イベントが 1 つで済むが、ステータスは Postgres の変更、
  presence は Redis の変更で、publish する場所（Lua スクリプトの中 / ユースケース）が違う。
  1 つにすると、Lua がステータスを読む必要が出てくる。

## 結果（トレードオフ）

- **`online` を返していた REST とイベントが、すべて `presence` に変わる**。Web 側も同時に直す（構築順 4）。
  生成した TypeScript の型（`make ts-types`）も入れ替わる。
- **離席の判定はクライアントの申告を信じる。** 改造したクライアントは、見ていなくてもオンラインでいられる。
  presence は権限に関わらない表示なので受け入れる（authz は別。CLAUDE.md ルール 9）。
- **ブラウザの都合で、`blur` や `visibilitychange` が来ないまま閉じることがある**（タブのクラッシュなど）。
  その場合も WebSocket が切れれば offline になるので、最悪でも 60 秒（`OnlineTTL`）で正しくなる。
- **期限切れのステータスは、ほかの人の画面ではタイマーで消える**が、タイマーを持たない経路
  （たとえばページを開いたまま日付をまたぐ、はタイマーで消える）以外に、`expires_at` を過ぎた値が
  サーバーから返ることはない。
- **ステータスを設定・解除するたびに、所属するワークスペースの数だけイベントが publish される**
  （手動の離席の場合）。ワークスペースの数は多くても数十で、頻度も低い。
- 手動の離席のために、chat が `users` を参照するテーブルをもう 1 つ持つ（`user_presence_settings`）。
  auth のテーブルではなく chat のもの、という境界を守るため、auth は presence を引き続き知らない。
