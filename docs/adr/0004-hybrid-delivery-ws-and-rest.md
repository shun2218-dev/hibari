# 0004. WebSocket と REST 差分取得のハイブリッド配信

- 状態: 採用
- 日付: 2026-09-13

## 背景

WebSocket は常に切れうる（モバイル回線の切り替え、スリープ、サーバーの再起動、デプロイ、ロードバランサのタイムアウト）。
さらに Phase 5 では、インスタンス間の配信に Redis Pub/Sub を使う。Pub/Sub は **at-most-once** で、購読者がいない瞬間や接続が切れた瞬間のメッセージは失われる。

## 決定

- **永続化と配信を分ける**。メッセージは REST（`POST /api/v1/rooms/{id}/messages`）で送信し、Postgres へのコミットをもって「確定」とする。WebSocket は確定したイベントを「速く届ける」ための経路にすぎない。
- クライアントはルームごとに**最後に受信した seq** を保持する。
- 再接続したとき、または seq の欠番を検出したときは `GET /api/v1/rooms/{id}/messages?after_seq=N` で差分を取得する。
- 送信には `client_msg_id`（クライアントが生成する ULID）を必須にし、`UNIQUE(room_id, sender_id, client_msg_id)` で冪等にする。重複した送信には既存のメッセージを 200 で返す。
- 配信は `Delivery` インターフェースで抽象化する（Phase 4: インメモリ、Phase 5: Redis、Phase 7: Push）。
- Redis が落ちたときは、永続化を成功させて配信だけを失敗として扱う（配信の失敗はログに残し、クライアントの差分取得で回復させる）。

## 理由

- **正しさの根拠を 1 箇所にする**: 「届いたかどうか」を WebSocket に頼ると、切断のタイミングによって永久にメッセージが失われる。Postgres と seq を正にすれば、配信の信頼性が低くても最終的に整合する。
- **冪等な再送**: ネットワークエラーで「送信できたか分からない」状態は必ず起きる。同じ `client_msg_id` で送り直せば二重投稿にならない。
- **Pub/Sub の弱点を受け入れられる**: 配信が落ちても差分取得が保険になるので、Kafka や Redis Streams のような at-least-once の基盤を最初から導入しなくて済む。
- **スケールアウトが単純になる**: 各インスタンスは「自分が持つ接続に流すだけ」でよく、配信の状態を保持しない。

## 検討した代替案

- **WebSocket だけで送受信する**: 往復は少ないが、ack と再送の仕組みをすべて自前で WS 上に作ることになり、再接続時の欠落を防げない。
- **ロングポーリング / SSE だけ**: 実装は単純だが、typing などのクライアント → サーバーのリアルタイムな経路が別に必要になる。
- **Redis Streams / Kafka で at-least-once 配信**: 取りこぼしは減るが、運用コストが増える。差分取得があれば当面は不要。

## 結果（トレードオフ）

- クライアントの実装が複雑になる（seq の管理、欠番の検出、差分取得、楽観的更新と ack の突き合わせ）。
- 再接続が集中すると、差分取得の REST に負荷が集まる。`limit` の上限とインデックス `(room_id, seq DESC)` で抑える。
- 送信経路（REST）と受信経路（WS）が分かれるので、送信直後のメッセージは「REST のレスポンス」と「WS の `message.created`」の両方で届く。クライアントは `client_msg_id` と seq で重複を排除する。
- `after_seq` のテストがこのアプリの信頼性を担うので、テストを最も厚くする。
