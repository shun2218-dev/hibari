# 0041. メンション（Phase 6.13。本文に ID で保存し、件数は行として積んで既読位置で数える）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6.13 では、本文でユーザーをメンションし、メンションされた人に分かるようにする。

オーナーと確定している前提（ロードマップ、2026-09-19）:

- 個人・`@channel`・`@here` の 3 種類
- サイドバーに、未読とは別にメンションの件数のバッジを出す（色は attention の系統）
- 入力欄に `@` の補完。本文の `@名前` を押すとプロフィールのカードが開く
- スレッドの中でメンションされた人は、そのスレッドに参加する（ADR 0036 の想定どおり、`thread_members` に行を足す）

ADR で決めることとして、本文での表し方、件数の数え方、`@here` の対象、`@channel` / `@here` を使える人、
スレッドの中の `@channel` の対象、非メンバーへのメンション、編集したときの件数が挙がっていた。

### フェーズの順序について

ロードマップでは、メンション（6.13）の前に本文の書式（6.10）とプロフィールのカード（6.9）、メッセージへのリンク（6.11）が並んでいる。
6.10 は「本文から特別な部分を見つける仕組み」を作るフェーズで、6.13 はその上に乗る想定だった。いまは 6.6 の Web が途中で、6.7〜6.12 は未着手。
（6.11 の前半は、並行して ADR 0040 で提案中。そちらも 6.10 を待たずに、本文からリンクを見つける最小の仕組みだけを置く形にしている。）

この ADR は**メンションを先に作る**前提で書く。順序を入れ替えても破綻しないように、次の 2 つを守る。

- 本文からトークンを見つける処理を `internal/chat/mention` の 1 パッケージに閉じ込め、6.10 の書式の解釈が来たときに**その中から呼ぶだけ**にする（解釈を 2 か所に書かない）。
- 表示（`<@ID>` を名前に置き換える）は Web の 1 コンポーネントに閉じ込める。6.10 が来たら、そのコンポーネントを書式の描画木の葉として呼ぶ。

先に作れない部分は、この ADR の範囲から外す。

- `@名前` を押して開くプロフィールのカード（6.9）。いまは押しても何も起きない。カードは 6.9 で足す。
- コードブロックや引用の中のメンションを除外すること（6.10）。いまはどこにあっても同じメンションとして扱う。
  6.10 でコードブロックを解釈するようになったら、**除外は「数える側」にも効く**ので、そのときに送信の解釈も合わせる。

## 決定

### 本文での表し方

本文には**ユーザーの ID を入れたトークン**で保存し、表示のときに名前へ置き換える。

| 書くもの | 意味 |
|---|---|
| `<@01J8XXXXXXXXXXXXXXXXXXXXXX>` | そのユーザー |
| `<!channel>` | ルームの全員 |
| `<!here>` | 送った瞬間にオンラインのルームのメンバー |

- ULID の 26 文字だけを受け付ける。読めない ID や存在しないユーザーのトークンは、ただの文字列として扱う（エラーにしない）。
- 保存するのは本文そのまま。置き換えた結果は保存しない。**表示名を変えても古いメンションが古い名前のまま残らない。**
- 入力欄で `@` を押して候補から選ぶと、Web がこのトークンに変換する。人が手で `<@...>` と打つことは想定しないが、打てても壊れない。

**対象を決めるのはサーバー**で、本文を解釈して決める。クライアントから「誰をメンションしたか」を受け取らない。
受け取ると、本文に出てこない相手の件数を増やせてしまう。

### スキーマ

`message_mentions` を足す。**行 1 つが「この本文にあるメンション 1 件」**を表す。件数を数えるためだけのテーブルで、表示には使わない。

```sql
CREATE TABLE message_mentions (
    room_id    uuid        NOT NULL,
    message_id uuid        NOT NULL,
    -- NULL は「ルームの全員」（@channel）。それ以外は 1 人。
    user_id    uuid,
    -- 数え方は kind で変えない（下の「件数の数え方」）。表示と、後から制限を足すときのために残す。
    kind       text        NOT NULL CHECK (kind IN ('user', 'channel', 'here')),
    created_at timestamptz NOT NULL,

    CONSTRAINT message_mentions_message_fkey FOREIGN KEY (room_id, message_id)
        REFERENCES messages (room_id, id) ON DELETE CASCADE,
    -- ルームを抜けた・外された人の行は DB が消す（thread_members と同じ。ADR 0036）。
    -- 読めないルームのメンションが件数に残らないことを、アプリのコードに頼らずに保証する。
    CONSTRAINT message_mentions_room_member_fkey FOREIGN KEY (room_id, user_id)
        REFERENCES room_members (room_id, user_id) ON DELETE CASCADE,
    CONSTRAINT message_mentions_kind_target_check CHECK ((kind = 'channel') OR user_id IS NOT NULL)
);
-- 同じ本文で同じ人を 2 回メンションしても 1 件。NULL は UNIQUE 制約で重複を防げないので、2 本に分ける。
CREATE UNIQUE INDEX message_mentions_message_id_user_id_idx ON message_mentions (message_id, user_id) WHERE user_id IS NOT NULL;
CREATE UNIQUE INDEX message_mentions_message_id_channel_idx ON message_mentions (message_id) WHERE user_id IS NULL;
-- 件数を数えるとき（ルームごと・自分宛て）の入口。
CREATE INDEX message_mentions_room_id_user_id_idx ON message_mentions (room_id, user_id);
```

- `user_id IS NULL` は `@channel` の 1 行だけ。**大きなルームでも `@channel` の書き込みは 1 行**で済む。
- `@here` は、送った瞬間のオンラインのメンバーに解決して 1 人 1 行にする（presence は Redis の TTL でしか持たないので、後から同じ集合を作り直せない）。
- 非メンバーの行は作れない（`room_members` への FK）。`@channel` の行にはこの FK が効かないが、数えるときにメンバーだけを見る。
- `kind = 'here'` の行は `user_id` を持ち、`kind = 'channel'` の行は持たない。**数え方は `user_id` だけで決まり、`kind` は見ない。**

### 件数の数え方

**行を積んで、既読位置より後のものを数える。** カウンタの列は持たない。

自分のルーム `R` のメンションの件数は、`message_mentions` の行のうち次を満たすものの数。

1. `user_id IS NULL`（ルーム全員宛て）または `user_id = 自分`
2. その本文が**自分にとってまだ未読**
   - チャンネルに出ている行（`messages.in_channel`）: `messages.user_seq > room_members.last_read_user_seq`（ADR 0033 の未読と同じ物差し）
   - スレッドだけの返信: `messages.thread_seq > thread_members.last_read_thread_seq`（ADR 0036 の物差し。参加していなければ数えない）
   - 「チャンネルにも投稿する」を付けた返信（ADR 0039）は 1 に当たるので、両方で数えて 2 件にしない

ルーム一覧では、この集計を**ルームごとに 1 回**にまとめて `mention_count` として返す（N+1 にしない。ADR 0036 のスレッドの未読数と同じ形）。

この形にすると、次が**何も書かずに**成り立つ。

- **自分の発言は数えない。** 送信のときに自分の既読位置がその発言まで進むので（ADR 0012 / 0036 / 0039）、条件 2 に当たらない。`@channel` を自分で送っても自分には出ない。
- **ルームを読むと消える。** 既読位置が進めば条件 2 に当たる行がなくなる。既読の API も配信も足さなくていい。
- **並行して送っても件数がずれない。** 共有のカウンタの行がないので、`@channel` を何人が同時に送っても、増やす対象の行ロックを取り合わない。デッドロックの経路も増えない。

### メンションの行を書くとき

行は**常に本文と一致させる**。本文が変わったら作り直す。送信・編集・削除と同じトランザクションの中で行う。

| きっかけ | すること |
|---|---|
| 送信 | 本文を解釈して行を入れる |
| 編集 | そのメッセージの行を消して、新しい本文で入れ直す |
| 削除（論理削除） | そのメッセージの行を消す（本文が空になるため） |
| メッセージの物理削除・ルームの削除 | FK の CASCADE |

**編集で足したメンションは、すでに読まれたメッセージでは件数にならない。**
件数は「未読の範囲にあるメンション」なので、既読位置より前のメッセージにメンションを足しても未読にはならない。
反対に、編集で消したメンションは件数から消える。この非対称は、件数を既読位置から導いていることの結果として受け入れる（「検討した代替案」）。

### `@here` の対象

**送った瞬間にオンラインの、そのルームのメンバー。** presence は Redis に TTL 付きで置いているだけなので（CLAUDE.md ルール 5）、正確な集合ではなく目安になる。

- presence の読み取りは**トランザクションの外（送信の前）**で行う。Postgres の行ロックを持ったまま Redis を待たない。
  読んだ後にオフラインになった人が混ざることはあるが、`@here` はもともと目安なので許容する。
- **Redis が読めないときは、`@here` の対象を空にしてメッセージの送信は成功させる。** 本文が届くことを優先する。落としたことは警告としてログに残す。
- `@here` は本文の解釈にオンラインのメンバーの列挙が要るので、ルームのメンバー数が多いほど重い。行を入れる件数の上限は設けず、必要になったら測ってから足す。

### `@channel` / `@here` を使える人

**最初は、そのルームに投稿できる人なら誰でも使える。** 判定は `internal/chat/authz` に `CanMentionEveryone` として置く。
いまは「投稿できるなら true」を返すだけだが、後からワークスペースの設定（admin だけ、など）で絞るときに、ハンドラを触らずに済む（絶対ルール 9）。

### スレッドの中の `@channel` / `@here`（オーナーと確認: Slack に合わせる）

**スレッドだけの返信（チャンネルに出していない返信）の `@channel` / `@here` は、誰の件数も増やさない。** 行を作らない。

Slack のヘルプ「[Notify a channel or workspace](https://slack.com/help/articles/202009646-Notify-a-channel-or-workspace)」に、
`@channel` / `@here` / `@everyone` は「通知が一時停止されているとき、および**スレッドの中で使われたとき**は通知しない」と書かれている。
オーナーの指示は「Slack と同じにする」なので、それに合わせる。

- スレッドに参加している人には、その返信自体がスレッドの未読として届く（ADR 0036）。`@channel` を書いても、それ以上のことは起きない。
- 個人へのメンション（`<@userID>`）はスレッドの中でも数える。Slack もそうなっている。制限がかかるのは全員宛ての 2 つだけ。
- **「チャンネルにも投稿する」を付けた返信（ADR 0039）は、チャンネルの投稿と同じに扱う**（`@channel` はルーム全員の 1 行、`@here` はオンラインのメンバー）。
  その返信はチャンネルのタイムラインに出て、`user_seq` を進める「チャンネルの発言」になるので（ADR 0039）、全員に向けられて構わない。
  Slack のヘルプはこの組み合わせに触れていないので、ここは hibari の判断。全員に知らせたいときの手段が 1 つ残る、という理由で選んだ。
- 入力欄では、スレッドで `@channel` / `@here` を打ったときに「チャンネルにも投稿する」を勧める（画面は Web の ADR で決める）。

### メンションされた人はスレッドに参加する

スレッドの返信でメンションされた人は、`thread_members` に行を足す（ADR 0036 が想定していたとおり）。

- 既読位置は **`thread_seq - 1`**（その返信だけが未読になる）。0 にすると、それ以前の返信まで全部未読になる。
- ルームのメンバーでなければ入れない（`thread_members` の FK）。メンションの行が作れない相手と同じ条件になる。
- すでに参加していれば何もしない（既読位置を戻さない）。
- **チャンネルの投稿（スレッドの親になっていない行）でのメンションでは、スレッドを作らない。** 返信が来るまでスレッドは存在しない。
- **`@channel` / `@here` では誰も参加させない。** 個人へのメンションだけが参加者を増やす。
  「チャンネルにも投稿する」を付けた返信の `@channel` でも同じ（ルームの全員をスレッドの参加者にしてしまうため）。

### ルームのメンバーでない人をメンションしたとき

**知らせない。** 行を作らないので、件数にも通知にもならない。ルームに参加した後の発言から数える。

- public のルームは、参加していなくてもワークスペースのメンバーなら読める。その人をメンションしても数えない。
- 本文のトークンは残るので、表示は `@名前` のまま出る（誰を指していたかは読める）。
- 入力欄の補完はルームのメンバーだけを出す。貼り付けなどで非メンバーの ID が入ったときに入力欄で警告するかは、Web の ADR で決める。

### API

パスは増やさない。既存のレスポンスに足すだけ。

- **送信・編集**: 変わらない。`mentions` のような対象の指定は受け取らない。
- **メッセージのレスポンス**（REST と WebSocket の `message.created` / `updated` / `deleted` で共通）に `mentions` を足す。

```json
"mentions": [
  { "kind": "user", "user": { "id": "01J8...", "handle": "miyuki", "display_name": "高橋 みゆき" } },
  { "kind": "channel" }
]
```

  - **本文から作る**（`message_mentions` の行からではない）。本文の出現順、重複なし。
  - ルームを抜けた人やメンバーでない人も含む。行は消えていても、**名前を表示できないと本文が読めなくなる**ため。
  - `users` を引くのはページ全体で 1 回（添付の `ListAttachmentsForMessages` と同じ形）。存在しないユーザーの ID は落とす。
  - `@channel` / `@here` は `kind` だけで、`user` は持たない。
- **ルーム一覧 / ルームの取得**に `mention_count` を足す（未読数 `unread_count` の隣）。
- **既読の API は変えない。** `POST /rooms/{id}/read` で既読位置が進めば件数は自然に減る。
  レスポンスと `room.read` のイベントに `mention_count` を足して、別の端末のバッジも揃える。

### 配信と同期

**イベントの型は増やさない**（ADR 0039 と同じ方針）。

- `message.created` / `message.updated` / `message.deleted` に `mentions` が載る。編集でメンションが変われば本文も変わり、`change_seq` が進むので、`after_change_seq` の差分でそのまま揃う。
- **「これは自分宛てか」をイベントに入れない。** 配信は 1 つのペイロードをルームの購読者に配る形（ADR 0015 / 0016）なので、受け取る人ごとに違う値を載せられない。
  クライアントは `mentions` を見て自分で判断し、手元のバッジを増やす。
  - `kind: "user"` は自分の ID があるかで分かる。
  - `kind: "channel"` / `"here"` は「自分も対象かもしれない」として増やす。ただし**スレッドだけの返信（`thread_root_id` があって `also_in_channel` が false）では増やさない**。サーバーが行を作らないため。
  - `@here` で自分がオフライン扱いだったときだけ、手元の件数が 1 多くなることがある。**ルームを開くか、ルーム一覧を取り直せば正しい値に戻る**（サーバーの `mention_count` が正）。
- 再接続の手順（ADR 0026）には、ルーム一覧を取り直すところで `mention_count` も受け取る、という 1 行が増えるだけ。

## 理由

- **本文に ID を入れる理由**: 表示名は変えられる。`@高橋` と書いて保存すると、改名した瞬間に古い発言が誰を指しているか分からなくなる。
  ID なら、表示のたびに現在の名前へ置き換えられる。Slack も同じ形（`<@U123>`）。
- **対象をサーバーが本文から決める理由**: クライアントの申告を信じると、本文に出てこない相手の件数を増やせる。
  同じ理由で、件数のイベントも「サーバーが持つ既読位置」から導く。
- **カウンタの列ではなく行を積む理由**: ロードマップで比べることになっていた 2 案のうち、行を積む方を採る。
  - `@channel` の書き込みが**ルームの人数によらず 1 行**で済む。カウンタ案は、ルームの全員の行を 1 回の UPDATE で増やすことになり、
    同じルームへの同時の送信どうしが `room_members` の同じ行の集合を取り合う。DoD の並行テスト（多数の goroutine が同時に `@channel`）が、まさにその形になる。
  - **減らす側が難しくない。** カウンタ案では、編集でメンションが消えたとき・メッセージが削除されたとき・ルームを読んだときに、誰の値をいくつ減らすかを毎回正しく求める必要がある。
    1 回でもずれると、二度と 0 に戻らないバッジが残る（既読位置と違って、真の値が別にないため）。
  - **既読位置と 1 つの物差しでそろう。** 「未読の中にあるメンションの数」という定義は、未読数（ADR 0033 / 0036）と同じ既読位置から導ける。
- **`kind` を数え方に使わない理由**: 数える条件を `user_id IS NULL OR user_id = 自分` の 1 行に保つため。
  `@here` のように「全員宛ての書き方だが、対象は送信時に解決済み」という組み合わせがあるので、宛先の広さは `user_id` だけで表す。
- **レスポンスの `mentions` を本文から作る理由**: 表示に必要なのは「誰の名前に置き換えるか」で、件数の対象とは別の集合になる。
  ルームを抜けた人のメンションは、件数には数えないが名前は出したい。2 つを同じ行から作ると、どちらかが壊れる。
- **既読の API を変えない理由**: 既読とメンションの件数を別々に動かすと、「読んだのにバッジが残る」状態を作る経路ができる。導いた値なら、その状態が存在しない。

## 検討した代替案

- **`room_members` にカウンタの列を足し、`@channel` で全員の行をまとめて 1 回の UPDATE で増やす**: 上の「理由」で不採用。
  書き込みは O(1) の文で済むが、減らす側の正しさと、同時送信での行の取り合いが割に合わない。
- **ユーザーごとの通知テーブルに `@channel` の行を人数分積む**: 数え方は素直（自分の行を数えるだけ）だが、`@channel` 1 回でルームの人数だけ行が増える。
  ロードマップが心配していた「大きなルームで送信が重くならないか」に真っ向から当たる。
- **本文に表示名を保存する**（`@高橋 みゆき`）: 改名で古くなる。誰を指すかを本文から復元できない。不採用。
- **クライアントが対象の ID を送る**: 偽れる。不採用。
- **メンションを送信のときに固定し、編集で作り直さない**（ADR 0039 の `in_channel` と同じ考え方）: 本文と行が食い違う。
  「本文にはもう自分の名前がないのにバッジが残る」状態を、ユーザーが消す手段がない。不採用。
- **編集で足したメンションも必ず数える**: 既読位置より前の行に「未読のメンション」を作ることになり、
  既読位置から導くという設計そのものを崩す（件数の実体を別に持つことになる）。不採用。必要になったら、編集を新しい発言として扱う形（Slack にもない）を別の ADR で検討する。
- **スレッドの中の `@channel` をルームの全員にする**: チャンネルに出ていない発言で全員のバッジを増やすことになる。Slack もそうしていない。不採用。
- **スレッドの中の `@channel` をスレッドの参加者に解決する**: 最初の案。参加者には返信自体がスレッドの未読として届くので、メンションの件数を足しても新しく伝わることがない。
  Slack に合わせる方針（オーナーの指示）とも食い違うので不採用。
  「チャンネルにも投稿する」を付ければ全員に向けられるので、手段は残っている。
- **`@here` を送信の時点ではなく表示の時点で判定する**: presence は TTL で消えるので、後から同じ集合を作り直せない。不採用。
- **`mentions_me` のような受け取る人ごとの値をイベントに載せる**: 配信が 1 ペイロードの broadcast なので、人数分のペイロードを作ることになる。不採用。

## 結果（トレードオフ）

- 件数が O(1) ではなくなる。未読の範囲にある行を数えるクエリになる（未読数の引き算とは違う）。
  未読の範囲は普通は小さく、`(room_id, user_id)` のインデックスから入って `messages` を引くだけだが、
  長く読んでいないルームで多くメンションされていれば、そのぶん行を読む。表示は「99+」で頭打ちにする。
- 既読にすると件数は戻らない。後から「メンションだけ見返す」には、別の一覧（Slack のアクティビティ）が要る。この ADR では作らない。
  `message_mentions` はその一覧の元になる形にしてある（既読位置の条件を外せば全件が引ける）。
- 編集で足したメンションは、すでに読まれたメッセージでは数えられない。
- `@here` は送った瞬間のスナップショットで、TTL のぶん実際よりオンラインを多く見積もる（最大 `OnlineTTL` = 60 秒）。
- public のルームに参加していない人には、メンションが届かない。
- `@here` は、オンラインの人数だけ行が増える。`@channel`（1 行）とは書き込みの重さが違う。
- スレッドの中で `@channel` と書いても何も起きないので、書いた人は「効いていない」ことに気づきにくい。入力欄で「チャンネルにも投稿する」を勧めて補う。
- メッセージのレスポンスが 1 つ増える（`mentions`）。メンションのない本文では空の配列になる。
- 本文の解釈が、サーバー（対象を決める）と Web（表示する）の 2 か所に要る。トークンの形は 1 つなので、
  形を変えるときは両方を直す。6.10 で書式の解釈が入るまでは、この 2 か所だけに閉じ込める。

## 実装の順序

1. **この ADR**（オーナーの確認を取る）
2. マイグレーション（`message_mentions`）、sqlc のクエリ、`internal/chat/mention` のパーサー
3. 送信・編集・削除で行を書く。`@here` / スレッドの `@channel` の解決。`thread_members` への参加
4. 件数の集計をルーム一覧と既読のレスポンスに載せる。メッセージのレスポンスの `mentions`
5. `docs/events.md` の更新、テスト（パーサーのテーブル駆動、並行の `@channel`、既読で消えること、非メンバー、編集）
6. **Web は別の ADR**（入力欄の補完、バッジの見た目、`/dev/preview` のスクリーンショットをオーナーに見てもらう）
