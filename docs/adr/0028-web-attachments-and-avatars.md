# 0028. Web の添付とアバターの表示（アップロードの流れ、署名付き URL の持ち方）

- 状態: 採用
- 日付: 2026-09-17

## 背景

ロードマップ Phase 6-2 の「本番のページの構築順 5」で、添付ファイルとアバター画像を画面につなぐ。
API の側は ADR 0013（添付）と ADR 0020（アバター）が決めている。どちらも **chat のレスポンスに署名付き URL を載せない** ので、クライアントが画面に出すものの ID を集めて引く必要がある。クライアントの側で決まっていなかったのは次のこと。

- アップロード中の添付をどこに持ち、送信とどうつなぐか。進み具合をどう取るか
- 申告する Content-Type と、サーバーの許可リストにない種類の扱い
- 署名付き URL（添付 5 分、アバター 1 時間）をいつ取り、期限が切れたらどうするか
- ダウンロードのさせ方

範囲はオーナーと確認して、**アバターは表示だけ** にした。画像のアップロードと削除（`settings/profile-avatar*.png`）は、設定の画面を作る構築順 6 で行う。

## 決定

### 層の分け方
| ファイル | 役割 |
|---|---|
| `web/lib/chat/uploads.ts` | ルームの入力欄に並べる添付。発行 → PUT → complete を進め、取り消しと再試行を扱う |
| `web/lib/chat/put-file.ts` | 署名付き URL への PUT（XMLHttpRequest） |
| `web/lib/chat/media.ts` | アバターと添付の画像の署名付き URL を持つストア |
| `web/lib/chat/store.ts` | 送信中のメッセージ（`outgoing`）に添付を持ち、`attachment_ids` として送る |

### アップロード
- 「ファイルを添付」で選ぶと、すぐに入力欄に並べ、1 つずつ並行して **発行（`POST /rooms/{id}/attachments`）→ ストレージに PUT → complete** を進める。中身は Go サーバーも Next.js も経由しない（CLAUDE.md ルール 10）。
- **PUT は XMLHttpRequest で送る。** fetch はアップロードの進み具合を取れず、デザイン（`chat/attachment-uploading.png`）に進み具合がある。Access Token は付けない（署名が URL に入っている）。
- 入力欄の添付は、入力欄の本文と同じく **ルームの画面を開いている間だけ持つ**。ルームを移ったら進行中の PUT を打ち切って捨てる。
- 取り消し（×）は PUT を打ち切り、それ以降の結果を捨てる。再試行は発行からやり直す（前の行は使わない）。サーバーに残った pending / uploaded の行は、掃除ジョブが 24 時間後に消す（ADR 0013）。
- 1 メッセージに 10 個まで。超えて選んだ分は並べない。
- **送れるのは、添付がすべて uploaded のときだけ。** アップロード中や失敗したものが残っていたら送信ボタンを押せない（付けたつもりの添付が抜けないように）。添付があれば本文は空でもよい。
- 送信したら、添付は送信中のメッセージ（`OutgoingMessage.attachments`）に移る。再送は同じ `client_msg_id` と同じ `attachment_ids` で送る。送信中のメッセージの添付は、ファイル名と大きさだけで出す（まだメッセージに付いていないので GET URL が取れない）。

### 申告する値
- **Content-Type**: ブラウザが判定した種類が、サーバーの検証に通る形（小文字、パラメータなし）ならそれを使い、そうでなければ `application/octet-stream`。
  発行が `content_type: invalid_value`（許可リストにない）で 422 になったら、**`application/octet-stream` で 1 回だけ発行し直す**。許可リストは設定値（`ATTACHMENT_ALLOWED_TYPES`）で、クライアントに同じ一覧を持たない。
- **寸法**: inline で表示する画像（PNG / JPEG / GIF / WebP）だけ、`createImageBitmap` で読んで申告する。読めなければ申告しない。
- **ファイル名**: サーバーが弾く文字（`/`・`\`・制御文字）は `_` に置き換え、255 文字で切る。ファイル名は表示とダウンロード時の名前にしか使わないので、弾いて失敗させるより通す。

### 署名付き URL の持ち方
`media.ts` のストアに、ID → URL（画像がなければ `null`）の表として持つ。どちらも読み込めなければ代わりの表示（頭文字、ファイル名の枠）があるので、失敗を画面に出さない。

- **アバター**: サイドバー（自分と DM の相手）・タイムラインの送信者・メンバーパネルが、画面に出す人の ID を頼む。同じ描画の中の依頼は **マイクロタスクでまとめて 1 回（200 人ずつ）** 送る。
  頼まれたときに、まだない人と **期限まで 5 分を切った人** の分だけ取り直す。画像がない人も 1 時間で確かめ直す。
  `Avatar` は読み込めなかった URL を覚えて頭文字に戻し、URL が変われば画像をもう一度試す。
- **添付の画像**: 開いているルームの、削除されていないメッセージの画像だけを 1 枚ずつ取る。**まだないときだけ取り、期限では取り直さない。**
  `<img>` が読み込めなかったら、URL を取ってから 1 分以上経っていれば期限切れとみなして取り直し、1 分以内なら諦めて（`null`）ファイル名の枠に戻す。画像は `loading="lazy"` にして、見えるまで読み込まない。404 も `null`。
- **ダウンロード**: 押すたびに GET URL を取り、`<a>` を押させる。URL は `Content-Disposition: attachment` で署名してある（ADR 0013）ので、ページは移らずに保存が始まる。

### 画像の枠
寸法があればその比率で枠を確保し（ADR 0013）、読み込みでタイムラインがずれないようにする。縦に長い画像は、高さを 320px で抑えて切り取る。

## 理由

- **アップロードをストアではなくルームの画面に持つ理由**: 入力欄の本文と返信先がルームの画面の状態（ADR 0027）で、添付だけ別の寿命にすると「本文は消えたのに添付だけ残る」ことになる。File は大きく、画面を離れたあとも持ち続ける理由がない。
- **アバターと添付で取り直し方を変える理由**: アバターは小さい画像なので、期限の前に URL を替えて読み込み直させても害が小さく、開きっぱなしの画面でも画像のまま保てる。添付は 1 枚で最大 25 MiB あり、表示できている画像の URL を替えると全部読み込み直しになる。表示できている `<img>` は URL の期限が切れても表示が消えないので、読み込みに失敗したときだけ取り直せば足りる。
- **失敗から 1 分で区切る理由**: 取った直後の URL でも読み込めないなら、期限ではなく中身の問題（オブジェクトがない、壊れた画像）で、取り直しても同じ。区切らないと取り直しと失敗を繰り返す。TTL（5 分）より十分短い。
- **送信の前に uploaded を待つ理由**: 送信のトランザクションは uploaded の添付しか付けない（ADR 0013）。アップロードの完了を待ってから送る仕組みにすると、送信の順番（ADR 0027 の 1 件ずつ）が添付の待ちで止まる。
- **許可リストにない種類を octet-stream で送り直す理由**: 種類の分からないファイルは octet-stream として添付できる（ADR 0013 の「原則すべてのファイルを添付できる」）。ブラウザで開かせるのは画像だけなので、それ以外の種類を落としても表示は変わらない。

## 検討した代替案

- **fetch で PUT する**: 進み具合が取れない。`ReadableStream` の本文でも、ブラウザは送った量を知らせない。
- **添付の画像の URL も期限の前に取り直す**: 上記のとおり、大きな画像を読み込み直させる。
- **ページを開いている間ずっと、アバターの URL をタイマーで取り直す**: 見ていない人の分まで取り続ける。頼まれたときに期限を見れば、画面に出ている人の分だけで済む。
- **送信中のメッセージの画像を、手元の File から `URL.createObjectURL` で出す**: 確定した瞬間に署名付き URL の画像に差し替わり、Object URL を捨てる時期の管理も要る。送信中の短い間だけのためには見合わない。
- **クライアントにも許可リストを持つ**: 設定値（`ATTACHMENT_ALLOWED_TYPES`）と二重になり、ずれる。

## 結果（トレードオフ）

- アップロードや送信の失敗の理由（大きすぎる、10 個を超えた、24 時間を過ぎて消えた）は出ない。デザインにないので「アップロードできませんでした」「送信できませんでした」だけになる（`docs/ui/README.md` の未解決）。
- 10 個を超えて選んだファイルは、何も言わずに並べない。
- 添付だけのメッセージは、サイドバーの最後のメッセージを仮の文言「添付ファイル」にしている。ルーム一覧の `last_message` に添付の情報がないので、ファイル名は出せない（`docs/ui/README.md` の未解決）。
- 送信した直後の自分の画像は、確定して GET URL が取れるまでファイル名の枠で出る。
- 画像を押しても何も起きない（拡大表示はデザインにない）。
- 期限切れの URL を持った画像を開き直すと、1 回読み込みに失敗してから取り直す（その間はファイル名の枠）。
- アバターの画像は、サイドバーで並びが変わらない限り、1 時間を過ぎても最初の URL で表示したままになる（表示できている画像は消えない）。
- 自分のアバターの画像の変更・削除はまだできない（構築順 6）。
- ブラウザの画面を実際に操作した確認はオーナーが手元で行う。自動の確認は、画面のテスト（偽の API と PUT）と、compose の API と MinIO に対して、Web のオリジンからの CORS の preflight・署名付き PUT・complete・`attachment_ids` 付きの送信・画像の GET（inline）が通ることまで。
