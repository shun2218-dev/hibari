# 0057. ブラウザ通知（Phase 6.14b。WebSocket で届いたメッセージを、クライアントが設定を読んで通知に変える）

- 状態: 提案
- 日付: 2026-09-22

## 背景

Phase 6.14b は、タブが開いている間に、ブラウザの Web Notifications で新しいメッセージを知らせる（ロードマップ）。
Push 通知（APNs / FCM / Web Push）は Phase 7 以降のまま。ここで作るのは、**hibari のタブがどこかで開いている間だけ**届く通知。

通知するかどうかの規則は、6.14a と 6.14c で決めてある（ADR 0055 決定 1、ADR 0056 決定 3）。この ADR は、その規則を
「いつ・どのタブが・何を出すか」に落とす。

### オーナーと確定した内容（2026-09-22）

- **ミュートしたチャンネルでメンションされても、通知は出さない**（ADR 0055 決定 1 のまま。サイドバーの `@N` は出る）
- **通知にメッセージの本文を出す。** 本文を隠す設定は作らない（必要になったら足す）
- **通知の音を鳴らす**（Slack と同じ）

## 決定

### 1. 通知するメッセージ

`message.created` のイベントで届いた、次のすべてに当てはまるメッセージ。

- 人の発言（`kind: user`）で、自分が送ったものではない
- **どのタブも見えていない**（`document.visibilityState` がすべてのタブで `hidden`）。見えているタブがあれば、そこで読める
- ADR 0055 決定 1・ADR 0056 決定 3 の規則で「対象」になる

```
ミュートしている                     → 出さない（メンションでも）
DM                                   → 全体の設定が none でなければ出す
それ以外は「通知する内容」（チャンネルの上書き、なければ全体の設定）で決める:
  all       → チャンネルの投稿はすべて出す。スレッドだけの返信は、下の「スレッド」に当たるときだけ
  mentions  → 自分宛てのメンションか、下の「スレッド」に当たるときだけ出す
  none      → 出さない（全体の設定だけが取れる値。チャンネルの上書きがあればそちらが勝つ）

スレッド: スレッドだけの返信で、自分宛てのメンションがあるか、参加していて返信の通知がオン（ADR 0056 決定 3）
```

- 「自分宛てのメンション」は `<@自分>` と `@channel`（ADR 0041）。全体が `none` でチャンネルの上書きがなければ、メンションでも出さない
  （「なし」は通知を出さないという意味。未読とバッジは出る）
- **`@here` は通知の理由にしない。** 通知を出すのはどのタブも見えていないとき、つまり自分が離席（idle）のときで、
  サーバーは `@here` の対象をアクティブな人に絞っている（ADR 0041 / 0049）。そのとき自分は対象になっていない
- 編集（`message.updated`）では出さない。再接続の差分で届いたメッセージでも出さない（まとめて何十件も鳴らさないため。未読とバッジで分かる）
- 判定に使う値（ルームの設定・全体の設定・参加中のスレッド）は、どれもストアが持っているものを読む。**判定は 1 つの純粋な関数**にして、表でテストする

**表示中のワークスペースのメッセージだけが届く。** WebSocket の購読は表示中のワークスペースとそのルームに限っているため（ADR 0015）。
ほかのワークスペースの通知は出ない。Slack はワークスペースをまたいで通知するが、購読の単位を変える話なので、必要になったら別に扱う。

### 2. 複数のタブで 1 回だけ出す

- **Web Locks の `hibari:notifier` を持ったタブだけが通知を出す**（ADR 0024 の refresh と同じ仕組み）。ロックを持つタブが閉じられたら、ほかのタブが引き継ぐ
- **どのタブも見えていないか**は、`BroadcastChannel`（`hibari:visibility`）でタブごとの見え方を知らせ合って、ロックを持つタブが判断する
- 念のため、通知の `tag` にメッセージの ID を入れる（同じメッセージの通知は OS が置き換える）
- Web Locks がない環境では、そのタブが見えていないときに、そのタブが出す（重複は `tag` で吸収する）

### 3. 通知の中身

- タイトル: チャンネルは「送信者の表示名（#チャンネル名）」、DM は「送信者の表示名」。スレッドの返信は「送信者の表示名（#チャンネル名 のスレッド）」
- 本文: メッセージの本文を平文にしたもの（書式の記号を外し、`<@ID>` は `@名前` に置き換える。最初の 100 文字）。本文のない添付だけの投稿は「ファイルを送信しました」
- アイコン: アプリのアイコン（送信者のアバターは署名付き URL で期限があるので使わない）
- 本文を隠す設定は作らない（オーナーの判断）

### 4. 押したとき

- そのタブをフォーカスし、メッセージへ飛ぶ（ADR 0042 の `?m=`。スレッドの返信なら `?t=` でパネルを開く）

### 5. 許可を求める

- ブラウザは、操作をきっかけにしない許可の要求を拒む（Chrome・Firefox・Safari）。**サイドバーの上に「デスクトップ通知を有効にする」の帯**を出し、押したときに `Notification.requestPermission()` を呼ぶ
- 帯は、許可がまだ決まっていない（`default`）ときだけ出す。「今はしない」で閉じられ、その端末では出さない（localStorage）
- 拒否された（`denied`）ら、通知を出そうとしない。ユーザー設定の「通知」に「ブラウザで通知が拒否されています。ブラウザの設定から許可してください」と書く
- 許可は端末（ブラウザ）ごとなので、サーバーには持たない

### 6. 通知の音

- 通知を出したときに短い音を鳴らす。**音の素材は持たず、Web Audio API で合成する**（ファイルとライセンスを持ち込まない）
- ユーザー設定の「通知」に「通知音」のオン・オフを置く。**端末ごとの好みなので localStorage**（テーマと同じ。ADR 0031）。既定はオン
- 自動再生の制限で鳴らせないとき（そのタブで一度も操作していない）は、黙って通知だけ出す

### 7. `Delivery` との関係

**配信先は増やさない。** ブラウザ通知は、既存の WebSocket の配信（`Delivery` の裏の Hub）で届いたイベントを、クライアントが通知に変えるだけ。
サーバーには何も足さない。Phase 7 で Push 通知を足すときは、サーバーの `Delivery` に配信先として加える（CLAUDE.md ルール 6）。
そのときも決定 1 の規則をサーバーで使えるよう、規則は ADR 0055 / 0056 に書いたとおりの形を保つ。

## 理由

- **クライアントで判定する理由**: 通知はタブが開いている間しか出せず、「どのタブも見えていない」はクライアントにしか分からない。
  設定もルーム一覧と参加中のスレッドとしてすでに手元にあり、サーバーに通知の経路を作る必要がない。
- **Web Locks でタブを 1 つに決める理由**: `tag` での置き換えだけだと、タブの数だけ音が鳴り、OS によっては通知が点滅する。
  ロックはタブが閉じられると自動で解放されるので、「通知係のタブ」が消えたまま残ることがない（ADR 0024 と同じ理由）。
- **音を合成する理由**: 短い通知音のために音声ファイルとそのライセンスを持ち込むより、数行の Web Audio で足りる。
- **差分で届いたメッセージを通知しない理由**: 再接続の直後に溜まった分を一斉に鳴らすと、通知として役に立たない（Slack が再接続の分をどう扱うかは未確認）。

## 検討した代替案

- **Service Worker と Web Push で出す**: タブを閉じていても届くが、購読の管理・VAPID の鍵・サーバーの配信先が要る。Phase 7 の範囲。
- **すべてのタブが出して `tag` で重複をまとめる**: 音と点滅が重なる。
- **`@here` でも通知する**: 通知を出す状況（どのタブも見えていない）では、自分は `@here` の対象になっていない（決定 1）。
- **本文を出さない**: オーナーの判断で不採用。

## 結果（トレードオフ）

- 表示中のワークスペースの通知しか出ない（購読の単位のため）。
- 再接続の差分で届いたメッセージは通知しない。切断中の新着は、未読とバッジで分かる。
- タブを全部閉じると通知は届かない（Push 通知は Phase 7 以降）。
