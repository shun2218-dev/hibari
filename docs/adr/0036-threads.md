# 0036. スレッド（返信をチャンネルのタイムラインから分け、ルームの seq を共有する）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6.5 では、メッセージへの返信をスレッドにまとめ、チャンネルのタイムラインを流れにくくする。
オーナーと確定している前提は次のとおり（ロードマップ、2026-09-17）。

- スレッドの返信はチャンネルのタイムラインに出さない
- スレッドの返信はチャンネルの未読数に数えない。スレッドは別に未読を持つ（参加しているスレッドの未読）
- 「チャンネルにも投稿する」は最初は作らないが、あとから足せる形にしておく
- Phase 6 の引用付きの返信（`reply_to_id`、`chat/composer-reply.png`）はスレッドに置き換える

フェーズの最初に決めることとして、スキーマ、seq、未読、配信、権限、画面が挙がっていた。

## 決定

### 順序と同期はルームの seq / change_seq を共有する

スレッドの返信も、チャンネルの投稿と同じ `UPDATE rooms ... RETURNING` で **ルームの `seq` と `change_seq` を採番する**。
「ルームの中の出来事は 1 本の列」という ADR 0002 / 0014 の形を保つ。

- `seq` の意味は「ルームの中の順序」。**チャンネルの通し番号ではない。** チャンネルだけを見ると、スレッドの返信の分だけ飛び飛びになる。
  欠落の検出は `change_seq` で行っていて（ADR 0014）、クライアントは `seq` の連続性に依存しない。これを今後も守る。
- スレッドの中の並びも `seq` で決める。
- 再接続の同期は、いまと同じ `GET /rooms/{id}/messages?after_change_seq=` の 1 本。返信も、編集も、削除も、親の返信数の変化も、全部ここで揃う。
  クライアントは受け取ったメッセージを `thread_root_id` の有無でチャンネルとスレッドに振り分ける。

### スキーマ

**messages**

| 列 | 内容 |
|---|---|
| `thread_root_id` | 親のメッセージの ID。チャンネルの投稿なら null。`(room_id, thread_root_id)` → `messages(room_id, id)` の複合 FK（`ON DELETE CASCADE`。メッセージの行が物理削除されるのはルームごと消えるときだけ） |
| `thread_seq` | スレッドの中で何番目の返信か（1 から）。返信の行だけが持つ。スレッドの未読に使う |
| `last_thread_seq` | 親の行だけが使う。`thread_seq` の採番カウンタ（減らない）。初期値 0 |
| `thread_reply_count` | 親の行だけが使う。削除されていない返信の数（表示用。返信の削除で減る）。初期値 0 |
| `thread_last_reply_at` | 親の行だけが使う。最後の返信の時刻（表示とスレッド一覧の並び用） |

- `thread_root_id` と `thread_seq` は両方 null か両方 non-null（CHECK）。`thread_root_id <> id`（CHECK）。
- 入れ子（返信への返信）と、システムメッセージを親にすることは、送信時に親の行をロックして確かめて拒む（CHECK では表せない）。
- インデックス
  - チャンネルのページング: `(room_id, seq DESC) WHERE thread_root_id IS NULL`。返信が多いルームでも、チャンネルの 1 ページを読むのに返信の行を読み飛ばさない
  - スレッドのページング: `(thread_root_id, seq) WHERE thread_root_id IS NOT NULL`
  - `UNIQUE (thread_root_id, thread_seq)`。採番は親の行ロックで直列にするので、これは最後の防御
- 既存の `messages_room_id_seq_idx`（`UNIQUE(room_id, seq)`）と `UNIQUE(room_id, change_seq)` はそのまま。

**rooms**

- `last_channel_seq` を足す。チャンネルのタイムラインに出る最後のメッセージ（人の発言とシステムメッセージ）の `seq`。
  ルーム一覧の「最終メッセージ」は `seq = last_channel_seq` の行を引く（いまは `last_message_seq` を引いているので、そのままでは返信が出てしまう）。
- スレッドの返信では `last_message_at` を更新しない。返信でサイドバーの並びが動かない（Slack と同じ）。

**thread_members**（スレッドへの参加と既読位置）

| 列 | 内容 |
|---|---|
| `room_id` / `thread_root_id` / `user_id` | 主キーは `(thread_root_id, user_id)` |
| `last_read_thread_seq` | 既読位置。未読数 = 親の `last_thread_seq - last_read_thread_seq` |
| `created_at` | |

- `(room_id, thread_root_id)` → `messages(room_id, id)`（`ON DELETE CASCADE`）
- **`(room_id, user_id)` → `room_members(room_id, user_id)`（`ON DELETE CASCADE`）。** ルームから抜けた・外された・ワークスペースから外れた人の参加は、DB が自動で消す。
  ルームのメンバーでない人がスレッドに参加している状態を、アプリのコードに頼らずに作らせない。
- `INDEX (user_id)`（スレッド一覧用）

**reply_to_id は消す**（オーナーと確認）

- `messages.reply_to_id` と `messages_reply_to_fkey` を削除する。既存の返信は、チャンネルの普通の投稿として残る（引用の表示だけが消える）。本番のデータはまだない。
- API とイベントの `reply_to` もなくなる。`chat/composer-reply.png` はスレッドの画面に置き換える。

### 未読

- **チャンネルの未読**: ADR 0033 の `user_seq` を「チャンネルの人の発言の数」と読み替える。スレッドの返信では `rooms.last_user_seq` を進めない（返信の行の `user_seq` は、直前の値をそのまま持つ）。
  未読数の式（`last_user_seq - last_read_user_seq`）は変わらず O(1)。
- **スレッドの未読**: `thread_seq` で同じ形にする。`last_thread_seq - last_read_thread_seq` で O(1)。
  削除された返信も数える（ADR 0002 と同じ、O(1) のための近似）。
- **自分の返信**で、自分の既読位置をその返信の `thread_seq` まで進める（チャンネルの送信と同じ）。

### スレッドへの参加（フォロー）

- 参加するのは **親の投稿者と、返信した人**（オーナーと確認）。明示的なフォロー / 解除の操作は、今回は作らない。
  - 返信した人: 送信と同じトランザクションで `thread_members` に入れる（既読位置は自分の返信）
  - 親の投稿者: 最初の返信のときに入れる（既読位置は 0。その返信が未読になる）。ルームを抜けていれば入れない（FK で入れられない）
- `thread_members` は「なぜ参加したか」を持たない。**メンションを作ったら、メンションされた人の行を同じテーブルに足すだけで、未読と通知の対象になる**（オーナーの想定。Slack と同じ）。
  手動のフォロー / 解除を足すときも、同じ行の追加・削除で表せる。

### 送信（返信）

ADR 0012 の送信に、手順 3・4・6 を足す。

1. 送信者の `room_members` の行を `FOR NO KEY UPDATE` でロックし、`CanWriteRoom` で判定する（いまと同じ）
2. `(room_id, sender_id, client_msg_id)` で既存を探す。あれば何も書かずに 200 で返す（いまと同じ。スレッドへの二重投稿もこれで防ぐ）
3. **親の行を `FOR NO KEY UPDATE` でロックする。** 見つからない・別のルーム → 422（`thread_root_id: invalid_value`）。親がシステムメッセージか返信 → 422（`thread_root_id: invalid_value`）
4. `UPDATE rooms`: `last_message_seq + 1`、`last_change_seq + 2`（返信と親の 2 つ分）。`last_user_seq`・`last_channel_seq`・`last_message_at` は進めない
5. `INSERT messages`（返信。`change_seq` は 1 つ目）
6. **親を更新する**: `last_thread_seq + 1`、`thread_reply_count + 1`、`thread_last_reply_at`、`change_seq`（2 つ目）。`RETURNING last_thread_seq` を返信の `thread_seq` にする
   （実装では 6 を 5 の前に行って `thread_seq` を得てから INSERT してよい。どちらも同じトランザクションの中）
7. `thread_members` に送信者（既読位置 = 自分の返信）と、最初の返信なら親の投稿者を入れる（`ON CONFLICT` で既存なら送信者の既読位置だけを進める）
8. コミットしてから配信する

- **ロックの順序は `room_members` → 親のメッセージ → `rooms` → `thread_members`。** 編集・削除の「`room_members` → メッセージ → `rooms`」（ADR 0012 / 0014）と同じ向きにそろえる。
  逆に `rooms` を持ったまま親の行を待つと、親の編集（親の行 → `rooms`）とデッドロックする。
- **削除済みの親にも返信できる。** ADR 0012 で削除済みへの返信を拒まなかった理由と同じ（削除と返信は並行して起きうるので、拒んでも結局生まれる）。親は tombstone のまま、スレッドは残る。

### 返信の編集・削除

- 権限はルームの規則（ADR 0012）をそのまま使う。スレッドのための別の規則は作らない。
- 返信の削除: 返信の行 → 親の行 → `rooms` の順にロックする。`thread_reply_count - 1` と親の `change_seq` を進める（`last_change_seq + 2`）。`last_thread_seq` は減らさない。
- 親の削除: いまの削除と同じ。返信には触らない。

### API

```
POST /api/v1/rooms/{id}/messages                        thread_root_id を受け取る（reply_to_id は廃止）
GET  /api/v1/rooms/{id}/messages                        チャンネルのタイムラインだけ（返信を含めない）。after_change_seq は返信も含めて返す
GET  /api/v1/rooms/{id}/threads/{rootID}/messages       スレッドの返信（before_seq / after_seq / limit。並びは seq の昇順）と、親のメッセージ
POST /api/v1/rooms/{id}/threads/{rootID}/read           スレッドの既読位置の更新（seq を受け取り、後退させない）
GET  /api/v1/workspaces/{id}/threads                    参加しているスレッドの一覧（最後の返信が新しい順、未読数つき）
```

- メッセージのレスポンスに `thread_root_id` / `thread_seq`、親には `thread`（`reply_count`・`last_reply_at`）を加える。`reply_to` は消す。
- スレッドの既読は、チャンネルと同じく `seq` を受け取り、サーバーが対応する `thread_seq` を引く（`seq` と `thread_seq` の取り違えを API に持ち込まない。ADR 0033）。
- スレッドの一覧のカーソルは `(thread_last_reply_at, 親の id)`。メッセージの順序ではなく「最近動いたスレッド」の表示の並びなので、時刻を使う（ADR 0002 が禁じているのはメッセージの順序とカーソルに時刻を使うこと）。
  返信のたびに並びが変わるので、ページをまたいだ取りこぼしや重複はありうる。一覧の件数は多くない前提で、`limit` の上限を設けてこれを受け入れる。
- ルーム一覧（`GET /workspaces/{id}/rooms`）に、未読のある参加中のスレッドの数を 1 つ足す（サイドバーの「スレッド」の表示用。1 回の集計で求める）。

### 配信（`docs/events.md`）

| type | 宛先 | いつ |
|---|---|---|
| `message.created` | room | 返信も同じ。`thread_root_id` で見分ける |
| `message.updated` | room | 本文の編集に加えて、**親の `thread`（返信数・最終返信）が変わったとき** |
| `thread.read` | 本人 | 自分のスレッドの既読位置が進んだ（別の端末を含む） |
| `thread.followed` | 本人 | 自分がスレッドに参加した（自分の返信・自分の投稿への最初の返信） |
| `typing.started` | room | `thread_root_id` を足す。スレッドで入力中の人をチャンネルには出さない |

- 返信はルームの購読者に届ける（スレッドの参加者だけに絞らない）。スレッドを開いている人も、親の返信数を見ている人も、同じルームの購読で受け取れる。
  絞ると「スレッドの購読」という新しい単位が増え、ADR 0015 の購読の authz と再接続の手順がもう 1 系統要る。
- `thread.followed` を送るのは、「誰が参加しているか」をサーバーだけが決めるため。クライアントに「自分が返信した・自分の投稿だ」と判定させると、メンションを足したときにクライアント側の規則もずれる。

### 権限

- スレッドを読める・返信できるかは、親のルームの `CanReadRoom` / `CanWriteRoom` だけで決まる。スレッドのための権限は持たない。
- DM でもスレッドを作れる。
- 参加していない public のルームのスレッドは読めるが、返信できない（チャンネルと同じ）。

### 画面

`docs/ui/` にないので、実装の前に既存のトークンで描いて `docs/ui/` に足す（オーナーと確認。撮り方は ADR 0032 と同じ）。
描くもの: スレッドのパネル（デスクトップは右、モバイルは全画面）、親のメッセージの「N 件の返信」、サイドバーの「スレッド」の入口と一覧、
スレッドの入力欄と入力中、削除された親、返信が 0 件のパネル。引用付きの返信（`chat/composer-reply.png`）は消す。

## 理由

### ルームの seq を共有する理由（スレッドごとの番号と比べて）

- **「チャンネルにも投稿する」を後から足しやすい。** チャンネルに流す返信は、チャンネルの並びの中の位置が要る。
  ルームの seq をもともと持っていれば「チャンネルにも出す」フラグを 1 つ足すだけで済む。スレッドごとの番号だと、その返信にだけ後からルームの seq も振ることになり、1 つのメッセージに 2 つの順序の体系が付く。
- **同期がルームの数で決まる。** 再接続はルームごとに `after_change_seq` を 1 回呼ぶだけで、スレッドの数に比例しない。障害のときに追う列も 1 ルームに 1 本。
- **スレッドごとの番号にしても、ルームの行ロックと change_seq からは逃げられない。** 見ていないスレッドに返信が来たことは、親の返信数の変化としてルームの差分で受け取るしかないので、ルームの change_seq は進める必要がある。
  そのうえでスレッドの中の返信・編集・削除用に、スレッドごとのカーソルと差分取得の API がもう 1 系統要る（同期が 2 段になる）。スループットの利点も実際にはほぼない。
- **メンションや通知を足しても、「このルームでどこまで処理したか」を 1 つの番号で表せる。** 監査やエクスポートでもルームの出来事を 1 本の順序で出せる。

### その他

- **`thread_seq` を別に持つ理由**: スレッドの未読を O(1) にするため（ADR 0033 の `user_seq` と同じ考え方）。順序の根拠にはしない。
- **`thread_reply_count` と `last_thread_seq` を分ける理由**: 表示の「N 件の返信」は削除で減ってほしいが、未読の番号は減ると既読位置との引き算が壊れる。
- **`last_channel_seq` を持つ理由**: ルーム一覧の最終メッセージを「チャンネルの最後の行」にするため。`WHERE thread_root_id IS NULL ORDER BY seq DESC LIMIT 1` をルームごとに引くのは LATERAL で書けるが、1 行の JOIN で引ける形を保つ（ADR 0012）。
- **`thread_members` を `room_members` に FK でつなぐ理由**: ルームから外れた人の後片付けを、キック・退出・ワークスペースの離脱のそれぞれに書かずに済む。書き忘れると、読めないスレッドの未読が残る。

## 検討した代替案

- **スレッドごとに別の番号（順序と同期の根拠）を持つ**: チャンネルの seq は連続したまま保てるが、上の理由で不採用（オーナーと比較して確認）。
- **`reply_to_id` を残し、スレッドと並べる / 既存の返信をスレッドに変換する**: 仕組みが 2 つ並ぶ、または変換で既存の返信がタイムラインから消える。本番のデータがないので、消すのが単純（オーナーと確認）。
- **スレッドを開いた人も参加者にする**: 見ただけで未読の対象が増える。明示的なフォローと一緒に、必要になってから足す。
- **返信をスレッドの参加者にだけ配信する**: 帯域は減るが、親の返信数の表示のために結局ルームへの配信が要り、購読の単位も増える。
- **親の返信数を返信の数え上げ（`COUNT(*)`）で出す**: 一覧で N+1 か、重い集計になる。

## 結果（トレードオフ）

- チャンネルの `seq` は飛び飛びになる。「seq の欠番 = 取りこぼし」の判定は使えない（もともと使っていない）。
- 返信 1 件で `change_seq` を 2 つ消費し、親の行も更新する。親の行（とインデックス）の書き込みが返信のたびに発生する。
- 返信も `rooms` の行ロックを取るので、同じルームの送信とスレッドの返信はすべて直列になる（ADR 0002 と同じ上限）。
- ルームの購読者は、開いていないスレッドの返信の本文も受け取る。
- 未読の番号が `user_seq` と `thread_seq` の 2 つに増える。どちらも「採番カウンタ - 既読位置」の同じ形にそろえて、取り違えを減らす。
- 既存の引用付きの返信は、引用の表示を失う。

## 追記

### 2026-09-19 API の細部（Phase 6.5 の構築順 3）

- メッセージの `thread` は `reply_count`・`last_reply_at` に加えて `last_thread_seq` を持つ。クライアントは自分の既読位置との差で、スレッドの未読をイベントだけで求め直せる。
  `thread` は一度でも返信がついた親にある（全部削除されて `reply_count` が 0 でも残す。スレッドは開ける）。
- `GET /rooms/{id}/threads/{rootID}/messages` は `root`・`messages`・`has_more`・`last_change_seq` と、自分の既読位置 `last_read_thread_seq`（参加していなければ null）を返す。
  返信やシステムメッセージを `rootID` に指定したら 404。
- `POST /rooms/{id}/threads/{rootID}/read` は、参加していないスレッドでもエラーにせず `following: false` を返す（参加していないスレッドを開くのは普通のことなので）。
- 参加中のスレッドの一覧のカーソルは、ほかの一覧と同じ `?after=<ID>`（前のページの最後の親の ID）。サーバーがその親の `(thread_last_reply_at, id)` を引いて比べる。
- ルーム一覧のバッジの数は `unread_thread_count`。
- 返信の送信では、送信者のチャンネルの既読位置を進めない（返信はチャンネルに出ていない）。
- **Web の暫定の状態**: API から `reply_to` を消したので、Web の引用付きの返信（入力欄の返信先、メッセージの引用の行）も同じ PR で取り除いた。
  スレッドを開く「返信」は、スレッドの画面をつなぐ構築順 5 まで出さない。同期で届いた返信はチャンネルのタイムラインに出さず、ルームの未読・最後のメッセージ・並びも動かさない。
