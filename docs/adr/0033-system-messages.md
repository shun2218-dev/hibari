# 0033. システムメッセージ（参加・退出・作成・名前の変更をチャンネルのログに残す）

- 状態: 採用
- 日付: 2026-09-19

## 背景

Phase 6 を通しで触ったオーナーから、「チャンネルに参加したことがチャンネルのログに残ってほしい」「チャンネル名を変えたら、
誰が何に変えたのかが出ると Slack らしい」という要望が出た。いまは参加も名前の変更も WebSocket のイベント
（`member.joined` / `room.updated`）で画面に反映されるだけで、**あとから開いた人には何も残らない**。

決めることは 4 つ。

1. どこに持つか（メッセージと同じ行か、別のテーブルか）
2. 未読数にどう影響させるか
3. どの操作を残すか
4. 画面にどう出すか（デザインにない）

## 決定

### メッセージの行として持つ

`messages` に `kind`（`user` / `system`）を足し、**システムメッセージも 1 行のメッセージとして seq を採番して入れる**。

| 列 | 内容 |
|---|---|
| `kind` | `user`（人の発言）/ `system`（ログ）。既定は `user` |
| `system_type` | `room_created` / `member_joined` / `member_left` / `member_removed` / `room_renamed` |
| `system_data` | `jsonb`。いまは `room_renamed` の `old_name` / `new_name` だけ |
| `user_seq` | その時点までの **人の発言の数**。未読数に使う（下記） |

- `sender_id` は **その行の主語**にする。参加・退出・外された行の sender は「その人」、作成・名前の変更の行の sender は「操作した人」。
  こうすると、一覧のクエリは送信者を JOIN するだけで文を組み立てられる（対象者を別に JOIN しない）。
- `body` は空にする。文言はクライアントが `system_type` と `system_data` から作る（時刻の文言と同じ考え方。ADR 0018）。
- `client_msg_id` はサーバーが ULID を生成して入れる。冪等性の仕組み（`UNIQUE(room_id, sender_id, client_msg_id)`）はそのまま。
- システムメッセージは **編集・削除・返信ができない**（サーバーが 403 で拒む）。掃除や tombstone も持たない。

### 未読数はシステムメッセージを数えない

未読は `rooms.last_message_seq - room_members.last_read_seq` の引き算で O(1) に求めている（ADR 0002）。
システムメッセージも seq を採番するので、そのままでは「誰かが参加した」だけでバッジが増える。
**人の発言だけを数える番号（`user_seq`）を並走させる。**

- `messages.user_seq`: その行までの人の発言の数。`kind = 'user'` の行で 1 増え、`kind = 'system'` の行は直前の値をそのまま持つ。
- `rooms.last_user_seq`: 人の発言の総数（採番の元）。
- `room_members.last_read_user_seq`: 既読位置（`last_read_seq`）に対応する `user_seq`。
- **未読数 = `rooms.last_user_seq - room_members.last_read_user_seq`。** 引き算のままなので O(1)。

既読を進めるとき（`AdvanceLastReadSeq`）は、`seq <= 新しい既読位置` の中で最大の `user_seq` を 1 回のインデックス走査で引いて入れる。
**順序と表示は `seq`、未読数は `user_seq`** と役割を分ける。削除済みのメッセージを数える近似（ADR 0002）は変えない。

### 残す操作

| system_type | いつ | 文言 |
|---|---|---|
| `room_created` | public / private のルームを作った | 「{sender} がこのチャンネルを作成しました」 |
| `member_joined` | 自分で参加した・追加された・招待の受け入れで既定のルームに入った | 「{sender} がチャンネルに参加しました」 |
| `member_left` | 自分でルームを抜けた | 「{sender} がチャンネルを退出しました」 |
| `member_removed` | 他人にルームから外された | 「{sender} がチャンネルから外されました」 |
| `room_renamed` | 名前が変わった | 「{sender} がチャンネル名を {old_name} から {new_name} に変更しました」 |

- **DM には出さない**（メンバーが固定で、名前もない）。
- **ワークスペースから外れた（キック・退出）ときは、各ルームに出さない。** 1 回の操作で所属していた全ルームに行が増え、
  その数だけ `rooms` の行ロックと採番が要る。チャンネルの出来事としては「ワークスペースを抜けた」であって、
  チャンネルごとのログにする価値が薄い。
- 作成者の `member_joined` は出さない（`room_created` があれば分かる）。
- 名前が変わらない更新（同じ名前で保存、`is_default` だけの変更）では出さない。

### 配信と画面

- 配信は既存の `message.created`（`docs/events.md`）。クライアントはメッセージとして受け取り、`change_seq` の同期もそのまま効く。
- ルーム一覧の `last_message` にも出る（サイドバーの 1 行に「参加しました」などが出る）。プレビューにも `kind` と `system` を載せる。
- 画面はデザインにないので、**日付の区切りと同じ中央寄せの控えめな 1 行**として足す（`chat/system-messages.png`）。
  撮り方は ADR 0032 と同じ（`/dev/preview` を headless Chrome で撮る）。

## 理由

- **別テーブルにしない理由**: 順序（seq）、ページング、`after_change_seq` の同期、配信、タイムラインの描画が、メッセージにはすでに全部ある。
  別テーブルにすると、同じ画面に出す 2 つの流れを時刻でマージすることになり、ADR 0002 の「順序は seq だけで決める」が崩れる。
- **`user_seq` を持つ理由**: 「人の発言だけ数える」を後から数え直すと `COUNT(*)` になり、ルーム一覧で N+1 になる。
  番号を 2 つ持てば引き算のままで済む。`seq` を人の発言だけに使う案（システムメッセージに seq を振らない）も考えたが、
  それでは順序が決められず、差分取得の対象からも外れる。
- **sender を主語にする理由**: 「誰が誰を」を出すには対象者のプロフィールをもう 1 回 JOIN する必要がある。
  外した人の名前を出さないのは、権限の強い人が誰かを一覧から推測させないためでもある。
- **文言をクライアントで作る理由**: 表示の文言を変えるたびに DB の行を書き換えたくない。`system_data` には名前のような
  「そのときの値」だけを入れる。

## 検討した代替案

- **クライアントだけで出す（WebSocket のイベントから作る）**: 開き直すと消える。履歴にならない。
- **未読数を「数える」ままにする**: 実装は何も要らないが、誰かが参加しただけでバッジが増える（オーナーと確認して不採用）。
- **システムメッセージに `seq` を振らない**: 並びと差分取得の根拠がなくなる。
- **`room_renamed` に old/new を持たず、変更後の名前だけ持つ**: 「何から何に」が出せない。名前は変わるので、そのときの値を残す。
- **ワークスペースのキックでも各ルームに残す**: 正確ではあるが、1 操作で多数の行ロックと採番が発生する。

## 結果（トレードオフ）

- `messages` の行が増える。ページの 50 件にシステムメッセージが混ざるので、人の発言だけを見たい人には 1 ページの情報量が減る。
- 未読の番号が 2 つになり、送信と既読の経路が少し複雑になる（`seq` と `user_seq` を取り違えるとバグになる）。
- サイドバーの最後の 1 行が「参加しました」になることがある。Slack も同じ挙動。
- 既存の行には `user_seq` を移行で埋める（`seq` の順に数え直す）。移行の後は、人の発言の数と `rooms.last_user_seq` が一致する。
- ワークスペースから外れた人は、各チャンネルのログには残らない（ルームから外されたときだけ残る）。
