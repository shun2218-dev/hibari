# 0066. 音声のハドル（Phase 6.18a。音声は必ず Cloudflare Realtime の SFU を通し、合図と参加の状態は Go が持つ）

- 状態: 採用
- 日付: 2026-09-26

## 背景

オーナーの要望（2026-09-26）。Slack のハドルミーティングのような通話を足したい。外部のサービスは Cloudflare のものを使う。

### オーナーと確定したこと（2026-09-26）

- **Cloudflare Realtime の SFU と TURN を使う。** 同じ Cloudflare の RealtimeKit（会議・参加者・権限の仕組みと SDK を持つ高水準のサービス）と、以前の検討で挙げた LiveKit は採らない。
- **範囲は Slack のハドルと同じく、DM とチャンネルの両方。** 1 対 1 だけに絞らない。
- **音声を先に作る（6.18a。この ADR）。カメラと画面共有は後（6.18b）で、別の ADR にする。**
  いちばん難しいのは通話の状態の管理（始まる・入る・抜ける・切れる・外される）なので、そこを音声だけで先に固める。

### Cloudflare の 3 つのサービス（2026-09-26 に公式のドキュメントで確かめた）

| | RealtimeKit | Realtime SFU | TURN |
|---|---|---|---|
| 何か | 会議・参加者・プリセット（権限）の仕組みと、Web / モバイルの SDK と UI 部品 | WebRTC の中継サーバー（SFU）の低水準な HTTPS API。部屋の概念はなく、**セッション**（1 本の `RTCPeerConnection`）と**トラック**だけ | NAT やファイアウォールを越えられないときの中継 |
| 合図・状態・誰が入れるか | Cloudflare が持つ | **こちらのサーバーが全部持つ** | — |
| 料金 | ベータの間は無料。正式版の予定は参加者 1 人あたり月 10,000 分まで無料、その後 0.002 ドル/分 | 送り出した量だけ 0.05 ドル/GB。**SFU と TURN を合わせて月 1,000 GB まで無料**。送り込む量と STUN は無料 | SFU と共通 |
| ローカルで動く版 | ない | ない | ない |

SFU の API の要点（`https://rtc.live.cloudflare.com/v1`、`Authorization: Bearer <アプリの秘密>`）。

- `POST /apps/{appId}/sessions/new` でセッションを作る。応答は `{ "sessionId": "..." }`。
- `POST …/sessions/{sessionId}/tracks/new` で、自分のトラックを**送る**（`location: "local"`。ブラウザの offer を渡すと answer が返る）か、
  ほかのセッションのトラックを**受ける**（`location: "remote"` と相手の `sessionId` / `trackName`。SFU から offer が返るので、ブラウザの answer を `PUT …/renegotiate` で返す）。
- `PUT …/tracks/close` でトラックを閉じる。`force: true` なら SDP なしで閉じられる。
- **1 つのセッションへの変更は直列にしなければならない**（前の要求と SDP のやり取りが終わる前に次を送ると 406）。
- 30 秒メディアが流れないトラックは片付けられる。WebRTC の接続が切れたセッションも 30 秒で使えなくなる。
- **切れたことをこちらに知らせる仕組み（webhook など）はない。** 公式のベストプラクティスは「明示的に抜ける呼び出しと、アプリ側の期限切れの両方を持つ。タブは片付けを送らずに閉じることがある」。
- 公式の例（Orange Meets）も、部屋の状態は自前の WebSocket で配り、15 秒の心拍が途絶えた人を外している。話している人の判定はクライアントがしている。

TURN の認証情報は `POST /turn/keys/{keyId}/credentials/generate-ice-servers`（`{ "ttl": 秒 }`、最長 48 時間）で発行する。
応答の `iceServers` をそのまま `RTCPeerConnection` に渡せる。ブラウザが弾くポート 53 の URL が混ざるので取り除く。`…/credentials/{username}/revoke` で取り消せる。

### Slack のハドルの振る舞い（2026-09-26 に公式のヘルプで確かめた）

| | 公式のヘルプの記述 |
|---|---|
| 始める | どのチャンネルでも DM でも、会話のヘッダーのヘッドフォンのアイコンから始める。始めると会話のメンバー全員が参加できる。どのハドルも音声だけで始まる |
| 見え方 | 参加しているチャンネルなら、サイドバーのチャンネル名の横にヘッドフォンのアイコンが出る。会話には「参加する」ボタン付きのメッセージが出る |
| DM | 相手にはポップアップの「参加」が出る |
| 終わり | 始めた人を含めて誰でもいつでも抜けられる。**最後の人が抜けると自動で終わる** |
| 残るもの | 「ハドルが始まった」メッセージとそのスレッドが会話に残る |
| 人数 | 有料プランは 50 人まで（ビデオは同時に 25 人まで）。フリープランは 2 人まで |
| 機能 | ミュート、ノイズの抑制、「常にミュートで参加する」の設定、カメラ、画面共有（同時に 2 人まで）、絵文字のリアクション、スレッド、トピック、音楽、字幕 |
| 権限 | 既定では、ワークスペースのメンバーなら誰でも始められる。管理者はチャンネルごとに無効にできる（有料プラン） |
| ショートカット | ハドルの開始・参加・退出は ⌘⇧H、ミュートの切り替えは ⌘⇧Space |
| ステータス | 環境設定で、ハドル中はステータスを「ハドルミーティング中」にできる |

ヘルプに書いていなかったことは、**オーナーが Slack の実物をもとに答えた**（2026-09-26）。

| | オーナーの回答 | この ADR |
|---|---|---|
| DM の呼び出し音 | 鳴る。何秒で止まるかは分からないが、合わせなくてよい。1 分くらいでよい | 60 秒で止める（決定 11） |
| 拒否のボタン | ない気がする。代わりに「もうすぐ参加する」のボタンがあり、押すと呼び出し音が止まる。待っている側にも、もうすぐ参加する旨が出たと思う | 「参加」と「もうすぐ参加する」（決定 11） |
| 出なかったとき | 不在着信が残る | 決定 12 |
| 1 人だけ残ったとき | 続けられる | 最後の人が抜けるまで続く（決定 5） |
| 同時に 2 つのハドル | 分からないが、需要がないので合わせなくてよい | 1 人 1 つ（決定 6） |
| 終わった後のメッセージ | 所要時間と参加者が出る。参加者は自分を含めて 2 人まで名前が出て、それより多ければ「ほか N 人が参加しました」 | 決定 12 |
| 人数の上限 | 50 人は多すぎる。無料のアプリなのに有料プランの上限に合わせるのはおかしい。多くても 20 人くらい | 20 人（決定 7） |

**まだ確かめていないこと**: 話している人の表示の形、アーカイブしたチャンネルでの扱い。どちらも Slack に合わせる根拠がないので、この ADR で決める（決定 10・7）。

## 決定

### 1. DM の 1 対 1 も含めて、音声は必ず SFU を通す

- 1 対 1 でも P2P（ブラウザどうしを直接つなぐ形）にしない。1 対 1 も 20 人も同じ経路にする。
- **相手に自分の IP アドレスが見えない。** P2P だと ICE の候補に互いのアドレスが載る。SFU を通せば、見えるのは Cloudflare のアドレスだけ。
- 費用は無料の枠に十分に収まる（「結果」の見積もり）。

### 2. アプリの秘密は Go が持ち、SFU の API は Go が中継する

- ブラウザは Cloudflare の API を直接呼ばない。Go に SDP を渡し、Go がアプリの秘密を付けて SFU を呼び、結果の SDP を返す。
- **音声そのものは Go を通らない**（ブラウザ ⇄ Cloudflare）。Go が扱うのは SDP（数 KB）と状態だけ。ファイルの中身を Go に通さないルール 10 と同じ考え方にする。
- **誰の音声を受けられるかを Go が決める**（決定 9）。ブラウザはアプリの秘密を持たないので、Go が許していないトラックを自分で受けに行けない。
  権限が変わったら、Go が Cloudflare に「このセッションのトラックを閉じる」と頼めば、その人はもう聞けない（決定 8）。
  RealtimeKit ではここを Cloudflare が持つが、SFU を選んだので、判断を authz に集めるルール 9 と、すぐに反映するルール 8 をそのまま守れる。
- クライアントには Cloudflare のセッション ID を見せない。API はユーザー ID と参加 ID で話す（Cloudflare の語彙を API に漏らさない）。

### 3. ハドルはルームに同時に 1 つ。履歴は Postgres、いま入っている人は Redis

- ルームごとに、進行中のハドルは 1 つまで。Postgres の部分 UNIQUE 制約で保証する（`huddles(room_id) WHERE ended_at IS NULL`）。
  2 人が同時に「始める」を押しても 1 つになり、後の人はそのハドルに入る。
- **Postgres に置くもの**（残らなければ困る履歴）
  - `huddles`: ルーム、始めた人、始めた時刻、終わった時刻、会話に残すメッセージ（決定 12）
  - `huddle_participants`: そのハドルに**一度でも入った人**と、最初に入った時刻。メッセージの参加者の表示に使う。人ごとに 1 回だけ書く
- **Redis に置くもの**（自動で変わる状態。ルール 5）
  - いま入っている人の一覧（参加 ID ごとに、ユーザー ID・sid・Cloudflare のセッション ID・トラック名・ミュート）と、心拍の期限
  - ハドルの状態の版（`huddle.updated` の順序を決める。決定 13）
  - ユーザーごとの「いま入っているハドル」（決定 6）
- 名前はコードも UI も「ハドル（huddle）」にする。「call」は関数の呼び出しと紛らわしい（ルームを room と呼ぶのと同じ理由）。UI の文言（Slack は「ハドルミーティング」）はデザインで決める。

### 4. 入る・抜けるの API

```
POST   /api/v1/rooms/{roomID}/huddle/ice-servers
       → { "ice_servers": [...], "expires_at": "..." }
POST   /api/v1/rooms/{roomID}/huddle/participants          入る（進行中のハドルがなければ始める）
       { "offer": "<SDP>" }
       → 201 { "huddle": {...}, "participant_id": "01J...", "answer": "<SDP>" }
POST   /api/v1/huddles/{huddleID}/participants/{participantID}/subscriptions     ほかの人の音声を受ける
       { "user_ids": ["01J...", ...] }
       → { "offer": "<SDP>", "tracks": [{ "user_id": "01J...", "mid": "3" }, ...] }
PUT    /api/v1/huddles/{huddleID}/participants/{participantID}/renegotiate
       { "answer": "<SDP>" }
POST   /api/v1/huddles/{huddleID}/participants/{participantID}/subscriptions/close   抜けた人の受信を閉じる
       { "mids": ["3"] }
PATCH  /api/v1/huddles/{huddleID}/participants/{participantID}                      ミュート
       { "muted": true }
DELETE /api/v1/huddles/{huddleID}/participants/{participantID}                      抜ける
```

- **ICE サーバーを先に取る。** ブラウザは `RTCPeerConnection` を作る時点で TURN の情報が要る。ここにも authz（決定 7）をかけ、ルームに入れない人には TURN の認証情報を出さない。
- **「入る」は、自分の音声を送り始める要求と同じにする。** Go は Cloudflare にセッションを作り、ブラウザの offer でマイクのトラックを送る設定をし、answer を返す。
  **それが成功してから**参加の状態を書いて配る。Cloudflare の呼び出しに失敗したときに、誰もいないハドルや音の出ない参加者が残らないようにするため。
- **ネットワークを待つ間はトランザクションを持たない**（ADR 0065 決定 10 と同じ）。Cloudflare の呼び出しを先に済ませ、その後の短いトランザクションで、
  進行中のハドルの行をロックして参加を書く（ハドルがその間に終わっていたら新しく始める）。「最後の人が抜けて終わる」と「入る」が同時に起きても、
  このロックで順番が決まり、終わったハドルに入ってしまうことはない。
- 参加 ID（ULID）は「この端末のこの参加」を指す。同じ人が別の端末から入り直すと参加 ID が変わり、古い参加 ID への要求は 409 になる（決定 6）。
- 1 つの Cloudflare のセッションへの変更は直列にしなければならない。**直列にするのはクライアント**（端末ごとに SDP のやり取りを 1 本の列に並べる）。
  サーバーは Cloudflare の 406 を 409 `huddle-negotiation-conflict` に変え、クライアントはやり直す。
  複数台の Go のどこに要求が届いても、同じ端末の要求は 1 本の列から来るので、サーバーにロックは要らない。
- 抜けるときは `DELETE`。タブを閉じるときも `pagehide` で `fetch(..., { keepalive: true })` を送る。届かなかったときは心拍の期限（決定 5）で外れる。

### 5. 生きているかは心拍で決め、期限切れは自前の掃除のジョブで見つける

- クライアントは入っている間、WebSocket で 10 秒ごとに心拍を送る（`huddle_heartbeat`、`participant_id` 付き）。サーバーは期限を 30 秒先に延ばす。
  REST にしないのは、すでに認証済みの接続があり、小さな定期的なメッセージは入力中の通知（`typing`）と同じ経路が合うため。
- 心拍の ack が `not_found` なら、クライアントは自分がもう外れたと分かるので、接続を片付けて「切断されました」を出す（WebSocket が長く切れていた場合など）。
- **Redis の期限切れはイベントにならない**（ADR 0049 の presence と同じ）。ただしハドルでは、消えた人をほかの人の画面から消し、最後の人が消えたらハドルを終わらせる必要がある。
  そこで、期限はハッシュの TTL ではなく**ソート済みセット（スコアが期限の時刻）**に持ち、掃除のジョブが 5 秒ごとに期限を過ぎた参加を Lua で取り除き、取り除いたものだけを配る。
  取り除くのは Lua の中なので、複数台で同時に動いても 1 台だけが同じ参加を片付ける。時刻は `Clock` から取る（テストで固定する）。
- 抜け方の区別なく、参加を外すときは Cloudflare のそのセッションのトラックを `force: true` で閉じる。
- タブが突然閉じた場合、ほかの人の画面から消えるまで最長で約 35 秒かかる（期限 30 秒と掃除の間隔 5 秒）。公式の例（最長 45 秒）より短い。

### 6. 1 人が入れるハドルは同時に 1 つ。別の端末から入ると移る

- 別のハドルに入ると、いまのハドルからは抜ける。同時に 2 つに入る需要はない（オーナーの判断。Slack に合わせなくてよい）。画面に出すハドルの窓も 1 つで済む。
- 同じハドルに別の端末から入ると、**前の端末の参加は外れて、新しい端末に移る。** 前の端末には `huddle.left`（`reason: "moved"`）が届く。
  同じ人が 2 台で入るとハウリングし、参加者の一覧に同じ人が 2 回並ぶため。
- 「いまどのハドルに入っているか」はユーザーごとの Redis のキーに持つ（心拍で延ばす）。

### 7. 入れるのは、そのルームに投稿できる人（authz に集める）

- `authz.CanJoinHuddle` を足す。中身は `CanWriteRoom` と同じ（ルームのメンバーで、アーカイブされていない）。始めるのも入るのも同じ判定にする。
  - public のチャンネルを読めるだけの人（参加していない人）は入れない。先にチャンネルに参加する。
    Slack はメンバーでない人を招待できるが、この ADR ではメンバーでない人の招待は作らない（「やらないこと」）。
  - アーカイブしたルームでは始められない（409 `room-archived`。ADR 0059）。**アーカイブした時点で進行中のハドルは終わらせる。** ルームを削除したときも同じ。
- ICE サーバー・入る・受ける・心拍のどれでも、参加 ID がそのユーザーのもので、まだハドルに入っていることを確かめる。受ける要求（決定 9）では、相手も同じハドルにいることを確かめる。
- **人数の上限は 20 人**（オーナーの判断）。Slack の有料プランの 50 人は、無料のこのアプリには多すぎる。超えたら 409 `huddle-full`。

### 8. 権限が変わったら、すぐにハドルから外す（ルール 8）

- 次のことが起きたら、該当する人をそのルームのハドルからすぐに外す。
  - ワークスペースからのキック・退出（そのワークスペースの全ハドル）
  - private のルームからの削除、ルームからの退出
  - アーカイブ・削除（そのルームのハドルの全員）
  - セッションの失効（ログアウト、Refresh Token の再利用の検知）。参加に sid を持たせ、失効した sid の参加を外す
- 外すときは、Cloudflare のそのセッションの**送るトラックも受けるトラックも**閉じる。ブラウザはアプリの秘密を持たないので、受け直すことはできない（決定 2）。
  TURN の認証情報も取り消す。
- 外された本人には `huddle.left`（`reason: "removed"`）、ルームには `huddle.updated` を配る。
- 仕組みは既存の `AccessChanges`（ADR 0015）と同じ場所から呼ぶ。ルームのメンバーであることが条件なので、ロールの変更だけでは外れない。

### 9. 誰の音声を受けるか

- 入った人は、**ほかの参加者全員の音声を受ける**（音声は小さいので、全部を受けても 20 人で約 1 Mbps）。
- `huddle.updated` で新しい参加者が届いたら、クライアントはその人の音声を受ける要求を出す。抜けた人の分は閉じる。
- Go はユーザー ID を、相手の参加の Cloudflare のセッション ID とトラック名に引き直して SFU に頼む。呼んだ人と相手が同じハドルにいなければ 403。
- 受ける前に相手が抜けた、などで一部のトラックに失敗したら、成功したものだけを返す（Cloudflare も 200 の中にトラックごとの失敗を返す）。

### 10. ミュートと話している人

- ミュートはブラウザでトラックを止める（`track.enabled = false`）。サーバーに知らせる（`PATCH`）のは、ほかの人の画面にミュートの印を出すため。
  **サーバーはミュートを強制しない**（止めているのは本人のブラウザ）。管理者がほかの人をミュートする操作は作らない。
- **話している人の判定はクライアントでする。** 受けた音声と自分のマイクの音量を Web Audio で測り、しきい値を超えた人に印を付ける。
  サーバーは関わらないので、話すたびにイベントを流さない（公式の例とも同じ。Cloudflare の SFU は話している人を教えてくれない）。
- マイクはブラウザのノイズの抑制・エコーの除去・音量の自動調整を有効にして取る（`getUserMedia` の制約。Slack のノイズの抑制に当たる）。

### 11. DM では相手を呼び出す

- DM でハドルが始まったら、相手（まだ入っていない方）のすべての接続に `huddle.ringing` を配る。チャンネルでは呼び出さない（Slack と同じ）。
- 呼び出しの画面には「参加」と「もうすぐ参加する」を出し、着信の音を鳴らす（ADR 0057 の通知の音と同じく Web Audio で作る）。
  **拒否のボタンは作らない**（Slack にない。オーナーの回答）。
- **60 秒で止める**（オーナーの判断。Slack の秒数には合わせない）。相手が入った・「もうすぐ参加する」を押した・ハドルが終わった・別の端末で参加か「もうすぐ参加する」を押した、でも止める。
- **「もうすぐ参加する」を押すと、ハドルに入っている人の画面に「〜さんがもうすぐ参加します」と出る。**
  - `POST /api/v1/huddles/{huddleID}/joining-soon` で知らせる。Redis に TTL 5 分で置き、ハドルの状態（決定 13）の `joining_soon` に載せる。
    自動で消える一時的な状態なので Postgres に書かない（ルール 5）。本人が入ったら消す。
  - 5 分はオーナーの確認済み（2026-09-26。Slack で表示がいつ消えるかは未確認）。
- どのタブも見えていないときは、ブラウザの通知も出す（ADR 0057 の条件と通知係に乗せる）。**ミュートした DM では呼び出さない**（ADR 0057 の「ミュートでは出さない」と同じ）。
- 出なかったとき、別の「不在着信」のメッセージは書かない。DM のハドルのメッセージ（決定 12）が、入らなかった人には不在着信として見える。

### 12. 会話にハドルのメッセージを残す

- ハドルが始まったら、会話にシステムメッセージ（ADR 0033）を 1 件書く。種類は `huddle`、データはハドルの ID。
  - **DM にも書く。** ADR 0033 は DM にシステムメッセージを書かないと決めたが、Slack は DM にもハドルのメッセージを残し、そこから入れる。例外として足す。
  - 既存のシステムメッセージと同じく `seq` を使う。チャンネルでは `user_seq` を進めないので未読にならない（DM は下の不在着信のため例外）。
- メッセージの `huddle` に、始めた人・始めた時刻・終わった時刻・参加した人（`huddle_participants`）を載せる。
  **一度も入っていなかった人が入ったとき**と**終わったとき**に、`change_seq` を進めて `message.updated` を配る。再接続の同期でもそろう（ルール 4）。
  入ったり抜けたりのたびには進めない（いま入っている人は `huddle.updated` で配る）。
- 進行中はメッセージに「参加」のボタンを出す。終わった後は所要時間と参加した人を出す（オーナーの回答にある Slack の形）。
  - 参加した人は、**自分を含めて 2 人まで名前を出し、それより多ければ「ほか N 人が参加しました」**。自分が参加していれば自分を先に出す。
  - 見る人で名前の並びが変わるので、並べるのは Web（メッセージには参加した人の ID を全部載せる。20 人までなので小さい）。
- **DM の不在着信**: DM のハドルが、相手が一度も入らないまま終わったら、そのメッセージは入らなかった人には「不在着信」として見える。
  始めた人には「応答なし」として見える。どちらも同じメッセージの見え方の違いで、参加した人の一覧から Web が決める。文言はデザインで決める。
- **DM のハドルのメッセージだけは未読に数える**（オーナーの確認: 2026-09-26）。不在着信に気づけるようにするため。
  - 送信と同じく、`user_seq` を進め、始めた人の既読位置も進める。こうすると、DM の相手にだけ未読が 1 つ付く（ADR 0033 の「システムメッセージは `user_seq` を進めない」の例外）。
  - チャンネルでは数えない。ハドルが始まるたびに全員のチャンネルが未読になるのを避けるため。
  - Slack の不在着信が未読になるかは未確認。
- ハドルのスレッドは作らない（「やらないこと」）。

### 13. イベントと再接続の同期

| type | 宛先 | いつ |
|---|---|---|
| `huddle.updated` | room | 始まった・入った・抜けた・外れた・ミュートが変わった・終わった |
| `huddle.ringing` | 本人（DM の相手） | DM でハドルが始まった |
| `huddle.left` | 本人 | 自分の参加が外れた（`reason`: `left` / `moved` / `removed` / `expired`）。別の端末で抜けた場合も届く |

- `huddle.updated` は**差分ではなく、そのときの全体**（参加者は 20 人までなので小さい）。`version` を付け、クライアントは手元より古い版を捨てる。
  Pub/Sub は at-most-once で、複数台から届く順序も保証されないので、全体と版にすれば取りこぼしても次の 1 件で正しくなる。
- 全体には、いま入っている人（ユーザー ID・ミュート）と「もうすぐ参加する」人（決定 11）が入る。
- 終わったら `huddle: null`。
- **再接続の同期**: ルームの一覧と 1 件の取得の応答（`GET /api/v1/rooms`、`GET /api/v1/rooms/{id}`）に、進行中のハドル（参加者つき）を載せる。
  WebSocket がつながり直したら、クライアントはここから取り直す（presence と同じく、Redis の状態は REST で読み直す）。ハドルのメッセージは `after_change_seq` でそろう。
- サイドバーのヘッドフォンの印は、購読しているルーム（サイドバーのルームは全部購読している）の `huddle.updated` で出し入れする。

### 14. TURN の認証情報

- `platform` の中で Cloudflare の TURN の API を呼び、ICE サーバーの一覧を作る。有効期間は 12 時間。長いハドルでは、切れる前にクライアントが取り直して `setConfiguration` で差し替える。
- 外されたとき（決定 8）は取り消す。取り消せなかったときも、期限で使えなくなる。
- STUN（`stun.cloudflare.com`）も同じ一覧に入れて返す。

### 15. 外部のサービスは platform に閉じ込める

- `internal/platform/sfu`（SFU の HTTPS API のクライアント）と `internal/platform/turn`（ICE サーバーの発行）を足す。chat は自分の側に interface を置き（`chat.Storage` と同じ形）、実装を注入する。
- **正直に書くと、この interface は Cloudflare の「セッションとトラック」の形に沿う。** LiveKit などに乗り換えるなら書き直しが要る（オーナーと確認した得失）。
  それでも、Cloudflare の JSON・URL・エラーの形を chat に漏らさないため、platform で包む。
- 設定: `CLOUDFLARE_REALTIME_APP_ID`、`CLOUDFLARE_REALTIME_APP_SECRET_FILE`、`CLOUDFLARE_TURN_KEY_ID`、`CLOUDFLARE_TURN_KEY_API_TOKEN_FILE`（秘密は `*_FILE`）。
  - **4 つが全部そろっていないときは、ハドルを無効にして起動する。** ハドルの API は 503 `huddles-unavailable` を返し、Web はボタンを出さない（Web がそれを知る経路は構築順 3 で決める）。
    Cloudflare のアカウントがなくても開発やテストができるようにするため。一部だけ設定されていたら、設定の誤りとして起動を止める。
  - 本番を止めたいとき（使いすぎのときなど）も、設定を外せば無効にできる。
- **ローカルで動く版はないので、開発でも本物の Cloudflare を使う。** 公式の推奨どおり、開発用と本番用で SFU のアプリと TURN のキーを分ける（オーナーが作る。手順は `docs/deploy.md` に書く）。
- テストは Cloudflare を呼ばない。chat のテストは `chattest` の偽の SFU と偽の TURN を使い、`platform/sfu` と `platform/turn` は `httptest` のサーバーで Cloudflare の JSON の形を確かめる。

### 16. ログ

- SDP を出さない（ICE の候補に利用者の IP アドレスが入る）。TURN の認証情報とアプリの秘密も出さない。
- 出すのは `huddle_id` / `participant_id` / `room_id` / `user_id` と、Cloudflare のエラーの種類（`errorCode`）だけ。

### 17. 画面（構築順 2 で描く）

- ルームのヘッダーにヘッドフォンのボタン（始める・入る）。
- サイドバーの、ハドルが進行中のルームにヘッドフォンの印。
- 入っている間は、サイドバーの下にハドルの窓（ルーム名・参加者のアバター・話している人の印・ミュート・抜ける）。Slack の「サイドバーのハドルウィンドウ」に当たる。拡大した窓は作らない。
- 会話のハドルのメッセージ（進行中は「参加」、終わったら所要時間）。
- DM の呼び出し（参加・無視）。
- マイクの許可がない・マイクがない・つながらない・再接続中・切断された、の表示。モバイル。
- 色の約束: 押せるもの（始める・参加）は primary（緑）。**「いま起きていること」（進行中の印・話している人）は attention（琥珀）で、押せるようにしない**（CLAUDE.md のトークンの決まり）。
- ショートカット: ハドルの開始・参加・退出は ⌘⇧H（Ctrl+Shift+H）、ミュートは ⌘⇧Space（Ctrl+Shift+Space）。Slack と同じ。
- 新しいトークンが要れば、デザインのときに確認する。

| | 理由 |

| ~~ハドルのスレッド~~・メモの canvas | ~~スレッドはシステムメッセージに付けていない。足すなら別に決める~~ → スレッド（ハドルのチャット）は入れる（下の追記 A）。canvas は入れない |
| メンバーでない人の招待・参加のリンク・アクセスの申請 | 決定 7。ルームに投稿できる人だけにしておくと、authz が 1 つの判定で済む |
| トピック・音楽・字幕・ハドルの中のリアクション・録音 | 通話の芯ではない |

## 追記（2026-09-26、構築順 2 の途中。オーナーが Slack の実物の画面を示した）

デザインを描いたあとで、オーナーが Slack のハドルの実物の画面（参加前のプレビュー、別のタブの大きな画面、ハドルのチャット、会話のメッセージの進行中と終了）を示した。
決定 12・17 と「やらないこと」の一部を、次のとおり改める（オーナーの確認: 2026-09-26）。

### A. ハドルのチャット（ハドルのメッセージのスレッド）を入れる

- Slack はハドルのメッセージにスレッドが付き、ハドルの画面の右でもそのスレッドを開ける（「ハドルチャット」）。終わった後も会話に「N 件の返信」として残る。
- **既存のスレッド（ADR 0036）にそのまま乗せる。** ハドルのシステムメッセージ（`system_type = huddle`）を、スレッドの親にできる例外にする。
  ほかのシステムメッセージ（参加・名前の変更など）は、これまでどおり親にできない（ADR 0036 の `isThreadRoot`）。
  - 返信・既読・未読（`thread_seq`）・参加者（ADR 0041）・通知・「チャンネルにも投稿する」（ADR 0039）は、普通のスレッドと同じ。
  - 親の投稿者は、ハドルを始めた人（システムメッセージの `sender_id` は主体。ADR 0033）。
  - 返信できるのは、ハドルに入っている人に限らない。そのルームに投稿できる人なら誰でも（普通のスレッドと同じ）。
- ハドルの画面（追記 C）の右に、同じスレッドのパネルを出す。チャットのタブで開くスレッドのパネルと同じ中身。

### B. 参加する前のプレビューを出す

- Slack と同じく、始める・入るの前に、**マイクとスピーカーの選択・マイクのオンとオフ・「キャンセル」「ハドルミーティングを開始する（参加する）」**の画面を出す。
- マイクの許可はここで求める（`getUserMedia`）。許可されない・マイクがないときは、この画面で知らせる（決定 17 の知らせをここに移す）。
- 選んだマイクとスピーカーは、端末ごとに覚える（`localStorage`。本人の設定だが、端末ごとにつながっている機器が違うので Postgres には置かない）。
  スピーカーの選択は `HTMLMediaElement.setSinkId` を使い、使えないブラウザ（Safari など）では出さない。
- カメラの選択とオンとオフは 6.18b で足す。Slack にある「プレビューを無効にする」の設定は作らない。

### C. ハドルの画面は別のタブ（about:blank）に出し、通話はチャットのタブが持つ

- Slack はハドルの画面を別のタブで開き、そのタブの URL は `about:blank` になっている（オーナーが確かめた）。
  中身を読み込まないタブなので、**開いた側（チャットのタブ）の JavaScript が、そのタブに画面を描いている**と考えられる。hibari も同じ形にする。
  - チャットのタブが `window.open("about:blank")` でタブを開き、React の portal でそのタブの `document` に描く。スタイルシートとテーマ（`data-theme`）はチャットのタブから写す。
  - **マイク・`RTCPeerConnection`・心拍（決定 5）は、チャットのタブが持つ。** ハドルのタブは画面だけ。ログインの更新と WebSocket はチャットのタブの 1 本で足り、2 つのタブで状態を受け渡す仕組みも要らない。
  - マイクを使っていることを示すブラウザの印（Chrome のタブの赤い丸）は、ブラウザが自動で出す。作るものはない。
- ~~**ハドルのタブを閉じたら、ハドルから抜ける。**~~ → **閉じても抜けない**（オーナーが Slack の実物で確かめた、2026-09-26）。
  ハドルのタブを開いていない間は、チャットのタブの下の端に全幅の**ハドルの帯**を出す（Slack と同じ）。
  帯には、ルーム名と参加の様子、ハドルの画面と同じ操作の列（マイク・機器の選択・ハドルのチャット）、「新しいウィンドウで開く」、「退出する」を並べる。
  「新しいウィンドウで開く」でハドルのタブを開き直し、開いている間は帯を隠す。
- チャットのタブを閉じる・再読み込みしたら抜ける（決定 4 の `pagehide`。通話を持っているのがチャットのタブなので、Slack と同じく切れる）。
- ブラウザがタブを開くのを止めた（ポップアップのブロック）ときと、**モバイル**では、同じタブの中で全画面に出す。全画面を閉じると、上のハドルの帯になる。
- ハドルの画面: 上に「#ルーム名 でハドルミーティングを行う」と人数、中央に参加者のタイル（アバター・名前・話している人の輪・ミュートの印・「もうすぐ参加します」）、
  下に操作の列（マイクのオンとオフと機器の選択、ハドルのチャット、「退出する」）、右にハドルのチャット（追記 A）。
  Slack の列にある招待・カメラ・画面共有・挙手・リアクション・canvas・背景のテーマのうち、カメラと画面共有は 6.18b、ほかは作らない（「やらないこと」）。
- **サイドバーの小さな窓は作らない**（決定 17 を改める。オーナーの判断）。代わりに上のハドルの帯を出す。
  ヘッダーのボタンは、入っている間は緑の地にし、押すとハドルのタブを前に出す（閉じられていれば開き直す）。
- **サイドバーのルームの行**には、ヘッドフォンの印に加えて、入っている人の顔と人数を出す（Slack と同じ。決定 13 の印を改める）。
- Slack にある、サイドバーの「ハドルミーティング」の一覧、ハドル中の印（名前の横と自分のアバター）、ハドルへのリンクのカードは、この ADR では作らない。Phase 6.18c で別の ADR にする（オーナーの判断、2026-09-26）。

### D. 会話のメッセージの形（決定 12 を改める）

- 始めた人のアバターと名前の行ではなく、**ヘッドフォンのアイコンの行**にする（Slack と同じ）。
  - 進行中: 見出しの横に「ライブ」の印と時刻。入っている人と、入っていなければ「参加」のボタン。
  - 終わった後: 「ハドルミーティングは終了しました」、所要時間と参加した人（決定 12 の「2 人まで名前、それより多ければほか N 人」）。1 人だけなら「1 人で参加しました」。
  - どちらも、下にスレッドの「N 件の返信」（追記 A）。
- Slack の文言（「この静けさをお楽しみください」「いい思索の時間でした」など）は写さない。事実だけを書く。
- 「ライブ」の印は、いま起きていることなので琥珀にする（Slack は緑。CLAUDE.md のトークンの決まりで、緑は押せるもの）。
- 進行中の行は、Slack と同じく行ごと地の色を付ける（琥珀の地。オーナーの指摘、2026-09-26）。

### E. 構築順 3 で決めたこと（2026-09-26）

- **発行した TURN の認証情報は、サーバーの側で覚える**（Redis の `huddle_ice:{userID}`。期限まで）。外したとき（決定 8）はそれを取り消す。
  クライアントから受け取ったユーザー名を信じると、他人の認証情報を取り消させられるため。
- **「1 人 1 つ」のキー（`huddle_user:{userID}`）の TTL は保険（1 日）でしかない。** 期限は `Clock` の時刻で `huddle_deadlines` に持ち、参加を外すときに必ず一緒に消す。
  Redis の時計に期限を任せると、テストで時刻を固定できない（決定 5 のとおり Redis の時計には頼らない）。
- 外すときは、Cloudflare のセッションの一覧（`GET session`）を読んで、送るトラックも受けるトラックも全部閉じる。セッションがもう消えていれば（410）成功にする。
- `huddle_deadlines` は全体で 1 つなので、テストではキーに名前空間を付けて分ける（並行に動くテストの掃除が、互いの参加を外さないように）。本番は名前空間なし。
- DM のハドルのメッセージは、送信と同じ採番（`user_seq` を進める）と、始めた人の既読位置の前進で書く（決定 12 の「DM では未読に数える」）。

## 理由

- **SFU を選ぶ**: オーナーの判断。合図・状態・誰が入れるかを自分で作るので、このプロジェクトの目的（リアルタイムの設計を自分で作って学ぶ）に合う。
  加えて、ブラウザが秘密を持たず Go だけが SFU を操作できるので、authz（ルール 9）と権限の即時の反映（ルール 8）を既存の形のまま守れる。料金も正式版で決まっている。
- **DM も SFU を通す**: 経路が 1 つで済み、相手に IP が見えない。
- **状態を Postgres と Redis に分ける**: 自動で変わるものは Redis、履歴は Postgres というルール 5 の線引きそのまま。
- **心拍と掃除のジョブ**: Cloudflare は切れたことを知らせてくれず、Redis の期限切れもイベントにならない。見つける仕組みを自分で持つしかない。
- **`huddle.updated` を全体と版にする**: at-most-once の配信（ルール 4）の上で、取りこぼしと順序の入れ替わりに強い。

## 検討した代替案

- **RealtimeKit**: 会議・参加者・権限があり、早く Slack に近づく。録音や字幕もある。
  ただ、通話の状態の大半が Cloudflare に移って学べる範囲が狭くなり、ベータで正式版の料金が変わりうる。UI 部品はトークンに従わないので使えない。オーナーの判断で不採用。
- **LiveKit（Cloud の無料枠とローカルの OSS 版）**: 以前の検討での候補。部屋の概念があり、ローカルで動く。オーナーが Cloudflare を選んだので不採用。
- **DM だけ P2P**: SFU を通さない分だけ転送量は減るが、無料の枠に十分に収まるので得が小さい。経路が 2 つになり、相手に IP が見える。不採用。
- **合図（SDP）も WebSocket で送る**: SDP のやり取りは要求と応答なので REST が素直。WebSocket は配るのと心拍（決定 5）だけに使う。
- **参加の状態を Postgres に書く**: 心拍で 10 秒ごとに書くことになる。ルール 5 に反する。
- **Cloudflare の `GET session` を定期的に見て生死を決める**: `active` でもメディアが流れているとは限らない（公式のドキュメント）。心拍の方が「このタブがまだ入っているつもりか」を正しく表す。

## 結果（トレードオフ）

- **費用の見積もり**（音声 1 本を約 50 kbps として。無料の枠は SFU と TURN を合わせて月 1,000 GB）
  - 1 対 1 は 1 時間に約 45 MB。約 22,000 時間分が無料の枠に入る
  - 5 人は 1 時間に約 450 MB で約 2,200 時間分。上限の 20 人は 1 時間に約 8.6 GB で約 115 時間分
  - Cloudflare には使用量で止める仕組みがない。オーナーがダッシュボードで請求の通知を設定する（`docs/deploy.md` に書く）。止めたいときは決定 15 の設定を外す
- **開発に Cloudflare のアカウントが要る。** ローカルで動く版がないため。設定がなければハドルだけが無効になり、ほかの開発はできる。
- **ハドルの実物の確認は CI でできない。** CI は偽の SFU で状態の管理を確かめ、音が届くかは実物で確かめる（DoD）。
- **Cloudflare から乗り換えるには、platform の実装だけでなく interface の書き直しが要る**（決定 15）。
- タブが突然閉じたとき、ほかの人の画面から消えるまで最長で約 35 秒かかる（決定 5）。
- 1 人しか残っていなくても、自動では終わらない（最後の人が抜けるまで続く。Slack と同じ。オーナーの回答）。
- サーバーの状態が 1 つ増える（Redis の参加の状態と掃除のジョブ）。掃除のジョブの goroutine は context のキャンセルで止まることをテストで確かめる。
