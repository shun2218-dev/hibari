# 0025. Web のワークスペースとルームの画面（URL、行き先、既読、履歴の読み込み）

- 状態: 採用
- 日付: 2026-09-17

## 背景

ロードマップ Phase 6-2 の「本番のページの構築順 2」で、ログインした後の画面（サイドバー、履歴、既読、ワークスペースが 0 件のときの表示）を REST だけで作る。
6-1 の presentational コンポーネント（ADR 0018）と、認証の状態（ADR 0024）はできている。決まっていなかったのは次のこと。

- 画面の URL の形と、ログインした後にどこを開くか
- いつ既読にするか、「ここから未読」をどこに出すか
- 古いメッセージをいつ読み込むか、そのときスクロール位置をどう保つか
- チャットの状態をどこに持つか

範囲はオーナーと確認して、ワークスペースの作成と切り替え、public ルームへの参加、古い履歴の読み込み、メンバーパネルまでを含めた。入力欄は送信（構築順 4）まで出さない。

## 決定

### URL と行き先
- **`/w/{workspaceID}` と `/w/{workspaceID}/r/{roomID}`。** ID は ULID をそのまま使う。
- `/` は、最後に開いたワークスペース（いまも一覧にあるとき）、なければ一覧の先頭に移る。一覧が 0 件なら `NoWorkspaces`。
- `/w/{id}` は、そのワークスペースで最後に開いたルーム → `is_default` のルーム（参加済み）→ 一覧の先頭の順に選んで移る。ルームが 0 件ならサイドバーの「まだチャンネルがありません」だけを出す。
- **最後に開いた場所は localStorage（`hibari:last-location`）に ID だけを置く。** 読み書きに失敗したら「覚えていない」と同じに扱う。
- 開けなかった場所（ワークスペースの一覧にない、ルームの一覧が 404、ルームが 404）は、覚えている場所から外して 1 つ上（`/` か `/w/{id}`）に移る。別のワークスペースのルームの URL なら、正しいワークスペースの URL に移し直す。

### 画面の組み立て
- `app/(app)/w/[workspaceId]/layout.tsx` が、サイドバー・ルーム・メンバーパネルをまとめて描く。`page.tsx` は URL を定義するだけで何も描かない。
- チャットの状態（`web/lib/chat/store.ts`）は、session と同じく自作のストアを `useSyncExternalStore` で購読する。`(app)` のレイアウトが、ログインしている間だけ user の ID を key にして置く。
  - ルームは ID ごとに 1 か所（`rooms`）に持ち、ワークスペースごとの一覧（`roomLists`）は ID の並びだけを持つ。一覧・1 件の取得・既読・参加がどれも同じ場所を更新する。
  - 同じ取得（ワークスペースの一覧、ルームを開く、メンバー一覧）は、実行中なら Promise を共有して 2 本送らない。
- API のレスポンスから表示用の型への変換（時刻の文言、日付と未読の区切り、続けて表示するか）は `web/lib/chat/views.ts` の純粋な関数で行う。時刻は見る人のタイムゾーンで整形する。

### 既読と未読の区切り
- **ルームを開いたら、画面に出したいちばん新しいメッセージの seq まで既読にする。** ルームの `last_message_seq` は使わない。
- **「ここから未読」は、開いた時点の `last_read_seq` で固定する。** 開いている間は、既読にしたあとも区切りを残す。「すべて既読にする」は区切りを消すだけで、API は呼ばない（開いたときに既読にしてある）。
- メンバーではない public ルームでは、既読にせず区切りも出さない（`last_read_seq` が null）。

### 履歴
- 開くたびに、ルームの情報と最新のページ（50 件）を取り直して置き換える。前に読み込んだ古いページはつなげずに捨てる。
- 並びは seq だけで決め、同じメッセージが 2 回届いたら `change_seq` の大きい方を残す（`mergeMessages`）。
- **いちばん上から 400px 以内までスクロールしたら、`before_seq` で古いページを読み込む。** 内容が画面に収まってスクロールできないときも読み込む。
- 描き直すときのスクロール位置は、いちばん下にいたら下に付いていき、そうでなければそれまで先頭だった要素が同じ位置に見えるようにずらす。
- 続けて表示する（アバターと名前を省く）のは、同じ送信者が 5 分以内に送り、間に日付や未読の区切りがなく、返信ではないとき。

### その他
- メンバーパネルは開くたびに取り直し、カーソルをたどって全員を取る。
- チャンネルの作成も含めた。作ったばかりのワークスペースにはルームがなく（ADR 0011）、作成できないと先に進めないため。DM の作成は含めない。
- 取得中・取得の失敗・作成や参加の失敗の画面はデザインにないので、何も描かない（または押せる状態に戻す）だけにし、コンソールに出す。

## 理由

- **ID の URL にする理由**: API が ID で引く形と 1 対 1 に対応し、slug から ID を引く API が要らない。slug は 3a では変更できないランダムな値なので、URL を読みやすくする効果も小さい。
- **最後に開いた場所を localStorage に置く理由**: サーバーに持つほどの情報ではなく、端末ごとに違ってよい。置くのは ID だけで、トークンや本文は置かない。別の人が同じブラウザでログインしても、その人の一覧にない ID は使わない。
- **表示したところまで既読にする理由**: `last_message_seq` まで進めると、ルームの情報とメッセージの 2 本の取得の間に届いたメッセージを、見せる前に既読にしてしまう。
- **区切りを開いた時点で固定する理由**: 開いてすぐ既読にするので、ルームの `last_read_seq` から区切りを求めると、描いた直後に消えてしまう。
- **開くたびに最新のページで置き換える理由**: いまは WebSocket で最新を追っていないので、手元の古いページと最新のページの間に抜けができうる。抜けのある履歴をつなげて見せるより、読み直す方が正しい。構築順 3 で `after_change_seq` による差分の同期を入れるときに見直す。
- **レイアウトでまとめて描く理由**: `ChatLayout` はサイドバー・本体・メンバーパネルを横に並べる 1 つの要素で、パネルだけをページに置くことができない。レイアウトはルームを移っても作り直されないので、サイドバーの検索語やスクロール位置も残る。

## 検討した代替案

- **`/{slug}/{roomID}`**: 上記のとおり、slug を ID に変える手段がない。
- **常に一覧の先頭のワークスペースを開く**: localStorage を使わずに済むが、複数のワークスペースを使う人が毎回切り替えることになる。
- **いちばん下まで読んだら既読にする（スクロールに合わせて進める）**: 開いたときは最新のページのいちばん下を見せるので、いまは開いたときに進めるのと変わらない。WebSocket で新しいメッセージが届くようになる構築順 3 で、下にいないときに届いた分をどう扱うかと合わせて決める。
- **「すべて既読にする」で API を呼ぶ**: 開いたときに既読にしてあるので、呼んでも変わらない。
- **IntersectionObserver で先頭の要素が見えたら読み込む**: スクロールの位置で判定するのと効果は同じで、テストで寸法を与えにくい。

## 結果（トレードオフ）

- ルームを開くたびに 2〜3 本（ルーム、メッセージ、既読）のリクエストが走る。
- ほかの人の送信や既読はリロードするまで反映されない（構築順 3）。
- モバイルで「チャンネル一覧に戻る」を押しても URL はルームのまま。リロードするとルームが開く。
- 取得の失敗や、チャンネル名の重複（`room-name-taken`）を伝える画面がない（`docs/ui/README.md` の「未解決」）。
- ワークスペース設定と設定の画面はまだないので、アカウントメニューのその 2 つは押しても何も起きない（構築順 6）。

## 追記（2026-09-17）: 構築順 3 での見直し

ADR 0026 で WebSocket をつないだので、「構築順 3 で見直す」とした 2 つを次のように変えた。

- **開くたびに最新のページで置き換える** → 一度開いたルームのタイムラインは手元に残し、開き直したら `after_change_seq` の差分だけを取る。差分が 1 ページで終わらないときだけ、最新のページを読み直す。
- **開いたときに既読にする** → 開いたときに加えて、最新を見ている間（タブが見えていて、いちばん下が見えている）に届いたメッセージも既読にする。「ここから未読」は開いた時点で固定したまま、見ていない間に届いた分の前に出す。
