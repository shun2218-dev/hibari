# 0027. Web のメッセージの送信（楽観的な表示、送る順番、失敗と再送、返信・編集・削除）

- 状態: 採用
- 日付: 2026-09-17

## 背景

ロードマップ Phase 6-2 の「本番のページの構築順 4」で、入力欄を出して送信をつなぐ。
サーバー側の冪等性（`UNIQUE(room_id, sender_id, client_msg_id)`、重複は 200 で既存を返す）は ADR 0004 / 0012 が決めている。クライアントの側で決まっていなかったのは次のこと。

- 送信中のメッセージをどこに持ち、確定したメッセージとどう突き合わせるか
- 続けて送ったメッセージの順番をどう守るか
- 何を「失敗」とし、再送と取り消しをどう扱うか
- 送信中にリロードしたときに二重投稿しないこと（ロードマップの DoD）
- 入力中を送る間隔

範囲はオーナーと確認して、返信・編集・削除（`chat/composer-reply.png`、`chat/message/message-menu.png`、`chat/message/message-editing.png`、`chat/message/message-delete-dialog.png`）も含めた。添付は構築順 5 に残す。

## 決定

### 送信中のメッセージ
- **確定していない自分のメッセージは、ストアの `outgoing`（ルームごと）に持つ。** タイムラインの `messages`（seq で並ぶ確定したメッセージ）には入れない。
- `client_msg_id` はクライアントが作る ULID（`web/lib/ulid.ts`。ライブラリを入れず `crypto.getRandomValues` で作る）。
- 表示では、確定したメッセージの後ろに、送った順で並べる。seq がないので、未読の区切りの判定には使わない。
- **確定は、送信の応答と `message.created` のどちらか先に届いた方で行う。** 自分が送信者で `client_msg_id` が一致したら `outgoing` から外し、タイムラインには seq で入る。後から届いた方は、既存の `mergeMessages`（`id` と `change_seq`）で重複しない。
- 送信したら、上の履歴を読んでいても、いちばん下まで移る（`Timeline` の `scrollToLatestKey`）。

### 送る順番
- **同じルームの送信は 1 件ずつ、入力した順に送る。** 並行して送ると、サーバーの採番の順（ADR 0012 の行ロックの取得順）が入力の順と入れ替わることがある。
- 1 件が失敗したら、後ろに並んでいたものも送らずに `failed` にする。先に送ってしまうと、失敗したものを再送したときに、後に書いたメッセージの方が前に並ぶ。
- 送信中の自分のメッセージにも返信できる。返信先は `clientMsgId` で持ち、送る時点で確定した ID に置き換える。順番に送るので、送る時点で返信先は確定している（確定していなければ、返信先が失敗して取り消されたので、返信も失敗にする）。

### 失敗と再送
- **失敗は、応答のエラー（通信の失敗、4xx、5xx）と、10 秒待っても応答がないとき。** 経路が黙って切れていると fetch はなかなか失敗しないので、送信中のまま止めない。
- 待ちきれずに失敗にした後で応答が届いたら、確定として扱う（再送を押す前でも後でも、同じ `client_msg_id` なので 1 件のまま）。
- 「再送する」は同じ `client_msg_id` で送り直す。実は届いていても、サーバーが既存のメッセージを返すので二重投稿にならない。
- 「削除」（失敗したメッセージの取り消し）は表示から消すだけ。待ちきれずに失敗にしたものが実は届いていた場合は、後で履歴に現れる。
- 非公開のルームや DM から外されたら、そのルームの `outgoing` を捨てる（もう投稿できない）。
- 本文が 4000 文字（rune）を超えたら、送信ボタンを押せなくする。送っても 422 で失敗にしかならない。

### 送信中のリロード
- **送信中のメッセージは端末に保存しない。** リロードすると消え、自動では送り直さない。届いていれば履歴に 1 件出て、届いていなければ失われる。
- `docs/ui/README.md` の「端末へのメッセージ保存は設計にない」（サーバーエラーの画面の文言を削った判断）と揃える。

### 入力中
- 入力欄の本文が変わるたびに `realtime.sendTyping` を呼び、**購読しているルームにだけ、3 秒に 1 回まで**送る。サーバーは 5 秒に 1 回に間引き、受け取った側は 6 秒で消す（`docs/events.md`）。空白だけの本文では送らない。

### 編集と削除
- 「…」を出すかどうかは `messageActions`（`web/lib/chat/views.ts`）が、`authz.CanEditMessage` / `CanDeleteMessage`（ADR 0012）と同じ規則で決める。
  - 自分のメッセージは、ルームのメンバーなら編集と削除ができる。送信中のメッセージには出さない（まだ ID がない）。
  - 他人のメッセージは、dm 以外で自分が admin 以上なら削除だけ。送信者のロールは、手元にメンバー一覧があってそこにいるときだけ分かり、自分より下でなければ出さない。**分からなければ出し、拒否（403）されたらダイアログを閉じる。** 判定の正はサーバー。
- 編集は応答のメッセージをそのまま反映する。削除は応答に本文がないので、差分（`after_change_seq`）を取って反映する（イベントが先に届いていれば何も変わらない）。
- 編集中に、そのメッセージが削除された（別のタブ、管理者）ら、編集をやめる。
- 編集・削除の失敗の表示はデザインにない。見つからない・削除済み（404 / 409）・権限がない（削除の 403）なら閉じ、それ以外は押し直せる状態に戻してコンソールに出す。

## 理由

- **`outgoing` を `messages` と分ける理由**: `messages` は seq の昇順で、差分の同期のカーソル（`advanceCursor`）もそこから求める。seq も change_seq もないメッセージを混ぜると、並びとカーソルの両方に例外が要る。
- **応答とイベントの先に届いた方で確定する理由**: 同じインスタンスでは、配信（`message.created`）が送信の応答より先に届くことがある。応答だけを待つと、その間タイムラインに同じメッセージが 2 件出る。
- **1 件ずつ送る理由**: 並びは seq だけで決める（CLAUDE.md ルール 3）ので、入力の順を守るには、採番の順を入力の順にするしかない。1 人が 1 つのルームに送る速さでは、直列にしても遅さは目立たない。サーバーも同じ送信者の同じルームへの送信を直列にしている（ADR 0012）。
- **時間切れで失敗にする理由**: 失敗にしないと、応答が返らない送信の後ろに、ほかの送信がすべて並んで止まる。冪等なので、失敗にしてから届いても害がない。
- **端末に保存しない理由**: 保存して起動時に送り直すと、失われるメッセージはなくなるが、ほかのタブ・ログアウト・別の人のログインとの扱いを決める必要があり、デザインにもない。DoD の「二重投稿されない」は、自動で送り直さないことで満たせる。
- **送信者のロールが分からないときに削除を出す理由**: ロールを知るためだけにワークスペースのメンバー一覧を取るのは重い。admin 以上が上位のロールの人のメッセージを消そうとするのはまれで、そのときはサーバーが拒否する。

## 検討した代替案

- **送信を並行に送り、表示だけ入力の順に並べる**: 確定した後は seq の順になるので、確定した瞬間に並びが入れ替わる。
- **失敗しても後ろの送信は続ける**: 通信が戻った後に送った分だけが先に並ぶ。切断中はどのみち全部失敗する。
- **sessionStorage に残して、リロード後に同じ `client_msg_id` で送り直す**: 送信中のリロードでも失われない。オーナーと確認し、上記の理由で採らなかった。
- **fetch を AbortController で打ち切る**: 打ち切っても、サーバーに届いていればコミットされる。応答を待つのをやめるだけで効果は同じなので、`session.request` に signal を足さなかった。
- **入力のたびに typing を送り、間引きはサーバーに任せる**: キーを押すたびにフレームを送ることになる。

## 結果（トレードオフ）

- 前の送信が時間切れになるまで（最大 10 秒）、同じルームの後ろの送信は待たされる。
- 失敗したメッセージを取り消しても、実は届いていたら後で履歴に出る。
- 送信中にリロードすると、届いていなかったメッセージは失われる。
- 入力欄の本文と返信先はルームを移ると消える（ルームごとに作り直す `RoomView` の状態）。
- 本文が長すぎて送れない理由、編集・削除の失敗、上位のロールの人のメッセージを削除できなかったことの表示はない（`docs/ui/README.md` の「未解決」）。
- 入力欄の「ファイルを添付」は、押しても何も起きない（構築順 5）。
- ブラウザの画面を実際に操作した確認（2 つのタブ、ネットワークの切断）は、オーナーが手元で行う。自動の確認は、画面のテスト（偽の API とソケット）と、compose の API に実物の fetch と WebSocket でつないだデータ層の確認まで。後者では、送信が別のタブに届く、切断中の送信が failed になり再送しても 1 件、応答が失われた送信を再送しても 1 件、再接続で切断中の他人のメッセージが揃う、返信・編集・削除が別のタブに反映される、を確かめた。
