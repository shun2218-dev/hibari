# 0014. 変更番号（change_seq）による差分同期

- 状態: 採用
- 日付: 2026-09-14

## 背景

ADR 0004 は「クライアントは最後に受信した seq を持ち、再接続時に `after_seq` で差分を取る」と決めた。
しかし seq が増えるのは**新しいメッセージ**だけなので、切断中に起きた既存のメッセージの編集・削除は `after_seq` では取得できない。
ADR 0012 はこれを既知の制約とし、Phase 4 で WebSocket のイベントを設計するときに解決策を決めることにしていた。

WebSocket の配信（Phase 5 の Redis Pub/Sub を含む）は落ちうる前提なので（CLAUDE.md ルール 4）、
「作成」だけでなく「編集・削除」にも、欠落を検出して取り戻す経路が要る。

## 決定

### ルームごとの変更番号
- `rooms.last_change_seq`（初期値 0）と `messages.change_seq` を追加する。
- メッセージの**作成・編集・削除のたびに**、`rooms.last_change_seq` を 1 増やし、その値を対象のメッセージの `change_seq` に書く。
  - 作成: `last_message_seq` と `last_change_seq` を同じ `UPDATE rooms ... RETURNING` で増やす（ADR 0002 の採番と同じ文）
  - 編集: 本文が変わったときだけ採番する。変わらなければ採番しない（イベントも出さない）
  - 削除: 未削除のときだけ採番する。削除済みへの削除（冪等な 204）は採番しない
- seq と同じく、ルームの行ロックとトランザクションで**ルーム内で欠番なく**採番する。ロールバックすれば採番も戻る。
- `UNIQUE (room_id, change_seq)` のインデックスを張る。差分取得の範囲条件と、同じ番号の二重使用の防止を兼ねる。
- 既存の行は `change_seq = seq`、`last_change_seq = last_message_seq` で埋める（編集・削除の履歴はないので、作成順の番号がそのまま使える）。

### seq と change_seq の役割
| 番号 | 何が増やすか | 用途 |
|---|---|---|
| `seq` | 作成だけ | メッセージの**順序**の唯一の根拠（ADR 0002）。履歴のページング（`before_seq` / `after_seq`）、未読数 |
| `change_seq` | 作成・編集・削除 | **同期**のカーソル。再接続時の差分取得と、WebSocket のイベントの欠落の検出 |

- seq と change_seq を 1 つの番号にまとめない。編集・削除で seq が進むと、seq に欠番ができて「seq の欠番 = 取りこぼし」という検出が使えなくなり、未読数（`last_message_seq - last_read_seq`）も壊れる。
- 表示の並びは常に seq で決める。change_seq でソートしない。

### 差分取得の API
- `GET /api/v1/rooms/{id}/messages?after_change_seq=N` を追加する。`change_seq > N` のメッセージを **change_seq の昇順**で返す（作成・編集・削除をまとめて返す。削除済みは tombstone）。
  - `before_seq` / `after_seq` と同時には指定できない（422）。`limit` と `has_more` の扱いは `after_seq` と同じ。
- メッセージのレスポンスに `change_seq` を加える。
- 履歴のレスポンスに `last_change_seq`（ルームの現在の値）を加える。
  - メッセージを読む**前**にルームの行を読んだ値を返す。READ COMMITTED では文ごとにスナップショットが変わるので、後から読むと「一覧に含まれていない変更」の番号まで進めてしまい、次の差分取得でその変更を取りこぼす。先に読めば、同じ変更を 2 回受け取ることはあっても取りこぼしはしない。
- クライアントのカーソルは「受け取ったメッセージの `change_seq`」と「レスポンスの `last_change_seq`」の最大値にする（`docs/events.md`）。

### ロックの順序
- 編集・削除は、対象のメッセージの行をロックしてから `rooms` の行をロックして採番する。
- メッセージの行ロックを `FOR UPDATE` から `FOR NO KEY UPDATE` に変える。
  返信の送信は `rooms` の行ロックを持ったまま、返信先の行に複合 FK の `FOR KEY SHARE` を取る。
  編集が返信先の行を `FOR UPDATE` で持ったまま `rooms` を待つと、互いを待ってデッドロックする。
  `FOR NO KEY UPDATE` は `FOR KEY SHARE` と競合しないので、この組み合わせでは待ち合わない（本文と削除時刻の UPDATE はキーを変えないので、`FOR NO KEY UPDATE` で足りる）。

## 理由

- **同期の経路を 1 本にできる**: 再接続したら `after_change_seq` だけを呼べば、新規・編集・削除がすべて揃う。`after_seq` と「表示中の範囲の取り直し」を組み合わせる方式は、クライアントがキャッシュしている範囲をすべて取り直さないと古い本文が残る。
- **WebSocket の欠落を検出できる**: イベントにも change_seq を載せるので、クライアントは「手元のカーソル + 1 ではない番号」を受け取った時点で欠落に気づき、REST で取り戻せる。seq だけでは、編集・削除のイベントの欠落に気づけない。
- **ADR 0002 の性質をそのまま使える**: 採番をルームの行ロックの中で行うので、読み手はコミット済みの change_seq に欠番を観測しない（`TestListMessagesAfterSeqSync` と同じ理由）。

## 検討した代替案

- **再接続時に表示中の範囲を取り直す**: スキーマの変更は不要だが、表示していない範囲のキャッシュが古いまま残り、イベントの欠落も検出できない。
- **seq を編集・削除でも進める**: 番号は 1 つで済むが、seq の欠番と未読数の意味が壊れる。
- **`updated_at` のタイムスタンプをカーソルにする**: 時計の精度と、コミットの順序と時刻の順序が一致しないことから、取りこぼしが起きうる（ADR 0002 が created_at を使わない理由と同じ）。
- **変更ログのテーブル（room_events）を別に持つ**: メッセージ以外の変更（メンバー・ルームの設定）も同じ仕組みで同期できるが、書き込みが 2 倍になり、ログの掃除も必要になる。いまはメッセージだけで足りる。

## 結果（トレードオフ）

- 編集・削除も `rooms` の行ロックを取るので、同じルームへの送信・編集・削除がすべて直列になる。送信はもともと直列（ADR 0002）なので、上限はほとんど変わらない。
- メッセージの行の更新で `(room_id, change_seq)` のインデックスも更新される（HOT 更新にならない）。編集・削除は送信より十分少ない前提で受け入れる。
- メンバーの増減・ルームやワークスペースの設定の変更は change_seq の対象外。これらは再接続時に REST（ルーム一覧・メンバー一覧）を取り直す（`docs/events.md`）。
- クライアントはルームごとに `seq`（表示・未読）と `change_seq`（同期）の 2 つのカーソルを持つ。
